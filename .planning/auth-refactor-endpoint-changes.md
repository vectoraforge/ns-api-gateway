# Implementation Brief (corrected)

The spec sections are confirmed. Here is the authoritative implementation brief.

## POST /auth/sync

**Description:** The business-state read-only auth resolution endpoint. It is the client's single reconciliation surface: after sign-in, after a lost response from any state-changing auth operation, and after losing the create-user race, the client calls /auth/sync and proceeds on current backend state. Route category: **authenticated** AND a **canonical state-changing auth operation by route** (inventory operation `sync`) — this is deliberate: it is on the audited attempt path even though its handler mutates nothing. It is NOT challenge-bearing and NOT pre-auth-callable. Caller: any client holding a Firebase ID token whose backend-verified (iss, sub) resolves to a linked, active identity. Credential: exactly one `Authorization: Bearer <Firebase ID token>` header — the sole identity carrier; no body field, header, cookie, or query parameter contributes identity.

**Business logic changes:**

1. **Barrier precondition (before the handler).** The shared pre-handler barrier — the only place JWT acceptance and identity resolution happen — verifies the token (RS256 against cached Google securetoken keys, `iss` exactly `https://securetoken.google.com/<project-id>`, `aud` = configured Firebase project ID, `exp`/`iat` validity, non-empty `sub`, no `checkRevoked`), resolves verified (issuer, subject) against `core.external_identities`/`core.users`, and admits only `identity_state = 'active'` AND user `active` exactly TRUE. The handler consumes the barrier's typed identity context (resolved `core.users` row + `core.external_identities` row, including stored provider and `registered_at`); it never re-verifies or re-resolves.
2. **No request modes.** No prepare mode; `challenge=true` is not a recognized signal here; the endpoint touches no `core.auth_challenges` row. The handler must not trust any earlier client snapshot — the returned view is advisory only.
3. **Reads (single evaluation time).** Derive everything from ONE captured evaluation time or one consistent database snapshot: grant selection, `current_period` computation, and the usage read. Tables read: `core.access_grants`, `core.access_tiers`, `core.user_monthly_usage`, plus the barrier-resolved `core.users`/`core.external_identities` rows. No locks needed (pure reads); if any lock path were taken it would follow grant-before-usage order, but sync takes none.
4. **Effective-grant selection.** Apply the shared effective-grant predicate — `status = 'active' AND starts_at <= now AND (ends_at IS NULL OR ends_at > now)` — never selection by `status` alone. Exactly one row may match:
   - **Zero effective grants:** return `type = "none"`, `status = "none"`, `tier_id = null`, `monthly_credits = null`, plus clock-computed `current_period` and `monthly_used = 0`. A lapsed, revoked, or time-ended-but-not-yet-flipped row reads identically to never having had a grant.
   - **One effective grant:** `type` from `core.access_grants.source` (`subscription | anonymous_device_grant | registered_account_grant | manual`), `status = "active"`, `tier_id` and `monthly_credits` from the joined `core.access_tiers` row. A `source='subscription'` grant is honored outright — never re-read or branch on the subscription row's status. A `manual` grant reports as `type = "manual"` like any ordinary grant.
   - **More than one `status='active'` grant:** internal integrity failure (the kept integrity tripwire). Log and fail closed — never break the tie, no precedence ranking over sources.
5. **`current_period` / `monthly_used`.** Always present, never null. `current_period` always comes from the clock under the shared period definition (`YYYY-MM`, UTC calendar month). `monthly_used` is the stored `core.user_monthly_usage.monthly_used` only when that row's `monthly_period` equals the computed current period; otherwise `0` (same answer whether no usage row exists or it names an earlier period — this is exactly the figure the next quota-checked request's lazy rollover would persist).
6. **Registration state.** Report the account's stored registration state, e.g. `identity_provider: 'anonymous' | 'google' | 'apple'`, sourced from the stored `core.external_identities.provider` column only — never from token claims, headers, or a providerData read — so the client can detect a stranded upgrade by comparing against local Firebase state. Reporting changes nothing.
7. **Strictly read-only.** No insert, no update, no triggered rollover, no grant-row flip (the lazy flip of a time-ended active row to `expired` happens only in the grant-issuance/replacement transaction), no profile overwrite, no reactivation of `active = FALSE`, no repair of the single-active-grant invariant. Every reported value is the value quota enforcement would independently act on at the same instant.
8. **Audit write (the endpoint's only write).** Exactly one `audit.auth_events` row with `operation = 'sync'` per attempt, appended before the response returns — see Security hardenings.
9. **Errors:**
   - `auth_required` (internal `invalid_external_jwt`): any token acceptance failure — missing/malformed/duplicated Authorization, bad signature, issuer or audience mismatch, expired/temporal invalidity, empty sub. Identical body, status, and timing across every branch; names no issuer or failed check.
   - `preauth_identity_not_allowed`: verified (issuer, subject) has no `core.external_identities` row. Remediation: complete POST /auth/create-user, then retry.
   - `account_unavailable`: historical identity (internal `historical_identity`) or blocked user (internal `blocked_user`) — one class, same status/code/copy, mutually indistinguishable; terminal for the client.
   - Internal integrity failure (multiple active grants; orphan user row with no identity row): fail closed as the ordinary internal-error outcome (internal result `internal_error`) — never invent an identity row, never reassign, never repair.
   - `429 Too Many Requests` with `Retry-After` when computable, carrying the shared JSON error body naming the class, for rate-limit rejection (admission phase — no audit row).
   - All errors use the one shared error response shape; internal `core.auth_event_result` values are never exposed.

**Security hardenings:**

- **Authentication:** backend cryptographic verification of the Firebase ID token on every request via the issuer-matched Firebase Admin integration (exactly one configured integration; no ambient/default/fallback client). Envoy's JWT filter is defense-in-depth only; the gateway forwards Authorization unchanged and injects no claim headers; the backend ignores every client/proxy identity header. `Bearer` scheme matches case-insensitively; token bytes are case-sensitive.
- **Route-inventory registration:** the route→operation mapping (`POST /auth/sync` → `sync`) lives in route metadata readable BEFORE the barrier runs, so a barrier rejection can be audited with the operation set. The route-enumeration assertion (CI/startup/integration) must show it in exactly the authenticated category.
- **Audit obligations (fail-closed, on-path):** every attempt reaching the route match writes exactly one durable `audit.auth_events` row with `operation = 'sync'`, `result` = the barrier's own result on rejection (`invalid_external_jwt` with all three actor fields NULL — CHECK-enforced; or `preauth_identity_not_allowed` / `historical_identity` / `blocked_user` with actor fields from the verified token/resolved identity) or `succeeded`. The row is a standalone durable write in its own transaction (no consuming/mutating transaction exists here), written before the response; never best-effort — if the audit write fails, log the failure and still return the outcome the attempt earned. `details.mutation` stays empty `{}`; `challenge_row_id` is NULL; `actor_subject_hash` is HMAC-SHA-256 with key version, raw subject never stored; `actor_provider` from the stored provider column for resolved linked identities, NULL otherwise, never fabricated. Barrier results are first-class — never collapsed into a generic 401 log line. Admission-control rejections ahead of the route match (gateway/backend rate limit, parsing, body-size, content-type, JSON syntax) write NO audit row and leave only rate-limit telemetry naming the limiter that fired. The `invalid_external_jwt` counter metric (labeled bounded reason × route) still increments wherever the barrier rejects.
- **Rate limits:** named backend entry `auth_sync`: `60/minute`, key `issuer+subject_hash` — key built only from the token claims the barrier verified, evaluated only after backend JWT verification succeeds; barrier-rejected requests are bounded only by IP-keyed limits and the generic default (`120/minute`, key `ip`, fail_closed). All limits via the Python `limits` library (`parse_many`, moving-window, shared Redis/Valkey in production), fully config-driven (limit string, key, cost, enabled, failure_mode — default fail-closed), never hard-coded. IP keys use only the Envoy trusted-proxy-resolved canonical client address (IPv4 /32, IPv6 /64 prefix; unresolved addresses share one bucket at 10 requests/minute).
- **Explicit DELETIONS — do NOT build:** no prepare mode, no challenge issuance/lookup/consumption; no providerData read and no Firebase Admin lookup of any kind (issuer mismatch is rejected by the barrier before any client selection); no device-check verification (DeviceCheck / Play Integrity / Device Recall) and no read or write of per-device grant state; no user creation, usage-state initialization, introductory-entitlement allocation, grant creation/finalization/flipping/repair; no restore-proof verification, no completion-operation selection, no restore reassignment target derivation; no identity linking, no marking historical, no user merging, no subscription modification, no profile-field update, no audit events implying mutation; no reactivation of a blocked user; no backend session/token minting; no `expired`/`revoked` values in the public status enum, generated types, examples, or tests; no per-request revocation check; no free-credit allocation ever.

## GET /users/me

**Description:** Returns the current user's backend profile and the account's already-persisted store purchase-attribution tokens, scoped per store provider, unconditionally for every store provider and platform (the iOS client reads the Apple `app_account_token` and passes that exact stored value into StoreKit at purchase time; Android analogously uses the Google Play `obfuscated_external_account_id`). Route category: **authenticated, routine traffic** — it is NOT in the state-changing operation inventory and is NEVER on the audited attempt path. Not pre-auth-callable. Caller: any client with a Firebase ID token resolving to a linked, active identity. Credential: exactly one `Authorization: Bearer <Firebase ID token>` header.

**Business logic changes:**

1. **Barrier precondition:** identical to /auth/sync — shared pre-handler barrier verifies the token and admits only a linked identity (`identity_state='active'`, user `active` TRUE); pre-auth, historical, and blocked identities are rejected at the barrier; the handler consumes the typed identity context and performs no identity work of its own.
2. **Handler steps, in order:**
   1. Load the resolved user's profile fields from `core.users` (canonical profile fields: `email`, `display_name`; email is never identity/ownership/authorization/recovery proof and may be stale).
   2. Read the persisted purchase-attribution tokens from `core.store_purchase_tokens`, scoped per store provider (`provider` here is the STORE enum `core.subscription_provider`: `'apple'` | `'google_play'` — never the Firebase identity provider; at most one row per (user_id, provider), owned by `core.users.id` for the account's life, unchanged across the in-place anonymous-to-registered upgrade).
   3. Return the profile fields, the account's stored registration state as the same `identity_provider` value POST /auth/sync reports (`'anonymous' | 'google' | 'apple'`, sourced only from the stored `core.external_identities.provider` column — enables client stranded-upgrade detection), and the read purchase tokens.
3. **Fixed response shape, no platform condition:** always an entry for EVERY store provider with that store's token, for every existing user. Both tokens are minted in the create-user transaction, so no null case exists; a missing token row is an internal invariant failure — fail closed (internal error), never a null entry, never a lazy re-mint. No client-supplied signal (User-Agent, X-Platform-style header, query parameter, body flag) and no gateway claim may change which tokens are loaded or appear. Payload carries only explicitly defined non-secret attribution identifiers (e.g. Apple `app_account_token`) — no store credentials, signed transactions, or purchase proofs. Clients ignore entries for stores they don't use. If backend `display_name` is NULL the client may show an IDP-local name for presentation only; that value never becomes backend data here.
4. **Errors:** same barrier taxonomy as /auth/sync — `auth_required` (internal `invalid_external_jwt`), `preauth_identity_not_allowed`, `account_unavailable` (historical/blocked, terminal) — via the shared response shape; internal results never exposed. Missing-token-row or orphan-user invariant failures fail closed as internal errors. `429` with `Retry-After` and the shared JSON body for rate-limit rejection.

**Security hardenings:**

- **Authentication:** identical barrier and wire contract to /auth/sync (single Bearer credential, strict exactly-one-Authorization-field/duplicate/malformed handling, backend RS256 verification against pinned issuer/audience, identity only from verified iss+sub, no claim headers, no checkRevoked).
- **No audit rows — ever.** GET /users/me is off the audited attempt path: a barrier rejection here writes NO `audit.auth_events` row. Instead the rejection keeps its stable internal result code in the structured security log and increments the mandatory bounded-cardinality counter metric labeled by result, bounded reason, and route (this counter — not audit.auth_events — is the required cross-route attack-volume alerting source; `invalid_external_jwt` stays first-class there). The handler must not append any `audit.auth_events` row that implies state-changing auth.
- **Attribution-token semantics (invariant 10):** one lifetime attribution token per store per `core.users.id`, bound via `core.store_purchase_tokens`, never derived from request-authenticated or client-asserted identity. The token is non-secret and confers nothing — knowledge/equality is never proof of purchase, identity ownership, restore authority, or entitlement, and unlocks no API access — but it is private account metadata: redact from routine logs, analytics, and error reporting; no secret-store machinery needed. Returning it to an authenticated bearer is no privilege escalation (accepted risk: a leaked ID token already reads profile/entitlement/chats until its exp).
- **Rate limits:** named backend entry `users_me`: `30/minute`, key `issuer+subject_hash`, evaluated only after backend JWT verification; otherwise the same shared `limits`-library, config-driven, fail-closed-by-default, canonical-client-IP contract as /auth/sync; barrier-rejected requests bounded only by IP-keyed limits and the generic default entry. Rate-limit rejections are admission-phase: 429 + Retry-After + shared JSON body, telemetry only, no audit row.
- **Explicit DELETIONS — do NOT build:** no creation, rotation, replacement, or lazy minting of purchase-attribution tokens (no administrative replacement path exists anywhere); no user creation; no mutation of `core.external_identities`, `core.access_grants`, `core.subscriptions`, or `core.store_purchases`; no challenge issuance or any `core.auth_challenges` touch; no restore-proof or device-check verification (DeviceCheck / Play Integrity / Device Recall) and no read/write of vendor per-device grant state; no providerData read or Firebase Admin lookup of any kind; no platform branching or "identity kind" condition in the response; no grant minting; no `audit.auth_events` writes; no per-request revocation check; no backend token/session minting; `display_name` never populated from auth context or the Admin record; no email sync or provenance tracking.

## Shared constraints binding both endpoints (implementers must honor)

- Handlers run behind the one mandatory shared barrier and never re-implement JWT acceptance or identity resolution; a route wired outside the barrier has no identity context and rejects `auth_required`. The route-enumeration assertion must place both routes in exactly one category (both authenticated; /auth/sync additionally mapped to operation `sync` in the inventory).
- Ownership: business data is keyed only by `core.users.id`; monthly usage rows by `core.access_grants.id`; no external subject (`sub`, uid) is ever an ownership key; no principal is ever loaded by `core.users.id` alone.
- A `core.users` row with no `core.external_identities` row is unresolvable: fail closed, never invent/reassign/repair.
- Neither endpoint allocates anything implicitly: no `core.access_grants` row is created or modified, neither claim path is invoked, and a `core.user_monthly_usage` counter is never treated as an entitlement.
- Stored provider is the sole classifier; `registered_at` is reporting-only; no rederivation against live Firebase providerData on these hot paths and no background reconciliation exists.
- Challenge TTL (300 s), mode-signal partition, claim/consume protocol, and `challenge_required`/`invalid_request` machinery apply ONLY to the four challenge-bearing operations (`create_user`, `upgrade_anonymous_to_registered`, `claim_anonymous_grant`, `claim_registered_grant`) — build none of it into these two endpoints.

## POST /auth/create-user

**Description:** State-changing auth operation `create_user` (enum `core.auth_operation` value `'create_user'`), challenge-bearing. First-time account creation only: creates one `core.users` row plus one `core.external_identities` row when the backend-verified Firebase `(issuer, subject)` is unlinked. Serves both anonymous first-time and registered (Google/Apple) first-time users; anonymous accounts are disposable — a user who lost an anonymous session registers via this endpoint (no anonymous-account recovery exists). It is the ONLY route (both its prepare and complete phases) declared pre-auth-callable: the shared pre-handler barrier admits a pre-auth (unlinked) identity here and nowhere else. Caller: any client holding a valid Firebase ID token, presented as `Authorization: Bearer <Firebase ID token>` (the sole identity carrier). Never performs a device check, CAPTCHA, proof-of-work, or attestation in either phase.

**Business logic changes:**

Request modes (exhaustive mode-signal partition, checked syntactically after the barrier and before any challenge processing):
- `challenge=true` in the query string AND no `challenge_id` in the body → prepare mode. `challenge=true` is the ONLY prepare-mode signal; never infer prepare from a missing challenge.
- `challenge_id` in the body AND no `challenge=true` → completion mode.
- Both together, or neither → reject `invalid_request`, HTTP 400, shared response shape naming the class. Also `invalid_request`: a `challenge` query param with any value other than exactly `true`, a duplicated `challenge` query param, a body `challenge_id` that is null, empty, or wrong type. This rejection has NO side effects (issues, looks up, consumes nothing; a corrected retry may reuse the same unexpired challenge), has no internal `core.auth_event_result`, belongs to the admission phase, writes NO `audit.auth_events` row, and is recorded only in the structured security log + counter metric. Never silently prefer one signal.

Prepare mode (`POST /auth/create-user?challenge=true`):
1. Consume the barrier's typed verified identity context (pre-auth `(issuer, subject)` from backend-verified token claims). Historical identity and blocked user were already rejected by the barrier (`account_unavailable`); an already-linked ACTIVE identity is rejected here with `identity_already_linked` (best-effort fail-fast only, racy, never authoritative; issues no challenge).
2. Enforce backend per-operation prepare limit — 08 entry `create_user_prepare` (recommended `10/minute`, key `ip`) — after barrier verification/identity resolution, BEFORE issuing or persisting any challenge.
3. Normalize the OPTIONAL client `provider` field by exact case-sensitive match against the identity-provider enum (`anonymous` | `google` | `apple`), defaulting to `anonymous`. Persist the normalized value as the challenge's `operation_variant` — immutable; completion can never choose or change it.
4. Issue a single-use challenge: `challenge_id` = 16 bytes from a cryptographically secure RNG, base64url-encoded without padding; it is simultaneously the row lookup key and the nonce (no second nonce exists). Persist one `core.auth_challenges` row: operation `create_user`, `operation_variant`, pre-auth binding `(preauth_issuer plaintext, preauth_subject_hash)` where `preauth_subject_hash = HMAC-SHA-256(k_actor_subject_vN, "actor-subject:v1:" || preauth_issuer || ":" || canonical_subject)` — same family and key as `audit.auth_events.actor_subject_hash`, current active key only, NO key version stored on the row (a key rotation invalidates outstanding challenges: completion then rejects `challenge_identity_mismatch` → `challenge_required`); raw subject never stored. `expires_at` = server clock + 300 seconds (the single universal TTL; never client-supplied, never extended, never renewed, no grace). Lifecycle state `issued` (one-way: issued → claimed → consumed).
5. Response body: exactly two fields — `challenge_id`, `expires_at` — nothing else disclosed; `Cache-Control: no-store`. Prepare mutates NO business state.

Completion mode flow (numbered order is normative rejection precedence — reject for the earliest failed step):
1. Barrier: token verification (failure → `invalid_external_jwt` → `auth_required`), route admission, historical-identity rule, blocked-user rule — all before any challenge check.
2. Backend per-operation completion limit — 08 entry `create_user` (recommended `10/minute`, key `ip`) — enforced at request receipt, as soon as route + gateway-resolved client address are known: before JWT decode, before any Firebase Admin call, before any DB write. Admission rejection: 429 + `Retry-After`, no audit row.
3. Locate challenge row by byte-for-byte `challenge_id` comparison. No row (definitively) → audit `challenge_not_found` → `challenge_required` (a DB outage during lookup is the ordinary infrastructure-failure result, NOT `challenge_not_found`; raw malformed identifier never logged).
4. Verify binding: request's verified issuer == `preauth_issuer` AND recomputed HMAC verifier == `preauth_subject_hash` (even if the subject has since become linked); operation must be `create_user`. Unknown-id/identity-mismatch/operation-mismatch rejections occur BEFORE the claim and leave the challenge unconsumed (a wrong presenter cannot burn the rightful user's challenge). A pre-auth row whose verifier was already cleared skips the comparison and takes the already-used rejection audited `challenge_consumed`.
5. Claim (step 8 of the shared procedure): ONE atomic conditional update issued→claimed, stamping this attempt's server-generated `claim_attempt_id`, conditioned on state still `issued` AND `expires_at` in the future. This is the single serialization point and the ONLY expiry evaluation anywhere (nothing downstream is time-gated). No-match: still-issued-but-expired → `challenge_expired`; already claimed/consumed → `challenge_consumed` (generic already-used conflict; never returns the stored outcome of the claim-holder — no idempotent replay; client reconciles via `/auth/sync`). The claim loser performs NO work at all: no proof verification, no Firebase Admin lookup, no mutation.
6. Provider-variant check on the claimed row: completion's REQUIRED `provider` field must equal the stored variant byte-for-byte — no trimming, defaulting, re-normalization, case-folding; a missing or differing value is a mismatch. Mismatch → `challenge_operation_mismatch` → `challenge_required`, CONSUMES the challenge (fresh prepare required), and runs BEFORE any Firebase Admin lookup. An anonymous challenge can never complete registered creation and vice versa.
7. Firebase Admin lookup gating (before `getUser`): budgets evaluated non-destructively in deterministic broadest-to-narrowest order — global `adapter_firebase_lookup` (recommended `30/minute`, key `deployment+firebase_project_id`), then `create_user_firebase_identity_lookup` (recommended `60/minute`, key `deployment` alone), then `create_user_firebase_identity_lookup_ip` (recommended `10/minute`, key canonical client IP alone). No counter increments unless ALL have capacity; when all clear, all are charged together immediately before the outbound call (and before each permitted retry); charges persist regardless of outcome. When multiple are exhausted, `adapter_firebase_lookup` is the primary reported result; every exhausted limiter goes in metrics. Exhaustion of ANY of these → client class `verification_temporarily_unavailable`. All three fail closed. Neither lookup counter is ever fused into a composite key, keyed on subject, or deferred to await an issuer/subject value.
8. Exactly ONE mandatory fail-closed Firebase Admin `getUser(subject)` providerData read, immediately before the write transaction, on EVERY completion — anonymous and registered alike; no branch skips it. Issuer-selected Admin client only (single configured integration; no ambient/default/fallback client). Retry: retryable causes (outage, malformed/indeterminate response, integration-auth failure) get up to TWO additional attempts, THREE total; non-retryable causes reject immediately without spending budget. No transaction, row lock, or open DB session held across the call.
9. Closed classifier on successful providerData: no entries → `anonymous`; exactly one `google.com` entry → `google`; exactly one `apple.com` entry → `apple`; every other shape (both providers, multiple entries, unrecognized entries) → reject, no persistence (internal `provider_not_linked` invalid-shape cause → `operation_not_allowed`, no flow named). Never take the first recognized entry; never classify non-empty providerData as anonymous; never read `firebase.sign_in_provider`. Declaration match: declared-anonymous requires EMPTY providerData; declared-registered requires the classified provider to equal the declaration. Determinate mismatches → `create_flow_mismatch`, HTTP 409, shared shape + mandatory `required_flow` field set exactly `anonymous` or `registered` ONLY from the Admin classification (registered provider linked → `registered`; empty → `anonymous`); never derived from the client declaration; internal audit `provider_not_linked` with bounded cause (empty | invalid-shape | supported-provider-mismatch). For google/apple, the matching entry's non-empty `uid` is the SOLE source of `provider_uid`; missing/empty uid = malformed/indeterminate lookup → reject, no persistence.
10. Consuming transaction (short, database-only; no provider call, no expiry re-check): re-resolve `(issuer, subject)` against `core.external_identities` INSIDE it (prepare-time pre-auth status never suffices). Active linked row → `identity_already_linked`, no business mutation. Historical/blocked → `account_unavailable` with distinct internal `historical_identity`/`blocked_user` results, no mutation. Otherwise, in the SAME transaction: insert `core.users` + exactly one ACTIVE `core.external_identities` row (either insert failing rolls back everything — no partial account); persist classified provider (`core.identity_provider` enum, never free text); `provider_uid` = NULL for anonymous (no sentinel — the row falls outside the provider-account reservation), or the providerData uid for google/apple under the partial unique index `(issuer, provider, provider_uid) WHERE provider_uid IS NOT NULL` (spans historical rows); set `registered_at` NULL for anonymous / non-null for registered (invariant: `registered_at IS NOT NULL` iff provider is google/apple — enforced in code by this transaction, no third state); copy `email` only when the same successful `getUser` response has a non-empty address AND `emailVerified = true`, else NULL; NEVER populate `display_name`; mint the purchase-attribution tokens EAGERLY on every branch (anonymous and registered): one `core.store_purchase_tokens` row per store — Apple `app_account_token` and Google `obfuscated_external_account_id` — each a random opaque server-generated UUID, no PII, not derivable from identity, `UNIQUE(user_id, provider-as-store)`, once per user per store for the account's life, never rotated or replaced; a rejected/replayed completion mints nothing. Create NO access grant, NO free credits, NO `core.user_monthly_usage` row, and read/modify NO per-device grant bits.
11. Provider-account uniqueness conflict on the registered binding write → internal `provider_account_already_linked` → client `operation_not_allowed`; roll back ALL business mutation (no user, identity, grant, profile, or attribution token).
12. Race arbitration: `UNIQUE (issuer, subject)` + `UNIQUE (user_id)` are the ONLY arbiters between two completions that both observed an unlinked subject. Loser: rolls back every business mutation, returns the same `identity_already_linked` conflict as the pre-check path, audits its own `identity_already_linked` result — and its challenge consumption + rejected audit row MUST survive the business rollback (acceptable mechanisms: consume-first atomic conditional update, savepoint around the business insert, or deterministic re-run taking the already-linked branch). The uniqueness violation must never escape as a generic 500 and never be audited as `invalid_external_jwt`; never idempotent success, never a merge, never overwrites the winner's provider. Grant side effects (none here anyway) run winner-only. No serializable isolation, distributed lock, generation CAS, or loser-challenge cancellation beyond single-use.
13. Consume the challenge exactly once — atomic conditional update to `consumed`, conditioned on still-claimed under this attempt's `claim_attempt_id` — in the same transaction as the audit row and any mutation, on success and rejection alike (every rejection at or after the Admin lookup consumes; retry requires a fresh prepare). Consumption clears `preauth_subject_hash` in the same state transition. Transient commit failure (lost ack included) retries the same local transaction under the same `claim_attempt_id`, never repeating a provider call.
14. Return the resulting backend state. NO backend token is issued — there is no backend session/token tier, no secondary auth state, no generation to advance; the same Firebase ID token simply resolves as linked on the next request.

Error classes (all shared response shape; each rejection on the audited path also writes the specific internal result):
- `auth_required` ← `invalid_external_jwt` (missing/malformed/duplicated Authorization, bad signature, issuer/audience mismatch, expiry, empty sub) and `firebase_user_unresolved` (Admin `getUser` definitively user-not-found: non-retryable, consumes no retry budget, persists nothing — a valid token for a deleted Firebase user must not create an account; NOT `verification_temporarily_unavailable`).
- `account_unavailable` ← `historical_identity`, `blocked_user` (barrier or in-transaction re-check; both phases; identical status/code/copy, mutually indistinguishable; a historical identity never gets `preauth_identity_not_allowed`).
- `identity_already_linked` ← `identity_already_linked` (prepare pre-check, completion re-resolution, or race loser). Remediation: `/auth/sync`.
- `challenge_required` ← `challenge_not_found`, `challenge_expired`, `challenge_consumed`, `challenge_identity_mismatch`, `challenge_operation_mismatch` (single collapsed class — completion is not a challenge-enumeration oracle).
- `create_flow_mismatch` — HTTP 409, with mandatory `required_flow` (see step 9).
- `operation_not_allowed` ← `policy_rejected`, `provider_account_already_linked`, and invalid-shape `provider_not_linked` (no flow named; routed to support).
- `verification_temporarily_unavailable` ← `firebase_lookup_unavailable` (transient/infra/selection/malformed/indeterminate lookup failure after the 3-attempt budget; persists nothing) and any Firebase-lookup budget exhaustion.
- `invalid_request` — HTTP 400, mode-signal violations only (no audit row, no internal result).
- `registration_temporarily_unavailable` — gateway-emitted 429 (see hardenings).
(The spec numerically pins only 400/409/429/403 statuses above; other classes use the statuses of the shared error registry in 00-overview.)

**Security hardenings:**
- Authentication: backend cryptographically verifies the Firebase ID token on every request in the shared pre-handler barrier (Firebase Admin `verifyIdToken()` or JWKS-backed equivalent): RS256 against cached Google securetoken keys (no per-request network call), `iss` exactly `https://securetoken.google.com/<project-id>`, `aud` exactly the project ID, `exp`/`iat` validity, non-empty `sub`. Reading claims without signature verification is prohibited. Exactly one Authorization field value with one well-formed Bearer credential (case-insensitive field name — differently-cased duplicates are duplicates; scheme matches case-insensitively, token bytes case-sensitive); zero/multiple/comma-joined values, empty token, or trailing content reject — never take first/last. Tokens never accepted from query, cookie, body, X-* headers, or gateway-projected claim headers; identity comes only from verified `iss`/`sub`; provider never from headers or token claims. Handlers must not re-implement verification or resolution; the route is registered behind the barrier with an explicit pre-auth-callable declaration (route-enumeration assertion at CI/startup enforces the three-way route partition).
- Challenge protocol: TTL 300 s, single-use, 128-bit CSPRNG opaque `challenge_id` (never sequential or identity/time-derived), server-held state only (nothing serialized to the client — no signing key, no challenge-token format), one-way lifecycle issued→claimed→consumed, claim = only expiry check, claimed rows are dead forever (no reset, no reclaim, no cleanup job, no recovery scan; expired/claimed/consumed rows retained indefinitely). Consumption dispositions: genuine identity-matched attempts consume on any terminal outcome (race loss included); identity/operation mismatches neither claim nor consume. No IP/device/TLS binding, no DPoP, no mTLS, no token-hash embedding. Where a provider nonce convention applies (Sign in with Apple), the client uses `challenge_id` as the embedded nonce and the backend hashes the STORED value, never trusting a client copy. The challenge binds no proof material. `challenge_id` is a secret capability handle: body-only transport, never in URLs, audit rows, logs, traces, analytics, or error text — correlation uses the non-secret `auth_challenges.id` row id.
- Firebase Admin confirmation: this endpooint's completion (anonymous AND registered) is 2 of the exactly 5 enumerated providerData read points. Fail closed on any failed/indeterminate lookup: never fall back to client declaration, token claim, header, or cached value; persist nothing on failure.
- Rate limits: Gateway (Envoy, required and load-bearing; via a global rate-limit service, never per-pod): per-client-IP 10 req/min (covers prepare AND complete) and deployment-wide 100 req/min AND 2,000 req/day across all sources; both fail closed as `registration_temporarily_unavailable` HTTP 429 + `Retry-After` (longest wait when multiple apply) + shared JSON body via gateway response-override (Envoy's default empty-body 429 does not satisfy the contract); identical neutral response for both buckets, never naming the exhausted bucket; sustained deployment-wide saturation must alert. A gateway-rejected request reaches no backend code: no challenge, users, identity, or audit row, no Admin lookup. Client-IP key = trusted-proxy-chain-resolved address only (`xff_num_trusted_hops` exact, outermost hop OVERWRITES forwarding headers; never client-supplied XFF/Forwarded/X-Real-IP/True-Client-IP/CF-Connecting-IP), normalized to binary, IPv4 /32, IPv6 /64 bucket (tunable /56–/48); unresolvable address → one shared unresolved bucket at the single-address ceiling (10/min); never unlimited. Backend (`limits` library, `parse_many()`, shared Redis/Valkey in production, all values in config, default fail-closed): `create_user_prepare` 10/min/ip before challenge issuance; `create_user` 10/min/ip at request receipt; `create_user_firebase_identity_lookup` 60/min deployment-wide + `create_user_firebase_identity_lookup_ip` 10/min/ip, both fail-closed, both gating `getUser` on both paths, non-destructive check + joint increment, never fused/composited (subject-keyed admission is useless here — fresh anonymous sign-ins mint a new subject per call); optional `issuer+subject_hash` secondary entry only after JWT verification, non-blocking telemetry only, never sole key, never fail-closed. No device-fingerprint key.
- Audit: request is on the audited path iff route+method matched the operation (route metadata identifies the operation before the barrier runs); exactly one durable `audit.auth_events` row per on-path attempt for its terminal outcome — inside the consuming transaction when one exists, standalone durable write for earlier rejections (barrier, prepare), always written before the response, never best-effort; if the write fails, log it and still return the earned rejection. `result` = specific internal `core.auth_event_result` (`succeeded` the only success value; no failure_reason column; never less specific than the client class). Barrier rejections on this route are first-class rows: `invalid_external_jwt` with all three actor fields NULL (CHECK-enforced) and a bounded reason (`missing_token`, `malformed`, `duplicate_authorization`, `bad_signature`, `issuer_mismatch`, `audience_mismatch`, `expired`, `empty_subject`) confined to details/metric labels — never client-visible; `historical_identity`/`blocked_user` carry actor fields. Actor subject stored only as HMAC-SHA-256 hash + key version; `actor_provider` from the stored provider column for linked events, NULL for pre-auth events, never fabricated. `details` JSON shape `{schema_version, context, verification, resolved, mutation, failure}`, non-secret only (no raw JWTs, tokens, payloads, device identifiers; redact before write); never the public `challenge_id`. Admission rejections (rate limits, budgets, mode-signal `invalid_request`, parse errors) write NO audit row — telemetry only, naming the limiter. The mandatory `invalid_external_jwt` counter metric (bounded reason × route) is the alerting source for attack volume/systemic breaks.
- Fail-closed rules: identity resolution admits only `identity_state='active'` AND `users.active=TRUE`; every other combination (historical, null, unrecognized, blocked) rejects, never falls through to pre-auth. A `core.users` row without an identity row is an internal error — fail closed, never invent/reassign an identity. Issuer mismatch rejects at the barrier (`invalid_external_jwt`/reason `issuer_mismatch`) before any Admin client selection. All error branches return identical body/status/timing (no issuer oracle). Accepted residual oracle: unlinked-vs-historical distinction at this route, bounded by the gateway limits and the need for a valid token.
- DELETIONS (must NOT be built): no backend-minted tokens or session tier; no device check/CAPTCHA/proof-of-work/attestation/integrity proof on this route in either phase or form; no anonymous-proof or restore_proof fields; no free-credit/grant/usage-row allocation at creation; no `display_name` population; no scheduled purge of challenge rows or empty anonymous users (indefinite retention); no per-request Firebase revocation check (`checkRevoked` off); no claim-header authentication; no gateway-conformance CI; no `challenge_replayed` result or stored-outcome replay; no distributed lock/lease/multi-phase commit/cleanup-scan serialization machinery; no `azp`/`nbf` rules; no per-Envoy-pod counters; no device-fingerprint rate key; no attribution-token rotation path.

## POST /auth/upgrade-anonymous

**Description:** State-changing auth operation `upgrade_anonymous_to_registered` (challenge-bearing). Authenticated, linked-identity-only route — NOT pre-auth (the barrier rejects unlinked callers with `preauth_identity_not_allowed`). Records exactly the same-Firebase-UID account-linking upgrade performed client-side by `linkWithCredential`: the anonymous and resulting registered identity share the same verified `(issuer, subject)`, and the backend flips the existing `core.external_identities` row's provider in place (never retire-and-attach, never a new identity row). It is also the REQUIRED repair path for a crash-stranded upgrade (client link succeeded, backend call lost) — its idempotence must not be optimized away. Caller: a client holding any valid Firebase ID token for the linked `(issuer, subject)` at ANY freshness, declaring the target provider `google` or `apple`.

**Business logic changes:**

Request modes: identical mode-signal partition, `invalid_request` semantics, and no-side-effect rules as create-user (`challenge=true` = prepare; body `challenge_id` = completion; both/neither/malformed shapes → HTTP 400 `invalid_request`, admission-phase, no audit row, no challenge touched).

Prepare mode (`POST /auth/upgrade-anonymous?challenge=true`):
1. Barrier resolves a linked ACTIVE identity (historical/blocked → `account_unavailable`; unlinked → `preauth_identity_not_allowed`).
2. Backend per-operation prepare limit — 08 entry `upgrade_anonymous_prepare` (recommended `5/minute; 20/hour`, key `ip+issuer+subject_hash`) — after barrier verification, BEFORE challenge issuance/persistence.
3. REQUIRED client `provider` field, `google` or `apple` (no default), normalized once by exact case-sensitive enum match; persisted as the challenge's immutable `operation_variant`.
4. Issue and persist the challenge exactly as create-user's mechanics, except identity binding is `bound_external_identity_id` = the resolved `core.external_identities.id` (binding to the row id, not merely the same user); TTL 300 s; state `issued`; response exactly `{challenge_id, expires_at}`, `Cache-Control: no-store`; no business mutation.

Completion mode flow:
1. Barrier checks (token, route admission, historical, blocked) before any challenge check. The standalone gateway limit (below) has already bounded the request.
2. Locate challenge by byte-for-byte `challenge_id`; verify operation binding and linked identity binding: currently resolved active identity's `external_identities.id` must equal `bound_external_identity_id`. Unknown/mismatch → reject before the claim, challenge left unconsumed (`challenge_not_found` / `challenge_identity_mismatch` / `challenge_operation_mismatch` → `challenge_required`).
3. Claim: same single atomic conditional update (issued + unexpired → claimed under `claim_attempt_id`); no-match → `challenge_expired` or `challenge_consumed` per row state; the claim loser performs NO work — and specifically never skips-nor-substitutes for the mandatory Firebase Admin confirmation the winner performs.
4. Variant check on the claimed row: completion's REQUIRED `provider` must equal the stored variant byte-for-byte (no re-normalization/defaulting); mismatch → `challenge_operation_mismatch` → `challenge_required`, CONSUMES the challenge, and runs BEFORE any Firebase Admin lookup. The declared target provider can never change after prepare.
5. Firebase Admin gating: budgets evaluated non-destructively, broadest-first — global `adapter_firebase_lookup` (30/min, `deployment+firebase_project_id`), then `upgrade_anonymous_to_registered_firebase_identity_lookup` (recommended `3/minute; 10/hour`, key `deployment+firebase_project_id+issuer+subject_hash`, fail-closed) — jointly incremented immediately before the outbound call (and each permitted retry); charges persist regardless of outcome; exhaustion of either → `verification_temporarily_unavailable`. This endpoint has NO backend per-operation completion request-rate entry (see hardenings).
6. Exactly ONE mandatory fail-closed Firebase Admin `getUser(subject)` providerData read immediately before the write transaction, on EVERY branch — the idempotent repeat included; no branch may skip it because the stored row already carries the declared provider. Issuer-selected Admin client only; same 3-attempt retry budget for retryable causes; no DB transaction/lock/session held across it. Provider and `provider_uid` derive ONLY from this read — never token claims, headers, client input, email, or display name.
7. Same closed classifier as create_user (no entries → anonymous; exactly one `google.com` → google; exactly one `apple.com` → apple; anything else invalid, no persistence; never first-recognized-entry, never non-empty-as-anonymous, never `firebase.sign_in_provider`). Classified provider must equal the declaration for any success. A matching registered entry must carry a non-empty `uid`; missing/empty uid = malformed/indeterminate lookup → reject, no persistence.
8. Consuming transaction: start ONE database transaction; resolve the existing identity row by verified `(issuer, subject)` and LOCK that row AND its `core.users` row (lock-and-revalidate FIRST); confirm identity and user are active. Case matrix:
   - (a) Mutable flip: stored provider `anonymous` + live classification confirms the declared provider → flip provider in place; assign `provider_uid` from the matching providerData `uid` (its ONLY assignment transition — NULL → confirmed uid, immutable thereafter); set `registered_at` if NULL; copy `email` only when stored email is still NULL, the address is non-empty, and the SAME `getUser` response reports `emailVerified = true`. All under the partial unique index `(issuer, provider, provider_uid) WHERE provider_uid IS NOT NULL` (includes historical rows). Provider, `provider_uid`, `registered_at`, and any email copy commit TOGETHER (pairing `registered_at IS NOT NULL` iff provider google/apple enforced in code; no third state). Never populate `display_name`. Set `users.updated_at`.
   - (b) Idempotent success: stored provider == declared, live classification confirms it, AND the matching live providerData `uid` == the immutable stored `provider_uid` → success with NO mutation, regardless of row history (rows created directly as registered included). The live Admin lookup + classifier agreement are still mandatory.
   - (c) Mutable-path rejection: live classification does not confirm the declaration (including EMPTY providerData — the client-side link never happened; client must run `linkWithCredential` first) → internal `provider_not_linked` → `operation_not_allowed`, no mutation; audited with a bounded cause (empty | invalid-shape | supported-provider-mismatch). Applies wherever the declared provider is unconfirmed — a stored-vs-live divergence is never answered with success.
   - (d) Conflict: stored provider is registered and diverges from the declared, Admin-confirmed binding (different provider, or same provider but live uid != stored `provider_uid`), or any providerData divergence on the idempotent repeat → internal `provider_transition_not_allowed` (distinct from `provider_not_linked`) → `operation_not_allowed`, no mutation; stored values never auto-rewritten, never converge by retry — manual operator repair only.
   - Provider-account uniqueness conflict on the flip's binding write (target `(issuer, provider, provider_uid)` triple already reserved by another identity row, active or historical) → internal `provider_account_already_linked` → `operation_not_allowed`, no mutation of user, identity, grant, or profile; the reserved uid is never reassigned; manual operator fix only. (This provider-account domain is distinct from the registered-grant `idp_account_hash` domain.)
   If the Admin lookup fails or the classifier rejects mid-completion, the transaction rolls back and nothing is mutated — no half-upgraded account.
9. Preservation: the same logical user throughout — same `core.users` and `core.external_identities` rows keep chats, credits, existing access grants, introductory value, grant-attached monthly usage, subscription records, and `core.store_purchase_tokens` (attribution tokens are never regenerated, moved, or retired). Do NOT create a new identity row, mark the source row historical, retire anything, mint any grant or free credit, create a `core.user_monthly_usage` row, read or write per-device grant bits, or count the call as a registered-grant claim — including repair/catch-up invocations, which update identity metadata ONLY. No reverse (registered→anonymous) transition and no registered-to-registered rebinding exist.
10. Consume the challenge in the same transaction as the audit row and the flip/no-op decision, on success and on any rejection at or after the Admin lookup (fresh prepare required to retry); same `claim_attempt_id` retry rule for transient commit failures, never repeating a provider call.
11. Success audit (same transaction): one `audit.auth_events` row, `result='succeeded'`, `operation='upgrade_anonymous_to_registered'`, details: movement classification `'upgrade'`; `source_user_id` (= destination user), `source_external_identity_id` (same row before the decision), `destination_user_id`, `destination_external_identity_id` (same row after), `current_identity_provider` sourced from the STORED `core.external_identities.provider` after the decision (never token claims/headers/client input); challenge correlation via the non-secret server-side challenge row id only — never the public `challenge_id`.
12. Return the resulting backend state; no backend token issued; the same Firebase ID token resolves as (still) linked next request.

Stranded-upgrade repair semantics: live providerData shows google.com/apple.com while the row still stores `provider='anonymous'`, `registered_at IS NULL` — a VALID state: not historical, not blocked, not pre-auth; no forced sign-out; no registered grant until repair succeeds; sign-out-everywhere stays fully effective. Client obligation (contract, not backend code): after every successful `linkWithCredential` and on every app start/authenticated bootstrap, compare SDK-cached providerData with backend-reported state (`/auth/sync`, `GET /users/me`); when Firebase shows a registered provider but the backend reports anonymous, silently re-invoke this endpoint — retrying transient failures, preparing a fresh challenge when the prior one expired or was consumed — until the backend reports the transition, and before claiming a registered grant or purchasing a registered-identity-dependent subscription. An `operation_not_allowed` conflict is TERMINAL: the repair loop stops (operator repair only).

Credential-already-in-use at Firebase: the client-side link failed, so there is nothing to record; a call made anyway fails the mandatory Admin confirmation (anonymous subject's providerData carries no registered provider) and rejects with no mutation of the source anonymous account. No merge. The subsequent provider sign-in yields a different `(issuer, subject)` handled by ordinary resolution with no special casing (linked → continue; no row → pre-auth → normal registered create-user; historical/blocked → rejected). The abandoned anonymous account is left entirely alone — active, keeping its user row, credits, and grant; nothing merged/transferred/retired/stripped; its anonymous grant not invalidated; required non-transfer product copy is display-only with no acknowledgment step.

Error classes (shared response shape; audit always records the more-specific internal result):
- `auth_required` ← `invalid_external_jwt`, `firebase_user_unresolved` (user-not-found: non-retryable, no budget spent, nothing persisted).
- `preauth_identity_not_allowed` ← unlinked caller rejected by the barrier (remediation: complete create-user, then retry).
- `account_unavailable` ← `historical_identity`, `blocked_user`.
- `challenge_required` ← `challenge_not_found`, `challenge_expired`, `challenge_consumed`, `challenge_identity_mismatch`, `challenge_operation_mismatch`.
- `operation_not_allowed` ← `policy_rejected`, `provider_not_linked`, `provider_transition_not_allowed`, `provider_account_already_linked`.
- `verification_temporarily_unavailable` ← `firebase_lookup_unavailable` (after the 3-attempt budget) and exhaustion of `upgrade_anonymous_to_registered_firebase_identity_lookup` or `adapter_firebase_lookup`.
- `invalid_request` — HTTP 400 mode-signal violations (admission phase, no audit row).
Rejection scope includes at minimum: unresolvable active linked identity; inactive resolved user/identity; missing or invalid declared target provider; failed closed live-provider confirmation; stored/live binding divergence; provider-account uniqueness conflict; lookup failure after budget; non-retryable lookup failure; policy rejection.

**Security hardenings:**
- Authentication: identical barrier contract as create-user (backend cryptographic verification, strict single-Authorization wire contract, verified-claims-only identity, no header identity, handlers never re-verify). Token freshness is explicitly irrelevant: any valid token for the pair suffices — safe because no token claim ever drives provider or grant decisions; flip content comes solely from server-verified providerData and every per-request decision reads the stored row.
- Proof basis (complete): the backend-verified Firebase ID token establishing `(issuer, subject)` + the existing linked identity row for that pair + the mandatory issuer-selected Firebase Admin providerData confirmation of the declared provider. The request carries NO attestation-key proof, NO integrity proof, NO restore_proof (restore_proof must be absent), NO device-check material; device-check tokens are never identity and this endpoint neither reads nor modifies per-device grant state.
- Challenge protocol: same shared mechanics as create-user (300 s TTL, single-use, CSPRNG 16-byte base64url id = nonce, server-held state, one-way lifecycle, claim-only expiry check, dead claimed rows, no serialization machinery beyond the two atomic conditional updates, no proof material bound, body-only secret transport, `Cache-Control: no-store`, no-store of `challenge_id` in audit/logs), with linked-row-id binding. Consumption dispositions identical: bound-identity attempts consume on any terminal outcome; identity/operation mismatch neither claims nor consumes.
- Firebase Admin confirmation: mandatory fail-closed `getUser(subject)` on EVERY branch, idempotent repeats included (one of the exactly five enumerated providerData read points); issuer-matched single-integration client only, no ambient/default/fallback client; selection failure fails closed as `firebase_lookup_unavailable` → `verification_temporarily_unavailable`; issuer mismatch never reaches the lookup (barrier `invalid_external_jwt` → `auth_required`).
- Rate limits: Gateway: standalone, load-bearing Envoy limit — default 3 requests/hour per linked subject, key `issuer+subject_hash` derived ONLY from Envoy's own JWT-filter-verified token metadata, evaluated only after gateway JWT verification, configuration-tunable, defined independently of any other endpoint's quota, living in gateway config (`gateway_rate_limits.upgrade_anonymous`), enforced BEFORE the Firebase Admin call (an over-limit request gets the normal rate-limit response and never reaches Firebase). Backend: `upgrade_anonymous_prepare` `5/minute; 20/hour` key `ip+issuer+subject_hash` before challenge issuance; the fail-closed `upgrade_anonymous_to_registered_firebase_identity_lookup` budget (`3/minute; 10/hour`) gating every `getUser`; global `adapter_firebase_lookup` 30/min ahead of it in the deterministic budget order, with non-destructive check + joint increment, global reported as primary on multi-exhaustion. Backend 429s carry `Retry-After` when computable; admission rejections write no audit row and leave telemetry naming the limiter. `user`-keyed limits (none here) may only ever run after barrier admission; identity-keyed limits only after that layer's JWT verification.
- Audit: one `audit.auth_events` row per on-path attempt, success or rejection (movement-audit contract): `operation='upgrade_anonymous_to_registered'`, specific internal result, details with movement classification `'upgrade'`, source/destination identity context for the same row before/after the flip or no-op decision, resolved user where known, non-secret challenge row id in its dedicated correlation field (never the public `challenge_id`), non-secret proof fingerprints where applicable; unresolvable fields omitted or NULL inside details. Written in the consuming transaction with challenge consumption when one exists; standalone durable write before the response for earlier rejections; never best-effort. Distinct-result obligations: `provider_not_linked` (with bounded empty/invalid-shape/supported-provider-mismatch cause), `provider_transition_not_allowed`, `provider_account_already_linked` each audited distinctly; barrier rejections first-class (`invalid_external_jwt` actor-NULL shape; `preauth_identity_not_allowed`/`historical_identity`/`blocked_user` with actor fields); `actor_provider` from the stored column, NULL for unresolved events; details JSON shape and redaction rules as in create-user.
- Lock ordering / transaction shape: the completion transaction locks the identity row and its users row first and revalidates before writing; it is short and database-only — the Admin call runs strictly before it, and no store/provider/network call ever runs while DB locks are held. It does not touch grant or usage rows; where any path does, the fixed order is grant row(s) FOR UPDATE first (ascending grant id), then their usage rows in the same order — never the reverse.
- Fail-closed rules: failed/indeterminate lookup persists nothing and never falls back to client-declared provider, token claim, header, or stored profile; exhausted retry budget is not success; no cached prior provider value stands in; divergent bindings are refused, never repaired in place; the one permitted transition is anonymous→google/apple; `provider_uid` immutable once set; stored provider is a monotonic server-confirmed transition record, never a mirror of live Firebase state, and is the sole per-request classifier once written.
- DELETIONS (must NOT be built): NO backend per-operation completion request-rate entry and no backend counter behind the gateway 3/hour limit (the dead backend `upgrade_anonymous` limiter entry is deleted with nothing in its place — the gateway limit is the one authoritative per-subject bound); no attestation/integrity/device-check requirement; no restore_proof handling; no grant minting, device-bit reads/writes, or registered-grant-claim accounting on any branch; no new identity row, no historical marking, no retire-and-attach, no reverse flip, no registered-to-registered rebinding; no auto-rewrite of divergent bindings; no new challenge type, webhook, polling, or scheduled reconciliation job for repair; no server-side confirmation step, target-account challenge binding, or abandoned-grant invalidation for credential-in-use fallback; no attribution-token regeneration/move/retirement; no backend token issuance or secondary auth state; no `display_name` population; no per-request providerData rederivation outside the enumerated read points and no background provider-state reconciliation.

## POST /auth/claim-anonymous-grant

**Description:** Challenge-bearing, state-changing auth operation `claim_anonymous_grant` — the only operation that may create a `core.access_grants` row with `source='anonymous_device_grant'`. Route category: **authenticated** (linked-identity-only; NOT pre-auth-callable; only `POST /auth/create-user` admits pre-auth). One of exactly four challenge-bearing operations (`create_user`, `upgrade_anonymous_to_registered`, `claim_anonymous_grant`, `claim_registered_grant`). Callers present a Firebase ID token as the single `Authorization: Bearer` credential, cryptographically verified by the backend's shared pre-handler barrier (gateway JWT filter is edge/defense-in-depth only; no claim headers). Claimants: **native** (iOS/Android) — an active linked identity that is either anonymous OR registered with stored provider `google`/`apple` (a registered claimant burns the device bit the same way; same grant, same cap); **web** — an active linked registered identity with stored provider `google`/`apple` AND stored `provider_uid` present. Stored `core.external_identities.provider` is the sole classifier; `registered_at` is never consulted. Introductory entitlement exists only as the grant this operation (or `claim_registered_grant`) creates — no other endpoint, counter, or flag allocates it.

**Business logic changes:**

*Request modes (mode-signal partition, syntactic, runs before any challenge processing, admission-phase):*
- `?challenge=true` in query, no body `challenge_id` → **prepare mode**. Body `challenge_id`, no `challenge=true` → **completion mode**. Both, neither, a `challenge` query param duplicated or with any value other than exactly `true`, or a body `challenge_id` that is null/empty/wrong type → **`invalid_request`, HTTP 400**, shared response shape naming the class. This rejection has NO side effects (issues/looks up/consumes nothing), has NO internal `core.auth_event_result`, writes NO `audit.auth_events` row (admission phase — structured security log + counter metric only). A corrected retry may reuse the same unexpired challenge. Never silently prefer one signal; never infer prepare from a missing challenge.

*Prepare mode (`POST /auth/claim-anonymous-grant?challenge=true`):*
1. Enforce prepare admission BEFORE issuing: named entry `claim_anonymous_grant_prepare` "5/minute; 20/hour" keyed by barrier-resolved `user`, plus independent `claim_anonymous_grant_prepare_ip` "10/minute; 60/hour" keyed by canonical client IP at route entry. Both must pass; never fused into one composite counter; neither key carries any device-check component.
2. Consume the barrier's typed identity context (handler never re-verifies token or re-resolves identity). Binding is always linked: `bound_external_identity_id` = the resolved `core.external_identities.id` (pre-auth callers were already rejected by the barrier).
3. Issue a single-use challenge: one `core.auth_challenges` row — `challenge_id` = 16 bytes from a CSPRNG, base64url without padding (it is both lookup key AND nonce; no second nonce); operation = `claim_anonymous_grant`; `operation_variant` = **NULL** (this operation has no client-selected variant and NO `provider` field on prepare or completion); `expires_at` from the server's own clock, TTL exactly **300 seconds** (the only TTL, no override, never extended/renewed, no grace); lifecycle state `issued` (one-way issued→claimed→consumed).
4. Response body contains exactly two fields — `challenge_id`, `expires_at` — nothing else; `Cache-Control: no-store`. Prepare performs no business-state mutation.

*Completion mode — ordered flow (order is normative rejection precedence; reject at the earliest failed step):*
1. Barrier: token verification, route policy, historical-identity and blocked-user checks — all before any challenge check.
2. Mode-signal partition (above).
3. Completion admission BEFORE the challenge is claimed: `claim_anonymous_grant` "2/minute; 6/hour; 20/day" keyed by `user` (identical key policy on every branch, native and web; no device-check/Device Recall/bot-check component); independent `claim_anonymous_grant_ip` "10/minute; 30/hour; 100/day" at route entry. Admission rejection = 429 + `Retry-After` (with shared JSON error body naming the class — a bare 429 does not satisfy the contract), leaves the challenge unclaimed, writes NO audit row.
4. Locate the challenge row by byte-for-byte `challenge_id` comparison. Verify operation binding and identity binding (resolved `external_identities.id` == `bound_external_identity_id`). Unknown id / bound-context mismatch / operation mismatch reject BEFORE the claim and leave any located challenge unconsumed (internal results: `challenge_not_found` for no-row incl. malformed; `challenge_identity_mismatch`; `challenge_operation_mismatch`; all surface `challenge_required`). DB outage during lookup is the ordinary infrastructure failure, not `challenge_not_found`.
5. **Claim** — ONE atomic conditional update: `issued`→`claimed`, stamping a server-generated `claim_attempt_id`, conditioned on still-`issued` AND `expires_at` in the future. This is the single serialization point and the ONLY expiry evaluation anywhere; nothing downstream is time-gated. No-match → `challenge_expired` (still issued but expired) or `challenge_consumed` (already claimed/consumed — one generic already-used conflict, never the claim-holder's recorded outcome; client reconciles via `/auth/sync`). The attempt that loses the claim performs NO endpoint work: no proof verification, no vendor call, no Firebase lookup, no mutation; never treated as an idempotent repeat.
6. **Branch selection** — deterministic, server-verified, from which complete evidence set the body carries: iOS = separate per-transaction DeviceCheck query AND update tokens; Android (Device Recall available) = one Play Integrity token covering Device Recall read AND write; web = Cloudflare Turnstile evidence (the ONLY web-gate body evidence). Exactly one complete set must resolve; zero, more than one, or a partial set is a request-shape error rejected before any eligibility check, vendor call, or ledger write — audited internal `proof_malformed` (shape cause in details), surfaced `proof_rejected`. No client-declared claim-channel/platform field exists or is consulted; branch selection never reads identity, stored provider, or User-Agent. A registered claimant presenting Turnstile evidence from a native app is a legitimate use of the web gate, not a bypass.
7. **Anonymous-claimant platform pinning**: `external_identities.native_claim_platform` is set once at the identity's first verified device attestation, immutable; material from the other platform is thereafter rejected.
8. **Post-claim gate work** (all after the claim, before the consuming transaction, with NO transaction/row lock/DB session held across any of it):
   - Device-bit provider budgets are checked after the claim, immediately before their own vendor call: `adapter_devicecheck_read` (30/minute, key deployment+apple_team_id) or `adapter_play_integrity_device_recall_read` (30/minute, key deployment+package_name) before the bit read; `adapter_devicecheck_write` (20/minute) or `adapter_play_integrity_device_recall_write` (20/minute) before the bit write. All fail-closed. Exhaustion → `verification_temporarily_unavailable` (NEVER the admission 429), no grant, the budgeted call is not attempted, the attempt IS on the audited path — single audit row with internal result `devicecheck_read_budget_exhausted` / `devicecheck_write_budget_exhausted` / `device_recall_read_budget_exhausted` / `device_recall_write_budget_exhausted` — and the claimed challenge is CONSUMED. A read-budget rejection stops every later step; a write-budget rejection stops write and grant even after a successful read. Additionally, the Play Integrity token/verdict verification performed on every Android claim runs under its own named fail-closed budget `adapter_play_integrity_verify` (recommended "60/minute", key `deployment+package_name`) — distinct from the `adapter_play_integrity_device_recall_read` (30/minute) and `adapter_play_integrity_device_recall_write` (20/minute) budgets — config-driven like every other entry, never hard-coded into the endpoint.
   - iOS: verify DeviceCheck proof, read **bit0** (anonymous-claimed) via the server-to-server API with configured Apple credentials and Apple team identifier; production DeviceCheck environment only. bit0=true (already claimed) → audit `native_claim_already_claimed`, reject `device_grant_exhausted`. The transaction must not touch bit1; never accept client-supplied bit values; query token never reused for the update.
   - Android: verify the Play Integrity token (under the `adapter_play_integrity_verify` budget above); Device Recall state is read ONLY from the server-side decoded verdict; a verified verdict lacking Device Recall → `proof_rejected` (no distinguishing absent capability from withheld material). Android without Device Recall has no anonymous path (forced registration).
   - Web: validate Turnstile via POST to Cloudflare siteverify (server-held secret; `remoteip` = trusted-proxy-chain-resolved canonical client address, never a client header; unresolvable address follows unresolved-address handling, never silent omission), under the fail-closed `adapter_cloudflare_turnstile_siteverify` budget (60/minute, key deployment; recommended 500 ms connect, 2 s per-attempt, 3.5 s total, max 2 attempts retrying only connection failures/429/5xx/`internal-error` under one idempotency key). Accept only `success: true` AND returned hostname on the configured production allow-list; any denial (invalid, expired, duplicate/replayed, hostname mismatch) → `verification_required`; `action`/`cdata` matching NOT required and never a denial basis. Then via the issuer-selected Firebase Admin client read `getUser(subject)` providerData and apply the closed classifier over the COMPLETE result (0 entries=anonymous; exactly one google.com=google; exactly one apple.com=apple; every other shape rejects — never "first matching entry"); classified provider must equal stored provider and the sole entry's non-empty uid must equal stored `provider_uid`; derive web `idp_account_hash = HMAC-SHA-256(k_idp_account_vN, "idp-account:v1:" || stored_provider || ":" || canonical_provider_account_id)` from that sole entry only (provider component = stored provider). Classifier/binding mismatch or empty result → `verification_required` (unsatisfied sign-in gate), never the duplicate branch.
   - Retry policy: retryable pre-grant reads, Cloudflare validation, Admin-client selection, and web providerData lookups retried in-request up to two additional times (three attempts total); exhausted budget → audit the specific dependency result, reject `verification_temporarily_unavailable`. Non-retryable rejections reject immediately without spending budget. Firebase user-not-found at the web read is non-retryable → audit `firebase_user_unresolved`, surface `auth_required`. Retries never lengthen challenge expiry and are not bounded by it.
9. **DB eligibility preflight** (after gate state, before any vendor bit or gate slot is burned): one lookup against the identity's permanent `free_grant_consumed_at` marker and the user's grant history. A set marker or ANY committed free grant of either source refuses (one free grant per account across BOTH claim endpoints, lifetime). An existing active `anonymous_device_grant` fails under the active-grant-invariant path — NOT idempotent success; no DB grant may substitute for or suppress the platform-gate read.
10. **Native bit write** (after preflight): write the anonymous-claimed bit; retry retryable failures up to two additional times; any exhausted failure/timeout/cancellation/ambiguity/inability → `verification_temporarily_unavailable` (internal `native_claim_write_failed`), no grant; only explicit vendor confirmation permits activation. Load-bearing: never best-effort/deferred/queued/out-of-band. NO execution-budget gate before the write. The read-write-activate sequence runs in a server context a client disconnect cannot cancel. Device-bit read/write are EXCLUDED from coalesced-result reuse — every claim performs its own read and own confirmed write.
11. **Activation transaction** (single, short, database-only — no provider calls, no expiry re-check): lock target user first, then the user's whole live `core.access_grants` set FOR UPDATE in ascending grant-id order, then their `core.user_monthly_usage` rows in the same order (fixed grant-then-usage lock order; no external call while holding locks). Re-resolve and reconfirm: user and identity active, identity unchanged (anonymous claimant still matching pinned platform, or registered claimant still carrying the stored provider+`provider_uid` the gate used), eligibility/marker/invariants still hold. Then insert: `core.access_grants` (`source='anonymous_device_grant'` — for both native and web; source never encodes platform — configured free tier, `status='active'`, `starts_at` not future-dated); the `core.access_grants_anti_abuse` row (native: `native_claim_provider` = `ios_devicecheck` | `android_play_integrity`, hash fields NULL — an Android claim must never record `ios_devicecheck`; web: `idp_account_hash` + `idp_account_hash_key_version`, `native_claim_provider` NULL; per-source CHECK, deferrable FKs allow either-order insert); on web, resolve-or-create the canonical `core.provider_accounts` row on (provider, provider_uid) and insert the `web_anonymous_gate` row in `core.provider_account_gate_consumptions` (unique (provider_account_id, consumption_kind), recording the produced grant_id); set `free_grant_consumed_at`; create the `core.user_monthly_usage` row (created here, never lazily by the quota path); consume the claimed challenge (second atomic conditional update, conditioned on still-claimed under this attempt's `claim_attempt_id`); append the success audit — all atomically. Platform goes in audit detail, never in `source`. A web gate-consumption conflict on the stable UID rolls back, audits `anti_abuse_already_claimed`, surfaces `device_grant_exhausted` (NEVER `account_already_claimed`). The lifetime partial unique index on (user_id, source) — no status predicate — is the concurrency-safe final eligibility check; any violation rolls back the whole transaction on its specific audited path. Transient commit failure (incl. lost ack) is retried as the same local transaction under the same `claim_attempt_id`, never repeating a provider call.
12. Success returns the resulting backend entitlement state (shared completion step 14; no backend token is issued). A crash after a confirmed vendor write but before commit burns the device slot with no grant; a lost write ack causes the whole-claim retry to read the set bit and return `device_grant_exhausted`. Accepted, uncompensated; bits never auto-cleared; remediation is an operator `manual` grant only.

*Error classes emitted (opaque, shared response shape):* `auth_required` (only `invalid_external_jwt` token-acceptance failures and non-retryable `firebase_user_unresolved` at the web read), `preauth_identity_not_allowed`, `account_unavailable` (internal `historical_identity` / `blocked_user`, indistinguishable to clients), `challenge_required` (internal `challenge_not_found` / `challenge_expired` / `challenge_consumed` / `challenge_identity_mismatch` / `challenge_operation_mismatch`), `invalid_request` (400), `proof_rejected` (every vendor-material failure: missing/malformed/vendor-rejected DeviceCheck or Play Integrity material, verified verdict lacking Device Recall, malformed Cloudflare evidence, ambiguous/partial evidence shape; unparseable material audits unified `proof_malformed`; a structurally valid proof failing verification uses the verification-failure result, never `proof_malformed`), `operation_not_allowed` (structural completion-time invariant violations only; a registered native claimant is legitimate), `device_grant_exhausted` (**HTTP 403**; internal `native_claim_already_claimed` for device state, `anti_abuse_already_claimed` for the web gate conflict; non-accusatory copy directing to the registered path; no device-check state/hashes/diagnostics disclosed), `verification_required` (internal `policy_rejected`, durable device-check read denial, server-validated Cloudflare denial, completed web providerData lookup failing classifier/stored-binding; durable — no timer retry, no guaranteed alternate), `verification_temporarily_unavailable` (internal `native_claim_unavailable`, `native_claim_write_failed`, `firebase_lookup_unavailable`, the four budget-exhausted results; Cloudflare dependency failures audit the class value `verification_temporarily_unavailable` itself — no `cloudflare_lookup_unavailable` exists; retry = whole new claim with fresh challenge + fresh vendor material). Transient failures must never surface as `device_grant_exhausted`/`verification_required` unless durable state was independently observed. Fail-closed behavior denies ONLY the free grant — never login, account creation, upgrade, sync, subscription restore, or paid entitlement.

**Security hardenings:**
- Barrier-only authentication: Firebase ID token verified via issuer-matched Firebase Admin/JWKS verifier (RS256 against cached Google keys, `iss` == `https://securetoken.google.com/<project-id>`, `aud` == project ID, temporal validity, non-empty `sub`); exactly one Authorization field with one well-formed Bearer credential (duplicates/multi-values/empty/trailing content rejected); identity only from verified (iss, sub) — never headers, cookies, query, body, or device-check material. Handlers consume the barrier's typed context and never re-implement verification/resolution. Exactly one Firebase integration; every Admin call through the issuer-matched client; no ambient/default/fallback client; issuer mismatch → audit `invalid_external_jwt` reason `issuer_mismatch`, surface `auth_required`, before any Admin work.
- Challenge protocol: 300 s TTL single-use; issued→claimed→consumed one-way; claim = the only expiry evaluation; a claimed challenge is dead — any post-claim failure consumes it, an abandoned attempt leaves it claimed forever, never reclaimed/reissued; identity/operation mismatch neither claims nor consumes (a leaked/guessed id cannot burn the rightful user's challenge); no idempotent replay — never return a stored result for a claimed/consumed challenge; no `challenge_replayed` result. `challenge_id` travels only in the prepare response body and completion request body (HTTPS), never in URLs, audit rows, or logs (log the internal `auth_challenges.id` for correlation); the challenge is never a bearer credential — completion always requires the current verified ID token. Challenge binds no proof material.
- Audit: this route is on the audited attempt path from route+method match (operation identified from route metadata before the barrier runs). Exactly one durable `audit.auth_events` row per attempt for its terminal outcome — barrier rejections included (`invalid_external_jwt` with all-NULL actor fields plus bounded reason in details: missing_token, malformed, duplicate_authorization, bad_signature, issuer_mismatch, audience_mismatch, expired, empty_subject; `preauth_identity_not_allowed`, `historical_identity`, `blocked_user` with actor fields). `succeeded` is the only success code; no failure_reason column. Written inside the consuming transaction when one exists, otherwise standalone before the response; never best-effort — an audit-write failure is logged and the client still gets the earned rejection. Actor subject stored only as HMAC-SHA-256 hash + key version; `actor_provider` from the stored column (NULL when unresolved, never fabricated); details JSON `{schema_version, context, verification, resolved, mutation, failure}`, redacted before write — no raw JWTs, DeviceCheck/Play Integrity/Turnstile tokens, attestation blobs, device identifiers, or the public `challenge_id`. Admission-control rejections and the mode-signal check write NO row (telemetry only). Audited internal result never less specific than the returned class.
- Rate limiting: Python `limits` library, `parse_many()` multi-window strings, shared Redis/Valkey storage in production, moving-window strategy, all values in the application config file (no hard-coding), default fail-closed for security-sensitive entries — this covers the request-rate entries and every named provider budget for this route (the four device-bit budgets, `adapter_play_integrity_verify`, `adapter_cloudflare_turnstile_siteverify`, `adapter_firebase_lookup`); user-keyed limits only after barrier admission (barrier-rejected requests never reach them); IP keys only from the gateway-resolved canonical address (trusted-proxy chain, unresolved-address shared bucket at 10 req/min); no raw proof/provider material as keys. Operational counters for allowed/429/storage-failure/budget-rejection/coalesced-reuse required.
- Device-check material is anti-abuse input only — never identity, ownership, recovery, or account-resolution evidence; vendor state never accepted from the client as verified; backend queries/updates vendor state only with configured Apple/Google credentials. Two-ledger model: DB authoritative for user-received-grant, vendor bit authoritative for device-slot; concurrent same-device race accepted (bounded to one extra grant). Dev/simulator bypasses of the device-check gate only via non-production server-side build/config, never enableable by any client input or production credential; no bypass for the Cloudflare gate. Per-environment Turnstile keys; production startup rejects Cloudflare test keys/dev secrets/dev hostnames; missing/invalid secrets = fail-closed misconfiguration + alert, never a client denial.
- **DELETIONS (must NOT be built):** no App Attest, Android Keystore, enrolled-key proof, per-attestation-key uniqueness, or attestation-key-derived identifiers anywhere (`invalid_attestation_or_integrity_proof` does not exist); no degraded verification mode; no client claim-channel/platform field; no proof-material age limit (no `timestampMillis` bound); no backend web-gate challenge/binding record (Turnstile single-use is the whole replay bound); no scheduled cleanup/recovery scans for challenges, web gate, or claimed rows; no distributed lock, lease renewal, or multi-phase provider commit; no pending-state machine or vendor-bit reconciliation/auto-clear; no separate claim-finalization table; no raw device IDs, installation IDs, device records, raw vendor tokens, or synthetic stable device-principal hashes in PostgreSQL; no device-check component in any rate-limit key (in any form); no cross-device anonymous recovery; no backend session/token minting; no `promo` grant source; no per-request Admin round-trips outside the enumerated providerData read points; no coalesced/cached substitute for the device-bit read or write; no `cloudflare_lookup_unavailable` audit value; no execution-budget gate before the device-bit write.

## POST /auth/claim-registered-grant

**Description:** Challenge-bearing, state-changing auth operation `claim_registered_grant` — the only operation that may create a `core.access_grants` row with `source='registered_account_grant'`. Route category: **authenticated**, linked-identity-only (pre-auth rejected by the barrier with `preauth_identity_not_allowed`). Caller: an active linked user whose current external identity has stored `provider` `google` or `apple` AND a stored `provider_uid`, presenting the Firebase ID token as the sole Bearer credential. Grants the registered free-credit allowance, superseding the user's active anonymous device grant where one exists (conversion is a transition of the one free allowance, never a second issuance). An upgrade (`upgrade_anonymous_to_registered`) never counts as a registered-grant claim; a claim after upgrade runs under normal rules including the account's grant history.

**Business logic changes:**

*Request modes:* identical mode-signal partition to claim-anonymous-grant: `?challenge=true` (exactly `true`, not duplicated) w/o body `challenge_id` = prepare; body `challenge_id` w/o `challenge=true` = completion; both/neither/malformed → `invalid_request` HTTP 400, side-effect-free, no audit row, admission-phase.

*Prepare mode (`?challenge=true`):* prepare admission BEFORE issuance: named entry `claim_registered_grant_prepare` "5/minute; 20/hour" keyed by `user`. Then issue one `core.auth_challenges` row: `challenge_id` = 16 CSPRNG bytes base64url unpadded (lookup key AND nonce), operation `claim_registered_grant`, `operation_variant` **NULL** (no client-selected variant; NO `provider` field on prepare or completion), `bound_external_identity_id` = resolved identity row id, `expires_at` = server clock + **300 s** (no override/extension/renewal), state `issued`. Response: exactly `{challenge_id, expires_at}`, `Cache-Control: no-store`, no mutation.

*Completion mode — ordered flow:*
1. Barrier (token verification, route policy, historical/blocked checks) before any challenge check. Pre-auth/unlinked → `preauth_identity_not_allowed`; inactive/blocked user or historical identity → `account_unavailable` (internal `blocked_user` / `historical_identity`).
2. Provider gate from stored state only: provider not `google`/`apple` (incl. `anonymous`) or absent `provider_uid` → audit `idp_account_not_eligible`, return `verification_required`. `registered_at` never consulted; live Firebase state never reclassifies the account; no registered→anonymous downgrade exists.
3. **`idp_account_hash` derivation runs BEFORE admission and before the claim** (needs no Firebase/vendor call): `idp_account_hash = HMAC-SHA-256(k_idp_account_vN, "idp-account:v1:" || stored_provider || ":" || stored_provider_uid)`, current key version, inputs only from the stored identity binding — never client input, headers, token claims, email, or display name. The Firebase UID is never the uniqueness anchor.
4. Completion admission: named entry `claim_registered_grant` "2/minute; 6/hour; 20/day" keyed `user + idp_account_hash`, enforced after derivation and BEFORE the mandatory Firebase providerData confirmation and before the challenge claim. Admission rejection: 429 + `Retry-After` with shared JSON body naming the class; challenge left unclaimed; no audit row.
5. Challenge lookup (byte-for-byte), operation + identity binding checks (mismatch rejects BEFORE the claim, challenge unconsumed), then the atomic **claim** (`issued`→`claimed` + `claim_attempt_id`, conditioned on still-issued AND unexpired — the ONLY expiry check; no-match → `challenge_expired` or `challenge_consumed`, both surfacing `challenge_required`). The losing duplicate performs no work — including never skipping or duplicating the Firebase confirmation. All later gate work runs after the claim with no DB session held across it.
6. **Mandatory fail-closed Firebase Admin providerData confirmation** — exactly one `getUser(subject)` read through the issuer-selected Admin client, on EVERY branch, the idempotent repeat included; no branch may skip it. The complete live result must pass the closed classifier (0 entries=anonymous; exactly one google.com=google; exactly one apple.com=apple; any other shape — both providers, multiple entries, unrecognized entries — rejects; never "first matching entry") AND match BOTH stored provider and stored `provider_uid`. A divergent result is a conflict that mutates nothing, denies ONLY this free grant, and never rewrites the stored binding (manual operator fix only). user-not-found: non-retryable, audit `firebase_user_unresolved`, surface `auth_required`. Transient failure (timeout/5xx/quota/permission/malformed response/integration-auth): retried in-request up to two additional times (three attempts total); exhausted → audit `firebase_lookup_unavailable`, surface `verification_temporarily_unavailable`. Never fall back to client-declared provider, token claims, or cached values.
7. **Claim-kind resolution** — server-side, solely from which complete evidence set the request carries: iOS = separate per-transaction DeviceCheck query + update tokens (unconditionally mandatory on every iOS claim, no availability gate); Android = one Play Integrity token (a verdict is mandatory on EVERY Android claim regardless of Device Recall; the token covers Device Recall read+write where required); web = Cloudflare Turnstile evidence plus the account rules. Zero/multiple/partial sets → `proof_rejected` before any eligibility check, vendor call, or ledger write; omitting native material can never turn a native claim into an account-only claim. Android Device Recall is additionally mandatory only where the checked-in server release policy (enumeration by package name, signing-certificate digest, release; classes `device_recall_required` | `no_device_recall`) requires it; an unenumerated release is rejected outright; `no_device_recall` releases carry no registered bit and rest on account rules alone. No client platform header participates. Accepted, documented bound: a native client may present as web and take the Turnstile gate; the account layer (stable provider-UID uniqueness, mandatory Turnstile, account history) still binds. The Play Integrity token/verdict verification performed on every Android claim — including `no_device_recall` releases — runs under its own named fail-closed budget `adapter_play_integrity_verify` (recommended "60/minute", key `deployment+package_name`), distinct from the Device Recall read and write budgets, config-driven like every other entry, never hard-coded.
8. **Device-checked kinds** read the registered-claimed state before the DB preflight: iOS **bit1** only (never touch bit0), read/updated via the DeviceCheck server-to-server API with configured Apple credentials + team identifier, production environment only; Android reads the distinct registered recall state from the server-side decoded verdict only (verdict lacking Device Recall → `proof_rejected`). Read/write are governed by the same four fail-closed device-bit budgets (`adapter_devicecheck_read` 30/min, `adapter_devicecheck_write` 20/min, `adapter_play_integrity_device_recall_read` 30/min, `adapter_play_integrity_device_recall_write` 20/min — the two Device Recall budgets distinct from the `adapter_play_integrity_verify` verdict-verification budget), checked after the claim immediately before each vendor call; exhaustion → `verification_temporarily_unavailable` (never 429), no grant, audited on the single row as `devicecheck_read_budget_exhausted` / `devicecheck_write_budget_exhausted` / `device_recall_read_budget_exhausted` / `device_recall_write_budget_exhausted`, claimed challenge CONSUMED. Already-set bit → `device_grant_exhausted` (403). Web kind: validate Turnstile before the DB preflight (siteverify with server secret, `remoteip` = canonical resolved client address, `success:true` + production hostname allow-list, under the fail-closed `adapter_cloudflare_turnstile_siteverify` budget 60/min); denial → `verification_required`; dependency failure → `verification_temporarily_unavailable`.
9. **DB preflight / destination eligibility** (after an unset bit, or immediately on web): inspect grant history + `free_grant_consumed_at` under the one-free-grant-per-account rule. An active anonymous grant is eligible only for supersession conversion; an existing committed registered grant selects the idempotent-repeat determination; no free-grant history selects new-grant creation; any other committed free grant refuses.
10. **Registered-bit write** (device-checked kinds; Android only where `device_recall_required`): after the preflight, before the completion transaction; retry retryable failures up to two additional times (three total); any exhausted failure/timeout/cancellation/ambiguity/invalid-or-withheld write material/inability → pre-activation refusal `verification_temporarily_unavailable`, no grant; only explicit vendor confirmation permits the transaction. Load-bearing write; no coalesced/cached substitute; uncancellable execution context; no execution-budget gate.
11. **Completion transaction** (short, database-only; lock target user first, then every live `core.access_grants` row + corresponding anti-abuse row FOR UPDATE in ascending grant-id order, then usage rows in the same order; no external call under locks):
    - Step 1: re-resolve and reconfirm user active/unblocked, identity active (not historical), and the exact stored provider/`provider_uid`/registered state used for the hash still apply; failures audit distinct internal results and surface `account_unavailable`, no mutation.
    - Step 2 — select exactly ONE destination, in this order: (a) **idempotent repeat FIRST**: a committed `registered_account_grant` already in history → after the (already-performed) mandatory confirmation, return that grant only when the registered gate-consumption rows identify the same grant; a consumption row belonging to a different grant is a conflict. (b) any other active grant (neither an anonymous device grant nor the user's own committed registered grant), under the shared effective-grant predicate (`status='active' AND starts_at <= now AND (ends_at IS NULL OR ends_at > now)` — a time-ended row does not block even before its lazy flip; this operation's own insert performs the flip) → audit `registered_grant_destination_incompatible`, reject `operation_not_allowed` carrying machine-readable `held_grant_ends_at` (the held grant's `ends_at`, or `null` when open-ended; nothing else about the held grant disclosed), mutating nothing — a wait, not a forfeit; and it is evaluated in the preflight AHEAD of the registered-bit write so an ordinary rejection burns no device slot. (c) active `anonymous_device_grant` → **supersession conversion**. (d) no free-grant history → **new-grant creation**.
    - Step 3 conversion: move the anonymous grant to `status='expired'`, `ends_at` = conversion time; `source` stays `anonymous_device_grant` forever; its anti-abuse row untouched. Insert the new active `registered_account_grant` with its own anti-abuse row (`idp_account_hash` + key version). Create the new grant's `core.user_monthly_usage` row in the same transaction carrying over the superseded grant's `monthly_period` AND `monthly_used` exactly — no reset, clamp, prorate, or top-up (the tier-sizing invariant — every registered tier's `monthly_credits` >= the anonymous tier's — makes this safe). One transition of the one allowance: afterwards history shows both free sources consumed, one active grant. In-place source mutation forbidden.
    - Step 4 new-grant creation: insert active `registered_account_grant`, anti-abuse row (hash + key version), usage row with current `monthly_period` and `monthly_used = 0`.
    - Step 5 (either mutating destination): resolve-or-create the canonical `core.provider_accounts` row for the confirmed stable UID (unique (provider, provider_uid); rows immutable, never deleted/reassigned); insert the `registered_account_grant` row in `core.provider_account_gate_consumptions` (unique (provider_account_id, consumption_kind), recording the produced grant_id); set `free_grant_consumed_at` where unset; deferred FKs checked at commit. A gate-consumption conflict rolls back, audits `idp_account_already_claimed`, returns `account_already_claimed` — final for that provider account regardless of hash key version (rotation never reopens the gate; required regression test: claim under a new key version for an account consumed under the old one must reject). Any other insertion/uniqueness failure (incl. the lifetime (user_id, source) partial unique index — the concurrency-safe final check — and the one-active-grant index) rolls back the whole transaction leaving the anonymous grant active and unchanged.
    - Step 6: consume the claimed challenge and append the success audit atomically with the mutation (audit: barrier actor context, stored provider, HMAC key version, destination case, grant id — never raw provider identifiers).
    - Step 7: **return the active registered grant, tier, and current usage state.** No backend token is issued.
    - Retries of the transaction (transient failure, lost commit ack) run under the same `claim_attempt_id`, never insert duplicate grants/anti-abuse rows, never invoke the destination mutation twice, never repeat a provider call, and are not bounded by challenge expiry.
12. A crash/lost-ack/rejection after a confirmed bit write leaves the bit set — burned slot, accepted, never auto-cleared or reconciled; remediation = operator `manual` grant only. Client retry after any failure is a whole new claim with fresh challenge and fresh vendor material.

*Error classes emitted (opaque, shared response shape):* `auth_required` (`invalid_external_jwt`; `firebase_user_unresolved` at the mandatory read), `preauth_identity_not_allowed`, `account_unavailable`, `challenge_required` (five internal challenge results as above), `invalid_request` (400), `proof_rejected` (only missing/malformed/partial client DeviceCheck or Play Integrity transaction material for the selected kind, incl. the evidence-set shape error; never for S2S/Turnstile dependency failures, which map to `verification_temporarily_unavailable`), `operation_not_allowed` (`registered_grant_destination_incompatible` + `held_grant_ends_at`, and other structural blocks), `device_grant_exhausted` (**403**, already-set registered device state), `verification_required` (`idp_account_not_eligible` — remediation: sign in with/upgrade to/link Google or Apple, then retry; also Turnstile denial), `account_already_claimed` (`idp_account_already_claimed`; terminal for the provider account; MUST NOT be conflated with `device_grant_exhausted`, and a web anonymous-gate conflict never maps here), `verification_temporarily_unavailable` (vendor outage after retry budget, `firebase_lookup_unavailable`, four device-bit budget-exhausted results). Non-retryable results reject immediately without consuming retry budget: `idp_account_not_eligible`, `idp_account_already_claimed`, `registered_grant_destination_incompatible`, `policy_rejected`. A durable `verification_required` or `account_already_claimed` promises no alternate free-credit path. Audited internal value never less specific than the returned class; grant-time `account_already_claimed`/`idp_account_already_claimed` and identity-write-time `provider_account_already_linked`/`operation_not_allowed` are distinct outcomes, never conflated.

**Security hardenings:**
- Same barrier/wire contract as claim-anonymous-grant: backend-only cryptographic verification of the Firebase ID token (RS256/iss/aud/exp/iat/non-empty sub; strict single Authorization field; no token from query/cookie/body/X-headers), identity solely from verified (iss, sub) resolved against `core.external_identities`; positive admit only `identity_state='active'` AND user `active=TRUE`; handlers never re-verify or re-resolve; single Firebase integration, issuer-selected Admin client, no ambient/default client, fail-closed selection.
- Challenge protocol hardenings identical to claim-anonymous-grant: 300 s TTL, single-use, one-way lifecycle, claim as sole serialization + sole expiry check, claimed-is-dead, mismatches reject pre-claim without consuming, duplicates get generic `challenge_consumed` conflict (never the claim-holder's outcome), no replay/stored-result, `challenge_id` never in URLs/audit/logs, challenge is never a bearer credential, binds no proof material; no distributed locks, lease renewal, cleanup jobs, or reclaim paths.
- Uniqueness/anti-abuse: global per-provider-account uniqueness enforced on the stable provider UID via `core.provider_accounts` + gate-consumption rows — never on hash bytes; `idp_account_hash` (+ key version) is a non-authoritative lookup/audit alias only; old HMAC key versions may stay valid for lookup during rotation, new writes use the current version, and any retained version must resolve to the same canonical row; if rotation cannot guarantee no gate reopening, do not rotate. Raw provider account identifiers persist ONLY in `core.external_identities` and `core.provider_accounts` — never in audit rows or anti-abuse records. `free_grant_consumed_at` is permanent non-PII state: set atomically in the grant-commit transaction, never cleared, survives expiration/conversion/sign-out/retirement/PII erasure; provider_accounts and gate-consumption rows also survive erasure.
- Firebase Admin confirmation points: this endpoint is one of exactly five providerData read points and is read-only (a confirmation, never a write of provider/provider_uid). Every call performs it, fail-closed, through the issuer-selected client; no path substitutes a client-declared or assumed provider; a failed/indeterminate lookup is never read as empty providerData and persists nothing.
- Rate limits (config-driven, `limits` library, parse_many, shared Redis/Valkey, moving-window, fail-closed default, all in the config file): `claim_registered_grant_prepare` "5/minute; 20/hour" key user; `claim_registered_grant` "2/minute; 6/hour; 20/day" key `user+idp_account_hash` (hash component derived only from the stored identity row, only in HMAC-derived form); generic default "120/minute" key ip backstops the route; four device-bit budgets + Turnstile budget as listed; `adapter_play_integrity_verify` "60/minute" key `deployment+package_name` damping the Play Integrity token/verdict verification performed on every Android claim (distinct from the `adapter_play_integrity_device_recall_read` 30/minute and `adapter_play_integrity_device_recall_write` 20/minute budgets); global `adapter_firebase_lookup` "30/minute" key deployment+firebase_project_id budgets Admin getUser traffic. User-keyed limits only after barrier admission; identity-keyed limits only after JWT verification at the evaluating layer; IP keys only from the canonical gateway-resolved address (unresolved bucket 10/min); no device-check material in any key, in any form. 429 rejections carry `Retry-After` and the shared JSON body naming the class.
- Audit: on the audited attempt path from route match; exactly one `audit.auth_events` row per attempt (barrier rejections included, with actor-NULL shape for `invalid_external_jwt`); success row written in the consuming transaction with challenge consumption and mutation; rejection rows durably appended before the response; `succeeded` sole success code; `challenge_row_id` = internal `auth_challenges.id`, never the public handle; details redacted, schema `{schema_version, context, verification, resolved, mutation, failure}`; success details include stored provider (from the stored column, never token claims), `idp_account_hash_key_version`, destination case, grant id, non-secret account context. Admission rejections: no row, telemetry only.
- Lock ordering: target-user lock first, then live grant set FOR UPDATE ascending grant id, then usage rows in the same order; no store/provider/network call while holding those locks (all provider work runs before the transaction opens).
- **DELETIONS (must NOT be built):** no `restore_proof`; no client-supplied provider account identifier (never required, accepted, or evaluated); no App Attest, Android Keystore, or any device material as identity/ownership/recovery/account-resolution evidence; no attestation-key verification or attestation-derived identifiers; no automatic registered→anonymous downgrade and no auto-rewrite of a divergent stored binding (manual operator fix only); no grant ranking, stacking, queued/pending claims, or any client-reachable call that ends/drops/replaces a held grant (an active `manual` grant is waited out); no `promo` source and no generic grant-writing path outside the source enumeration (`subscription`, `anonymous_device_grant`, `registered_account_grant`, `manual` — exhaustive, fail-closed); no idempotent replay of a consumed challenge; no per-operation TTL override; no `challenge_replayed` result; no scheduled cleanup of challenge rows; no coalesced/cached device-bit reads or writes; no device-check key component in admission keys; no raw vendor tokens, device identifiers, or synthetic device-principal hashes in PostgreSQL; no `registered_at` as an eligibility input; the Firebase UID never as the uniqueness anchor; no execution-budget gate before the registered-bit write; no retry/compensation machinery for burned device slots (manual-source remediation only).

# Implementation Brief: Restore + Store Webhooks (auth refactor)

## POST /auth/restore-subscription

**Description:** Canonical state-changing auth operation `restore_subscription` (`core.auth_operation` enum value `restore_subscription`). Category: **authenticated, state-changing auth operation** — behind the shared pre-handler barrier, on the audited attempt path, but **NOT challenge-bearing**. Called only by the native iOS and Android apps by a signed-in, **linked, registered, active** user, presenting `Authorization: Bearer <Firebase ID token>` (cryptographically verified by the backend) plus a `restore_proof` body field carrying the store artifact alone: a signed StoreKit transaction (iOS/Apple) or a Google Play purchase token (Android/Google Play). Its purpose: attach verified paid store-subscription entitlement to the current authenticated user, without rebinding any prior account, chats, or identities. Verified store proof is authoritative for subscription entitlement only.

**Business logic changes:**

*Request contract*
- Single call. No prepare phase, no `challenge=true` mode signal, no `challenge_id`, no operation variant, no `core.auth_challenges` row (the DB CHECK refuses one for this operation). The store artifact is the entire proof set; no App Attest, Play Integrity, or any attestation/integrity proof is required or accepted.
- Reject any request that omits `restore_proof` or substitutes non-store-proof material.
- Native-only surface gate: a web call, or any call presenting no native store-artifact family, or one store's artifact presented from the other platform, is rejected deterministically with the shared class `operation_not_allowed` (NOT `proof_rejected` — there is no proof to evaluate). This gate fires **before** restore's client error mapping; it is not a restore internal result and does not enter the restore mapping table.
- No prior-account recovery credential of any kind exists or parameterizes restore; authorization = backend-verified ID token + server-verifiable store proof, nothing else.
- Destination is always the current authenticated user; the client never selects a branch (no transfer endpoint, no transfer flag).

*Branch model*
- Two server-determined branches, resolved from verified server state alone by comparing the canonical `core.subscriptions` row's current owner (`user_id`) against the destination user: equal → **same-account**; unclaimed (`user_id` NULL) or no canonical row → **adoption** (adoption-with-creation when no row exists); different linked account → reject `store_transaction_already_linked`. Cross-account entitlement transfer is **never** performed.
- Lifetime binding, applied on every attempt independent of branch: the verified transaction's stable identity (Apple `originalTransactionId`; Google Play purchase token + linked purchase) is bound to one account for life via `core.subscriptions.restore_bound_user_id`. Destination equals a non-NULL binding → idempotent re-restore success; destination differs from a non-NULL binding → `store_transaction_already_linked`, never silently re-linked (moving the binding is manual operator repair only); successful restore of either branch sets the binding where still NULL, in the same transaction; never changed once set.
- Destination must be an active, **registered** account. "Anonymous" = zero provider-bearing `core.external_identities` rows (no `google`/`apple` row). Anonymous destination → audit `restore_destination_anonymous`, rejected before any ownership, grant, or cap change, enforced by the backend from stored identity state.

*Two-phase flow — pre-transaction steps (after the shared barrier admits):*
1. Verify `restore_proof` server-side, including the embedded signed transaction, directly against the store (never the device): StoreKit JWS verified against Apple's certificate chain or via App Store Server API Get Transaction Info (bundle ID, product ID, environment checked); Google purchase token via Play Developer API `purchases.subscriptionsv2.get` (package name, product, subscription state checked). Invalid/malformed/failed proof → reject (internal `invalid_restore_proof`), no restore mutation. Runs before branch determination.
2. Resolve the store subscription identity through `core.subscriptions` by a **non-locking** read of the canonical `(provider, external_id)` row. No row → mark the attempt **adoption-with-creation** (row created inside the locked transaction) — a missing row is NOT a rejection.
3. Extract the purchase UUID from the verified transaction where carried (Apple `appAccountToken`, Google `obfuscated_external_account_id`). A transaction carrying no UUID is NOT rejected (store-initiated transactions legitimately omit it); bookkeeping later uses a server-generated internal purchase UUID.
4. Resolve the `core.store_purchases` row directly by `(provider, external_id)` (never token-only resolution — one token spans an account's whole purchase history), non-locking. Missing row → created later in the locked transaction, no rejection. Carried UUID differing from the resolved row's recorded `identity_value` → reject `restore_purchase_uuid_mismatch`, no mutation.
5. Determine the provisional branch from the owner read in step 2: equal → same-account; unclaimed/no row → adoption; different account or non-NULL `restore_bound_user_id` differing from destination → reject, audited `restore_source_user_inactive` where the linked source account is inactive (blocked/retired), `store_transaction_already_linked` otherwise. The locked phase re-confirms.
6. Same-account skips steps 7–8 (no live store-state verification) and goes straight to the locked phase.
7. Adoption only: short-circuit — if the canonical row read in step 2 is not currently product-entitled → reject `restore_subscription_not_entitled`, no mutation, no provider call. Not applicable on adoption-with-creation.
8. Adoption only: **live store-state verification** — exactly **one** outbound provider call (Apple App Store Server API, e.g. Get All Subscription Statuses, for the verified `originalTransactionId`; or Google Play Developer API `purchases.subscriptionsv2.get` for the verified purchase token + subscriptionId), using backend-held credentials, inputs only from server-verified restore material and locally resolved state. Missing/unknown/expired/revoked/refund-voiding/non-entitled live state, or **any** failure or timeout of the single call (transient or non-retryable) → reject `restore_store_state_unverified`, no mutation. **No in-request retries, no retry knob.** Record the outcome with the resolved `(provider, external_id)`, the specific `core.subscriptions.id` covered (or note of its absence on adoption-with-creation), and a server-issued verification timestamp — this record is what the locked phase consumes.

*Locked mutation transaction steps:*
9. Deterministic lock order: (a) store-subscription-level serialization for `(provider, external_id)` (on adoption-with-creation, serialization keyed on store-verified identifiers IS this lock) together with the canonical `core.subscriptions` row where one exists; (b) grant rows — current-term (most recent) subscription-backed grant where one exists, and any current active grant of the destination — FOR UPDATE in **ascending grant id (primary key) order**; (c) their `core.user_monthly_usage` rows in the same order; (d) the resolved `core.store_purchases` row. **No account/user-row lock at all.** Lock-wait timeout, deadlock, or serialization failure → roll back and re-run the locked transaction in full, at most **ONE** retry per attempt; the retry repeats no pre-transaction step and makes no provider call (reuses the recorded verification, still subject to the step-17 freshness recheck); the rolled-back audit row rolls back too, so the attempt still writes exactly one row; a retry that finds the outcome settled by a concurrent transaction returns that state rather than mutating again; after the single retry, fail through the ordinary rejected-attempt path.
10. Re-resolve subscription state, grant, ownership, purchase row, and destination entitlement from locked rows. The locked phase performs only database-local checks — **no Apple/Google calls, no provider retries while holding locks**.
11. Confirm product-entitled under locked state (statuses exactly `active` and `grace_period`, per the `product_entitled_subscription_id` generated column; `billing_retry`/`expired`/`revoked` are not entitled) else reject `restore_subscription_not_entitled`. On adoption-with-creation, applies to the store-verified state the row is created at.
12. Confirm the `(provider, external_id)` still has its canonical row corresponding to the pre-transaction subscription; gone/different → `restore_subscription_unlinked`. On adoption-with-creation, a row that appeared since (late ingestion, concurrent restore) becomes the resolved row and is re-evaluated under ownership rules; otherwise creation proceeds here.
13. Confirm the purchase row is still present — missing → `restore_purchase_uuid_unknown`; recorded attribution no longer matching the carried UUID → `restore_purchase_uuid_mismatch`. On the creation path, an appeared row becomes the resolved row and is re-evaluated.
14. Confirm destination `active = TRUE` else `blocked_user`; confirm the identity is still linked to the destination; re-confirm registered destination else `restore_destination_anonymous`; re-confirm lifetime binding — non-NULL `restore_bound_user_id` differing from destination → `store_transaction_already_linked`.
15. Compare locked canonical `core.subscriptions.user_id` with the subscription-backed `core.access_grants.user_id` **directly, before branch re-confirmation and any mutation**; differ → `restore_subscription_grant_owner_mismatch`, no mutation, movement_classification `unclassified`, no transfer-cap state touched.
16. Resolve the outcome from locked state (same-account / adoption / `store_transaction_already_linked` with `unclassified`). Any divergence in any direction from the pre-transaction determination → `restore_branch_inconsistent`, no mutation, `unclassified`; the locked phase must NOT silently adopt the locked-state outcome. Evaluated before step 17, so a diverging same-account attempt surfaces as `restore_branch_inconsistent`, never `restore_store_state_unverified`.
17. Adoption only: confirm the recorded pre-transaction live verification is still fresh under the configured freshness bound (deployment policy) and corresponds to the locked subscription — matching `(provider, external_id)` and, where recorded, matching `core.subscriptions.id`; on adoption-with-creation the `(provider, external_id)` match is the whole correspondence. Stale or non-corresponding → `restore_store_state_unverified`, no mutation, **no re-run/refresh/extension of live verification under any circumstance**.
18. Apply branch-specific preconditions and perform the branch mutation from locked, re-resolved local state only, preserving one-active-grant and ownership invariants; set `restore_bound_user_id` to the destination where still NULL, same transaction.
19. Write one `audit.auth_events` row for every attempt (see Security).

*Same-account branch:*
- Entry: current owner = destination (agreeing with grant `user_id`), destination active. An already-owned restore — even when `core.store_purchases.purchase_user_id` names a different historical token-bound user — IS this branch, never `restore_destination_already_entitled`.
- Grant settlement, exactly one case: (a) entitled + grant already active → **idempotent success** (no owner change, grant keeps its id, usage row stays on the same `grant_id`, `last_cross_account_transfer_month` untouched); (b) entitled + grant expired → **reactivate** the current-term (most recent) grant row via UPDATE in the same transaction — status back to `active`, entitlement/expiry fields re-derived from the subscription's current paid period — reusing the row, never minting a new one; (c) entitled but a **different** active grant stands (any source, e.g. a manual grant issued during the lapse) → reject `restore_destination_already_entitled`, never expiring the other grant, no source exempt or outranking; (d) not entitled → `restore_subscription_not_entitled`, never activate.
- An entitled, owned subscription with **no** subscription-backed grant row at all is data corruption: fail closed with `internal_error`, never create the grant on this branch.
- Purchase rows: never update/revoke; if the verified transaction resolves to no `core.store_purchases` row, insert it once from store-verified data (server-generated internal purchase UUID where the transaction carries none; destination = current owner as `purchase_user_id`); immutable once written.
- Any policy-permitted state refresh (tier/status confirmation from verified proof) updates the canonical row and grant in the same transaction under the regular subscription-state dedupe rules. No fresh monthly counter — the usage row stays attached to the same `grant_id` for the grant's life.

*Adoption branch (successor of the former cross-account transfer branch — configuration entries, admission-limit names, and API surfaces named `cross_account` continue to govern it unchanged):*
- Entry: canonical row unclaimed (no linked account, binding unset) or absent (adoption-with-creation); no source user exists; destination active, registered, holding **no** different active grant of any source else `restore_destination_already_entitled` (hard reject — never expire/replace/revoke another grant to make room); product-entitled at pre-transaction read and under lock; live verification run pre-transaction, fresh and corresponding at the recheck.
- Mutations, all inside the locked transaction: (1) attach by updating the canonical row in place — set `user_id` to destination, leave status/tier at the current product-entitled state — or on adoption-with-creation create the canonical row from store-verified data under `(provider, external_id)` uniqueness, status at the live-verified state, `tier_id` from the server-controlled store-product-ID-to-tier mapping (never client-supplied); (2) create the subscription-backed `core.access_grants` row for the destination at the subscription's current `tier_id`, linked to the canonical subscription, together with its `core.user_monthly_usage` row, in the same transaction, so `core.subscriptions.user_id` = grant `user_id` holds at commit (the grant-activating statement runs against a grant-free destination under the expire-first ordering); (3) created grant: `status='active'`, `starts_at <= now`, `ends_at IS NULL`; (4) never mutate any existing active grant on the destination; (5) move/mutate/rebind **nothing else** — no chats, messages, identities, profile fields, anonymous device grants, manual grants, or non-subscription usage rows; (6) beyond the insert-once creation of a missing purchase row (store transaction identifiers, echoed or server-generated UUID, destination as `purchase_user_id`), no `core.store_purchases` insert/update/revoke; (7) allocate no free-credit or manual grant; (8) mutate no `core.external_identities` row.
- No user-facing notification on success; the user observes entitlement through the existing `/auth/sync` reporting.
- Postconditions: destination is `user_id`, lifetime binding set, grant `user_id` = destination; later restores of this transaction are same-account for the destination, `store_transaction_already_linked` for anyone else.

*Grant-mutation ordering (restore paths only):*
- `ix_access_grants_one_active_per_user` is a plain, **non-deferrable** unique index enforced per statement, so expire-then-insert/activate is mandatory: superseded or stale grant rows **of the same subscription only** are expired (never deleted) in their own earlier statement(s) with a recorded reason code (e.g. `superseded_by_restore`) in the audit row's mutation details before any statement makes the subscription-backed grant active; the destination may momentarily hold zero active grants. A **different** active grant is never expired to make room — that is the conflict rejection. All entitlement/ownership/linkage validation completes before any grant mutation; commit only after all writes succeed, rolling back earlier expiries on failure. No DEFERRABLE replacement and no application rejection path for the index (unreachable under correct ordering; if it fires, the transaction fails as a conflict/retry-class error).
- Restore never creates a second active subscription-backed grant for the same store subscription; later terms come from ingestion's per-term renewal, never from restore. Restore never moves a grant to another user and never mints a fresh monthly counter for the same paid entitlement.

*Response and error classes:*
- Success returns the resulting backend state; entitlement is subsequently reported through `/auth/sync`.
- Shared classes, exactly per 00-overview: `auth_required` (internal `invalid_external_jwt` only — barrier token-acceptance failures: missing/malformed/duplicated Authorization, bad signature, issuer/audience mismatch, temporal invalidity, empty sub; `firebase_user_unresolved` cannot arise here because restore performs no Firebase Admin getUser/providerData lookup of any kind — restore is not one of the five enumerated providerData read points), `preauth_identity_not_allowed` (unlinked caller), `account_unavailable` (historical_identity / blocked_user, including a blocked destination), `operation_not_allowed` (surface gate, pre-mapping). `challenge_required` is **not** a restore class. `restore_destination_anonymous` keeps its own distinct operation-specific rejection in the shared response shape.
- Restore-specific mapping table (exhaustive; every internal result past the gates maps to exactly one class; no shared class appears in it; no internal value reaches the client raw):
  - `restore_proof_rejected` ← `invalid_restore_proof`, `restore_store_state_unverified`. Remediation: re-prepare proof from current store state, retry; on repeated failure, contact support.
  - `restore_not_found` ← `restore_subscription_unlinked`, `restore_purchase_uuid_unknown`, `restore_purchase_uuid_mismatch`, `restore_subscription_not_entitled`. Terminal: "no active subscription found — cannot be restored"; not a rebuild-and-retry.
  - `restore_transfer_rejected` ← `store_transaction_already_linked`, `restore_source_user_inactive`, `restore_subscription_grant_owner_mismatch`. Terminal; response exposes no source-account state.
  - `restore_already_entitled` ← `restore_destination_already_entitled`. Terminal but benign; client must not retry; refresh entitlement state and return to the subscribed experience.
  - `restore_temporarily_unavailable` ← `restore_branch_inconsistent` AND the fail-closed mapping for any restore internal result the table does not name (logged and alerted server-side, never serialized to the client). Remediation: later user-initiated retry only.
- Admission-control rejections: HTTP **429 Too Many Requests** with `Retry-After` when computable; gateway over-limit rejections must carry the shared JSON error body naming the class (a bare 429 does not satisfy the contract).

**Security hardenings:**

*Authentication / barrier*
- Behind the shared, mandatory, default-on pre-handler barrier: backend cryptographic verification of the Firebase ID token (RS256 against cached Google securetoken keys; `iss` exactly `https://securetoken.google.com/<project-id>`; `aud` = the configured Firebase project ID; temporal validity; non-empty `sub`) on every request; strict Authorization wire contract (exactly one field value, one well-formed Bearer credential; duplicates/comma-joins/empty/trailing content rejected as `invalid_external_jwt`). Identity is only the verified `(iss, sub)` resolved through `core.external_identities`/`core.users`. Handler consumes the barrier's typed identity context; it never re-verifies tokens or resolves identity itself. `core.users.id` is never an authentication key.
- Barrier rejects pre-auth (unlinked) callers here with `preauth_identity_not_allowed`; historical identities and blocked users with `account_unavailable` (internal `historical_identity`/`blocked_user`). Positive test: admit only `identity_state='active'` AND user `active=TRUE`.
- Restore performs **no** device-check verification and neither reads nor modifies per-device grant state (DeviceCheck / Play Integrity Device Recall). No attestation of any kind. Restore also performs **no** Firebase Admin getUser/providerData lookup — the five enumerated providerData read points (CONTEXT.md ruling #8: anonymous create-user completion, registered create-user completion, upgrade-anonymous completion, the web anonymous-grant gate, and claim_registered_grant completion) do not include restore; do not build one here.

*Challenge protocol — explicit DELETIONS*
- Build NO challenge mechanics for this endpoint: no prepare mode, no `challenge=true` signal, no `core.auth_challenges` row (DB CHECK refuses one for `restore_subscription`), no claim step, no consumption step, no TTL, no single-use ledger. Restore's replay protection is the lifetime `restore_bound_user_id` binding plus per-`(provider, external_id)` serialization. Restore's former challenge-issuance and challenge-validation-failure limits are **deleted**; the restore request-rate limits replace them.
- DELETED / must not exist: separate transfer endpoint or transfer flag; prior-account recovery credential; App Attest / Play Integrity proof on restore; web attestation surface, WebAuthn, browser integrity signal, restore-from-web-with-receipt lane; any new throttling mechanism beyond the named admission limits; restore job queue, skip-locked handoff, per-user restore singleton, background worker, separate restore lock service, advisory lock beyond the store-subscription serialization; any read/write of `core.subscriptions.last_cross_account_transfer_month` (retained as schema, stays NULL forever; no monthly transfer cap is evaluated); free-credit allocation during restore; any Firebase Admin getUser/providerData lookup on this route.

*Rate limits (all in the config file, `limits` library, `parse_many()`, shared Redis/Valkey in production, default fail-closed; initial values below are deployment policy, config is source of truth):*
- `restore_subscription_user`: "10/day", key `user`.
- `restore_subscription_subject`: "20/day", key `issuer+subject_hash`.
- `restore_subscription_proof_fingerprint_failed`: "5/hour", key `restore_proof_fingerprint`; `restore_subscription_proof_fingerprint_total`: "20/day", same key (fingerprints are redacted server-derived/HMAC values, never raw proof).
- `restore_subscription_store_subscription_cross_account`: "3/hour", key `provider+external_id`; `restore_subscription_store_subscription_live_verification`: "1/minute", key `provider+external_id`; `restore_subscription_destination_rejected_cross_account`: "3/day", key `user`.
- Global provider-call budgets, separate per store: `provider_apple_store_live_verification_global` "300/minute" key `deployment`; `provider_google_play_live_verification_global` "300/minute" key `deployment`. Adapter budgets: `adapter_apple_store_status` "30/minute" key `deployment+bundle_id`; `adapter_google_play_subscription_status` "30/minute" key `deployment+package_name`.
- Ordering: request-rate limits first (before a junk request can force an audit row); proof-fingerprint, store-subscription, and destination-user limits before proof verification; then proof verification; then coalescing and the provider call. User-keyed limits only after barrier admission; identity-keyed limits only after JWT verification; IP-keyed limits anywhere (canonical Envoy-resolved client address only, /32 IPv4, /64 IPv6 default, unresolved-address shared bucket at 10 req/min).
- Provider-call budget accounting: unit = the actual **outbound provider attempt**, atomically checked and consumed immediately before each dispatch, enforced atomically across replicas; a dispatched call consumes its unit regardless of outcome; a reserved-but-unused unit is released; no borrowing, queuing, partial refunds, sub-budgets, or burst allowances. No unit → no call, reject 429, no mutation, no audit row, counted on the provider-call budget rejection counter; budget exhaustion is never audited as `restore_store_state_unverified` nor surfaced as `restore_proof_rejected`.
- Coalescing: live verification for the same `(provider, external_id)` is serialized/coalesced. A request may join an in-flight call or reuse a fresh cached result **only after its own `restore_proof` has independently verified (cryptographically and structurally, no provider call) and resolved to that exact `(provider, external_id)`**; a failed-proof request never joins and never sees the result; merely waiting on the lock confers nothing. Waiters share the leader's terminal outcome and never launch another call when it fails; only the dispatcher debits the budget (once per shared call). Shared payload is the raw store-state observation only — every follower independently completes its own authorization, conflict checks, and transactional processing. Reuse only while fresh under the configured freshness bound.
- Operational counters required: allowed restore admissions, restore admission 429 rejections, provider-call budget rejections, coalesced provider verification reuse (plus the shared counters: allowed requests, 429s, storage failures).

*Audit obligations*
- On the audited attempt path from the **route match**. Every attempt — success, rejection, same-account, adoption, barrier-rejected, or pre-branch failure — writes exactly **one** `audit.auth_events` row before the response: locked-phase outcomes (success or locked-phase rejection) inside the locked mutation transaction; pre-transaction rejections (invalid proof, mismatched subscription, mismatched UUID, non-entitled pre-transaction state, failed live verification) in their own standalone rejection transaction; barrier rejections as their own standalone row (result `invalid_external_jwt` with all three actor fields NULL, or `preauth_identity_not_allowed`/`historical_identity`/`blocked_user` with actor fields from verified context), `operation='restore_subscription'` from route metadata. Audit writes are fail-closed, never best-effort; if the write fails, log it and still return the rejection the attempt earned.
- `result` values: `succeeded` (only success code) or the specific internal result — never a generic placeholder, never less specific than the client class.
- `details` (schema `{schema_version, context, verification, resolved, mutation, failure}`) must record: `movement_classification` on every attempt — `same_account`, `adoption`, or `unclassified` (for `store_transaction_already_linked`, `restore_subscription_grant_owner_mismatch`, `restore_branch_inconsistent`, and any failure before the branch is knowable); source/destination users and identity contexts where known; touched subscription/store-purchase/access-grant rows; non-secret proof fingerprints; grant-expiry reason codes; `details.verification` for adoption = provider, API surface called, high-level decision (entitled / not entitled / unavailable), optional provider result codes. `challenge_row_id` is NULL; no challenge material anywhere. A same-account row's recorded source user is NULL or the current owner — never `purchase_user_id` when it differs. Redaction: raw JWTs, raw `restore_proof`, purchase tokens, signed transaction payloads, and raw provider responses are secret bearer material — never in logs, analytics, crash reports, audit rows, or durable storage outside the minimum verification path; redact before write.
- Admission-control (429) rejections write NO audit row and no per-rejection DB row — bounded aggregate telemetry only, naming the limiter that fired.

*Fail-closed rules & lock ordering*
- Fixed global lock order: grant row(s) FOR UPDATE first (ascending grant id), usage rows second (same order), never the reverse; no account/user-row lock tier ahead of grant locks; **no store/provider/network call while holding any of these locks** — remote work runs before the locked transaction opens or after it commits. Store-subscription serialization + canonical row lock precede the grant tier as listed in step 9.
- Fail closed on: orphan user rows (no identity row → `internal_error`); entitled owned subscription with no grant row (`internal_error`); missing usage row for an existing grant (server-side data error — never mint a counter); unmapped internal results (`restore_temporarily_unavailable`); single-provider-call failure of any kind (`restore_store_state_unverified`); stale verification at the recheck (reject even if it originally succeeded).
- Live verification must not trigger any webhook-equivalent canonical-state update on `core.subscriptions`; canonical-state updates belong to the ingestion pipeline (or the adoption mutation for owner changes). Entitlement for adoption is never derived from cached state, prior webhook deliveries, or `core.subscriptions` alone — the current row's status is necessary but not sufficient.

## POST /webhooks/app-store

**Description:** Apple App Store Server Notifications ingestion. Category: **provider-callback** — one of exactly two routes in the closed provider-callback category, enumerated in the route registry by exact path (never a `/webhooks/*` wildcard), never on the public allowlist, outside the shared pre-handler barrier. Caller is Apple's store server (machine-to-machine), presenting **no Authorization header, no shared secret, and no Firebase ID token**; the request body is a single `signedPayload` field (a JWS Apple signed), and verifying that payload is how the notification is both authenticated and read. NOT a canonical state-changing auth operation: it writes **no** `audit.auth_events` row and answers with plain HTTP status codes, never the shared client-visible error classes.

**Business logic changes:**

*Ingestion transaction (verified purchase / lifecycle event):*
- Resolve the owning user by matching the store-echoed attribution token (`appAccountToken` from the verified transaction) through `core.store_purchase_tokens` by `(provider, identity_value)`. Attribution is server-authoritative, keyed by store provider + lifetime attribution token, with **no identity-kind dimension**, never from client-asserted identity.
- In **one** transaction: (a) upsert the canonical `core.subscriptions` row for the `(provider, external_id)` — globally unique; renewals, grace-period/billing-retry transitions, expirations, revocations, tier changes, and restore-driven owner changes all update the **same row in place**, never a second row for another state of the same lifecycle — with the resolved user as `user_id`; (b) write one immutable `core.store_purchases` row (provider, `identity_value`, store transaction ids when available, `purchase_user_id`, `resolved_token_value` copied from the resolved token with composite FK `(provider, resolved_token_value) → core.store_purchase_tokens (provider, identity_value)`, `external_id`; subscription row written first in the same transaction; composite FK `(provider, external_id) → core.subscriptions`, no cascading delete); (c) create the paid entitlement — `core.access_grants` row `source='subscription'`, `status='active'`, linked to the canonical subscription, `tier_id` from the **server-controlled store-product-ID-to-tier mapping** (never client-supplied) — plus its `core.user_monthly_usage` row seeded `monthly_used=0` (free-tier usage never copied into the paid counter). Grant creation is part of this transaction, never separate, never backfilled by restore or the quota path.
- Unattributed case: an echoed token resolving to no binding — or a verified purchase carrying no echoed token (offer-code redemption, store-managed resubscription, Ask to Buy) — is attributed to **no user**: create `core.subscriptions` unclaimed (`user_id` NULL), `core.store_purchases` unattributed (`purchase_user_id` NULL, `resolved_token_value` NULL so the token FK is skipped under MATCH SIMPLE), recording a server-generated internal purchase UUID as `identity_value` where the store supplies no usable value, with **no grant and no usage row**. Restore's adoption later links it.
- Expire-then-insert (because `ix_access_grants_one_active_per_user` is non-deferrable): any index-blocking grant (buyer's active free grant, or previously active subscription grant) is expired first in its own earlier statement — never deleted — with a recorded reason, before inserting the new active grant. A verified purchase for a second, genuinely different subscription while another subscription-backed grant is active: **newest verified purchase wins** — prior grant expired, new grant active, both canonical subscriptions and purchase records kept, fresh zeroed counter for the second subscription.
- Renewal inserts a new grant row **per term** via flip-then-insert (flip any time-ended `status='active'` row, then insert the new term's row); `ends_at` never extended in place. A re-reported/re-verified event for the same term is an idempotent no-op before touching grant or usage state (no duplicate grant, no usage reset). A new `external_id` under the same token inserts a new purchase row; repeat/lifecycle events for an existing `(provider, external_id)` update the canonical subscription in place with no second purchase row.
- Status/tier/owner changes: whenever ingestion changes `status`, `tier_id`, or `user_id`, it must update the corresponding subscription-backed grant in the **same transaction**; a transition out of the product-entitled set (`active`, `grace_period`) must mark the grant `expired` or `revoked` and set `ends_at` in that same transaction, or the deferrable FK fails the commit (no reconciliation sweep exists — a writer's bug surfaces as a loud commit failure). When state becomes entitled again, ingestion **never reactivates** the grant: reactivation belongs to user-invoked restore alone; the entitled-subscription/expired-grant state persists until restore. After newest-wins supersession, a later notification about the superseded subscription may update its canonical row but must not silently reactivate its grant.
- Attribution conflict: if an existing `(provider, external_id)` purchase row's recorded `identity_value` differs from a newly presented token, ingestion **refuses** as an attribution conflict rather than silently reassigning — an owner change is an operator problem.
- Idempotency/replay: keyed on Apple's notification UUID, recorded as `audit.subscription_events.notification_uuid` (UNIQUE); a valid replay may be acknowledged again and repeats no side effect. Every accepted observation appends one `audit.subscription_events` row (append-only, per-subscription history; `event_type` = the Apple notification type as received, not an internal enum; `old_tier_id`/`new_tier_id` record tier transitions, NULL when none), readable after the canonical row moves on.
- Responses: HTTP **401** for a missing, malformed, or invalid payload (envelope or any nested payload) — no ingestion, no entitlement effect, before any business logic. HTTP **200** only once the notification is durably persisted or applied; internal failure returns **5xx** (never 200) so Apple's retry schedule covers transient errors.

**Security hardenings:**
- Named verifier declared in the route registry: Apple's signed-payload (JWS) verifier. A generic external/unauthenticated bypass never stands in for it. Verify the `signedPayload` JWS signature and its `x5c` certificate chain up to Apple's Root CA **using Apple's official App Store Server Library** (no hand-written chain logic) before treating the notification as authentic. Validate the decoded bundle ID and environment against configured values, and the App Apple ID where carried. Verify **each nested signed payload** — the signed transaction and the signed renewal information — on its own before using it as purchase evidence; the outer envelope alone is insufficient. Any failure → 401, fail closed.
- Route registration: not registered at all while Apple's store integration is unconfigured; startup fails closed if the registered route lacks configuration its verifier requires. Membership joins the provider-callback category only by exact path via a spec change. The route-enumeration assertion (CI/startup/integration) must prove: reachable with no Firebase ID token; rejects missing/invalid provider credential; does **not** accept a valid Firebase user token in place of provider verification; the provider credential opens no route behind the barrier.
- Gateway: Envoy's Firebase JWT requirement is exempted for this exact path only; the gateway mints/trusts no identity header here, never parses or verifies Apple's `signedPayload`, and forwards the request as sent. Gateway keeps only TLS termination and per-IP/per-URL rate limiting on this path — never a substitute for backend cryptographic verification.
- Rate limits: IP- and URL-keyed gateway limits only (canonical Envoy-resolved client address); the route resolves no identity at either layer, so **no identity-keyed limiter of any kind**.
- Handler authority is narrow: a verified notification carries the store's authority over **entitlement only** — it may update the canonical `core.subscriptions` row for its `(provider, external_id)`, append to `audit.subscription_events`, and update the corresponding subscription-backed `core.access_grants` row, acting only on the account the subscription is already linked to (token resolution through `core.store_purchase_tokens`, or the canonical row's current `user_id`). It **never** creates a session, mints/issues any token, creates a `core.users` or `core.external_identities` row, or grants any privilege beyond the store event's entitlement effect. It writes no `audit.auth_events` row.
- Client-submitted purchase evidence never arrives on this route: a signed-in user submitting a receipt/purchase token uses `POST /auth/restore-subscription` behind the Firebase barrier — client-submitted purchase evidence never makes a route provider-callable.
- Explicit DELETIONS: no secret URL token, no IP allowlist, no certificate pinning beyond Apple's own root, no mTLS (primary or supplementary). Apple's documented signed-payload mechanism is the whole control set. No raw signed payloads or purchase tokens persisted outside the minimum verification path.

## POST /webhooks/google-play/rtdn

**Description:** Google Play Real-Time Developer Notifications (RTDN) ingestion via a Cloud Pub/Sub **push subscription**. Category: **provider-callback** — the second of exactly two such routes, enumerated by exact path, never on the public allowlist, outside the shared pre-handler barrier. Caller is Google's Pub/Sub push infrastructure (machine-to-machine), presenting a **Google-signed OIDC JWT** as `Authorization: Bearer`, minted for the operator-designated push service account — a Google service-account token, **not** a Firebase ID token — which the backend itself verifies. NOT a canonical state-changing auth operation: writes **no** `audit.auth_events` row, answers with plain HTTP status codes, never shared client error classes.

**Business logic changes:**
- **Message is a trigger only.** Once the OIDC token verifies, validate the expected Play package name and expected subscription, then fetch authoritative subscription state from the Google Play Developer API (`purchases.subscriptionsv2.get`) and derive **every** mutation from that response. A purchase token or product identifier carried in the message is never trusted directly — a forged authenticated message could only trigger a truthful lookup.
- Deduplicate on the Pub/Sub **message ID**, recorded as that observation's `audit.subscription_events.notification_uuid` (UNIQUE), so redelivery repeats no side effect; each accepted observation appends one `audit.subscription_events` row (`event_type` = the RTDN type as received; `old_tier_id`/`new_tier_id` NULL when no tier transition).
- Ingestion transaction — identical one-transaction rule as the Apple route: resolve the owning user via `core.store_purchase_tokens` by `(provider, identity_value)` where for Google Play `identity_value` is the **obfuscated external account ID** returned for the verified purchase; upsert the canonical `core.subscriptions` row by `(provider, external_id)` (globally unique, all lifecycle transitions update the one row in place, never a duplicate state row); write one immutable `core.store_purchases` row; create the `core.access_grants` row (`source='subscription'`, `status='active'`, server-mapped tier) plus its `core.user_monthly_usage` row seeded `monthly_used=0`, all in the same transaction.
- Unattributed case: unmatched or absent obfuscated external account ID → subscription created unclaimed (`user_id` NULL), purchase row unattributed (`purchase_user_id` NULL, `resolved_token_value` NULL), server-generated internal purchase UUID as `identity_value` where needed, **no grant, no usage row**; only restore's adoption later links it. `purchase_user_id` is resolved only via the echoed token — never from request-authenticated or client-asserted identity.
- Expire-then-insert, newest-wins, per-term flip-then-insert renewal, same-term-redelivery idempotent no-op, same-transaction grant update on status/tier/owner change, non-entitled transition marking the grant `expired`/`revoked` with `ends_at` set in the same transaction, never-silently-reactivate (reactivation is user-invoked restore only), and the attribution-conflict refusal (differing `identity_value` against an existing `(provider, external_id)` row) — all exactly as specified for the Apple route above; implement once, shared.
- Responses: HTTP **401** for any authentication failure — no ingestion, no business logic first. HTTP **200** acknowledges the message only once the resulting state is durably persisted or applied; internal failure returns **5xx** so Pub/Sub redelivers.

**Security hardenings:**
- Named verifier declared in the route registry: the **Pub/Sub OIDC verifier**. Verify the token's signature against Google's published signing keys, its issuer, its expiry, and its `aud` against the **exact configured audience** for this push subscription; verify the token's service-account **email claim** against the one dedicated push service account provisioned for this subscription; require `email_verified`. Any failure → 401, fail closed.
- Route registration: not registered while the Google integration is unconfigured; startup fails closed if registered without required verifier configuration. Exact-path membership only (no wildcard/prefix); additions only via spec change; never on the public allowlist. The route-enumeration assertion must prove: reachable with no Firebase ID token; rejects missing/invalid provider credential; does not accept a valid Firebase user token in place of the OIDC verification; the provider credential opens no barrier route.
- Gateway: Firebase JWT requirement exempted for this exact path only; the gateway forwards any Authorization header present (Google's Pub/Sub OIDC bearer) to the backend **unchanged** — the backend performs the OIDC verification itself. Gateway keeps only TLS termination and per-IP/per-URL rate limiting; never a substitute for backend cryptographic verification of the Pub/Sub OIDC credential.
- Rate limits: IP- and URL-keyed gateway limits only; no identity-keyed limiter of any kind (route resolves no identity at either layer).
- Handler authority: entitlement only — update the canonical `core.subscriptions` row, append to `audit.subscription_events`, update the corresponding subscription-backed `core.access_grants` row; act only on the account the subscription is already linked to. Never creates a session, mints/issues tokens, creates `core.users`/`core.external_identities` rows, or grants any privilege beyond the store event's entitlement effect. No `audit.auth_events` row. Client-submitted purchase evidence never arrives here (users go through `POST /auth/restore-subscription`).
- Explicit DELETIONS: no secret URL token, no IP allowlist, no mTLS. The Pub/Sub OIDC verification **plus the authoritative Play lookup** is the whole control set. No raw purchase tokens, RTDN payloads, or provider responses persisted outside the minimum verification path.

# Implementation Brief — POST /auth/sign-out-all + Pre-existing Route Contracts

## POST /auth/sign-out-all

**Description:** The single sign-out endpoint the backend exposes (there is exactly one; no other sign-out route exists). It requests global sign-out ("sign out everywhere") through the external IDP for the current linked user by revoking the Firebase refresh tokens of the resolved identity's verified subject. Route category: **authenticated, state-changing auth operation** — it is in the canonical state-changing auth operation inventory under operation `sign_out_all` (a value of the `core.auth_operation` enum) because it revokes the subject's Firebase refresh tokens; inventory membership is read from the inventory table, never inferred from the path name or from whether the handler writes business state. It is **not challenge-bearing**: authorized by the verified Firebase ID token alone. Caller: any linked, active user (anonymous or registered alike), presenting a single `Authorization: Bearer <Firebase ID token>` credential — the sole identity carrier. Clients call it only for sign-out-everywhere; current-device-only sign-out is a pure client action (clear local client session state and local IDP session) that calls no backend endpoint.

**Business logic changes:**

Request contract:
- Method POST, path `/auth/sign-out-all`. Authentication is the single `Authorization: Bearer` credential carrying the Firebase ID token as a compact JWT (RFC 6750). Exactly one Authorization field value with exactly one well-formed Bearer credential; zero values, multiple field instances (case-insensitive field-name duplicates included), comma-joined/folded values, multiple credentials, an empty token, or trailing content after the token are rejected as `invalid_external_jwt` → `auth_required` — never resolved by taking first/last or by concatenation. No request body is defined; no body or query field contributes anything. There is **no prepare mode**: `challenge=true` on this endpoint is not a recognized signal; the mode-signal partition and all challenge-variant/prepare-phase rules written for the challenge-bearing subset do not apply here.
- The endpoint is one of the enumerated routes requiring the client-presented external IDP ID token for backend verification (req~shared-id-token-endpoint-sign-out-everywhere~1).

Handler steps, in order (the shared pre-handler barrier has already run — see Security hardenings):
1. Call Firebase Admin refresh-token revocation for the **verified subject** through the Admin client selected by the **request-verified issuer** (Firebase Integration Selection), **without loading or consulting the stored provider classification** — revocation is unconditional for every account, anonymous and registered alike; `POST /auth/sign-out-all` is explicitly *not* a consumer of the stored `core.external_identities.provider` value and never reads or branches on it. The backend may retry the revocation call a small bounded number of times within the request before treating the outcome as unconfirmed.
2. Append the attempt's single `audit.auth_events` row for the observed outcome **before returning the response** — on confirmed revocation, failure, and ambiguity alike (see Security hardenings for row content).
3. Return success **only when Firebase confirmed the revocation**.

Semantics:
- Success means only that Firebase confirmed refresh-token revocation for the subject. It does **not** mean already-minted ID tokens are invalid; those remain valid until their own `exp` (~1 hour with Firebase defaults). Verification runs without `checkRevoked`; there is no per-request revocation check anywhere.
- Revocation is idempotent and whole-subject: re-revoking only re-asserts the subject's valid-after timestamp, so retrying after any outcome — ambiguous included — is always safe. **The client is the retry path**: the backend keeps no retry queue, runs no background reconciliation, stores no durable revocation state.
- Coalescing: concurrent **in-flight** revocations for the same subject *may* be coalesced to share one revocation result; that shared result must **never** be reused for a later sequential request (the user may have re-authenticated with fresh refresh credentials in the meantime).
- For an anonymous identity, revocation is a one-way door: anonymous re-sign-in mints a new Firebase uid, so the revoked account becomes unreachable — immediately for anyone holding only a refresh token, and for the legitimate user once the current ID token hits its `exp` (at most ~1 hour). The `core.users` row with its chats, credits, and grants remains in PostgreSQL but no later sign-in ever resolves to it (there is no anonymous-account recovery path). Sign-out never clears the identity's permanent free-grant-consumed marker and never reopens a free-grant slot.
- **No PostgreSQL business-state mutation**: the handler must not mutate `core.users`, `core.external_identities`, `core.access_grants`, or any other business-state table. Appending the `audit.auth_events` row is operational logging, not business state, and is the only durable write. It creates, reads, and consumes **no** `core.auth_challenges` row.
- **No backend token**: nothing is issued or reissued; authentication remains per-request via the Firebase ID token only.

Error classes and triggers (all use the shared response shape; no new client-visible error class is added by this endpoint):
- `auth_required` — barrier token-acceptance failure (missing/malformed/duplicated Authorization, bad signature, `iss` ≠ configured issuer, `aud` ≠ Firebase project ID, expired/temporally invalid token, empty `sub`). Internal result `invalid_external_jwt`. Response identical in status, body, and timing across every acceptance-failure branch; names no issuer, integration, or failed check.
- `preauth_identity_not_allowed` — verified (issuer, subject) resolves to no `core.external_identities` row (pre-auth/unlinked caller). Remediation: complete `POST /auth/create-user`, then retry.
- `account_unavailable` — matching identity row with `identity_state` ≠ `'active'` (internal result `historical_identity`) or linked user's `active` not exactly TRUE (internal result `blocked_user`). Same status, same machine-readable code, same generic copy for both — mutually indistinguishable to clients. **The barrier admits no route-specific exception here**: a blocked or retired subject stays closed out of sign-out-all exactly as on every other route (ruling: "POST /auth/sign-out-all for a blocked or retired subject — stays closed"). Nothing is stranded, because operator block and identity retirement revoke that account's Firebase refresh tokens as part of the same administrative operation.
- Retryable server-side failure (no new class; ordinary server-error surfacing) — **every** non-confirmed revocation outcome: Firebase error response, timeout, transport failure, permission/configuration error, quota failure, lost response leaving the result ambiguous. Never returned as success. A *definitive* configuration failure may be surfaced as non-retryable, but is never success. Internal audit result: `revocation_unconfirmed`.
- `429 Too Many Requests` — gateway per-IP / per-user rate-limit rejection only (see below); carries `Retry-After` where computable and the shared JSON error body naming the class (a bare 429 does not satisfy the contract). These rejections never reach the handler and write no audit row.

Response: success only after Firebase-confirmed revocation (no response-body fields are specified by the spec beyond success/error class semantics). Client contract: clear local state and local IDP session only **after** success; on any non-success other than `account_unavailable`, keep the credential and report sign-out unconfirmed/retryable (a local-only sign-out offered alongside must be labeled local-only, stating global revocation was not confirmed); on `account_unavailable`, terminal handling — discard tokens, stop all authenticated calls including retries of this route. Before an anonymous session calls this endpoint, the client warns that it permanently ends access to the account's chat history and credits on every device and that registering with Google or Apple first keeps them.

**Security hardenings:**

Barrier and verification:
- The shared, mandatory, default-on pre-handler barrier runs before the handler and is the only place token acceptance and the four identity-resolution outcomes are evaluated. Order: (1) cryptographically verify the Firebase ID token via Firebase Admin `verifyIdToken()` or an equivalent JWKS-backed verifier — RS256 signature against cached Google securetoken keys (one local RSA verification per request, no network call), `iss` exactly `https://securetoken.google.com/<project-id>`, `aud` exactly the configured Firebase project ID, `exp`/`iat` temporal validity, non-empty `sub`; reading claims without signature verification is prohibited. (2) Resolve verified (issuer, subject) against `core.external_identities`/`core.users` — the exclusive identity inputs; no header, cookie, query parameter, body field, or gateway-projected claim header ever contributes identity. (3) Admit only when `identity_state` is exactly `'active'` AND the linked user's `active` is exactly TRUE; every other combination rejects. The handler consumes the barrier's typed identity context (resolved `core.users` row + `core.external_identities` row) and must not re-implement acceptance or resolution.
- Firebase Admin client selection: the revocation call selects the Admin client of the single configured Firebase integration by matching the **request-verified issuer**. No ambient/default/global Admin client and no fallback client exists. An issuer mismatch fails **before** any Firebase Admin call: audited `invalid_external_jwt` with bounded reason `issuer_mismatch`, surfaced as `auth_required`. Selection fails closed.
- The gateway (Envoy JWT filter) is defense-in-depth only: it forwards `Authorization` unchanged, supplies no claim headers, and no backend correctness depends on it. Trusted claim headers do not exist (CONTEXT.md ruling).

Rate limits — exact contract (CONTEXT.md ruling: the per-subject sign-out-all cap is **removed**):
- **No backend-enforced quota of any kind**: sign-out-all has **no named entry** in the backend `rate_limits` config and is **exempt from the backend generic default entry** (the `120/minute` key `ip` default). No backend counter may ever reject an authenticated request to this endpoint; no dedicated per-subject quota; no new backend counter; no route-specific deployment-wide counter.
- Its **only** bounds are the gateway's standard per-IP and per-user rate limits, applied exactly as on every other authenticated route. It also takes **no exemption** from those gateway limits: no bypass token, no priority lane, no rule treating the route as unauthenticated/anonymous for limiting. Per-IP key = the canonical Envoy-resolved trusted-proxy-chain client address (never a client-supplied forwarding header; unresolvable addresses share one bucket at the single-address ceiling, default 10 requests/minute; IPv4 /32, IPv6 /64 default). Per-user gateway keys derive only from Envoy's own JWT-filter-verified token metadata, evaluated only after gateway JWT verification. Accepted trade-off: the per-user key is shared between the account owner and a stolen-token holder for the same subject; the per-IP limit is independent, and the per-user ceiling is configured generously because legitimate use is rare.

Audit obligations (audited attempt path — entry is route-scoped, decided by route match alone):
- Route metadata identifies operation `sign_out_all` **before** the barrier runs. Every attempt on the path writes **exactly one** durable `audit.auth_events` row with `operation = 'sign_out_all'` for its terminal outcome, before the response returns, never best-effort. If the audit write fails, log the failure and still return the rejection the attempt earned — never a different outcome.
- Permitted `result` values (from the `core.auth_event_result` enum): barrier rejections `invalid_external_jwt` (actor-NULL row shape: `actor_issuer`, `actor_subject_hash`, `actor_subject_hash_key_version` all NULL, CHECK-enforced; bounded reason — one of `missing_token`, `malformed`, `duplicate_authorization`, `bad_signature`, `issuer_mismatch`, `audience_mismatch`, `expired`, `empty_subject` — lives only in `details`/metric labels, never client-visible), `preauth_identity_not_allowed`, `historical_identity`, `blocked_user` (these four carry actor fields from the verified token/resolved identity); `revocation_unconfirmed` — the **single** value for definitive Firebase failure, a local dependency preventing the call, or timeout/lost response/disconnect ambiguity (no parallel values; the operator block/retirement paths reuse this same value); or `succeeded` — the only success code, never a second one. `result` alone carries the outcome; there is no separate failure_reason column and no second outcome field in `details`.
- Row content minimum: operation, hashed actor subject (`actor_subject_hash` = HMAC-SHA-256 under the actor-subject key with `actor_subject_hash_key_version`; raw subject never stored), request identifier in `details.context`, event timestamp. `actor_provider` from the stored provider column for resolved linked identities, NULL otherwise, never fabricated. On `revocation_unconfirmed`, `details` carries a sanitized error category only. Prohibited in the row: raw Firebase messages, credentials, tokens, raw JWTs, stack traces, high-cardinality exception text, vendor response payloads.
- Admission-phase rejections (gateway rate limit, HTTP parsing, body-size, content-type, route/method mismatch, overload shedding) precede path entry: they write **no** `audit.auth_events` row, appear only in aggregate access/rate-limit telemetry naming the limiter that fired. A `revocation_unconfirmed` attempt is safe to retry; each retry is a new attempt with its own single row.
- Barrier rejections also increment the mandatory bounded-cardinality counter metric (labeled by result, bounded reason, route) that drives the invalid_external_jwt spike alert — this applies on-path too.

Fail-closed rules:
- Never return success on any unconfirmed outcome. Exhausting the bounded in-request retry budget is unconfirmed, not success.
- The barrier rejects blocked/historical with no exception (self-service scope is only subjects that can still authenticate); a malformed/unexpected `identity_state` value never authorizes and never falls through to pre-auth.
- A `core.users` row with no identity row is an unresolvable owner: fail closed as an internal error; never invent, reassign, or repair an identity row.

Explicit DELETIONS (must NOT be built):
- No prepare phase, no operation variant, no `core.auth_challenges` row, no challenge mechanic of any kind for `sign_out_all`.
- No per-device backend sign-out endpoint (ID tokens are stateless; revocation is whole-subject). Current-device sign-out calls no backend endpoint.
- No backend rate-limit entry, no per-subject cap (removed by ruling), no backend counter, no route-specific deployment-wide counter, no gateway exemption/bypass.
- No stored-provider read or branch anywhere in the handler.
- No retry queue, no background reconciliation, no durable revocation state, no revocation-pending marker, no compensation machinery, no scheduled jobs.
- No reuse of a coalesced revocation result for a later sequential request.
- No new client-visible error class; no exposure of `core.auth_event_result` values to clients.
- No PostgreSQL business-state mutation; no `core.access_grants` creation or modification, no introductory-entitlement allocation (this operation allocates nothing implicitly).
- No per-request `checkRevoked` and no forced expiry of already-minted ID tokens.

## Pre-existing routes (GET /, GET /examples, /chats family, GET /health/ready)

The spec names no chat routes directly; these routes are bound only by category-level contracts. Implementers must not add endpoint-specific auth, audit, or error machinery beyond what follows.

**Route partition and barrier.** Every registered route must sit in exactly one of three categories: (1) **public** — an explicit enumerated allowlist outside the barrier, which the spec defines as the health/readiness probes (`GET /health/ready` belongs here); (2) **provider-callback** — exactly the two store-webhook routes (Apple App Store Server Notifications, Google Play RTDN), named individually, never by wildcard/path-prefix, never on the public allowlist, each verified by its own named provider verifier; (3) **authenticated** — the default for everything else. The public allowlist is exactly the health and readiness probes (`GET /health/ready`). `GET /` and `GET /examples` are not health/readiness probes, so they belong to the authenticated category behind the shared pre-handler barrier under the default route policy (linked, active identity required); they may not be added to the public allowlist without a spec change, and a route carrying no declaration receives the strictest treatment and must never silently become public. The `/chats` family is ordinary **authenticated** traffic behind the shared pre-handler barrier: full token verification (RS256/iss/aud/exp/iat/non-empty sub via the issuer-matched verifier), strict one-Authorization-header wire contract, and the four resolution outcomes — pre-auth rejected `preauth_identity_not_allowed` (chat routes are not pre-auth-callable; only the two `create-user` phases are), historical/blocked rejected `account_unavailable`, token failures `auth_required`. Handlers consume the barrier's typed identity context and never re-implement acceptance or resolution; a route wired outside the barrier has no identity context and fails loudly as `auth_required`. A required CI/startup/integration assertion enumerates all registered routes and fails if any route is in zero or multiple categories or a provider-callback route is admitted by a generic bypass; these pre-existing routes must be registered so that assertion passes.

**Off the audited attempt path.** Chat routes, `GET /`, and `GET /examples` are not in the state-changing operation inventory, so they are routine traffic: an authentication/identity-resolution rejection there writes **no** `audit.auth_events` row ever. Instead the rejection keeps its stable internal result code (`invalid_external_jwt` with bounded reason, `preauth_identity_not_allowed`, `historical_identity`, `blocked_user`) in the structured security log and increments the mandatory bounded-cardinality counter metric labeled by result, bounded reason, and route — the required alerting source for cross-route attack volume and systemic verification breaks. These routes issue, present, validate, and consume no challenges.

**Shared error body.** All rejections on these authenticated routes surface through the shared client-error taxonomy with the single shared response shape (machine-readable class code); internal `core.auth_event_result` values are never exposed. Rate-limit rejections — gateway ones included — return 429 with `Retry-After` where computable **and the shared JSON error body naming the class**; a bare 429 violates the contract (Envoy's default empty-body 429 must be overridden via gateway response-override configuration).

**Rate limits.** Gateway standard per-IP and per-user limits apply as on every authenticated route; IP keys use only the canonical Envoy-resolved client address (trusted-proxy-chain, /32 IPv4, /64 IPv6 default, unresolved-address shared bucket at 10 requests/minute), and identity keys only Envoy-JWT-verified metadata evaluated after gateway JWT verification. Backend limits use the Python `limits` library over shared Redis/Valkey storage, all values in the application config file (nothing hard-coded), parsed with `limits.parse_many()`; routes without a named entry fall under the generic backend default entry — `120/minute`, key `ip`, `failure_mode: fail_closed` — which covers `GET /`, `GET /examples`, and chat routes (sign-out-all alone is exempt from it). Backend `user`-keyed limits may be evaluated only after the barrier has admitted a linked active user; barrier-rejected requests are bounded only by IP-keyed limits and the default entry. Admission rejections write no audit row and leave only aggregate telemetry naming the limiter that fired.

**Quota admission for chat POSTs.** Any chat request that consumes credits is a quota-checked business request. Before **any** database quota mutation (before lazy rollover writes, before usage-row creation, before increment) it must pass the named `quota_checked_request` backend admission limit — recommended `120/minute`, key `user` (the authenticated internal `core.users.id`); this is operational admission control, not entitlement, and passing it grants nothing. Then the quota flow: resolve the single effective grant under the shared predicate (`status='active' AND starts_at <= now AND (ends_at IS NULL OR ends_at > now)`; >1 active grant → invariant-violation rejection; `source='subscription'` honored outright with no subscription re-read; no active grant → allowance 0) and lock it FOR UPDATE **first**, then its `core.user_monthly_usage` row FOR UPDATE **second** — the fixed grant-then-usage lock order, grants in ascending grant-id order, never reversed, with no store/provider/network call while holding the locks; a missing usage row fails closed (never lazily minted). Lazy rollover: if stored `monthly_period` ≠ current (`YYYY-MM`, UTC), set it current and reset `monthly_used = 0`. Allowance comes from the grant's tier (`core.access_tiers.monthly_credits`); `remaining = max(0, allowance - monthly_used)`, never negative; `remaining = 0` rejects as ordinary quota exhaustion (never a distinct error class); otherwise increment `monthly_used`. All derivations use one captured evaluation time / consistent snapshot per request; no background job; read paths perform no repair; nothing here creates or modifies a `core.access_grants` row or allocates introductory entitlement.

**Deletions binding these routes:** no per-route audit rows, no challenge machinery, no per-request Firebase Admin reads (`providerData` reads are confined to the five enumerated points, none of which is a chat route), no rederivation of provider on ordinary requests (stored provider is the sole classifier), no backend-minted sessions or tokens, no header-derived identity, and no recalculation of client IP from raw forwarded headers.
