<objective>
Remove `core.auth_challenges.operation_variant` outright (D-13) — the column, its Ruling-9.8 CHECK arms, its model field, its `ChallengeStore.issue()` parameter, and every test that asserts it.

Purpose: D-12 deletes the client flow declaration. `operation_variant` exists only to freeze that declaration, and it cannot be derived at prepare time — §02 step 8 pins exactly one Firebase Admin lookup, at completion, immediately before the write transaction. A nullable column would leave a field nothing ever writes; the column goes.

Output: a schema, model, and store that carry no variant, applied to the real dev/test database, with the full suite green.

**This is a destructive, one-way schema change.** Task 1 is a blocking decision checkpoint because the mechanism collides with a shipped requirement (SCHEMA-01, "no incremental migration files are added") and with a live passing test (`tests/schema/test_apply_rollback.py::test_exactly_one_sql_file`).

**Flagged forward, explicitly NOT this phase's to solve:** the same Ruling-9.8 CHECK pins `upgrade_anonymous_to_registered` to `operation_variant IN ('google','apple')`. Phase 40 (`POST /auth/upgrade-anonymous`) therefore loses its provider binding and needs its own answer for how it binds the target provider. Phase 37 removes the column; it does not design Phase 40's replacement. The rewritten CHECK must still leave Phase 40's rows insertable.
</objective>

  <options>
    <option id="option-a">
      <name>Edit the single initial migration in place, then drop and re-apply the dev/test database</name>
      <pros>SCHEMA-01 survives untouched. `test_exactly_one_sql_file` stays green with no edit. The migration keeps reading as one from-empty apply, which is what every harness in the repo assumes. The `Ruling 9.8` comment block stays adjacent to the CHECK it describes.</pros>

    </option>
    <option id="option-b">

      <cons>Contradicts SCHEMA-01, a requirement already marked complete, so the requirement has to be amended or flagged.     </option>
  </options>

SCHEMA-01 is a locked, shipped requirement with a live test enforcing it, and the only thing option-b buys — an audit trail of a schema change — has no audience in a pre-launch repo with no deployed database.
