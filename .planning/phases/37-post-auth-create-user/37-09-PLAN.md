<objective>
Fill in the consuming transaction's rejection arms — the authoritative in-transaction re-resolution, the savepoint rollback, and conflict discrimination by constraint name — and prove ROADMAP success criteria 3 and 4 against a real, committing PostgreSQL.

Purpose: 37-07's tracer built the transaction's *shape* and proved its happy path. This plan proves the two properties the shape exists for: **a forced mid-transaction failure leaves no partial account**, and **two concurrent creates for the same `(issuer, subject)` yield one account with the loser reconciling via `/auth/sync`**.

**Where these tests live, and why not in `tests/e2e/`.** Both criteria need genuinely committed, concurrent transactions. The e2e harness wraps every test in one outer transaction with savepoint-joined sessions (`tests/e2e/conftest.py:93-115`), so two "concurrent" sessions there share one connection and neither criterion is expressible. `tests/schema/` already owns a disposable scratch database created per session with per-test connections, and is the only harness in the repo that can commit for real. Do **not** add a second commit-for-real fixture to `tests/e2e/` — it would defeat the isolation every other module in that package relies on.

**The savepoint rationale is settled by execution and must not be re-litigated.** 37-CONTEXT.md's original default was a consume-first conditional update with no savepoint. RESEARCH disproved it empirically on 2026-08-22 against live PostgreSQL 17.11 under the *exact* e2e harness configuration: without a savepoint, the post-`IntegrityError` query and the commit both raise `PendingRollbackError`; with `begin_nested()`, the post-rollback query works and the commit succeeds. That is a correctness failure, not a tradeoff.
</objective>

  <action>
Complete `auth/creation.py`'s rejection arms.

**Step 10's re-resolution is authoritative.** Query `core.external_identities` for `(issuer, subject)` **inside** the consuming transaction — the prepare-time pre-auth status never suffices, and 37-07's prepare-mode pre-check is explicitly best-effort. An ACTIVE row → `identity_already_linked`, no business mutation. A `historical` row or an ACTIVE row whose user is inactive → `account_unavailable` with the distinct internal results `historical_identity` and `blocked_user`, no mutation. Both surface identically to the client at 403 — §02 makes them mutually indistinguishable, and a historical identity never gets `preauth_identity_not_allowed`. Note `core.users` without an identity row is an internal error that fails closed and never invents or reassigns an identity.

**The savepoint arm.** Wrap the three business inserts in `savepoint = await session.begin_nested()`; on `IntegrityError`, `await savepoint.rollback()` — which rolls back to the savepoint and leaves the **outer** transaction live — then classify, then run the consume and the audit write on that still-live outer transaction and commit. Write the reason in the code, once, so nobody later "simplifies" the savepoint away: without it, PostgreSQL aborts the whole transaction on the failed statement, SQLAlchemy mirrors that by requiring an explicit rollback, and `ChallengeStore.consume` plus `AuditWriter.write_in_transaction` both raise `PendingRollbackError` — violating §02 step 12's "consumption + rejected audit row MUST survive the business rollback" and producing exactly the generic 500 step 12 forbids. Consuming *earlier* in the same transaction does not help; the abort rolls the consume back too.

**Conflict discrimination by constraint name, never by message.** Read `exc.orig.__cause__` and take `constraint_name` off it — asyncpg populates it for both table-level UNIQUE constraints and standalone partial unique *indexes* (RESEARCH verified this empirically against PostgreSQL 17.11 on 2026-08-22). Parsing `str(exc)` is brittle and locale-fragile and is forbidden here. Declare the mapping as two module-level constants — a frozenset of the two race constraints and the single provider-account index name — with the live names as RESEARCH queried them from the running database:

- `external_identities_issuer_subject_key` (`UNIQUE (issuer, subject)`) → `identity_already_linked` → 409
- `external_identities_user_id_key` (`UNIQUE (user_id)`) → `identity_already_linked` → 409
- `ix_external_identities_provider_account` (`UNIQUE (issuer, provider, provider_uid) WHERE provider_uid IS NOT NULL`) → `provider_account_already_linked` → 403

Anything else — including `external_identities_check`, the provider/provider_uid agreement CHECK, which must be unreachable — **re-raises**. Swallowing an unrecognized constraint as a business branch turns a programming error into a plausible client response.

Why the two client classes must not collapse: `identity_already_linked` tells the caller to reconcile through `/auth/sync`; `operation_not_allowed` is terminal and routes to support. They are different instructions and collapsing them is a client-contract bug.

**Explicitly do not build**, per §02 step 12: no serializable isolation, no distributed lock, no advisory lock, no generation CAS, no multi-phase commit, no cleanup-scan serialization, and no loser-challenge cancellation beyond single-use. `UNIQUE (issuer, subject)` and `UNIQUE (user_id)` are the ONLY arbiters. Do not add a pre-SELECT-then-INSERT duplicate check either — it has a window the constraint does not.

Also, the loser's disposition, spelled out: it rolls back every business mutation, returns the **same** `identity_already_linked` conflict as the pre-check path, and audits its own `identity_already_linked` result. Never idempotent success, never a merge, never an overwrite of the winner's provider. Grant side effects — there are none here anyway — run winner-only.

Write `tests/unit/test_conflict_classification.py` covering the nine behaviors above by constructing `IntegrityError`s with synthetic `orig.__cause__` objects carrying each `constraint_name`, and by driving the re-resolution branches against a substituted session. No database needed for this file.
