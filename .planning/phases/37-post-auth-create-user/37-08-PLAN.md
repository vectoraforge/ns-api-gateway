<objective>
Expand the tracer's single happy path into §02's full completion rejection precedence — the challenge rejections (steps 3-5), the Firebase Admin outcomes (step 8), and the closed-classifier rejection (step 9) — with the correct client class, the correct internal audit result, and the correct consumption disposition for each.

Purpose: §02's numbered completion flow **is** the rejection precedence ("reject for the earliest failed step"), and it distributes eleven internal results across four client classes. Getting the mapping wrong is a client-contract bug the client cannot detect: `challenge_required` tells a client to prepare again, `auth_required` tells it to re-authenticate, `verification_temporarily_unavailable` tells it to back off and retry the whole operation, and `operation_not_allowed` is terminal and routes to support. Those are four incompatible instructions.

Output: every rejection arm of the completion handler, each with a unit case pinning its class, its internal result, and whether it consumed.

Note what D-12 removes from §02: step 6's provider-variant check is gone (there is no declaration to compare), so nothing sits between the claim and the Admin lookup, and `create_flow_mismatch` is not a class this route can emit. `challenge_operation_mismatch` remains live — it fires when a challenge issued for a *different operation* is presented here.
</objective>

  <action>
Implement §02 completion steps 3, 4 and 5 in the completion handler, in that order.

**Step 3, locate.** `ChallengeStore.locate` returning `None` is a *definitive* no-row and rejects as `challenge_not_found`. A database outage during the lookup is **not** `challenge_not_found` — it raises out of `locate` and stays the ordinary infrastructure failure, because answering "no such challenge" to an unreachable database tells a legitimate client to throw away a challenge that exists. Do not wrap `locate` in a broad `except`. The raw malformed identifier is never logged.

**Step 4, verify binding.** Call `ChallengeStore.verify_binding(row, identity)` and map its `ChallengeRejection` members straight through — every member's value is also an `AuthEventResult` member precisely so the caller needs no private mapping table. In the same step, check `row.operation is AuthOperation.create_user` and reject `challenge_operation_mismatch` otherwise. Both checks run **before** the claim and leave any located challenge unclaimed and unconsumed, so a wrong-endpoint or wrong-identity presentation cannot burn the rightful user's in-flight challenge. Do not write a `compare_digest` here — `verify_binding` already routes the comparison through `HmacKeyring.actor_subject_matches`, and a second comparison would be a second answer.

**Step 5, claim.** One `ChallengeStore.claim` call, in its own committed transaction, conditioned on state still `issued` AND `expires_at` in the future. This is the single serialization point and the **only** expiry evaluation anywhere in the protocol — do not read `expires_at` at any other point in the handler. On `False`, re-read the located row and distinguish: still-issued-but-expired → `challenge_expired`; already claimed or consumed → `challenge_consumed`. Re-read rather than issuing a second conditional update; `challenges.py:168-172` states that explicitly. The claim loser performs **no** work at all — no Firebase lookup, no mutation — and never returns the claim-holder's stored outcome: there is no idempotent replay and no `challenge_replayed` result, and the client reconciles through `/auth/sync`.

All five rejections surface to the client as the single collapsed class `challenge_required` (409). §02 says why in one line: "completion is not a challenge-enumeration oracle". Byte-identical body and status across all five; only the audit row differs.

Consumption disposition, stated explicitly in a comment because it is the part that is easy to get backwards: identity and operation mismatches **neither claim nor consume**; the claim losers (`challenge_expired`, `challenge_consumed`) never held a claim so there is nothing to consume; `challenge_not_found` has no row at all. So **none** of the five consumes. Consumption begins at the Admin lookup (Task 2).

Each of the five is on the audited path with no consuming transaction in play, so each writes a **standalone durable** audit row through `AuditWriter.write_standalone`, before the response returns, carrying the located row's non-secret `AuthChallenge.id` as `challenge_row_id` where a row exists.

Write the nine behaviors above as `tests/unit/test_create_user_precedence.py`'s first class, using 37-07's shared fake adapter (whose call count is what proves "the claim loser performs no work") and a recording audit writer.
