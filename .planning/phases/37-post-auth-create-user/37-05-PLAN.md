<objective>
Build the codebase's first concrete provider adapter — the issuer-selected Firebase Admin integration behind foundation's `§7.1` seam — and §02 step 9's closed providerData classifier.

Purpose: `firebase-admin>=7.3.0` is declared at `pyproject.toml:24` and imported **nowhere** in `src/`. Phase 35 removed the last Firebase client at boot (`app/lifespan.py:66-69`) and this phase reintroduces Firebase — behind the seam, never as an ambient startup client.

Output: `auth/firebase.py` (the adapter and the boot-time app builder), `auth/classifier.py` (the closed classifier and §02 step 10's email-copy predicate), and a two-field additive amendment to foundation's `ProviderDataResult` — all unit-tested without a network and without a credential.

**This plan settles the email carrier, in wave 2, on purpose.** §02 step 10 copies `email` "only when the same successful `getUser` response carried a non-empty address AND `emailVerified` was true". "The same response" is the constraint that decides the shape: the address cannot be re-fetched later, so it must ride out of the adapter on the one result object the `getUser` call returns. Foundation's `ProviderDataResult` (`auth/adapters.py`) declares only `outcome` and `entries`, so it grows two defaulted fields here — `email: str | None = None` and `email_verified: bool = False` — and Task 2 populates them from the same `UserRecord`, in the same `try`, inside the same threadpool call that materializes `provider_data`. This is a **Phase 35 foundation amendment** and is recorded as one: `auth/adapters.py` is Phase 35's module. It is purely additive and purely declarative — two annotated fields with defaults on an existing frozen dataclass, no function, no method body, no import — so every existing construction site (`ProviderDataResult(ProviderDataOutcome.selection_failure)`) is unchanged and `tests/unit/test_adapter_interfaces.py`'s zero-implementation, allowed-imports, and frozen-dataclass assertions all still hold. — **Reversibility:** reversible (a defaulted field is removable without touching any caller that does not read it).

37-07's `auth/creation.py` therefore takes an already-resolved `email: str | None` and 37-10's substituted adapter scripts `ProviderDataResult(outcome=ok, entries=..., email=..., email_verified=...)`. Neither plan discovers this shape; both consume it.

**Under D-12 the classifier does one job only.** RESEARCH described `auth/classifier.py` as owning the classification *plus* the declaration match *plus* `required_flow` derivation; D-12 deletes the client flow declaration, so the declaration match (§02 step 9's second half) and `required_flow` do not exist. The closed classifier itself is unchanged. A rejecting shape is an unclassifiable **account**, not a declaration mismatch, and routes to `operation_not_allowed` via the invalid-shape `provider_not_linked` cause. `provider_not_linked`'s bounded cause therefore loses `supported-provider-mismatch`; `empty` and `invalid-shape` remain.
</objective>
