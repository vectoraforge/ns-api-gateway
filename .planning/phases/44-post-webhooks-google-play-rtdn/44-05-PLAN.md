<objective>
Measure, on a real PostgreSQL, the three database behaviours the Google path inherits from Phase 43
and one it can break from a new cause — and re-prove Apple's mapping after the status word moved
into the provider classes.

Purpose: PLAYHOOK-02 binds this phase to Phase 43's service rather than a fork. That is a claim
about runtime behaviour, and it is only true if a Google notification produces the same replay,
ordering, race and grant outcomes an Apple one does. Three of these are deselected by default,
so a plan that runs only the quick suite proves none of them.

Output: the Google cases in the two schema test files, and the Apple mapping case.
</objective>

    Give the `_notification` factory a `provider` keyword defaulting to `PurchaseProvider.apple`,
    plus the `status` and `tier_id` keywords the promoted value type now requires, so a Google
    variant is one call rather than a second factory.

    Add the **idempotency** case: ingest one Google notification, then ingest a second notification
    built from the same RTDN — the same purchase token, the same `eventTimeMillis` and the same
    notification type, therefore the same `notification_uuid` under the key scheme plan 44-01
    settled. Assert exactly one `audit.subscription_events` row for that key, exactly one
    `core.subscriptions` row for `(google_play, external_id)`, and that no second grant row was
    written. This is the property OQ-4 exists to protect and it fails silently: a key that is not
    stable across a Pub/Sub redelivery raises no UNIQUE violation, it just writes a second audit row
    and runs a duplicate grant write.

    Add the **grace-period** case: ingest a Google notification whose status is
    `SubscriptionStatus.grace_period` and whose `grace_period_expires_at` equals its `expires_at`,
    both after `evaluated_at`. Assert the `core.access_grants` row written for it is effective at
    `evaluated_at` — its end is after `evaluated_at` and is not null. Then add the negative control
    that makes the case non-vacuous: a notification in grace with `grace_period_expires_at` of
    `None` writes an ineffective grant, which is exactly the Phase 43 CR-02 defect this case exists
    to stop the Google path reproducing from a different cause. Google carries no separate
    grace-period field, so the value must come from the line item's own expiry.
  </action>
