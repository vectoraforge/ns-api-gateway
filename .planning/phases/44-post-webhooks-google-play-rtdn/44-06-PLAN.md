  <action>
    Extend `tests/e2e/test_google_play_webhook.py` with the matrix, copying the structure and the
    voice of the App Store e2e file. Define the shared bodies once as both parsed objects and raw
    bytes, so the refusals are compared on the wire and not after parsing, and set `PATH` to
    `/webhooks/google-play/rtdn`.

    **The refusal matrix.** Parametrise over every `stage` the Google path can refuse with, asserting
    401 and a byte-identical body each time. Add the control the Apple file already carries: a case
    asserting every reachable refusal arm is covered by exactly one parameter, so an arm added later
    without a parameter fails here rather than shipping untested. A single class and a single body
    for every arm is the anti-oracle property; a richer body on any arm must fail this file.

    **The fail-closed pair.** With `unconfigured_google_play`, assert the route answers 503 with the
    unavailable body, and assert in a separate case that the route is still a registered route while
    the seam is unconfigured — 503, never 404. That pair is what makes D-14 and D-18's promise
    testable rather than a claim, and it is the same pair the Apple file carries.

    **The two arms that answer 200 without writing.** Script a verified token with a `message.data`
    that is not decodable base64, assert 200, assert one ERROR record, and assert under
    `_db_transaction` that nothing was written. Then script a verified push whose decoded body
    carries `pendingRefundReviewNotification` and no `subscriptionNotification`, assert 200, assert
    one INFO record naming the body, and assert the scripted Play fake recorded **no** call. Use
    `pendingRefundReviewNotification` deliberately rather than `testNotification`: it is the body
    D-05 does not name, so it is the one a closed three-member list would let fall through.

    **The three arms that answer 500.** Script the Play fake to raise `InternalError` (a failed Play
    call), `UnmappedStoreProduct` and `AttributionConflict` in turn; assert 500 and the shared
    internal body each time, and assert nothing was written. 500 is the answer that makes Pub/Sub
    redeliver, which is the point.

    **A Firebase token changes nothing.** Assert that sending a valid Firebase bearer alongside a
    bad push token still produces the same 401, mirroring the Apple case: this route reads only its
    own credential and the application's own identity gate must not leak into it.

    **The sensitive-value walk.** Spy on the error-handler and service loggers as the Apple file
    does — a spy rather than `capture_logs`, because the module-level logger caches its binding —
    and assert no record carries the OIDC token, the base64 envelope, the attribution token, or the
    Google purchase token. The purchase token is now persisted as `external_id` under the D-10
    flagged divergence, and it must still never reach a log line.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller → the route's response | The response body is the only thing an attacker can read back; every refusal must look the same |
| route → structured logs | Logs are the operator's channel and must carry no credential or payload value |

## STRIDE Threat Register (ASVS L1)

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-44-25 | Information disclosure | refusal oracle | high | mitigate | The refusal matrix compares raw response bytes across every arm, plus a control asserting the parameter set is complete, so an arm with a richer body fails here |
| T-44-26 | Information disclosure | logs | medium | mitigate | The sensitive-value walk covers the OIDC token, the envelope, the attribution token and the purchase token |
| T-44-27 | Spoofing | credential confusion | medium | mitigate | A valid Firebase bearer is asserted not to change the refusal, so the application's own identity gate cannot leak into this route |
| T-44-28 | Denial of service | redelivery loop | medium | mitigate | The two 200-without-writing arms are proved on the wire, so a payload that can never parse is acknowledged rather than retried until retention expires |
| T-44-SC | Tampering | package installs | low | accept | No package is installed by this plan |
</threat_model>
