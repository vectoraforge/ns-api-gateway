    `SubscriptionStatus.expired`. Keep one inline comment per non-obvious arm: on hold is Play's

    omission: `subscriptionsv2` exposes no citable revocation signal, and a revoked subscription

    - `developer_notification_from` given a base64 string that does not decode, or that decodes to something that is not the expected JSON object, logs one ERROR record and the dependency returns `None`; the caller answers 200 and writes nothing.
    - A decoded notification carrying `testNotification`, `oneTimeProductNotification`, `voidedPurchaseNotification` or `pendingRefundReviewNotification` logs one INFO record naming the body it carried, makes no Play call, and yields `None`.
    - A decoded notification whose `packageName` differs from the configured value raises `NotificationRejected` before any Play call.
    - A Play GET answering 404 or 410 logs one ERROR record and yields `None`.
    - A Play GET answering any other non-2xx status, or raising `httpx.HTTPError`, raises `InternalError`.
  </behavior>
  <action>
    Write each arm's case first, then build it.

    **D-04.** Decode failures are caught around `base64.b64decode(value, validate=True)` and
    `json.loads`. One ERROR record with closed-set labels only, then a `None` result, then 200 from
    the handler. The correction to record here: `44-CONTEXT.md` D-04's stated ground is factually
    wrong — Cloud Pub/Sub acknowledges only 102, 200, 201, 202 and 204 and resends on every other
    status, so there is no 4xx-is-permanent rule and a 400 would loop for the whole retention
    window. The decision is unchanged and better supported: 200 is the only answer that stops a
    redelivery loop on a payload that can never parse. Put that reason in the one-line comment above
    the arm, not the wrong one.

    **D-05.** Decide the arm on the **presence of `subscriptionNotification`**, never on the absence
    of a list of names. Google ships five notification bodies and D-05 names three of them; a
    three-member allow-list lets `pendingRefundReviewNotification` fall through an `else` into a
    Play call that has no purchase token to make. Log one INFO record naming which body was present,
    from a closed set of body names, and yield `None`.

    **D-18.** Compare `packageName` to `GooglePlayConfig.package_name` and raise
    `NotificationRejected` with its own `stage` label before any Play call. This runs after the
    token check and before the network, so a token that verifies for a different application still
    costs no outbound call.

    **OQ-5.** In `PlayDeveloperSubscriptions.read`, order the response arms so nothing falls through
    to a default, following the classification function in `auth/devicecheck.py`. Treat 404 and 410
    as definitive: a purchase token Google says is gone can never resolve, so a 500 there is an
    infinite redelivery until retention expires — the same loop D-04 exists to avoid, on a different
    arm. Log one ERROR record and yield `None`. Every other non-2xx status, and every
    `httpx.HTTPError`, raises `InternalError` so Pub/Sub redelivers, which is D-20's blanket rule.
    Community sources rather than Google's own error reference are the basis for the 410 reading, so
    keep it to one `if` and do not build a taxonomy on it.

    Every refusal keeps the single `NotificationRejected` class and the shared one-field body; the
    distinguishing detail lives in the `stage` log field alone, which is the anti-oracle property
    APPLEHOOK-01 records.
  </action>

| T-44-12 | Spoofing | claim pins | high | mitigate | `email` and `email_verified` compared after `jwt.decode`, each with its own `stage`; pinning `aud` alone would admit any Google ID token minted for an audience an attacker learned |
