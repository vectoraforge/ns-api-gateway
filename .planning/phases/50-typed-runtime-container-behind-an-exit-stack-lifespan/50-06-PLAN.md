<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Apple / Google store callback → this pod | Both webhook routes are unauthenticated at the gateway; the payload or the push token is the one credential |
| Client-presented restore proof → `get_restore_service` | An authenticated but untrusted artifact |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-50-06-01 | Spoofing | `verify_app_store_notification`, `verify_google_play_notification` | high | mitigate | Both stay route dependencies resolved before `get_db`, so a refused payload still opens no database session. `get_runtime` performs no I/O, so inserting it ahead of them adds no work to the refusal path. The existing resolution-order cases in `tests/unit/test_app_wiring.py` run in the unit gate. |
| T-50-06-02 | Tampering | `verify_google_play_notification` ordering | high | mitigate | The token check stays the first statement, the body decode stays after it, and the package comparison stays before the Play call — stated in the task action and covered by `tests/unit/test_google_play_notifications.py`. |
| T-50-06-03 | Information disclosure | `runtime.config` reachable from any dependency | medium | accept | Any dependency that declares `get_runtime` can read the whole config, where before it read one attribute. The container is never logged (T-50-03-01), and `_declared` is pinned per route by plan 50-05 task 2, so the widening is visible in the route table. |
| T-50-06-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is installed or upgraded; `uv.lock` is not touched. |
</threat_model>
