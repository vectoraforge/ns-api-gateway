<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Pod boot → serving traffic | A pod that becomes Ready with a `None` verifier serves a route whose credential nothing checked |
| Environment / mounted secret → builder | An unreadable or corrupt root certificate file is operator input |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-50-02-01 | Spoofing | `build_google_push_verifier` | high | mitigate | A `PyJWTError` at warm-up now raises `RuntimeError`, so the pod never becomes Ready holding a verifier it could not build for a transient reason. ASVS V2. Pinned by the inverted cases in `TestTheJwksWarmUpGuard`. |
| T-50-02-02 | Spoofing | `build_app_store_verifier` | high | mitigate | A root certificate that exists but does not parse raises instead of yielding `None`; Phase 43 measured that an unchecked root builds a verifier that rejects every genuine Apple notification. |
| T-50-02-03 | Denial of service | the whole pod | medium | accept | D-08 trades a degraded route for `CrashLoopBackOff` when Google's metadata server or JWKS endpoint is briefly unreachable at pod start. That is the intent; record it in the summary so the operator is not surprised. |
| T-50-02-04 | Information disclosure | the new `RuntimeError` messages | medium | mitigate | Each message names the setting, the URL or the file path and the failure class only — never the file bytes, a credential or `DatabaseConfig.url`, following `_prove_database_reachable` at `lifespan.py:124-133`. |
| T-50-02-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package is installed or upgraded; `uv.lock` is not touched. |
</threat_model>
