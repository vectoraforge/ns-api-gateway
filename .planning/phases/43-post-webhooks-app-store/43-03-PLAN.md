<objective>
Attach the purchase to an account, or record honestly that it belongs to nobody yet.

Purpose: a store purchase arrives with an attribution token or with none. The token is the only link
Apple gives from a subscription to one of this project's users, and getting the link wrong once is
worse than not linking at all — restore (Phase 45) can still adopt an unclaimed subscription, but it
cannot un-give an entitlement handed to the wrong account.

Output: the `core.store_purchases` model, the inverse token read, the attribution decision in the
service, and `AttributionConflict`.
</objective>

  <behavior>
    - Attributed: the token resolves to a user; the subscription row carries `user_id` and the purchase
      row carries `purchase_user_id` and `resolved_token_value` equal to the token.
    - Unattributed: no token, or a token with no binding; the subscription row carries `user_id` NULL
      and the purchase row carries NULL owner, NULL resolved value and a generated `identity_value`.
    - Repeat for a known `(provider, external_id)` with the same `identity_value`: the subscription row
      updates in place and no second purchase row is written.
    - New `external_id` under the same token: a new purchase row is written.
    - Conflict: a known `(provider, external_id)` whose purchase row holds a different
      `identity_value` raises `AttributionConflict` and nothing is written.
  </behavior>

  <action>
Add the attribution half to the crud class and the decision to the service.

In `src/nativespeaker/api/crud/subscriptions.py` add `read_purchase(provider, external_id)` returning
the `StorePurchase` row or `None`, and `insert_purchase(...)` which adds the row and flushes. The
insert takes plain values only — provider, identity value, external id, the two store transaction ids,
the owning user id or `None`, the resolved token value or `None`, and the captured instant — and never
a notification object; crud receives values, not payloads. The flush sits alone inside its `try` and
its `except IntegrityError as violation` arm reads the SQLSTATE straight off the wrapped error as
`crud/grants.py:174-181` does, returning the lost-race member for `23505` and re-raising anything else.
The subscription row must already be flushed when `insert_purchase` runs, because
`core.store_purchases` carries a composite foreign key on `(provider, external_id)` into
`core.subscriptions`; state that in one line above the call, not as a docstring.

In `src/nativespeaker/api/services/subscriptions.py`, resolve the user **before** the transaction's
locks and writes begin, exactly as D-16 requires: when the notification carries an attribution token,
call `PurchasesDB.resolve_user(PurchaseProvider.apple, attribution_token)`; when it carries none, do
not read at all. A `None` answer and an absent token are the same outcome — unattributed — and the
code should say so once rather than branch twice.

Then extend `ingest` with the attribution decision, written as an ordered set of arms with the order
itself stated once in the preamble comment, in the shape `services/auth.py:118-119` uses:

1. Read the existing purchase row for `(provider, external_id)`. If it exists and its `identity_value`
   differs from the value this notification presents, raise `AttributionConflict(provider, external_id)`
   and write nothing. An existing row's identity value is never reassigned — a purchase that changed
   owner is a fact this route cannot verify and Apple retries on its own schedule, so refusing costs a
   retry and repairing could hand an entitlement to the wrong account.
2. If it exists and agrees, write no second purchase row; the canonical subscription row still updates
   in place (D-19).
3. If it does not exist, insert one. For an attributed notification the identity value is the
   attribution token, `purchase_user_id` is the resolved user and `resolved_token_value` is the same
   token — the table's `CHECK` allows the resolved value to be NULL or exactly the identity value and
   nothing else. For an unattributed notification the identity value is a freshly generated UUID
   string, because the column is `NOT NULL` and the store gave none, while `purchase_user_id` and
   `resolved_token_value` are both NULL; the second composite foreign key is MATCH SIMPLE, so the NULL
   resolved value skips the token check and the row still records.

Carry the resolved user id onto the `core.subscriptions` row's `user_id` in the same transaction, and
leave it NULL for the unattributed case. Restore (Phase 45) is the only path that links an unclaimed
subscription later; this route never invents a link.

Nothing in this task takes a lock and nothing reads the clock — the one captured instant is already on
the service.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `appAccountToken` → `core.users.id` | The only link Apple gives from a purchase to an account; a wrong link hands entitlement to the wrong user |
| verified payload → `core.store_purchases` | Values from a verified payload are trusted facts; the request envelope is never a source |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-43-07 | Elevation of Privilege | the attribution decision in `services/subscriptions.py` | high | mitigate | An existing purchase row's `identity_value` is never reassigned; a disagreement raises `AttributionConflict`, answers 500 and writes nothing, so Apple retries rather than the backend guessing an owner |
| T-43-12 | Spoofing | `core.store_purchases.identity_value` for an unattributed purchase | medium | mitigate | The generated value is a server-side UUID, and `resolved_token_value` stays NULL so the MATCH SIMPLE foreign key skips the token check; no fabricated value can ever satisfy the token binding |
| T-43-06 | Information Disclosure | the ERROR log line on `AttributionConflict` | high | mitigate | `log_fields()` returns exactly `provider` and `external_id`; the attribution token is not among them, and an e2e case asserts positively that it appears in no captured record |
| T-43-13 | Tampering | the write order into `core.store_purchases` | medium | mitigate | The subscription row is flushed first, so the composite foreign key on `(provider, external_id)` is satisfied by a committed-order write rather than by a deferred check |
| T-43-SC | Tampering | package-manager installs | low | accept | This plan installs no package and edits no dependency file |
</threat_model>
