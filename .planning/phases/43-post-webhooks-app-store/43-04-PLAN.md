<objective>
Turn a verified subscription into an entitlement the rest of the application already knows how to
read: one active `core.access_grants` row on the mapped tier with its `core.user_monthly_usage` row,
written under the project's fixed lock order in the same transaction as the subscription row.

Purpose: this is where ingestion stops being bookkeeping and starts changing what a user can do.
Every rule here is a rule about *when to write*, and each is ultimately arbitrated by an index that
already exists — the application's job is to ask the questions in the right order under the right
locks.

Output: the subscription-grant writer, its measured behaviour on real PostgreSQL, its lock-tier
proof, and a single-writer walk so Phase 45's restore cannot quietly become a second writer.
</objective>

  <behavior>
    - Attributed and entitled, no prior subscription grant: the buyer's active free grant is expired
      and flushed, then a `subscription` grant is inserted on the mapped tier with `starts_at` at the
      purchase date and `ends_at` at the expiry, with a fresh usage row at `monthly_used = 0`.
    - Attributed and entitled, an active subscription grant for the same subscription with the same
      `ends_at`: nothing is written to either the grant or the usage table.
    - Renewal — same subscription, a later `ends_at`: the old grant becomes `expired` with `ends_at`
      set, flushed alone and first, then the next term's grant and its fresh usage row are inserted.
    - Not entitled — the subscription's status is anything other than `active` or `grace_period`: the
      subscription grant becomes `expired`, or `revoked` when the subscription is revoked, with
      `ends_at` set, and no replacement is inserted.
    - A second subscription for the same buyer: the newest verified purchase wins through the same
      expire-then-insert path.
    - Unattributed: no lock is taken and no grant or usage row is written.
  </behavior>

  <action>
Add the grant half to `SubscriptionsDB` and put it in the service's transaction in the right place.

**The lock order comes first and is not negotiable.** In the writer, before any question whose answer
a concurrent writer could change: lock the buyer's effective grant rows ascending by id, then lock
each of their usage rows. Reuse `GrantsDB.lock_effective_grants` and `GrantsDB.lock_usage` rather than
writing a second pair of statements — a second spelling of the lock order is a second thing to keep
correct. Take no third tier: no lock on `core.subscriptions`, on `core.store_purchases` or on the user
row. A subscription-row lock would sit ahead of the grant locks and would break the global order the
whole project holds. The replay read plan 43-01 put in the service must sit **after** these locks, not
before them.

**The term is the grant's `ends_at`.** Write `starts_at` from the notification's purchase date and
`ends_at` from its expiry. "Same term" means: an active grant whose `source` is
`AccessGrantSource.subscription`, whose `subscription_id` is this subscription, and whose `ends_at`
equals this notification's expiry. When that row is present and the resolved tier id is unchanged, the
grant half is a no-op reached **before** any grant or usage write. Condition the no-op on the tier as
well as the term, because D-19 requires a tier change to be applied in the same transaction; a
term-only test would silently swallow it. Record in one line that a mid-term tier change is handled by
the same expire-then-insert path rather than by an in-place `tier_id` update, so the superseded term
stays in history — the choice is moot with one paid tier today and this is the answer if a second one
is added.

**Expire, flush, then insert.** Copy `crud/grants.py:216-239` including its reason: set the superseded
grant's `status`, `ends_at` and `updated_at` from the captured instant, flush that alone and first,
then insert the replacement. `ix_access_grants_one_per_subscription` is partial and enforced per
statement, so two active grants for one subscription are refused mid-flush unless the update lands
first. Every flush sits alone in its `try`, and the `except IntegrityError` arm reads the SQLSTATE
straight off the wrapped error and returns the lost-race member for `23505`, re-raising anything else.

**The buyer's free grant is expired, never deleted (D-18).** Before inserting the paid grant, mark any
active grant whose source is in `FREE_GRANT_SOURCES` as `expired` with `ends_at` at the captured
instant, in the same flush-first position. This spends the lifetime free slot permanently, because
`ix_access_grants_one_free_grant_per_user_source` carries no status predicate — so when the
subscription later lapses, the buyer holds no grant at all. That is a product consequence this phase
accepts, not a defect: ingestion never reactivates a grant and restore (Phase 45) is the only path
back. Say that in one line where the expiry happens.

**Leaving the entitled set.** The entitled set is exactly `active` and `grace_period` — that is fixed
by `core.subscriptions.product_entitled_subscription_id`, which is generated over those two, and by
the two deferrable foreign keys that bind an active subscription grant to it. When `status_at` returns
anything else, mark this subscription's active grant `revoked` when the subscription is revoked and
`expired` otherwise, set `ends_at`, and insert no replacement. Leaving the grant active would not be a
quiet wrong answer: the deferrable foreign key would fail the commit. Prefer the explicit transition
anyway, and say in one line that the constraint is the backstop rather than the mechanism.

**The fresh usage row** is inserted with the grant, in the pair shape at `crud/grants.py:157-168`:
`monthly_used = 0` and `monthly_period` from the captured instant, spelled exactly as
`services/quota.py:54-60` and `services/sync.py:26-27` spell it. Never mint a usage row for an
existing grant that lacks one — a missing usage row is a detectable broken invariant and minting one
would turn it into a silent free allowance.

**Unattributed** notifications skip all of this: with no user there is nothing to lock and no grant to
hold, and the unique indexes on the subscription and the event row are what serialize that case.

Keep every comment to one line, in Simplified Technical English (D-25), above the line it explains.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| verified notification → `core.access_grants` | This is where a store event becomes something a user can spend; a wrong write is a wrong entitlement |
| concurrent writers → the grant tables | Two deliveries, or a delivery and a claim, can reach one buyer's grant rows at once |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-43-14 | Elevation of Privilege | double entitlement for one buyer | high | mitigate | The same-term test is reached before any grant or usage write, and `ix_access_grants_one_active_per_user` and `ix_access_grants_one_per_subscription` refuse a second active row per statement; the writer flips and flushes before it inserts |
| T-43-15 | Tampering | deadlock or lost update across concurrent writers | high | mitigate | The fixed global lock order — grant rows ascending by id, then their usage rows, no third tier — reusing `GrantsDB`'s own lock methods rather than a second spelling, and asserted over the SQL the writer emits |
| T-43-16 | Elevation of Privilege | a lapsed subscriber regaining a free grant | medium | accept | The free slot is lifetime-once and expiring it spends it permanently; ingestion never reactivates a grant, so a lapsed buyer holds none until restore. A product consequence D-18 accepts, recorded rather than mitigated |
| T-43-17 | Tampering | a silent free allowance from a minted usage row | high | mitigate | A usage row is never minted for an existing grant that lacks one; the missing row stays a detectable broken invariant that fails closed |
| T-43-18 | Repudiation | a superseded term disappearing from history | medium | mitigate | A grant row is expired, never deleted, and a tier change flips and inserts rather than updating in place, so every term is still readable |
| T-43-SC | Tampering | package-manager installs | low | accept | This plan installs no package and edits no dependency file |
</threat_model>
