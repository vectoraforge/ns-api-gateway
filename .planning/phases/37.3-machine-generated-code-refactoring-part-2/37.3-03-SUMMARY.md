**The providerData read now classifies and applies the email rule inline and raises the outcome it
discovered, the retry policy catches an internal marker instead of inspecting a returned value, and
an exhausted budget answers the 503 the caller is owed rather than tenacity's 500.**

## Accomplishments

- `ProviderDataOutcome`, `ProviderDataEntry` and `ProviderDataResult` are gone. One frozen, slotted
  `VerifiedProviderIdentity` crosses the seam, and `adapters.py` still imports no provider SDK.
- The lookup-arms group exists in `auth/exceptions.py`: `ProviderLookupError` carrying `stage` and an

  inside the same `try` because `record.provider_data` is lazy, and the security comment at the
  Firebase-error arm still says why `detail` exists.
- `retry_if_result(_is_retryable)` became `retry_if_exception_type(RetryableLookupError)`, so
  `UserNotFound` and `NotLinked` propagate after one attempt. `_exhausted` raises `Unavailable`
  inside the retry frame; both of the frame's now-false comments were rewritten, not carried.

- The classifier's `ACCEPTED` and `REJECTED` tables live at adapter level with **every prose reason
  intact**, and `tests/unit/test_provider_classifier.py` is deleted rather than left as a shim.

## Decisions Made

### The shared fake scripts the seam's answer, not the read's inputs

The plan's Task 3 says "a scripted exception is raised, a scripted `VerifiedProviderIdentity` is
returned". Taken literally that means `FakeFirebaseAdapter.script(...)` can no longer accept
`entries=`, because entries are now an implementation detail *behind* the seam it stands in for.

The alternative was tempting and was rejected: the fake could have kept `script(entries=...)` and
called `_resolve_provider` / `_verified_email` itself, which would have left roughly a dozen unit and
e2e call sites completely unedited. That would have made the fake a second executor of rules whose
whole point is that they now live in exactly one place — and the copy is the thing that drifts. The
fake scripts one answer; the rules are tested against the real `_read` in `test_firebase_adapter.py`,
where a monkeypatched SDK lets the same tables drive production code.

Two consequences worth recording for plan 04:

- Router-level and e2e cases now assert *the answer a rejection earns*, not *which shape earns it*.
  Both facts are still asserted; they are asserted at the layer that owns each.
- The e2e email-rule table kept all five rows by scripting `_verified_email(email, email_verified)`
  — production evaluates the rule, and the e2e still proves the decided address reaches the column
  verbatim ("not lowercased, not trimmed").

### Task 1 and Task 2 are one atomic change

Deleting three types from the seam breaks `firebase.py`, `routers/auth.py`, `tests/unit/conftest.py`
(via `routers/__init__`), and four test suites simultaneously. There is no ordering in which Task 1
lands green on its own: even `pytest tests/unit/test_adapter_interfaces.py` loads the shared unit
conftest, which loads the routers, which load the adapter.

So `pytest -q` is **red at `d319326`** and green from `210be5f` onward. Task 1's acceptance criteria
never claimed a full-suite pass (unlike Task 2's), and its commit message says plainly that it is the
first half of a single contract change. Every other commit in this plan is green on all three
selections.

### `test_a_failed_lookup_beats_a_rejecting_shape` was relocated, not repointed

That case set up two facts at once — a not-found lookup *and* a providerData shape that would reject
— and asserted the 401 wins. The seam admits one answer per call now, so the router-level fake cannot
express both. The precedence itself did not disappear: it became structural, since `_read`'s `try`
block resolves the lookup before `_resolve_provider` is ever called. The case moved to
`test_firebase_adapter.py`, where a not-found `get_user` on a record carrying a rejecting shape still
sets up both facts against real code. The comment left in the precedence suite says where it went.

## Issues Encountered

- **A seam-type deletion is not decomposable into green commits.** The four-task split assumes the
  seam can be changed independently of its consumers; it cannot, because `tests/unit/conftest.py`
  reaches the adapter through `routers/__init__`. Worth carrying to plan 04: a task that deletes a
  type shared by production and both conftests is one commit, however many tasks describe it.
- **`tenacity`'s exhaustion path has two wrong answers, not one.** The plan named `RetryError`
  (tenacity's default) but `reraise=True` is the other trap — it surfaces `RetryableLookupError`,
  which has no `error_class` at all. Both are asserted as named negatives now, because a test that
  only checks "something raised" passes on either.
- **`git archive` is the safe way to measure a baseline** in a checkout where stashing is forbidden:
  extract the base commit to `/tmp` and run it with `PYTHONPATH` pointing at the base `src/`, which
  wins over the editable install's `.pth` entry.
