# Phase 37.3: Machine-generated code refactoring, part 2 - Context

**Gathered:** 2026-08-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Continue 37.1/37.2's de-complication by killing the last big machine-generated pattern: functions
that *return* a rejection vocabulary (enums, result dataclasses, mapping dicts) which callers then
translate into client responses. It is replaced with DRF-style exceptions that carry their own
`ErrorClass`, raised where the rejection is discovered and answered by one FastAPI handler.

Four sites convert, in this order (D-19):

1. **The consuming transaction** (`auth/creation.py`) — conflict classification and the
   existing-identity results become raised exceptions.
2. **Identity resolution** (`auth/identity.py::resolve_identity`) — the `Admit | Reject` union dies.
3. **The provider lookup** (`auth/adapters.py` + `auth/firebase.py`) — the
   `ProviderDataOutcome`/`ProviderDataResult` result types become a raised `ProviderLookupError`
   hierarchy, and the classifier and email rule move inline into the read.
4. **The challenge binding** (`auth/challenges.py::verify_binding` and the challenge rejections in
   `routers/auth.py::_complete`) — last, on its own plan (D-16).

A standing sweep rides along: **everything with zero consumers dies** (D-13), which this discussion
already resolved to include `get_preauth_identity`, `ErrorClass.copy`, the `ChallengeRejection`
enum, and the entire `AuthEventResult` enum.

**Zero client-visible change.** Every status code, error class, body, header, consumption semantic,
and admission decision is preserved exactly. Log events change shape (D-02) — that is the only
observable difference, and it is sanctioned.

**Out of scope:** which routes are authenticated, the auth dependency mechanism (37.1 D-06/D-07/D-09
stand), the e2e/precedence contract itself, phases 38–46's own work, and
`secret-manager-integration` (reviewed, not folded — third time).

<decisions>
## Implementation Decisions

### The exception family (developer's directive 1, plus discussion)

- **D-01: New `src/nativespeaker/api/auth/exceptions.py`: base `AuthRejected(Exception)` with class
  attribute `error_class: ErrorClass`; one subclass per client-visible outcome** (e.g.
  `IdentityAlreadyLinked` → `IDENTITY_ALREADY_LINKED`; `AccountUnavailable` → `ACCOUNT_UNAVAILABLE`
  covering both the blocked and historical arms — their indistinguishability to clients is
  preserved). CRUD/auth code raises; only the handler reads `error_class`. `AuthRejected` is a plain
  `Exception`, not a `ServiceError` — it gets its own `add_exception_handler` entry.

- **D-02: The handler derives the log event name from the exception class name, snake_cased.** One
  generic handler: `logger.warning(camel_to_snake(type(exc).__name__), route=..., ...)`, then
  `return error_response(exc.error_class)`. This supersedes the directive's original
  `result=type(exc).__name__` wording — the developer chose class-name-as-event over a shared
  `auth_rejected` event with a `result` field. Consequences: there is no single greppable rejection
  event anymore (accepted knowingly); the `auth_rejected`, `create_user_challenge_rejected` and
  `create_user_transaction_rejected` events are replaced by per-class events; `route` (from the
  handler's `Request`) and `bounded_reason` (off the exception, when present) survive as fields.
  Tests update their asserted event names — a vocabulary change only.

- **D-03: The return-value plumbing is deleted:** `CLIENT_CLASS_FOR_RESULT`, `_LOOKUP_REJECTIONS`,
  the `Admit`/`Reject` dataclasses and the `AdmissionDecision` union, the
  `ChallengeRejection`→`AuthEventResult` conversion, `classify_insert_conflict`,
  `_conflicting_constraint_name` and the constraint-name constants in `creation.py`. The
  `IntegrityError` arm rolls back the savepoint and raises `IdentityAlreadyLinked` — with one check
  the planner must keep: today an *unmapped* constraint name re-raises the original error (a 500
  tripwire, `creation.py:93`). Preserve that fail-loudly property rather than classifying every
  IntegrityError as a 409.

- **D-04: CRITICAL — rejections after the provider read still consume the challenge and COMMIT.**
  Raising must not skip `_consuming_rejection`'s semantics: `_complete` catches locally
  (`AuthRejected` from `create_account`, `ProviderLookupError` from the lookup), consumes the
  challenge, commits, then re-raises for the handler to answer. These exceptions never escape the
  route uncaught-by-`_complete`. — **Reversibility:** reversible, but a miss here is a live bug: an
  escaped exception hits `get_db`'s rollback and un-consumes a challenge the client already spent.

- **D-05: Preserved exactly:** the single savepoint around the three inserts,
  rollback-before-anything in the conflict arm, the pre-check via `resolve_existing_identity`, and
  the blocked/historical indistinguishability to clients.

### Identity resolution and the admission path (directive 3.1, plus discussion)

- **D-06: `resolve_identity` raises `AuthRejected` subclasses directly; `_reject()` and
  `AuthRejectionError` both die.** The handler is the one logging site — `route` comes from the
  `Request` it receives. No thin re-logging catch survives in `dependencies.py`.

- **D-07: The JWT/wire arm joins the same family, raised inline from `get_request_context`.**
  `extract_bearer` and `JwtVerifier.verify` keep their current return-a-tuple signatures —
  `wire.py` and `verification.py` are untouched. `get_request_context` raises an
  `InvalidExternalJwt`-style subclass carrying the `BoundedReason` for the handler to log.

- **D-08: The live fail-closed guards stay.** `get_quota_gate`'s unreachable pre-auth guard and the
  `AuthenticationError` class survive as-is — they are tripwires, not the returned-enum pattern this
  phase kills.

### The provider lookup (developer's directive 2, verbatim except D-12)

- **D-09: Delete `classify_provider_data`, `email_to_persist`, `_LOOKUP_REJECTIONS`,
  `ProviderDataOutcome`, `ProviderDataEntry`, `ProviderDataResult`.** `adapters.py` gains
  `VerifiedProviderIdentity(provider, provider_uid, email)` and a `ProviderLookupError` hierarchy
  (NOT `ServiceError` subclasses) whose classes carry `error_class: ErrorClass`, `stage`, and
  optional `cause`: `UserNotFound` (→ `AUTH_REQUIRED`), `Unavailable`
  (→ `VERIFICATION_TEMPORARILY_UNAVAILABLE`), `NotLinked` (→ `OPERATION_NOT_ALLOWED`, `cause` names
  the real reason). The Protocol returns `VerifiedProviderIdentity`. Per D-12 the directive's
  `result: AuthEventResult` attribute is dropped from these classes.

- **D-10: `firebase.py::_read` resolves the identity inline** (empty → anonymous; exactly one
  recognized entry with a uid → that provider; else `NotLinked`) and applies the email rule
  (verified + non-empty, never normalized); failures raise. Retry via `retry_if_exception_type` on
  an internal `RetryableLookupError` only; `UserNotFound` and `NotLinked` never spend retry budget;
  exhausted retries and issuer-selection failure raise `Unavailable`. Keep 3 attempts and all
  existing log events at this layer (`firebase_get_user_not_found`,
  `firebase_provider_data_malformed`, `firebase_credential_unavailable`, `firebase_get_user_failed`).

- **D-11: `routers/auth.py::_complete` wraps the lookup in `try/except ProviderLookupError`** and
  feeds the consuming-rejection path (D-04) from the exception's attributes. The exception must
  never escape the route: challenge consumption depends on catching it locally.

### AuthEventResult and the delete-unused sweep

- **D-12: `AuthEventResult` dies entirely — all 43 members.** After the four conversions nothing
  logs it: exception class names are the outcome vocabulary now. `ProviderLookupError` drops the
  `result` attribute directive 2 originally specified (the developer chose this explicitly when the
  conflict was surfaced). Future phases (38–46) name their outcomes as exception classes, not enum
  members. `AuthOperation` stays — the `core.auth_challenges` table uses it. — **Reversibility:**
  reversible in code (git history), but phases 38–46 briefs reference the enum vocabulary; their
  planners inherit the exception idiom instead.

- **D-13: STANDING RULE — delete everything with zero consumers, without re-asking per instance.**
  The developer stated this generally and confirmed it twice. Resolved instances:
  `get_preauth_identity` (`dependencies.py:102`, zero declarers — Phase 40 can resurrect from git),
  `ErrorClass.copy` (16 strings that never reach a client; the field and its test assertions go),
  the `ChallengeRejection` enum, `AuthEventResult` (D-12). The planner applies the same rule to any
  further zero-consumer helper the refactor strands, and does NOT bring instances back for
  discussion.

### The challenge binding (directive 3.2, plus discussion)

- **D-14: `verify_binding` raises; five subclasses share one base whose `error_class` is
  `CHALLENGE_REQUIRED`:** `ChallengeNotFound`, `ChallengeExpired`, `ChallengeConsumed`,
  `ChallengeIdentityMismatch`, `ChallengeOperationMismatch`. The client still sees exactly one 409
  body for all five — the anti-oracle property holds structurally, in the shared base. Each logs as
  its own event per D-02.

- **D-15: Pre-claim challenge rejections escape to the handler; no local catch.** `get_db` already
  rolls the session back on any exception, and the handler answers. `_challenge_rejected` is
  deleted. The claim-loss probe (claim returns `False` → `refresh` → `claimed_at` distinguishes
  expired from consumed, `routers/auth.py:112-120`) stays imperative in `_complete` and ends by
  raising the matching subclass. `ChallengeStore.claim`/`consume` keep returning `bool` — only
  `verify_binding` converts.

- **D-16: The binding conversion is its own plan, last, never bundled with the Firebase refactor.**
  The developer's own risk note, recorded verbatim in spirit: the rejection precedence order in
  `_complete` IS the spec of that block ("the order of the rejections below is the rejection
  precedence"), it is pinned by the 526-line precedence suite, and the transactional choreography
  (rollback on pre-claim rejections, the deliberate commit after claim, consume+commit on consuming
  rejections) must survive exactly. The precedence tests are the safety net for both the lookup and
  the binding refactor — they change for one reason at a time.

### Sequencing and gates

- **D-17: Plan order: directive 1 (exceptions.py + handler + creation) → 3.1 (resolve_identity) →
  2 (provider lookup) → 3.2 (verify_binding).** Each its own plan and commit. The small
  resolve_identity conversion proves the handler under the admission tests before the lookup work
  builds on it.

- **D-18: Test migration preserves every asserted status, error class, consumption semantic, and
  log event's *presence* — event names and vocabularies update per D-02.**
  `tests/unit/test_conflict_classification.py` imports deleted names — rewire.
  `tests/unit/test_provider_classifier.py` cases move to adapter-level tests. The e2e
  `FakeFirebaseAdapter` scripts raise-or-return. `tests/unit/test_auth_package_shape.py` updates its
  shape literals (regrowth stays a visible edit). `tests/e2e/test_admission.py` and
  `tests/unit/test_create_user_precedence.py` must pass with zero edits to any status code or body
  literal — log/import edits only.

- **D-19: Amend the adapter-seam entry in `.planning/REQUIREMENTS.md`** (FOUND-08's Phase 37.2
  amendment describes the `ProviderData*` surface this phase deletes) in the established style:
  amended, with a dated note. Reconcile ROADMAP.md's 37.3 stub entry with the real goal in the same
  phase.

### Claude's Discretion

  directive places it) or consolidates into `auth/exceptions.py`.
- The `camel_to_snake` mechanism and where it lives; what extra structured fields each exception
  contributes to its log line.
- Whether `InvalidExternalJwt` is one class for both wire arms (absent token / failed verify) with
  `bounded_reason` distinguishing, or two.
- How `VerifiedProviderIdentity.email` interacts with the anonymous arm (no email by construction).
- What else the D-13 sweep catches (e.g. `STATUS_TO_CLASS` entries, `assert_registry_total` arms
  that reference deleted fields).
- Whether 37-REVIEW's CR-02/WR-01 are still live in the code this phase rewrites — verify during
  planning; fix in place if the touched lines contain them (the 37.1/37.2 standing note).

## Existing Code Insights

### Reusable Assets

- **`errors.py` already has the DRF-style precedent:** `ServiceError` carries `error_class` as a
  class attribute and `service_error_handler` is data-driven. `AuthRejected` copies the shape with
  its own handler; nothing about the registry, `error_response`, or `register_class` changes.
- **`get_db` already rolls back on exception** (`dependencies.py:38-45`) — D-15's escape path costs
  nothing.
- **`exception handler dispatch walks the MRO`** — one `add_exception_handler(AuthRejected, ...)`
  entry covers every subclass.
- **tenacity is already the retry idiom** (37 D-04/D-05); D-10 swaps `retry_if_result` for
  `retry_if_exception_type` in the same `AsyncRetrying` frame.

### Established Patterns

- Plain-English prose register (37.1 D-16) — all new/moved code follows it.
- `Depends()`-only routes, DI in `app/dependencies.py`; handlers never take `Request`.
- Delete machinery whose justification fails re-examination — this phase is the fifth consecutive
  instance (RejectionCounter, BudgetGate, audit writer + registry, mode signal + adapters, and now
  the result-enum plumbing).
- The challenge handle is a secret: never logged, never in error text — every new log line the
  handler emits must keep that rule.

### Integration Points

- `app/errors.py::register_exception_handlers` — one new registration, ordered so `AuthRejected`
  never falls through to the generic 500 handler.
- `app/lifespan.py` — `assert_registry_total` still runs; verify it survives the `copy` deletion.
- The deliberate mid-handler commit after claim (`routers/auth.py:123`) — unchanged; everything
  after it is the consuming-transaction choreography D-04 guards.
