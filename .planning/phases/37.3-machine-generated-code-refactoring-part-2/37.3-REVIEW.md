## Critical Issues

### CR-20: An entitled store notification whose term has already ended writes an active grant outside its term, and destroys the buyer's working grant

**File:** `src/nativespeaker/api/services/subscriptions.py:110-116`
**Also:** `src/nativespeaker/api/crud/subscriptions.py:286-332`, `src/nativespeaker/api/crud/grants.py:25-37`
**Contrast:** `src/nativespeaker/api/services/restore.py:63-66`

**Issue:** The guard compares the term end against `starts_at`, not against the evaluation instant:

```python
starts_at = (self.evaluated_at if notification.purchased_at is None
             else notification.purchased_at)
term_ends_at = term_end_for(status, notification)
if status in ENTITLED_STATUSES and (term_ends_at is None or term_ends_at <= starts_at):
```

`starts_at` is a store-supplied purchase date that is by construction *before* the term end
(`auth/app_store.py:70-72` — `transaction.purchaseDate` / `transaction.expiresDate`;
`auth/google_play.py:277` — `subscription.startTime`, the original subscription start). So the
predicate `term_ends_at <= starts_at` is satisfied only by a nonsensical payload. A term that
ended *before now but after the purchase date* passes the guard untouched.

Reachable on both stores:

- **Apple.** `status` comes from `data.status` in the signed envelope (`auth/app_store.py:113-115`),
  frozen at signing time. Apple retries an unacknowledged notification for up to three days, so a
  `status = 1 (active)` envelope whose `transaction.expiresDate` has since passed is an ordinary
  redelivery. In the sandbox, where a subscription term is minutes long, it is the common case.
- **Google.** `_status_for` (`auth/google_play.py:182-192`) maps `SUBSCRIPTION_STATE_ACTIVE`
  straight to `SubscriptionStatus.active` with no expiry comparison at all — only the
  `_CANCELED_STATE` arm consults `expiry > evaluated_at`. A live read returning state `ACTIVE`
  with an `expiryTime` a moment in the past therefore yields `status = active` and a past
  `term_ends_at`.

What is then written (`crud/subscriptions.py:290-332`): because `entitled` is true, **every**
grant the destination holds is superseded (`status = expired`, `ends_at = evaluated_at`) — the
buyer's free `registered_account_grant` included — and a replacement `subscription` grant is
inserted with `ends_at = term_ends_at`, already in the past. `CHECK (ends_at > starts_at)` holds,
and `product_entitled_subscription_id` is non-NULL for an `active` subscription, so both deferred
FKs are satisfied. The row commits.

The result is exactly the state phase 43's `CR-02` was raised and fixed for, reached through a
different door: `_effective_grants_statement` (`crud/grants.py:33-34`) requires
`ends_at > evaluated_at`, so the new grant is **never effective**, yet it is `status = 'active'`
and therefore occupies `ix_access_grants_one_active_per_user`. The account is left with:

- `SyncService.read_entitlement` → `type=none, status=none` (`services/sync.py:31-37`);
- `QuotaService.charge` → `QuotaExceededError("No effective grant for this user")` on every chat
  (`services/quota.py:52-56`);
- every free-grant claim refused with `ActiveGrantOutsideItsTerm` (`services/auth.py:192-193`,
  `:241-243`) — the one-active slot is taken;

and no self-service path out. Recovery waits for the store to send a *non*-entitled notification
for the same subscription.

The block comment is also provably false: it claims this refuses "exactly as `RestoreService.restore`
refuses the same shape", but `restore.py:64` compares against `self.evaluated_at` and does refuse.

**Fix:** Make the webhook guard say what the restore guard says — the term must be open at the
instant the grant is evaluated — while keeping the `starts_at` comparison that protects the row's
own CHECK:

```python
term_ends_at = term_end_for(status, notification)
if status in ENTITLED_STATUSES and (term_ends_at is None
                                    or term_ends_at <= starts_at
                                    or term_ends_at <= self.evaluated_at):
    # An entitled status carrying a term that is absent, inverted, or already closed would
    # commit an active grant that `_effective_grants_statement` never reads, occupying the
    # one-active slot with no allowance. Refused before any write, as `RestoreService.restore`
    # refuses the same shape; the store resends.
    logger.error("store_notification_without_term", event_type=notification.event_type)
    raise InternalError
```

Add a service-level case: an `active`/`grace_period` notification whose `expires_at` (respectively
`grace_period_expires_at`) is before `evaluated_at` must leave `core.access_grants` untouched, and
must leave a pre-existing free grant still `active`.

### WR-40: `RestoreService` inserts the subscription row before taking the grant locks, inverting `SubscriptionsService`'s order — the buy-then-restore race deadlocks

**File:** `src/nativespeaker/api/services/restore.py:84-103`
**Also:** `src/nativespeaker/api/services/subscriptions.py:58-59,117-124`, `src/nativespeaker/api/crud/subscriptions.py:117-150`

**Issue:** The two writers acquire the same two resources — the `core.subscriptions` lifecycle-key
slot and the buyer's `core.access_grants` rows — in opposite orders.

`RestoreService.restore`:

```
88   insert_subscription(...)          # crud/subscriptions.py:149-150 -> session.add + flush
103  lock_grants_of(accounts)          # FOR UPDATE on core.access_grants
```

`SubscriptionsService.ingest`:

```
59   lock_grants(owner, evaluated_at)  # FOR UPDATE on core.access_grants
117  upsert_subscription(...)          # -> read_subscription (miss) -> session.add + flush
```

The insert at `restore.py:88` is flushed inside `_flush_or_lose`, which is what makes
"a row another writer committed first is a lost race" work — a second inserter of the same
`(provider, external_id)` blocks on `ix_subscriptions_provider_external_id` until this transaction
ends. That is a real wait edge held *before* the grant locks, which contradicts both this module's
own docstring ("the subscription row is never locked", `restore.py:2`) and SHARED-INVARIANTS'
fixed global lock order.

Deadlock, on an ordinary sequence — the app calls restore right after purchase while the store
delivers the first notification for the same subscription:

| | T1 = restore (user A) | T2 = webhook (attribution token resolves to A) |
|---|---|---|
| 1 | `insert_subscription(S)` flushes; holds the unique-index slot for S | |
| 2 | | `lock_grants(A)` — `FOR UPDATE` on A's grant rows |
| 3 | `lock_grants_of([A])` — blocks on T2 | |
| 4 | | `upsert_subscription(S)` → insert → blocks on T1's index slot |

Postgres's deadlock detector covers the transaction-id wait at step 4, so one side aborts with
`40P01`. That is an `OperationalError`, not an `IntegrityError`, so neither `_settle` nor
`is_unique_violation` sees it: it escapes as an unclassified 500. Reachable whenever a webhook
carries an attribution token that resolves (`services/subscriptions.py:47-48,55`) for a
subscription not yet in `core.subscriptions`, which is the first delivery for every purchase.

**Fix:** Move the creation arm below the grant locks. `accounts` does not depend on `stored`
(`current_owner` is `None` whenever `stored is None`), so the reorder is mechanical and preserves
insert-only semantics:

```python
        # One statement for every account this restore touches: a move also takes from the old owner.
        accounts = [destination] if current_owner is None else [current_owner, destination]
        marked_active = await self.subscriptions_db.lock_grants_of(accounts)

        if stored is None:
            # Adoption-with-creation, taken under the grant locks: the lifecycle-key slot is never
            # held ahead of them, so this path and `SubscriptionsService.ingest` agree on one order.
            stored, outcome = await self.subscriptions_db.insert_subscription(
                provider=proof.provider, external_id=proof.external_id, user_id=None,
                tier_id=proof.tier_id, status=proof.status, signed_at=None,
                evaluated_at=self.evaluated_at)
            await self._settle(outcome, proof)
        subscription_id = stored.id
        tier_id = stored.tier_id
```

Add a `tests/schema` case in the style of `test_grant_locks.py`: an adoption restore and a first
webhook for the same lifecycle pair, interleaved, must both complete without `40P01`.
