# Phase 37.3: Code Review Report

**Reviewed:** 2026-08-27T08:56:10Z
**Depth:** standard
**Files Reviewed:** 31
**Status:** issues_found

## Summary

The phase converted the auth module from result/outcome unions to a raised exception family. I
attacked the two things the phase staked itself on — byte-identical client responses, and
transactional correctness around raised rejections — and could not break either. I am reporting
that as a verified negative, not as a pass:

**Status-code / body equivalence (verified, no divergence found).** I enumerated every deleted
mapping against its replacement: `CLIENT_CLASS_FOR_RESULT` (4 entries), `_LOOKUP_REJECTIONS`
(3 entries), the two `Reject(...)` sites in `identity.py`, the two `_reject(AUTH_REQUIRED, ...)`
sites and the `PREAUTH_IDENTITY_NOT_ALLOWED` site in `dependencies.py`, and the five
`ChallengeRejection` values. All 15 land on the same `ErrorClass`, hence the same status and the
same one-field body. `error_response` is the sole body factory and still emits `{"code": ...}` only.
The deleted `AuthRejectionError` was a `ServiceError` whose `extra_headers()` returned `None`, so
dropping it costs no response header (in particular, the 401s never carried `WWW-Authenticate`
before and still do not). `ErrorClass.copy` was never rendered into a body.

**Transactional correctness (verified, no defect found).** The dangerous case is
`_insert_account` raising `IdentityAlreadyLinked` after `savepoint.rollback()`, followed by
`_complete`'s `except AuthRejected` arm writing the consume on the same session and committing. I
checked SQLAlchemy 2.0.46's `SessionTransaction._restore_snapshot`: a nested rollback expunges the
pending `User`/`ExternalIdentity`/`StorePurchaseToken` states to transient and expires only
`dirty_only` states, so the later `session.commit()` cannot resurrect the rolled-back inserts and
does not expire `challenge`. Pre-claim rejections raise past `get_db`, which rolls back before the
handler renders. Post-claim rejections consume and commit before the bare `raise`, and
`session.rollback()` on a session with no active transaction is a no-op, so a consumed challenge
stays consumed. `raise conflict` for an unmapped constraint name escapes `except AuthRejected` and
500s with the handle left claimed-but-unconsumed — which is fail-closed and byte-identical to the
old `classify_insert_conflict` behaviour.

**Handler coverage (verified).** `app.add_exception_handler(AuthRejected, ...)` covers every
subclass via Starlette's MRO walk; `AuthRejected` is outside the `ServiceError` tree so there is no
dispatch ambiguity; `Exception` is handled by `ServerErrorMiddleware` and does not shadow it.
`tenacity` can no longer surface `RetryError` or `RetryableLookupError` because
`retry_error_callback=_exhausted` converts unconditionally. `ruff`, `ty`, and the 788-test default
suite all pass.

What I did find is a ring of load-bearing invariants that the new design *states in comments* and
*does not enforce* — several of which the phase itself weakened by moving code around. Those are
the warnings below. The single highest-value one is WR-02: the refactor turned a fail-closed call
site into a fail-open one.

## Warnings

### WR-01: A failure inside the post-claim consume replaces the owed status with a 500

**Severity:** WARNING
**File:** `src/nativespeaker/api/routers/auth.py:137-144`, `src/nativespeaker/api/routers/auth.py:150-163`
**Issue:** `_consume_and_commit` runs *during* exception handling. If either
`challenge_store.consume()` or `session.commit()` raises (connection drop, serialization failure,
statement timeout — all realistic on the transaction that has just been through a savepoint
rollback), that exception replaces the in-flight `AuthRejected`. The client receives 500
`internal_error` instead of the 409/403/401/503 it was owed, and the security log line for the
original rejection is never written, because `auth_rejected_handler` never runs. The original
rejection survives only as `__context__` on an exception the `generic_error_handler` logs as
"Unhandled exception".
**Fix:** Guard the spend so it cannot displace the answer, and log the divergence:

```python
    except AuthRejected:
        try:
            await _consume_and_commit(session, context=context, challenge=challenge,
                                      challenge_store=challenge_store)
        except Exception:
            # The handle stays claimed, so it is still unusable; the client keeps the class it earned.
            logger.exception("challenge_consume_failed", challenge_row_id=str(challenge.id))
        raise
```

### WR-02: `verify_binding` is now a bare statement, which turns a fail-closed call site into a fail-open one

**Severity:** WARNING
**File:** `src/nativespeaker/api/routers/auth.py:102`
**Issue:** The old call site was `rejection = challenge_store.verify_binding(...)` followed by
`if rejection is not None: reject`. Any future breakage of the seam — making the method `async`,
or a duck-typed store returning a rejection instead of raising — produced a *rejection*, because a
coroutine object or a non-`None` return is not `None`. The new call site is a bare statement whose
only effect is a side effect. If `verify_binding` ever becomes `async`, `challenge_store` is
swapped for a store that returns rather than raises, or the raise is lost in an edit, the identity
binding check silently becomes a no-op and **any authenticated caller can spend any challenge
handle they can guess or observe**. `ruff` is configured with `select = ["E","W","F","I","UP"]`
(pyproject.toml:69) — neither `ASYNC` nor `RUF` is enabled, so an un-awaited coroutine statement
here is not caught by lint, and `ty` does not flag it either. `_FakeChallengeStore.verify_binding`
in `tests/unit/test_create_user_precedence.py:76-77` is a duck-typed store already, which is
exactly the shape that could drift.
**Fix:** Make the check structurally impossible to no-op — either keep a consumed return value, or
assert the seam is synchronous at the call site:

```python
    # Not a bare statement: a seam that stops raising must not become a silent admission.
    outcome = challenge_store.verify_binding(challenge, identity)
    if outcome is not None:
        raise ChallengeIdentityMismatch()
```

Alternatively, enable ruff's `ASYNC`/`RUF` rule groups so an un-awaited coroutine statement fails CI.

### WR-03: The handler splats `log_fields()` into a call that already binds `route`

**Severity:** WARNING
**File:** `src/nativespeaker/api/app/errors.py:55-57`
**Issue:** `logger.warning(event, route=..., **exc.log_fields())` raises
`TypeError: got multiple values for keyword argument 'route'` if any family member ever returns a
`route` key. The failure happens *inside the exception handler*, so it surfaces as a 500 in place
of the owed status — the exact failure mode the `log_fields()` docstring was written to prevent, on
a different axis. Nothing in `test_rejection_vocabulary.py` forbids the key.
**Fix:** Build the payload defensively, and add a case to the vocabulary test:

```python
    fields = {"route": getattr(request.scope.get("route"), "path", None), **exc.log_fields()}
    logger.warning(camel_to_snake(type(exc).__name__), **fields)
```

and in `test_rejection_vocabulary.py`, assert `"route" not in cls().log_fields()` for every
constructible family member.

### WR-04: "`log_fields()` is the only channel into this line" is false

**Severity:** WARNING
**File:** `src/nativespeaker/api/app/errors.py:50-52` (claim) vs `src/nativespeaker/api/logs.py:61-66` (reality)
**Issue:** The handler comment states that `log_fields()` is "the only channel into this line --
which is how the challenge handle stays out of it", and that "`route` is the matched route's path
template, never the caller's raw path". Both are wrong. `RequestLoggingMiddleware.dispatch` calls
`structlog.contextvars.bind_contextvars(request_id=..., method=..., path=request.url.path)`, and
structlog's `merge_contextvars` processor merges those into *every* event emitted during the
request — including this one. So each rejection line already carries the caller's raw path, and a
second, uncontrolled channel into the line exists. No handle leaks today (the handle travels in the
request body, never the path), but the design argument that makes the handle safe is not the one
the code actually implements, so a future route that puts a capability in a path segment would leak
it without anyone editing this file.
**Fix:** Correct the comment to describe the real contract ("`log_fields()` is the only channel
this handler controls; `request_id`, `method` and the raw `path` are bound by
`RequestLoggingMiddleware` and appear on every line"), and state the actual handle-safety
invariant — capability handles travel in bodies only, never in a path or query string.

### WR-05: The scalar-only `log_fields()` invariant is tested for 8 of 13 raisable classes

**Severity:** WARNING
**File:** `src/nativespeaker/api/auth/exceptions.py:33-42`; `tests/unit/test_rejection_vocabulary.py:131-138`
**Issue:** The base docstring states the rule as a hard requirement and spells out the exact
consequence of breaking it — a rollback expires an ORM instance, the handler's attribute read
attempts I/O outside a greenlet, the handler raises, and the client gets 500 where 409 was owed.
`test_every_logged_value_is_a_plain_string` is parametrized over only the three
`ProviderLookupError` arms; `test_no_arm_can_carry_anything_into_its_log_line` covers the five
challenge arms. `InvalidExternalJwt`, `AccountUnavailable`, `PreAuthIdentityNotAllowed`,
`IdentityUnresolvable`, `IdentityAlreadyLinked` and `ProviderAccountAlreadyLinked` are unguarded.
All are clean today; nothing stops the next arm from carrying an `ExternalIdentity` row.
**Fix:** Enforce the invariant over the whole walked family, not a hand-picked subset:

```python
_CONSTRUCTIBLE = [InvalidExternalJwt(bounded_reason=None), PreAuthIdentityNotAllowed(),
                  IdentityUnresolvable(), IdentityAlreadyLinked(), ProviderAccountAlreadyLinked(),
                  AccountUnavailable(cause="blocked_user"), *(arm() for arm in CHALLENGE_ARMS),
                  UserNotFound(stage="s"), Unavailable(stage="s"), NotLinked(stage="s")]

@pytest.mark.parametrize("rejection", _CONSTRUCTIBLE, ids=lambda r: type(r).__name__)
def test_no_arm_carries_a_non_scalar_into_its_log_line(rejection):
    assert all(value is None or isinstance(value, (str, int, UUID))
               for value in rejection.log_fields().values())
```

### WR-06: Undocumented dependency on `expire_on_commit=False` across the post-claim boundary

**Severity:** WARNING
**File:** `src/nativespeaker/api/routers/auth.py:119`, then `src/nativespeaker/api/auth/creation.py:56,61` and `src/nativespeaker/api/routers/auth.py:156,161`
**Issue:** `_complete` commits the claim at line 119, then four later reads of the `challenge` ORM
instance (`challenge.challenge_id` and `challenge.id`, in both `create_account` and
`_consume_and_commit`) happen on a post-commit instance. These are safe only because
`app/lifespan.py:45-46` builds the session factory with `expire_on_commit=False`. Under
SQLAlchemy's default (`True`), the commit expires every instance, the next attribute read triggers
a lazy refresh, and in this async context that is `MissingGreenlet` — a 500, with the challenge
claimed and unconsumed. Neither `routers/auth.py` nor `creation.py` names this dependency, and no
test in the default suite can catch a regression: `test_create_user_precedence.py` uses
`_StubSession`, whose `commit()` is a counter, and the schema tests build their own factory that
already sets `expire_on_commit=False` (`tests/schema/test_create_atomicity.py:86-87`).
**Fix:** Name the invariant where it is relied on, at `routers/auth.py:119`:

```python
    # Deliberate commit: an uncommitted claim across the provider call would let a second attempt
    # win the challenge. Every later read of `challenge` depends on the lifespan's
    # `expire_on_commit=False`; with the SQLAlchemy default this commit would expire the row and
    # the next attribute read would be I/O outside a greenlet.
    await session.commit()
```

and add an assertion in `app/lifespan.py` (or a unit test over the factory) that the session
factory is configured with `expire_on_commit=False`.

### WR-07: The consume-and-commit choreography is duplicated in two modules

**Severity:** WARNING
**File:** `src/nativespeaker/api/auth/creation.py:55-63` and `src/nativespeaker/api/routers/auth.py:150-163`
**Issue:** Two near-identical blocks now spend the handle: the same `challenge_store.consume(...)`
call with the same three keyword arguments, the same
`logger.error("challenge_consume_did_not_match", challenge_row_id=str(challenge.id))` on a `False`
return, and the same `await session.commit()`. Before this phase there was one. This is the
security-critical single-use step, and the two copies can drift — a fix to one (for example WR-01's
guard, or promoting the `False` return from a log line to a raise) will not reach the other. The
router comment at line 138 asserts "every raising arm past the claim leaves the consume here",
which is already inaccurate: the unmapped-constraint `raise conflict` at `creation.py:115` escapes
`except AuthRejected` and reaches neither copy.
**Fix:** Extract one spend function (e.g. `auth/challenges.py::spend`) taking
`(session, store, challenge, context)` and call it from both sites; correct the router comment to
say "every *rejection* arm past the claim", since the unmapped-constraint tripwire deliberately
does not consume.

### WR-08: `_flush_account` commits a savepoint that `_insert_account` owns and rolls back

**Severity:** WARNING
**File:** `src/nativespeaker/api/auth/creation.py:94-101`, `src/nativespeaker/api/auth/creation.py:118-151`
**Issue:** `_insert_account` opens the savepoint and rolls it back; `_flush_account` — a different
function, which receives the handle as an unannotated `savepoint` parameter — commits it at line
150. One resource, two owners, and the `except IntegrityError` clause only covers one of the two
failure shapes: if `_flush_account` raises anything that is not an `IntegrityError` (a `DataError`
from an over-long `provider_uid`, a `ProgrammingError`, or a plain `TypeError` from a model change),
the savepoint is neither committed nor rolled back and the exception escapes as a 500. It is
recovered only incidentally, because `get_db` rolls the whole outer transaction back. The
unannotated parameter also means neither `ty` nor a reader can tell what `savepoint` is.
**Fix:** Keep savepoint lifetime in one function using the context-manager form, so no branch can
leave it open:

```python
async def _insert_account(session, *, evaluated_at, identity, provider, provider_uid, email) -> UUID:
    try:
        async with session.begin_nested():
            return await _flush_account(session, evaluated_at=evaluated_at, identity=identity,
                                        provider=provider, provider_uid=provider_uid, email=email)
    except IntegrityError as conflict:
        ...
```

and drop the `savepoint` parameter from `_flush_account` entirely.

### WR-09: Unbounded caller-controlled `operation` string is written into the structured log

**Severity:** WARNING
**File:** `src/nativespeaker/api/models/auth.py:29-30`, `src/nativespeaker/api/routers/auth.py:47-52`
**Issue:** `ChallengeRequest.operation` is a bare `str` with no `max_length`. On the reject path
the router logs it verbatim: `logger.warning("auth_challenge_operation_not_issuable", ...,
operation=body.operation)`. The comment at line 48 claims the value is "caller-supplied and
bounded" — it is not bounded by anything in this codebase. Any authenticated caller can push an
arbitrarily large string into the security log with one request (log volume, storage cost, and
downstream log-pipeline pressure). Envoy's per-IP/per-user rate limits and any gateway body-size
limit are the only mitigations, and neither is expressed here. Pre-existing, but it sits in a
reviewed file behind a comment that asserts the opposite.
**Fix:** Bound the field so the claim becomes true, and keep the 400 semantics:

```python
class ChallengeRequest(BaseModel):
    """The issuance body. `operation` is a plain `str`, never a Literal: an unissuable value is the
    handler's 400. Bounded so the rejected value is safe to log verbatim."""
    operation: str = PydanticField(..., max_length=64)
```

`CreateUserRequest.challenge_id` (line 42) has the same unbounded shape; it is never logged, so the
exposure is smaller, but a `max_length` there costs nothing since a valid handle is 22 characters.

### WR-12: Constraint names inlined as magic strings, pinned by a brittle AST string scan

**Severity:** WARNING

### WR-13: The two intermediate bases answer 500, and the vocabulary test deliberately skips them

**Severity:** WARNING
**File:** `src/nativespeaker/api/auth/exceptions.py:126-147`; `tests/unit/test_rejection_vocabulary.py:86-88`
**Issue:** `ProviderLookupError` declares no `error_class`, so it inherits `AuthRejected`'s
fail-closed `INTERNAL_ERROR` and would answer 500. "Never raised itself" is asserted only in a
docstring. `_undeclared()` explicitly `continue`s on any class with subclasses, so the guardrail
that exists for leaves does not exist for the two group bases. A future arm that raises
`ProviderLookupError(stage=...)` directly — a plausible edit, since it has a usable `__init__` and
the leaves do not add anything — answers 500 instead of the 401/503/403 the group is for, and the
vocabulary test passes.
**Fix:** Make "never raised" structural rather than documentary — either give the group bases
`__init_subclass__`-free abstractness (raise `TypeError` from `ProviderLookupError.__init__` when
`type(self) is ProviderLookupError`), or add a case asserting the intermediate bases are never
instantiated:

```python
def test_the_group_bases_cannot_be_raised(self):
    for base in (ProviderLookupError, ChallengeRejected):
        assert base.__subclasses__(), f"{base.__name__} is documented as never raised"
```

combined with an explicit assertion that `ProviderLookupError.error_class is INTERNAL_ERROR` is a
tripwire and not an answer any caller relies on.

### IN-07: The same broken identity→user link earns 403 in one module and 500 in another

**Severity:** INFO
**File:** `src/nativespeaker/api/auth/identity.py:32-34` vs `src/nativespeaker/api/auth/creation.py:81-83`
**Issue:** `resolve_identity` treats an identity row whose user does not resolve as
`IdentityUnresolvable` (500, "unresolvable state, read fail-closed"). `_reject_existing_identity`
treats the identical condition (`user is None`) as `AccountUnavailable(cause="blocked_user")` (403),
folding a broken invariant in with a legitimately deactivated account so it never surfaces as a
defect. Behaviour is unchanged from before the phase, but the conversion to one exception family
puts the two readings side by side for the first time.
**Fix:** Split the condition in `_reject_existing_identity` so the two are told apart:

```python
    user = (await session.exec(select(User).where(col(User.id) == existing.user_id))).first()
    if user is None:
        raise IdentityUnresolvable()
    if user.active is not True:
        raise AccountUnavailable(cause="blocked_user")
```

Note this changes a client-visible status (403 → 500) for a state that a foreign key makes
unreachable, so it needs a decision rather than a silent edit.
