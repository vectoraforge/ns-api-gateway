**The completion flow's rejection precedence now raises instead of returning, in exactly the order it
always fired; five distinct log events collapse to one 409 declared once on a shared base that no
subclass may override; the pre-claim rollback belongs to `get_db` alone; and the 44-member outcome
enum that started this phase is gone.**

## The verdict on the preserved uncommitted work

**Intended RED. Committed as written, unchanged, as `1c14013`.**

The dead session left two files modified — `tests/unit/test_create_user_body.py` and
`tests/unit/test_create_user_precedence.py` — each with the same edit: the `get_db` dependency
override changed from `lambda: session` to an async generator with `try` / `yield` / `commit` /
`except` / `rollback` / `raise`. That left `2 failed, 50 passed` across the two files, both failures
in `test_create_user_body.py`.

**The evidence that this is the RED and not breakage:**

1. **The double is faithful.** It matches `app/dependencies.py::get_db` (lines 24–31) statement for
   statement. Nothing about it is approximate, and it carries a comment saying what it mirrors.
2. **The failure is produced by exactly the code Task 2 is defined to change.** At `4b6568b` the
   challenge-not-found arm still *returned* a `Response` via `_challenge_rejected`. A normal return
   means the generator reaches `await session.commit()` — and `_UnlinkedSession.commit` in that file
   is a deliberate tripwire: `raise AssertionError("no path in this module may commit")`. So the two
   cases that reach the completion handler 500 where 409 is owed. No other case in either file
   reaches that arm, which is exactly why only two failed.
3. **The GREEN half fixes them without touching them.** Once the arm raises, control takes the
   generator's `except` branch: one rollback, no commit, the exception propagates, the handler answers
   409. Both cases pass unedited, and `session.rollbacks == 1` still means what it always meant.
4. **The plan asked for precisely this edit,** naming both override sites and forbidding the
   assertions from being weakened to `== 0`.

**One honest correction to the plan's prediction.** The plan expected the RED to present as
`rollbacks == 0` — "once the explicit rollback moves into `get_db`, those assertions fail against a
double that never rolls back". Because the prior executor made the double faithful *before* moving
the rollback, it presented instead as the commit tripwire firing. The diagnosis and the fix are
identical: the double must be faithful, the arm must raise, and neither assertion may be relaxed.
Nothing was discarded and nothing was committed unexamined.

## Decisions Made

### `_RejectionLog` was cleaned up in Task 2, not left as a stale reference

The precedence suite's recorder carried `_EVENTS = frozenset({"create_user_challenge_rejected"})` —
the router event this task retires — and a `results` property that branched on which logger a record
came from. With that set emptied, a rejection logged at the router would have been silently dropped
from `results`, quietly weakening `test_every_rejection_is_recorded_exactly_once`.

Both loggers now feed one list and every entry is a result. The router spy stays, and its purpose
inverted from "span the migration" to "prove the migration finished": a rejection re-logged at the
router now appears as a second entry and **fails** the exactly-once cases rather than disappearing.
This is a log edit under the plan's own rule for that file, and it strengthens rather than relaxes.

### The enum members became plain strings, not new assertions

`AuthEventResult` was a `StrEnum`, so `AuthEventResult.challenge_not_found == "challenge_not_found"`
was already true — which is exactly why the precedence suite's asserted strings survived Task 2 with
no edit at all, as the plan predicted. Task 3's substitution is therefore mechanical: fifteen
references, each replaced by the literal it already equalled. No assertion changed meaning, and no
status or body literal was touched.

### The two stale REQUIREMENTS.md references outside FOUND-08

Two passages in the file this plan amends still described code this phase deleted:

- **FOUND-05's compensating-control paragraph** said the rejection log "lives in
  `app/dependencies.py::_reject`" and "still emits the `auth_rejected` structured security-log event".
  Both were deleted by plan 02. This paragraph is the compensating control for a **withdrawn**
  requirement carrying a **flagged conflict** — leaving it false would mislead precisely the reader
  the flag exists for.
- **SCHEMA-06's consequence note** said `AuthEventResult` "survives in Python as a plain 44-member
  `StrEnum` backed by no database type". This plan deleted it.

Both were corrected with short dated notes in the established style rather than rewrites, and neither
changes a treatment, a checkbox or a flagged conflict. Recorded as a deviation below.
