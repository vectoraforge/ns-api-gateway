## Decisions Made

### `InvalidExternalJwt` is one class, not two

The plan left this to the executor's discretion via plan 01. One class: today the absent-token and
failed-verify arms produce the same 401 and the same body, and `bounded_reason` is the only thing
that separates them. Splitting them would encode that distinction in the class name — which D-02
makes the log event name — without either half meaning anything different to a caller. If a future
phase gives the two arms different client-visible outcomes, that is the moment to split.

`log_fields()` returns `{"bounded_reason": None if ... else str(...)}`, stringified exactly as the
deleted `_reject` stringified it, so the field's type in the log pipeline is unchanged (T-37.3-11).

### The event name diverges from the error code, deliberately

`camel_to_snake("PreAuthIdentityNotAllowed")` is `pre_auth_identity_not_allowed`, while the
client-visible `ErrorCode` remains `preauth_identity_not_allowed`. Both spellings are now live and
they are not the same string.

This is not a defect and was not "fixed" by renaming the class, for three reasons: the plan's
acceptance criteria pin the class name literally; `PreAuthIdentity` in `auth/context.py` is the
house spelling of the concept, so the class is consistent with the codebase it sits in; and plan 01
established that nothing downstream keys on event names. **The client-visible code did not change** —
the zero-client-visible-change guarantee holds. A comment in `test_rejection_vocabulary.py` records
the divergence so a later reader does not "correct" one side into disagreement with the other.

### `Reject.actor_issuer` / `actor_subject` were already dead

Two cases in the resolution suite asserted that a rejection carried the verified actor. Tracing the
value: `dependencies.py` called `_reject(decision.error_class, decision.result, None, route)` — the
actor was never read, and the log line it fed had no actor field. So the data was already
zero-consumer before this plan touched it, and D-13 removes it.

Rather than deleting the two cases, both were retargeted to assert the property that now holds and
is worth holding: **no rejection carries actor material at all**, so no issuer or subject can reach
a log line. That is T-37.3-11's mitigation stated positively. Recorded here because it is the one
place this plan changed what a case means rather than how it says it.

## Issues Encountered

- **`Bearer not.a.jwt` is a *verification* failure, not a wire failure.** It is well-formed on the
  wire — one Bearer credential, two space-separated parts — so `extract_bearer` passes it through
  and the verifier rejects it as `bad_signature`, not `malformed`. The failed-verify case now says
  so in a comment, because "not.a.jwt" reads like a malformed token and the next person to touch
  that parametrize will assume the same thing.
- **`camel_to_snake` splits `PreAuth`**, which is correct behaviour for a two-word prefix and is the
  source of the event-name divergence documented above. Worth knowing for plans 03 and 04: any class
  name whose concept is spelled as one word in `ErrorCode` but two words in Python will diverge the
  same way.
