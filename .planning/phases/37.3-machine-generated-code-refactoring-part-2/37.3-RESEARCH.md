## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01: New `src/nativespeaker/api/auth/exceptions.py`: base `AuthRejected(Exception)` with class attribute `error_class: ErrorClass`; one subclass per client-visible outcome** (e.g. `IdentityAlreadyLinked` → `IDENTITY_ALREADY_LINKED`; `AccountUnavailable` → `ACCOUNT_UNAVAILABLE` covering both the blocked and historical arms — their indistinguishability to clients is preserved). CRUD/auth code raises; only the handler reads `error_class`. `AuthRejected` is a plain `Exception`, not a `ServiceError` — it gets its own `add_exception_handler` entry.

- **D-02: The handler derives the log event name from the exception class name, snake_cased.** One generic handler: `logger.warning(camel_to_snake(type(exc).__name__), route=..., ...)`, then `return error_response(exc.error_class)`. This supersedes the directive's original `result=type(exc).__name__` wording — the developer chose class-name-as-event over a shared `auth_rejected` event with a `result` field. Consequences: there is no single greppable rejection event anymore (accepted knowingly); the `auth_rejected`, `create_user_challenge_rejected` and `create_user_transaction_rejected` events are replaced by per-class events; `route` (from the handler's `Request`) and `bounded_reason` (off the exception, when present) survive as fields. Tests update their asserted event names — a vocabulary change only.

- **D-03: The return-value plumbing is deleted:** `CLIENT_CLASS_FOR_RESULT`, `_LOOKUP_REJECTIONS`, the `Admit`/`Reject` dataclasses and the `AdmissionDecision` union, the `ChallengeRejection`→`AuthEventResult` conversion, `classify_insert_conflict`, `_conflicting_constraint_name` and the constraint-name constants in `creation.py`. The `IntegrityError` arm rolls back the savepoint and raises `IdentityAlreadyLinked` — with one check the planner must keep: today an *unmapped* constraint name re-raises the original error (a 500 tripwire, `creation.py:93`). Preserve that fail-loudly property rather than classifying every IntegrityError as a 409.

- **D-04: CRITICAL — rejections after the provider read still consume the challenge and COMMIT.** Raising must not skip `_consuming_rejection`'s semantics: `_complete` catches locally (`AuthRejected` from `create_account`, `ProviderLookupError` from the lookup), consumes the challenge, commits, then re-raises for the handler to answer. These exceptions never escape the route uncaught-by-`_complete`. — **Reversibility:** reversible, but a miss here is a live bug: an escaped exception hits `get_db`'s rollback and un-consumes a challenge the client already spent.

- **D-05: Preserved exactly:** the single savepoint around the three inserts, rollback-before-anything in the conflict arm, the pre-check via `resolve_existing_identity`, and the blocked/historical indistinguishability to clients.

- **D-06: `resolve_identity` raises `AuthRejected` subclasses directly; `_reject()` and `AuthRejectionError` both die.** The handler is the one logging site — `route` comes from the `Request` it receives. No thin re-logging catch survives in `dependencies.py`.

## Summary

This is a pure structural refactor with **zero client-visible change**, fully specified by CONTEXT.md's D-01…D-19. There is no library selection to make, no new dependency to install, and no external API to learn. The entire research value therefore lies in **verifying the mechanisms the decisions assume** and **finding the places the decisions do not yet cover**. I read all ten source files this phase reshapes, ran all three test suites to establish a green baseline, and empirically probed the four framework behaviors the design depends on.

**Everything D-01…D-04 assumes about the framework is true.** Starlette's handler dispatch walks `type(exc).__mro__`, so one `add_exception_handler(AuthRejected, ...)` really does cover every subclass [VERIFIED: probe]. `request.scope["route"].path` really is available inside the handler — FastAPI sets it in `APIRoute.matches`, and Starlette builds the handler's `Request` from that same mutated scope [VERIFIED: fastapi/routing.py:800-804 + probe]. Most importantly, D-04's choreography is safe: after `session.commit()` the session holds no transaction, so `get_db`'s rollback-on-exception does **not** un-consume the challenge [VERIFIED: probe against PostgreSQL 17.11]. And tenacity's `retry_error_callback` may raise, which expresses D-10's "exhausted retries raise `Unavailable`" in the same `AsyncRetrying` frame the code already uses [VERIFIED: probe, tenacity 9.1.4].

**Three findings are not covered by the decisions and need planner action.** First, `tests/unit/test_auth_package_shape.py` enforces a one-way complexity ratchet whose class ceiling this phase provably cannot meet: the auth package holds 19 classes today, the minimum viable exception design lands it at ~32, and the test asserts strictly-below `BASELINE` of 28 on every axis. D-18 authorizes updating the `CURRENT` literal but not relaxing the `BASELINE` assertion — this is a decision, not a mechanical edit. Second, two **schema-marked** tests (`test_create_atomicity.py`, `test_create_race.py`) drive `create_account` directly and assert its `AuthEventResult` return value; they are deselected by the default `addopts`, so a plan that runs only the default suite will not see them break. Third, CR-02's failure mode — `MissingGreenlet` from reading an expired ORM attribute after a rollback — **recurs structurally** under D-15 if any exception carries an `AuthChallenge` instance the handler later reads.

**Primary recommendation:** Execute the four plans strictly in D-17 order as four sequential waves (no parallelism is available — each plan's tests depend on the prior plan's handler). Gate every plan on the full suite run with all three markers (`-m "not e2e and not schema"`, `-m e2e`, `-m schema`), not the default `addopts` alone. Make the package-shape ceiling a `checkpoint:human-verify` in plan 1, and adopt a hard rule that **exceptions carry only plain scalars, never ORM instances**.

### Pattern 1: Class-attribute error metadata with a data-driven handler

**What:** The exception class carries its client-visible metadata as a class attribute; one handler reads it. This is exactly the shape `ServiceError` already uses.

**When to use:** Every `AuthRejected` subclass.

```python
# Source: the in-repo precedent, src/nativespeaker/api/errors.py:229-233 (read this session)
# One `error_class` per subclass, so a status and a code can never be named in disagreement.
class ServiceError(Exception):
    """Base exception for service layer errors."""
    error_class: ErrorClass = INTERNAL_ERROR
    log_level: int | None = None
```

D-01's family copies this, but is **not** a `ServiceError` subclass, so it must never inherit `INTERNAL_ERROR` by accident:

```python
# src/nativespeaker/api/auth/exceptions.py  (new)
class AuthRejected(Exception):
    """An admission or completion rejection. The handler is the only reader of `error_class`."""
    error_class: ErrorClass = INTERNAL_ERROR   # fail-closed default; every subclass overrides

class IdentityAlreadyLinked(AuthRejected):
    error_class = IDENTITY_ALREADY_LINKED

class AccountUnavailable(AuthRejected):
    """Both the blocked-user and historical-identity arms. Indistinguishable to clients, on purpose."""
    error_class = ACCOUNT_UNAVAILABLE

class ChallengeRejected(AuthRejected):
    """The shared 409 base: the anti-oracle property lives here, structurally (D-14)."""
    error_class = CHALLENGE_REQUIRED

class ChallengeNotFound(ChallengeRejected): pass
class ChallengeExpired(ChallengeRejected): pass
class ChallengeConsumed(ChallengeRejected): pass
class ChallengeIdentityMismatch(ChallengeRejected): pass
class ChallengeOperationMismatch(ChallengeRejected): pass
```

Because the five 409 subclasses set no `error_class` of their own, no future edit can make one of them answer a different status without deliberately overriding the base — which is precisely what "the anti-oracle property holds structurally, in the shared base" (D-14) means.

### Pattern 2: One registration covers the whole hierarchy

Starlette resolves handlers by walking the raised exception's MRO:

```python
# Source: .venv/lib/python3.14/site-packages/starlette/_exception_handler.py (read this session)
def _lookup_exception_handler(exc_handlers: ExceptionHandlers, exc: Exception) -> ExceptionHandler | None:
    for cls in type(exc).__mro__:
        if cls in exc_handlers:
            return exc_handlers[cls]
    return None
```

So `app.add_exception_handler(AuthRejected, auth_rejected_handler)` is the only registration needed [VERIFIED: probe — a raised `IdentityAlreadyLinked` reached a handler registered for `AuthRejected` and produced the subclass's own `error_class`].

Registration **order does not matter**, contrary to what the CONTEXT.md integration note implies ("ordered so `AuthRejected` never falls through to the generic 500 handler"). Two independent mechanisms guarantee it: dispatch is by MRO specificity, not insertion order; and Starlette routes the `Exception` key to `ServerErrorMiddleware` rather than into the same lookup table:

```python
# Source: starlette/applications.py build_middleware_stack (read this session)
for key, value in self.exception_handlers.items():
    if key in (500, Exception):
        error_handler = value          # → ServerErrorMiddleware, outermost
    else:
        exception_handlers[key] = value  # → ExceptionMiddleware's MRO table
```

`AuthRejected` and `ServiceError` are unrelated types, so no ambiguity exists between them either.

### Pattern 3: The consuming-rejection choreography (D-04)

```python
# routers/auth.py::_complete — the post-claim region
try:
    identity_facts = await lookup_with_retry(adapter, identity.issuer, identity.subject)
    user_id = await create_account(session, context=context, identity=identity,
                                   challenge=challenge, provider=identity_facts.provider,
                                   provider_uid=identity_facts.provider_uid,
                                   email=identity_facts.email,
                                   challenge_store=challenge_store)
except (ProviderLookupError, AuthRejected):
    # Consume + commit BEFORE re-raising: the client spent this handle and must not get it back.
    await _consume_and_commit(session, context=context, challenge=challenge,
                              challenge_store=challenge_store)
    raise
return JSONResponse(content=CompletionResponse(identity_provider=identity_facts.provider)
                    .model_dump(mode="json"))
```

**Why the bare `raise` is safe:** after `session.commit()` inside `_consume_and_commit`, the session holds no transaction, so `get_db`'s `except Exception: await session.rollback(); raise` cannot undo the consume [VERIFIED: probe against PostgreSQL 17.11 — `in_transaction after commit: False`, and the inserted row survived a subsequent `rollback()`].

**Note `create_account` raises `AuthRejected` (not `ProviderLookupError`), and `create_account` commits internally** (`creation.py:74`). When it raises, it must have consumed and committed *itself* or left the consume to this arm — the planner must pick one and pin it with a test, because double-consume returns `False` and trips `challenge_consume_did_not_match`. Recommended: keep the consume inside `create_account` for the success path (as today), and have `create_account`'s raising arms consume before raising, so `_complete`'s except arm handles only `ProviderLookupError`. That preserves today's structure most closely — today `create_account` consumes on "success and rejection alike" (`creation.py:65`).

### Anti-Patterns to Avoid

- **Carrying an ORM instance on an exception.** See Pitfall 1. Carry `str(challenge.id)`, never `challenge`.
- **Letting `RetryError` escape.** See Pitfall 2. `tests/unit/test_firebase_retry.py::test_no_outcome_lets_a_retry_error_escape` exists precisely because this was already considered once [VERIFIED: tests/unit/test_firebase_retry.py:94].
- **Classifying every `IntegrityError` as a 409.** D-03 is explicit; `creation.py:93` is a deliberate 500 tripwire. See Pitfall 3.
- **Logging the challenge handle.** `challenges.py:1` states the module holds no logger so none is logged. The new handler emits log lines on the challenge path — it must log `route` and the exception class name, never `challenge_id`.
- **Re-logging in `dependencies.py`.** D-06: "No thin re-logging catch survives." The handler is the one logging site; a second catch would double-count rejections in the log pipeline.

|---------|-------------|-------------|-----|

## Common Pitfalls

### Pitfall 1: An exception carrying an ORM instance → `MissingGreenlet` in the handler (CR-02's failure mode, recurring)

**What goes wrong:** An `AuthRejected` subclass carries the `AuthChallenge` row so the handler can log a correlation id. Under D-15, the exception escapes to the handler *through* `get_db`, which calls `session.rollback()` on the way. Rollback expires every instance in the session. The handler then reads `exc.challenge.id`, triggering a lazy refresh — I/O attempted outside a greenlet context.

**Why it happens:** SQLAlchemy's async session expires ORM instances on rollback; attribute access then needs I/O that async SQLAlchemy cannot perform outside `greenlet_spawn`.

**Verified, not assumed** [VERIFIED: probe against PostgreSQL 17.11, this session]:

```
before rollback: label = hello
after rollback RAISED: MissingGreenlet greenlet_spawn has not been called; can't call await_only() here.
```

This is the *same* failure 37-REVIEW.md recorded as CR-02 ("`_prepare` reads an expired ORM attribute after `session.rollback()` — ... raises `MissingGreenlet`", 37-REVIEW.md:212-226). CR-02's original site is gone — `routers/auth.py` has no `_prepare` and no audit writer today — so CR-02 itself is **not live**. But its failure *mode* becomes newly reachable in this phase, at a new site.

**Consequence if missed:** the handler itself raises, so the request falls through to `ServerErrorMiddleware` and the client gets **500 `internal_error` instead of 409 `challenge_required`** — a client-visible regression in a phase whose whole contract is zero client-visible change.

**How to avoid:** a hard rule — **`AuthRejected` and `ProviderLookupError` instances carry only plain scalars** (`str`, `UUID`, `BoundedReason`, `None`). Snapshot at raise time: `raise ChallengeExpired(challenge_row_id=str(challenge.id))`. Never `raise ChallengeExpired(challenge=challenge)`.

**Warning signs:** any exception `__init__` whose parameter is an ORM model; any handler that reads a dotted attribute off the exception.

### Pitfall 2: `RetryError` escaping as a 500 after the retry predicate flips

**What goes wrong:** D-10 swaps `retry_if_result(_is_retryable)` for `retry_if_exception_type(RetryableLookupError)`. With tenacity's defaults, exhausting the budget raises `RetryError` — not the `Unavailable` the contract promises. `RetryError` matches no registered handler, so it becomes 500 `internal_error` where the client is owed **503 `verification_temporarily_unavailable`**.

**Why it happens:** the current code is shielded by `retry_error_callback=lambda retry_state: retry_state.outcome.result()` (`firebase.py:153`), which *returns* the last result. When the adapter raises instead of returning, `retry_state.outcome.result()` **re-raises** the last exception rather than returning it — so even keeping the existing callback unchanged silently changes behavior.

**Verified** [VERIFIED: probe, tenacity 9.1.4] — three attempts in every case:

| Configuration | Outcome |
|---|---|
| defaults | raises `RetryError` ← the trap |
| `reraise=True` | raises the last `RetryableLookupError` — still not `Unavailable` |
| `retry_error_callback` that raises | raises `Unavailable` ← expresses D-10 directly |
| a non-retryable exception (`UserNotFound`) | propagates after **1** attempt ← confirms "never spend retry budget" |

**How to avoid:**

```python
def _exhausted(retry_state) -> NoReturn:
    """Three retryable attempts spent; the client is owed the unavailable pair, never a 500."""
    raise Unavailable(stage="provider_lookup") from retry_state.outcome.exception()

retrying = AsyncRetrying(stop=stop_after_attempt(FIREBASE_LOOKUP_ATTEMPTS),
                         retry=retry_if_exception_type(RetryableLookupError),
                         retry_error_callback=_exhausted)
```

**Warning signs:** any test asserting a 503 that starts reporting 500; `test_firebase_retry.py::test_no_outcome_lets_a_retry_error_escape` failing.

### Pitfall 3: Collapsing the unmapped-constraint tripwire into a 409

**What goes wrong:** the `except IntegrityError` arm becomes `raise IdentityAlreadyLinked(...)` unconditionally, so a *new* constraint violation — a bug — is reported to the client as a benign 409 and never surfaces.

**Why it happens:** the classification the tripwire lives inside is being deleted, and the tripwire is one line of it:


D-03 names this explicitly: "today an *unmapped* constraint name re-raises the original error (a 500 tripwire, `creation.py:93`). Preserve that fail-loudly property."

### 3. `resolve_identity` after conversion (D-06)

```python

async def resolve_identity(session: AsyncSession, *, issuer: str, subject: str,
                           allow_preauth: bool) -> LinkedIdentity | PreAuthIdentity:

    statement = (select(ExternalIdentity, User)
                 .join(User, col(ExternalIdentity.user_id) == col(User.id), isouter=True)
                 .where(col(ExternalIdentity.issuer) == issuer,
                        col(ExternalIdentity.subject) == subject))
    row = (await session.exec(statement)).first()

        raise PreAuthIdentityNotAllowed(issuer=issuer, subject=subject)
```

### 5. `camel_to_snake` (discretion item)

```python
# The two-substitution form: handles acronym boundaries, which a single \B([A-Z]) rule does not.
_FIRST = re.compile(r"(.)([A-Z][a-z]+)")
_REST = re.compile(r"([a-z0-9])([A-Z])")

def camel_to_snake(name: str) -> str:
    """`ChallengeNotFound` -> `challenge_not_found`; `InvalidExternalJwt` -> `invalid_external_jwt`."""
    return _REST.sub(r"\1_\2", _FIRST.sub(r"\1_\2", name)).lower()
```

**Where it lives:** `app/errors.py`, beside its only caller. Putting it in `auth/` would add a function to the package-shape budget (see below) for no benefit, since the handler is the only consumer.

**Pin it with a test** enumerating every subclass: `{camel_to_snake(c.__name__) for c in all_subclasses(AuthRejected)}` compared against a hand-written literal set.
