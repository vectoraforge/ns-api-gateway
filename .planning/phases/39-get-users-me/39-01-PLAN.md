## Assumptions — probe edges (all 6 unresolved, recorded, none dropped)

The deterministic edge probe returned six applicable edges for PROF-01/PROF-02, all `unresolved`.
They are recorded here as explicit assumptions for the whole phase; plans 39-02, 39-03 and 39-04
refer to this table rather than restating it.

| # | Req | Category | Probe | Standing assumption | Settled by |
|---|-----|----------|-------|---------------------|-----------|
| E1 | PROF-01 | adjacency | Two things exactly equal or just touching — merge, collide, or separate? | `IdentityProvider.apple` and `PurchaseProvider.apple` share the string `"apple"` and stay separate at every seam. Neither is ever constructed from the other's value. | CONTEXT § Naming Hazard; D-01 field typing |
| E2 | PROF-01 | empty | Result for empty, single-element, or null input? | Zero token rows and one token row both fail closed with the same opaque 500; they are never a 200 with a missing or null key. A NULL `email`/`display_name` is a legitimate `null` **inside** `profile` and is not the "null entry" criterion 4 forbids. | D-06, D-07, criterion 4 |
| E3 | PROF-01 | ordering | When elements compare equal, is output order specified and stable? | Only the **key set** of `purchase_tokens` is contractual, never the key order. The client indexes by key; JSON object order is not asserted anywhere. | D-01, D-07 |
| E4 | PROF-01 | idempotency | What happens if this runs twice on the same input? | The route is read-only, so two identical requests return identical bodies and leave every table byte-identical. Nothing is minted, repaired, or rotated on the second call. | D-03, PROF-02; asserted by plan 39-04's unchanged-table-state case |
| E5 | PROF-01 | concurrency | If interrupted or run in parallel, what is guaranteed? | Exactly one unlocked SELECT under the request's own snapshot. A concurrent mint or delete either lands entirely before the snapshot or entirely after it; a torn read of one row is impossible because completeness is checked against the enum on the returned set. No lock is taken and no serialization is promised beyond that single statement. | D-06 (no lock), D-07 |
| E6 | PROF-02 | concurrency | If interrupted or run in parallel, what is guaranteed? | Nothing durable is written, so concurrent attempts have nothing to interleave. Each attempt independently earns one `request` line from the middleware plus, on rejection, one line from the shared error handler. | PROF-02; Phase 38 D-02 |
