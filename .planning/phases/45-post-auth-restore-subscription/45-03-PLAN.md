    - The conditional UPDATE returns true when the row still holds the owner and the transfer month the pre-transaction read saw.

Order inside the method, after the store call and the non-locking reads:
  1. Entitlement (D-06). A `core.subscriptions` row that exists decides with its own `status`
     against `ENTITLED_STATUSES`; restore never writes that status from the proof, because
     canonical state belongs to the webhooks. Where no row exists, the proof's own status decides.
     Not entitled raises `RestoreSubscriptionNotEntitled` before anything is written.
  2. Attribution. `PurchasesDB.resolve_user` maps the carried token to a user, and returns None
     rather than raising when the caller holds no row for that store — use `resolve_user` only,
     never the completeness-checking token read (RESEARCH Q5). A recorded attribution naming another account raises
     `RestoreAttributionMismatch`.
  3. Branch on the stored owner. Owner equal to the caller is the same-account path 45-01 built:
     it changes no owner, so it must skip the conditional UPDATE entirely rather than run a no-op
     one — running it would make "zero rows means a lost race" untrue for that branch
     (RESEARCH Q2). Owner NULL, or no row at all, is adoption. Owner another account is the move,
     which 45-04 adds; until then that arm raises `RestoreSubscriptionNotEntitled` and says so in
     one inline comment naming plan 45-04.
  4. Adoption-with-creation: where no row exists, call `upsert_subscription` to create it at the
     proof's own status and tier, then flush, then continue. `tier_id` comes from the provider
     class's own product map; the service holds no map.
  5. Take the locks: the two-user lock from Task 1, which for adoption holds one user id. Grant
     rows ascending by id, then their usage rows.
  6. Call `claim_subscription_owner` with the owner and month the pre-transaction read saw. Zero
     rows means another attempt won: roll back, re-read the subscription row, and answer as the new
     state earns — the sync body when the destination now owns it, otherwise the refusal that state
     earns. Do not read the stale in-memory `Subscription` object after the update.
  7. Insert the `core.store_purchases` row when none exists, once and never updated, with a
     `uuid7()` identity value when the proof carries no attribution token — copy the shape and the
     comments from `SubscriptionsService.ingest`.
  8. `write_subscription_grant` unchanged, then `commit()`.
Write the rows in the order the RESEARCH diagram gives — owner update, then the grant expiries,
then the grant insert — because the two deferred foreign keys are checked at COMMIT as SQLSTATE
23503 and are a backstop, not control flow. Catch `IntegrityError` by SQLSTATE 23505 only.
