    - A subscription whose owner is another account, whose stored transfer month is NULL or an earlier month, moves to the caller.
    - The move writes the first day of the captured instant's UTC month into `last_cross_account_transfer_month`.

    then the grant insert. The two deferred foreign keys check `(subscription_id, grant.user_id)`

Extend the recording session so it records the SQLSTATE raised at `commit()` as well as at
`flush()`. The deferred foreign keys are checked at COMMIT, so a recorder that only wraps `flush`

exactly this observable; no case in the repository sets it yet.

Four cases, each on two real connections where the case is about a race:
  1. Two callers adopt one unowned subscription at once. Assert exactly one grant row is committed
     for that subscription, that the loser's attempt wrote nothing, and that the loser answers
     either the sync body or the refusal the winner's state earns — never a 500. Record the
     loser's SQLSTATE and assert it is 23505 if any was raised.
  2. A move, then a second move of the same subscription in the same UTC month. Assert the second
     answers 409 and that the owner, the transfer month, both accounts' grants and both usage rows
     are exactly what the first move left.

     subscription still names the old owner and no new grant row exists.
  4. The deferred-foreign-key case (Pitfall 2). Deliberately mis-order the writes — change the
     owner without expiring the old owner's active subscription grant in the same transaction —
     and assert the violation arrives at `commit()` with SQLSTATE 23503, not at any flush with
     23505. This case exists so a future reader knows where this class of failure surfaces; it is
     the one place in the repository that proves it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> the move branch | A verified proof moves a paid subscription away from the account that holds it. |
| two concurrent restores -> one subscription row | The conditional UPDATE is the only arbiter; the unique index is the backstop. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-45-01 | Elevation of Privilege | the move branch | high | mitigate | D-10's one-move-per-UTC-month cap, per subscription. One stolen proof reaches at most two accounts in a month. The developer accepted that loss on a sub-$5 subscription; strengthening it further would reopen D-10. |
| T-45-09 | Tampering | `claim_subscription_owner` under concurrency | high | mitigate | Task 3 case 1 proves on two real connections that exactly one grant is committed and the loser writes nothing. |
| T-45-10 | Denial of Service | repeated moves of one subscription | medium | mitigate | The cap refuses the second move in a month before any lock is taken and writes nothing. |
| T-45-11 | Tampering | the write order against the deferred foreign keys | high | mitigate | Task 3 case 4 proves the violation surfaces at COMMIT as 23503; Task 1 fixes the write order so it never fires in production. |
| T-45-SC | Tampering | npm/pip/cargo installs | low | accept | This plan installs no package; `pyproject.toml` is unchanged. |
