  <behavior>
    - A 2xx `subscriptionsv2.get` body yields a `RestoredSubscription` whose `external_id` is the purchase token, whose `tier_id` comes from the class's own product map, and whose `status` comes from `_status_for`.
    - A 404 and a 410 each raise `ProofRejected`, not a returned `None`.
    - A 500 from Play, and an `httpx.HTTPError`, each raise `Unavailable`.
    - An absent credential raises `Unavailable`.
    - A product id outside the configured map raises `UnmappedStoreProduct`, and it is not converted into `Unavailable`.
    - A subscription in the grace state carries the line item's `expiryTime` as `grace_period_expires_at`.
  </behavior>
  <action>
Add a second entry point to `PlayDeveloperSubscriptions` for the restore path — RESEARCH names
this the preferred option over reusing `read` with synthesized `event_type`, `notification_uuid`
and `signed_at` values, which restore has no source for. Name it `read_for_restore` and give it
keyword-only `package_name` and `purchase_token`. It returns `RestoredSubscription`.

Reuse, never re-implement: `_get` sends the one signed read; `_status_for` derives the status;
the class's own `_products` map supplies the tier and raises `UnmappedStoreProduct`; the
`in_grace` rule sets `grace_period_expires_at` to the line item's `expiryTime` only in the grace
state. No second httpx client and no second credential (D-05). The URL shape, the host and the
`tokens/` path segment are what Phase 44 shipped and are under test — do not change them.

The entry point classifies its own answer, in this order and no other:
  1. `self._credential is None` raises `Unavailable(stage="play_restore_read")`.
  2. `httpx.HTTPError` from `_get` raises `Unavailable(stage="play_restore_read")`.
  3. A status in `_GONE_STATUSES` raises `ProofRejected(stage="play_token_gone")` (D-05: a gone
     token is a rejected proof, not the webhook's 500).
  4. Any other non-2xx raises `Unavailable(stage="play_restore_read")`.
  5. Only then parse the body, resolve the product and build the value type.
`UnmappedStoreProduct` is raised after that classification and propagates untouched.

This is RESEARCH Pitfall 1 and it is the single most likely defect in the phase:
`UnmappedStoreProduct` subclasses the base internal-error class, and so does the bare error the
webhook path raises for a transport failure. Do not catch that base class anywhere on the restore
path — classify the answer at the source, as the ordered list above does. If a caught-and-mapped
shape is used anyway, the `UnmappedStoreProduct` re-raise clause must come first. The observable
rule: an unmapped Play product on the restore route answers 500, not 503.

D-11 lists "package mismatch" among the proof-rejection stages. The package name travels in the
Play URL path, so a token belonging to another package answers 404 and reaches
`play_token_gone`. Do not invent a separate stage for it. Record the reasoning in one inline
comment; 45-05 records it in REQUIREMENTS.md.

Extend `tests/unit/test_restore_proof.py` with the Google cases, on
`test_google_play_notifications.py`'s shape: fixed instants, `_FakeCredential`, a body builder,
and a `_restore_through` helper calling the new entry point with the arguments the dependency
passes in production. Script every answer with `httpx.MockTransport`. The unmapped-product case is
mandatory — it is the Pitfall 1 control.

`tests/unit/test_auth_package_shape.py` — re-measure `CURRENT` by running the test and reading
the number it reports. Do not guess it.

Every docstring stays at three lines or fewer; every comment is one ASD-STE100 line (D-15).
