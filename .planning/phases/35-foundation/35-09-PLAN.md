<objective>
Build the `audit.auth_events` writer: two write modes, the exact row shape the schema enforces,
the six-key `details` object, and redaction before write.

Purpose: `§4.1` makes auditing an obligation of the audited attempt path, never best-effort and
never a side effect of challenge consumption. Every endpoint phase from 37 on writes through this
one writer, and the schema's CHECK constraints mean a writer that guesses at the actor fields
fails at insert time rather than at review time.

Note the shape of this phase: foundation declares `operation = None` on all eight routes it
registers, so **no production request in Phase 35 is on the audited attempt path**. The writer is
built and proven here against a route declared with an operation in a test-local registry; phases
37-45 supply the real call sites.

Output: the `AuthEvent` model, the writer, the details builder with redaction, and the barrier
hook that invokes it.
</objective>

`build_details` always returns exactly the six §4.4 top-level keys with every subobject present,
empty `{}` when unused — the schema CHECK enforces that shape, so building it in one place is
what stops a caller shipping five keys. `context` carries non-secret request and routing context:
route, method, operation, attempt id, mode signals as booleans, and the client-IP **bucket kind**.
`verification` carries which proof families were checked, verifier error codes, adapter attempt
counts, and budget names consulted. `resolved` carries resolved internal ids and redacted
server-derived identifiers. `mutation` carries the actual committed state change including partial
state on fail-closed paths, and `{}` where nothing changed. `failure` carries the rejection stage,
machine-readable reason context including the bounded `invalid_external_jwt` reason, and
retryability metadata; a successful event leaves it `{}`.

`redact` runs before every write and drops, at any nesting depth: raw JWTs, raw restore proofs,
purchase tokens, signed transaction payloads, attestation blobs, attestation private keys, raw
device identifiers, raw provider responses, raw provider account identifiers, email addresses,
the public challenge handle, and any other secret material. It returns a new object and never
mutates its argument. `audit.auth_events` is not a proof archive. Do not record the raw client
address or any stable per-client identifier — only the bucket kind — so the audit log cannot
become a behavioural-tracking archive; that is the prohibition this plan carries. What each row
must still suffice to reconstruct is: the verified actor when one exists (or that none was
available), which non-secret challenge row was involved, which operation was attempted, which
non-secret verification and identity metadata were available, what state changed including
partial state, and why the request was rejected.

`AuditWriter` takes the `HmacKeyring` at construction and exposes the two §4.1 modes. Both build
the row identically; they differ only in the session they use and whether they commit.
`write_standalone(session_factory, ...)` opens its own session from the factory passed in — the
caller reads `scope["app"].state.session_factory` per request and hands it over, so the writer
never caches app state and the e2e rollback fixture's factory swap still applies — writes the row,
and commits before the response returns. Under the test harness's
`join_transaction_mode="create_savepoint"` that commit releases a savepoint rather than the outer
transaction, so the row is visible to a session on the same connection and still rolls back at
the end of the test. `write_in_transaction(session, ...)` takes the caller's `AsyncSession` and
writes inside it, atomically with challenge consumption and any state change, and does not commit.

Derive `actor_subject_hash` through `keyring.actor_subject_hash(issuer, subject)` and record
`keyring.active_version` in `actor_subject_hash_key_version`. Raise a clear error before touching
the database when `result` is anything other than `invalid_external_jwt` and any of
`actor_issuer` / `actor_subject` is `None`: the CHECK admits all-NULL actor fields only for that
one result, and a writer that guesses produces a constraint violation instead of a diagnosable
message. This is exactly the `internal_error` case — at that point the token *has* been verified,
so issuer and subject are known and must be populated; `actor_provider` stays NULL because no
identity row resolved. The same rule applies to `preauth_identity_not_allowed`.

`actor_provider` is populated only from the stored `core.external_identities.provider` column of
a resolved linked identity. It is never fabricated and never taken from token claims, headers, or
client input.

Auditing is never best-effort, but it also never changes the client's outcome: wrap each write so
a failure is logged with full context and the caller still returns the outcome the attempt earned
— never a different outcome, never a 500 substituted for a business rejection.

Construct `app.state.audit_writer = AuditWriter(app.state.hmac_keyring)` in `app/lifespan.py`
under its own comment banner, after the keyring.
