<objective>
Ship the keyed-hashing seam both the audit writer and the challenge store depend on: one shared
key, two pinned domain-separation prefixes, and a fail-closed startup policy that aborts on a
missing active key but only warns on a missing historical one.

Purpose: `§4.3` and `§6.4` couple explicitly — the challenge store's `preauth_subject_hash` uses
the same family and the same key as the audit writer's `actor_subject_hash`. Building one shared
derivation helper is what holds that coupling; building two would let them drift, and a drift
here is silent until a challenge stops matching.

Output: `auth/keys.py`, the `hmac:` configuration block, and startup validation.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <decision>Pin the on-disk encoding of HMAC key material: base64 text in `config/config.yaml`, decoded to raw bytes once at configuration load.</decision>
  <context>
This is a one-way door. `actor_subject_hash` and `preauth_subject_hash` are derived with
`hmac.new(key_bytes, message, sha256)`. If the key is instead treated as its base64 *text*, every
derived hash differs — and both derivations "work", so nothing fails loudly. Once a single
`audit.auth_events` row or `core.auth_challenges` row exists, changing the encoding invalidates
every stored hash and there is no migration that can recompute them, because the raw subject was
never stored.

Research assumption A5 recommends base64-in-YAML decoded to bytes at load, and the developer
directive for this planning run confirmed A5 stands. This checkpoint exists because the choice
was never put to the developer as a decision with alternatives, and the reversibility rating is
`one-way` rather than `costly`. Approving it pins the encoding for the life of the product.

Related accepted consequence, already decided in D-20 and not being re-asked here:
`config/config.yaml` is tracked in git, so the key material is committed and rotating a key
leaves its predecessor readable in history. `.planning/todos/pending/secret-manager-integration.md`
is the mitigation path and exists for exactly this reason.
  </context>
  <options>
    <option id="base64-yaml">
      <name>Base64 text in config.yaml, decoded to bytes once at load (A5, recommended)</name>
      <pros>Human-readable and diffable in a YAML file; `openssl rand -base64 32` produces it directly; a single decode point makes it impossible to accidentally hash over the text; length is validated at load.</pros>
      <cons>Key material is committed to git per D-20; the encoding cannot be changed once rows exist.</cons>
    </option>
    <option id="hex-yaml">
      <name>Hex text in config.yaml, decoded to bytes once at load</name>
      <pros>Same single-decode property; slightly less ambiguous than base64 about padding.</pros>
      <cons>Longer strings; no other advantage; equally one-way.</cons>
    </option>
    <option id="env-only">
      <name>Move key material to an environment variable now instead of config.yaml</name>
      <pros>Keeps the key out of git immediately.</pros>
      <cons>Reverses D-20, which the developer already decided; the YAML is authoritative over env for any field it declares (Pitfall 9), so a hybrid would silently ignore the env value; the Secret Manager follow-up already covers this properly.</cons>
    </option>
  </options>
  <resume-signal>Select: base64-yaml, hex-yaml, or env-only</resume-signal>

  <action>
Create `src/nativespeaker/api/auth/keys.py`.

Pin the two domain-separation prefixes as module-level `bytes` literals — `ACTOR_SUBJECT_PREFIX
= b"actor-subject:v1:"` and `IDP_ACCOUNT_PREFIX = b"idp-account:v1:"`. They are never
parameterized, never built from a format string, and never read from configuration; pinning them
as literals is what stops them drifting.

`HmacConfig` is a pydantic model with `active_version: int` bounded `ge=1, le=32767` and
`keys: dict[int, SecretStr]`. The upper bound matches
`audit.auth_events.actor_subject_hash_key_version`, which is `SMALLINT`, so a bad configuration
fails at load rather than at the first insert. A `dict` keyed by version is deliberate over a
list of objects — it validates version uniqueness for free and reads directly as
`keys[active_version]`.

Add a `model_validator(mode="after")` implementing D-22: the configuration is rejected when
`keys` has no entry for `active_version`, when that entry is empty or whitespace, or when its
material decodes to fewer than 32 bytes. Nothing can be written without the active key, so a
missing one aborts. A missing *older* version is **not** rejected — it only means historical
audit hashes cannot be recomputed, which no request path needs, and requiring every version
1..active would mean keys could never be retired and losing an old key would brick the app.

`HmacKeyring.__init__` decodes every configured key from base64 into `bytes` exactly once and
keeps only the bytes. Never call `hmac.new` on a `str`: it raises `TypeError`, and the "fix" of
calling `.encode()` silently derives the HMAC over the base64 *text* instead of the 32 key bytes.
Both derivations produce a plausible digest; only one matches whatever wrote the existing rows.
`warn_missing_older(log)` iterates versions 1 through `active_version - 1` and emits a warning
event naming each absent version.

`actor_subject_hash(issuer, subject, *, version=None)` computes
`hmac.new(key, ACTOR_SUBJECT_PREFIX + issuer.encode() + b":" + subject.encode(),
hashlib.sha256).digest()` using the requested version or the active one, and returns the 32-byte
digest for the `BYTEA` column. `idp_account_hash` is the parallel derivation under
`IDP_ACCOUNT_PREFIX`. Use `hmac.compare_digest` wherever a stored hash is compared; never `==`.

D-21 is why there is one shared method rather than two: the challenge store calls
`actor_subject_hash` for `preauth_subject_hash` and stores **no** key version, because
`core.auth_challenges` has no such column and verification uses the active key alone. The
accepted consequence is that a key rotation invalidates outstanding challenges — completion then
fails the binding comparison, rejects `challenge_identity_mismatch`, and the client simply
prepares a fresh one inside the 300-second TTL. Do not add a key-version column to that table.

Add `hmac: HmacConfig` to `AppConfig` in `src/nativespeaker/api/config.py`, and an `hmac:` block
to `config/config.yaml` with `active_version: 1` and a `keys:` map holding version 1. Generate
the development key with `openssl rand -base64 32` and commit it. Add a comment above the block
recording that the file is tracked in git, that a rotated key stays readable in history, and that
`.planning/todos/pending/secret-manager-integration.md` is the mitigation path. Also record that
the YAML is authoritative for anything it declares — pydantic-settings ranks `init_settings`
above `env_settings` and `AppConfig` is built as `AppConfig(**yaml_data, ...)`, so an environment
variable cannot override a key the YAML declares, and the Secret Manager follow-up must *remove*
these entries rather than shadow them.

In `app/lifespan.py`, construct `app.state.hmac_keyring = HmacKeyring(config.hmac)` under its own
comment banner and call `warn_missing_older` with the module logger. Validation failure raises out
of `EnvironmentConfig()` before the lifespan reaches this point, which is the fail-closed
behaviour D-22 wants. Update `tests/unit/test_config.py` for the new field.
