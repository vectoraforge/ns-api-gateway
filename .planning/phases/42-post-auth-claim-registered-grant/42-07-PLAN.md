<objective>
Close CR-01 and the four warnings that share its root cause: `return False` from the crud writers
means both "you lost a race, re-read the winner's row" and "your write was impossible, there is
nothing to read". The route cannot tell them apart, so it answers 200 for both — and on the
registered route it first spends Apple's one-way DeviceCheck bit1.

Purpose: the application asks one question in one place when it is really two.

1. "What is this person entitled to right now?" The time window belongs here. This is
   `_effective_grants_statement`, and it does not change.
2. "Would an insert be refused?" The time window must **not** be here. This question must match the
   index predicate exactly, which means `status` alone for `ix_access_grants_one_active_per_user`,
   and `source` alone at any status for `ix_access_grants_one_free_grant_per_user_source`.

Question 2 gets its own reads, and the claim preflight asks them. The service then learns it will be
refused **before** it spends the Apple bit. A residual genuine race remains after that, and the
three-valued writer outcome closes it: the route answers 403 where the write was impossible, and 200
only where the winner's row exists to be read.

The two index predicates are not editable and are not the defect. A partial index predicate must be
IMMUTABLE, so `now()` cannot appear in one. `status` is the only enforceable form of "is this live",
which is why `migrations/20260818_01_initial-release.sql:255` already says that a correct caller
expires before it activates. The application must therefore hold the second rule itself.

Output: both claim routes refuse, before Apple and before the transaction, every state the indexes
will refuse; both writers name why they refused; and every state the review reproduced against the
live database is a passing case that fails without the fix.

**In scope:** CR-01, WR-01, WR-02, WR-03, WR-04 — the five findings the review names as sharing one
root cause.

**Out of scope, and left open for a follow-up:** WR-05 (the untested `free_grant_consumed_at`
branch), WR-06 (D-02's understated consequence table), WR-07 (the byte-identical
`device_grant_exhausted` diagnostics) and IN-01 … IN-05. None of them shares this root cause, and
none is a wrong answer to a caller. They are named here so a later reader knows they were seen and
left, not missed.
</objective>

<the_defect_stated_once>
`_effective_grants_statement` (`crud/grants.py:22-34`) selects a grant only when `status = active`
**and** `starts_at <= evaluated_at` **and** `(ends_at IS NULL OR ends_at > evaluated_at)`.
`ix_access_grants_one_active_per_user` (`migrations/20260818_01_initial-release.sql:256-258`) is
`UNIQUE (user_id) WHERE status = 'active'` — no time predicate at all.

A row with `status='active'` whose `ends_at` has passed therefore sits inside the index and outside
the read. Nothing in `src/` sets `status` to `expired` when `ends_at` elapses, and nothing may be
added here that does. For such an account `_claim_registered_grant` takes the new-grant arm, writes
the irreversible bit1 at `services/auth.py:222`, then calls the writer at `:224`, which hits the
index, swallows the `IntegrityError` and returns `False`. The service rolls back and the route
answers 200 with `type: none`. The bit is spent and the caller got nothing. The same shape exists on
`_claim_anonymous_grant` with bit0.

The verifier confirmed the fact pattern independently and added one fact: no writer of a `manual` or
`subscription` grant exists in `src/` today, so no caller can reach this through the API yet. Phase
43 ships `POST /webhooks/app-store`, whose whole purpose is to write subscription grants with a term
`ends_at`. This plan is the fix chosen over accept-and-gate.
</the_defect_stated_once>
