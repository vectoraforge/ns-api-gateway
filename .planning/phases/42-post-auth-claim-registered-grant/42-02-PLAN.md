proof, not behaviour: the case matrix (42-03), the structural single-writer and ordering walks
(42-04), and the two-connection race (42-05).

<assumption_delta_decision>
**Signal.** The detector fired on ROADMAP criterion 4, *"An account that already consumed its free
grant as anonymous does not receive a second free entitlement"* — kind `pluralization`, on the word
"second". A second free grant source now exists beside the anonymous device grant, so "one free
grant" has become a per-account notion spanning two sources rather than a per-source one.

**The noun that is now primary.** The account's single free-entitlement slot, spanning the whole set
of free sources — not the anonymous device grant, and not any one source.

**Decision: `add-alongside`, accepted as debt.** The generalisation was half-made already: Phase 41
promoted the *set* into `FREE_GRANT_SOURCES` in `tables/grants.py`, bound by a schema test to the
live index predicate, and this phase adds the second member's writer beside the first without
changing any key. It stops there because the schema still names the narrower noun.
`ix_access_grants_one_free_grant_per_user_source` is `UNIQUE (user_id, source)` with the predicate
`source IN ('anonymous_device_grant','registered_account_grant')` — the key **includes** `source`, so
the index permits one row of *each* free source per user, which is exactly what D-10's conversion
needs and is also exactly why the index does **not** enforce one free grant per account
(`42-RESEARCH.md` Pitfall 3). The account-level rule is enforced by the application: D-09's grant
history read by source **and** status, and nothing else.

**What would force a promote.** A third free source, or any requirement to enforce the account-level
rule without the application read — for example if a second writer ever gained the ability to insert
a free-source grant. Promoting means re-keying the index to `(user_id)` with the same predicate,
which the conversion would then have to satisfy by expiring the anonymous row first — it already
does, so the promote is available and was declined only because it buys nothing today and costs
another in-place migration edit.

**Companion invariant, planned rather than suggested.** Plan 42-03's precedence matrix carries the
generalised claim as a named case — an account with `anonymous_device_grant` in history and no active
free grant is refused — and plan 42-05's conversion race asserts the account holds free entitlement
from exactly one source at any instant. Both are cheap and both fail if the application guard is ever
replaced by a `free_grant_consumed_at` test.
</assumption_delta_decision>

**`services/auth.py::_claim_registered_grant` — D-09's decision, in D-09's order.** First statement:
the stored provider test, positive and closed — `identity.identity.provider` must be
`IdentityProvider.google` or `IdentityProvider.apple`, otherwise raise `ClaimantNotRegistered`. No
Firebase read anywhere on this route. Then read the caller's effective grants **once** into a local,
using `read_effective_grants(identity.user.id, self.evaluated_at)`, and decide in exactly this order:
an active grant whose source is `registered_account_grant` is the repeat — bare `return`, nothing
written, Apple never reached; any other active grant whose source is not `anonymous_device_grant`
raises `OtherActiveGrantHeld` with no field; an active `anonymous_device_grant` is the conversion; no
active grant and no free-source grant in history is the new grant; free-grant history with no active
free grant raises `FreeGrantAlreadyConsumed`. **Do not copy the two lines from
`_claim_anonymous_grant` that test `identity.identity.free_grant_consumed_at is not None` or call
`has_prior_free_grant` as a blanket guard** — both are already true on the conversion path, and
copying them refuses the destination this phase exists to add. The history read still uses
`has_prior_free_grant`, but only inside the arm where no active grant is held.

**The Apple gate, on the new-grant arm only (D-01, D-02, D-03).** Inside the new-grant arm and
nowhere else: `state = await read_bits_with_retry(self.devicecheck, device_token)`; if `state.bit1`
is true raise `DeviceGrantExhausted(stage="devicecheck_read", cause="already_set")` — the same class,
the same copy and the same keyword values Phase 41 uses, with no device state in the body; otherwise
`await write_bits_with_retry(self.devicecheck, device_token, bit0=state.bit0, bit1=True)`, carrying
bit0 forward from the read exactly as Phase 41 carries bit1. Both calls run after the claim's commit
and before the writer is called, so no lock is held and no transaction is open across them. The
conversion arm reaches neither call: the caller already paid one device slot to hold an anonymous
grant, and a conversion issues no new allowance.

**`crud/grants.py::activate_registered_account_grant` — one writer, two destinations
(Open Question 1).** One method with an internal branch, not two methods: D-09 requires the
destination to be re-decided inside the lock after the same prologue, and two methods would either
duplicate that prologue or share a private helper that `AGENTS.md` § Function shape would then ask to
inline. One method also keeps exactly one construction site for
`AccessGrant(source=AccessGrantSource.registered_account_grant)`, which is what REGGRANT-01 is about.

Signature: keyword-only `user_id`, `identity_row`, `tier_id`, `evaluated_at`, returning `bool`.
Prologue, copied verbatim from `activate_anonymous_device_grant`: `lock_effective_grants` ascending by
id, then `lock_usage` for each returned grant — **capture the returned usage row per grant** rather
than discarding it, because the conversion needs the old row's counters — then a plain
`IdentitiesDB(self.session).resolve_existing(...)` re-read, never `lock_identity_and_user`. Re-check:
a `None` row, or a row whose provider is neither `google` nor `apple`, returns false. Re-decide the
destination from the locked grant list on the same rules as the preflight; a repeat, a held other
source, or spent free-grant history all return false, and the service's caller answers exactly as the
repeat does.

Conversion branch: set the anonymous grant's `status` to `expired`, its `ends_at` to `evaluated_at`
and its `updated_at` to `evaluated_at`, leaving `source` unchanged; **emit that expiry before the
insert**. `ix_access_grants_one_active_per_user` is a non-deferrable, per-statement partial unique
index, and SQLAlchemy's unit of work orders inserts before updates within a single flush regardless
of Python statement order — so an attribute assignment plus `session.add()` in one flush would emit
the INSERT first and every conversion would look like a race loss. Force the order either by flushing
