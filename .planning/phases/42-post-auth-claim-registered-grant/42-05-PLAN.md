<objective>
Prove both destinations of the registered claim under real contention: two attempts, two connections,
one barrier, against real PostgreSQL.

Purpose: no unit or end-to-end test can reach this. On a first claim there is no grant row to lock,
so `FOR UPDATE` locks nothing and the guarantee rests entirely on two partial unique indexes refusing
the second write. The same proof on the anonymous claim in Phase 41 found a genuine 500 on the
loser's path that a green 1310-case suite had said nothing about — this is the class of defect the
proof exists to produce.

Output: two new race classes, one per destination, each asserting one narrow fact per case on its own
connection.
</objective>

Add the second race class: two simultaneous conversions on one account that already holds an active
anonymous device grant.

**Seeding.** Reuse Task 1's registered account helper, then seed one active `anonymous_device_grant`
with its usage row. The grant's `starts_at` must be **strictly earlier** than the module's fixed
instant — the table's CHECK is `ends_at IS NULL OR ends_at > starts_at` with a strict `>`, so a
same-instant `ends_at` fires the CHECK, rolls the whole transaction back, and the writer reports it
as a race loss. A case that passes because the grant was never effective is the failure mode Phase 41
recorded by name. Give the usage row a distinctive period and a non-zero used count, so "the counters
were carried" is distinguishable from "a fresh usage row was minted".

**The cases**, one narrow fact each, read on their own connections after both attempts finish:
- exactly one `core.access_grants` row for the user has status `active`, and its source is
  `registered_account_grant` on the `registered` tier;
- exactly one row has status `expired`, its source is still `anonymous_device_grant` — the source is
  never rewritten — and its `ends_at` equals the fixed instant;
- the user holds exactly two grant rows in total: one expired, one active, so no third row was
  created by the loser;
- exactly one usage row is attached to the active grant, and its `monthly_period` and `monthly_used`
  equal the seeded values exactly — carried once, neither doubled nor reset;
- both challenges are consumed;
- the loser answered 200 with a body equal field for field to the winner's;
- the loser's `IntegrityError` surfaced at the flush and not at the commit.

**One invariant case beyond the race.** Assert that at the end of the run the user holds free
entitlement from exactly one source: exactly one grant row for that user is `active`, across both
free sources. This is the generalised rule the phase's assumption-delta record names — the schema's
lifetime index is keyed by `(user_id, source)` and therefore permits one row of each free source, so
this account-level fact is enforced by the application and must be checked rather than assumed.

**Mutation-test the conversion race before trusting it.** Remove the writer's flush boundary between
the expiry and the insert, observe the race class fail with both attempts reporting a loss at flush,
then revert and confirm the source file is byte-identical. Record the mutation, the failing node ids
and the observed messages in the summary — this is the contention-level counterpart of plan 42-02's
statement-order proof, and together they close research assumption A1 at both levels.

**Report, do not adjust.** As in Task 1, a failure is reported with exactly what the production code
did.
