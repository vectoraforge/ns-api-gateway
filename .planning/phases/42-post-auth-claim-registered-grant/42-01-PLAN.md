<objective>
Take three tables out of the single v2.0 migration — the anti-abuse receipt table and the two
provider-account tables — together with everything only they need, and carry the deletion through the
model layer, Phase 41's writer and the six test files that read them.

Purpose: the receipt row decided nothing. Every fact on it exists elsewhere — the grant's own
`source`, the identity row's `native_claim_platform`, the identity row's `provider_uid` — and the two
provider tables were never written by any code. This lands first because Phase 42's writer edits the
same function and the same test files; merging it with the new writer would make a failure ambiguous
between "the deletion broke something" and "the new writer is wrong".

Output: an edited migration, both disposable databases rebuilt from it, and three green suites with
one fewer row written on every anonymous claim.

Scope note: this plan touches 10 files across 3 tasks, which is the warning band of the files-per-plan
guide, and the count is accepted deliberately. Task 3's six-file test cascade is the direct read side
of Task 2's deletion; splitting it into its own plan would make a failure ambiguous between "the
deletion is wrong" and "the test re-baseline is wrong", which is the exact ambiguity this plan was
sequenced first to avoid. The token estimate sits at 45% of budget, so the count costs nothing.
</objective>
