### The five assertions `assert_tree_total()` makes

Walking `AppError.__subclasses__()` recursively, collecting into one `problems` list and raising once:

1. **No code is declared at two different statuses.** A code and a status are declared together, so a code bound to two statuses is a class pair that disagrees about what the client is told.
2. **The set of codes the tree carries equals `get_args(ErrorCode)` exactly**, with the two directions reported as separate problems.
3. **Every leaf has a declaring strict ancestor below the root.** A class with subclasses is an intermediate that answers through its leaves and is skipped; a leaf relying only on the base's 500 is a defect.
4. **Every class declares `status` and `code` together or neither** — `("status" in vars(cls)) == ("code" in vars(cls))`. This is the mandatory replacement for the frozen-pair guarantee `ErrorClass` gave.
5. **The classes marked `answers_framework_status = True` yield exactly one class per status**, built into a mapping *inside* the check and discarded when it returns.

Assertion 1 is **not** the plan's literal wording. See Deviations, item 1.

## Deviations from Plan

### Auto-fixed issues

**1. [Rule 1 — Bug in the plan's own specification] Assertion 1 as written is unsatisfiable**

- **Found during:** Task 1, while designing `assert_tree_total`.
- **Issue:** The plan's action says the check asserts *"no two classes claim the same `code`"*, mirroring `assert_registry_total`'s `:187-192`. But that loop ranges over **`ErrorClass` registry entries**, of which there were 16 and each of which was unique by construction. In the merged tree the ranging is over **exception classes**, and several legitimately share a code. The same task mandates two of them: *"`TransientLLMError` and `PermanentLLMError` keep `log_level = None` and keep re-declaring their own status and code"* — both then declare `service_unavailable`. `auth_required` is likewise declared by `AuthRequired`, `AuthenticationError`, `InvalidExternalJwt` and `UserNotFound`; `internal_error` by seven classes. Literal uniqueness would fail on the tree the plan itself specifies.
- **Fix:** The assertion became **"no code is declared at two different statuses"**. That is the property the registry actually guaranteed (a code was 1:1 with a status, forever) and the one whose violation is client-visible: two classes answering `not_found` at 404 and 451 is a contract split, whereas two classes answering `service_unavailable` at 503 is just two failures with one answer.
- **Verification:** `tests/unit/test_error_registry.py::TestTreeTotalityCatchesDefects::test_a_code_claimed_at_a_second_status_is_reported_and_names_both_classes`, plus a control proving the same check reports nothing when the synthetic class does not exist.
- **Committed in:** `447f27f`, tests hardened in `f818748`.

**2. [Rule 1 — Bug introduced by 02-T1] `routers/auth.py`'s `except AuthRejected` stopped catching the account-unavailable arms**

- **Found during:** Task 2, while repointing imports in `routers/auth.py`.
- **Issue:** `_complete` wraps the create-user call in `except AuthRejected:` and, on that arm, calls `_consume_and_commit` so a raising path still spends the challenge handle exactly once. Task 1 moved `HistoricalIdentity` and `BlockedUser` to `AppError`, which is **not** an `AuthRejected`. Between `447f27f` and `f818748`, a create-user attempt that hit a historical identity or a blocked user would have propagated past that arm with the handle **unconsumed** — a single-use handle becoming replayable. No test caught it: the suite was green at `447f27f`.
- **Fix:** `except AppError:` — now that one tree covers both former trees, this is the correct and total arm.
- **Files modified:** `src/nativespeaker/api/routers/auth.py`
- **Verification:** `tests/unit/test_create_user_precedence.py::TestEveryProviderStageRejectionConsumes` and `::TestTheTransactionRejectionIsObservedAtTheHandler` pass; the schema-marked atomicity and race suites pass.
- **Committed in:** `f818748`
- **Worth a reviewer's eye.** This is the sharpest edge in the plan's task decomposition: moving a class out of a tree silently narrows every `except` naming that tree, and nothing in the suite pinned this arm's breadth.

**3. [Rule 3 — Blocking] The lifespan swap moved from Task 1 to Task 2**

- **Found during:** Task 1.
- **Issue:** Task 1 says to replace `assert_registry_total()` with `assert_tree_total()` in `app/lifespan.py`. But Task 1's tree contains only `AccountUnavailable` and its two leaves, carrying one of sixteen codes. Assertion 2 (vocabulary equality) therefore *must* fail, so the app would not boot. The only ways to comply literally are to weaken assertion 2 for one commit and re-tighten it in Task 2, or to pull Task 2's whole migration into Task 1 and lose the tracer.
- **Fix:** Task 1 wrote `assert_tree_total()` complete with all five assertions but left the lifespan calling `assert_registry_total()`; Task 2 swapped the call once the tree was total. Strictly the safer ordering: the registry stayed guarded at boot throughout Task 1, and no assertion was ever shipped weakened.
- **Verification:** `src/nativespeaker/api/app/lifespan.py:31` now reads `assert_tree_total()`; `tests/e2e/test_startup_assertion.py` passes.

**4. [Rule 2 — Missing critical functionality] Nine generic framework classes, all silent**

- **Found during:** Task 2.
- **Issue:** Assertion 2 requires the tree to carry every code in `ErrorCode`, but no exception class carried `method_not_allowed`, `validation_error` or `rate_limited` — those existed only as `ErrorClass` constants the status map pointed at. And the plan requires the framework adapters to *construct the tree's own exception and delegate*, which needs a class per framework status.
- **Fix:** Added `InvalidRequest`, `AuthRequired`, `NotFound`, `MethodNotAllowed`, `ChallengeRequired`, `ValidationError`, `RateLimited`, `InternalError`, `ServiceUnavailable`. Each is named exactly for the code it carries, so its `camel_to_snake` event name and its code agree.
- **The silence is the load-bearing part.** Today a mapped framework status logs *nothing* (`test_a_mapped_status_logs_nothing` pins it). Each generic class therefore declares `log_level = None`. Two classes that would otherwise have been reused were deliberately *not* marked: `AuthenticationError` (401) and `ChallengeRejected` (409) both log at WARNING, and marking either would have started emitting a security-log record for every bare framework 401 or 409. `AuthRequired` and `ChallengeRequired` exist so that neither the framework path gains a record nor the real rejections lose one.

**5. [Rule 2 — Missing critical functionality] `log_level = None` declared wherever a class is silent today**

- **Issue:** The plan's discretion item 5 sets the base default to `logging.WARNING` and names only `TransientLLMError` and `PermanentLLMError` as needing `None`. But **twelve** classes are silent today (every `ServiceError` subclass that does not declare a level). Taking the plan literally would have made ten previously-silent classes — including `InvalidChatError`, a routine 404 — start emitting a WARNING per occurrence.
- **Fix:** `log_level = None` is declared on the generic bases (`InvalidRequest`, `NotFound`, `RateLimited`, `ServiceUnavailable`, `InternalError`, …) and inherited by their service subclasses, so today's logging behaviour is preserved **exactly** while keeping the declaration count low. T-37.4-09's residual risk is unchanged; its realised risk is zero.
