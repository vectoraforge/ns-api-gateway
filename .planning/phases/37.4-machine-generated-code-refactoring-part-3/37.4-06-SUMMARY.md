# Phase 37.4 Plan 06: Conflict-Path Collapse and Extractor Replacement Summary

Collapsed the create-user conflict path onto one already-linked answer and replaced the 43-line
hand-rolled bearer extractor with `fastapi.security.HTTPBearer(auto_error=False)`, closing four
37.3-REVIEW warnings in the lines being rewritten and removing 827 lines against 351 added.

## What was built

**06-T1 — the conflict path (`8857cdb`).** `_insert_account` and `_flush_account` merged into one
function, `_insert_account`, which performs the user insert, the identity insert and the two eager
purchase-token mints and returns the new user id. The savepoint, the cause-chain walk, the
three-way constraint map, both constraint-name literals and the unmapped-constraint re-raise are
gone. Any `IntegrityError` from the insert becomes one `IdentityAlreadyLinked`. The pre-check —
`resolve_existing_identity` and `_reject_existing_identity` — is byte-for-byte unchanged, so the
common already-linked case still earns its distinct answer before the insert (D-04).
`ProviderAccountAlreadyLinked` is deleted; `operation_not_allowed` survives in the vocabulary on
`NotLinked`, which still raises it, so `assert_tree_total()` stays satisfied.

**06-T2 — the extractor (`57135d5`).** `HTTPBearer(auto_error=False)` is declared once at module
level in `app/dependencies.py` and taken as a `Depends()` parameter on `get_identity`. A `None`
credential raises `InvalidExternalJwt` from our own code, so the 401, the `auth_required` code and
the `invalid_external_jwt` log event are unchanged. No status re-mapping is written.
`auth/extract_bearer.py`, `tests/unit/test_wire_contract.py` and `tests/e2e/test_wire_contract.py`
are deleted — 260 lines. `BoundedReason` now lives in `auth/jwt_verifier.py` with exactly the five
members the verifier produces.

**06-T3 — the record (`531bc94`).** Eight cases in `tests/unit/test_identity_accessors.py` state
what the wire does now, including the losses.

## Checkpoint 06-C1

Raised as a blocking decision and resolved by the user as **option-a**. Reconnaissance was run
read-only before returning and is preserved in `37.4-06-CHECKPOINT.md` (`b581383`). Two of its
findings changed the shape of the work:

- **RESEARCH assumption A5 is false.** Envoy Gateway configuration *does* ship in this repository:
  `k8s/templates/security-policy.yaml` is a `SecurityPolicy` with a Firebase JWT provider bound to
  the app-routes and llm-routes `HTTPRoute`s. It does **not** confirm the mitigation — no
  header-normalisation filter ships anywhere in the chart, and `SHARED-INVARIANTS.md:20` says
  verbatim that *"Envoy's JWT filter is defense-in-depth only; no backend correctness depends on

  line forbids. `service.type` is `ClusterIP` and no `NetworkPolicy` ships, so the residual is an
  in-cluster caller reaching the pod directly.
- **A-05's premise correction is confirmed empirically.** With `auto_error=True` the installed
  FastAPI answers **401** with `WWW-Authenticate: Bearer`, not the 403 D-10 anticipated.

## Deviations from plan

**1. [Rule 1 — plan premise wrong] The sanctioned status move was not in the file the plan named.**
The prohibition required exactly one status/code pair to move in
`tests/unit/test_create_user_precedence.py`. That file needed **zero** changes: its only
403 `operation_not_allowed` is the `NotLinked` provider-data shape, which survives untouched, and
its transaction rejection was already `IdentityAlreadyLinked`. The move actually belonged to
`tests/e2e/test_create_user.py::TestTheProviderAccountReservation`, where a reserved provider
account refusing a second subject went from 403 `operation_not_allowed` to 409
`identity_already_linked`. Exactly one status/code pair moved across the whole repository; the
prohibition's intent is honoured and its file reference was stale.

**2. [Rule 1 — bug the plan would have introduced] The savepoint was load-bearing for a reason the
plan does not name.** SQLAlchemy's full `Session.rollback()` expires *every* state in the identity
map; a savepoint rollback expires only the dirty ones. Removing the savepoint therefore made the
route's post-rollback read of `challenge.challenge_id` a lazy refresh — `MissingGreenlet`, a 500
where a 409 was owed. Fixed by capturing `challenge_row_id` before the rollback and changing
`_consume_and_commit` to take plain `challenge_id` and `challenge_row_id` strings instead of the ORM
instance. Without this the plan's stated design would have shipped a 500 on every conflicting
create-user.

**3. [Rule 3 — blocked] `ProviderAccountAlreadyLinked` was referenced outside `files_modified`.**
`tests/unit/test_exception_handlers.py` and `tests/unit/test_error_registry.py` both imported it.
The registry's `operation_not_allowed`-at-403 assertion was repointed at `NotLinked`, which still
declares it, and the handler suite's rejection case was replaced by a `NotLinked` case so the
"two 403 codes stay distinct" property keeps a live subject.

**4. [Rule 3 — blocked, authorised by coordinator] `tests/unit/test_jwks_offload.py`.**
`test_a_duplicate_authorization_never_reaches_the_jwks_transport` asserted that a duplicate
`Authorization` rejects before any JWKS fetch. After the substitution the first value is used and
verification proceeds, so it failed. Repointed at the credential-less path.
**Reasoning for why the lost protection is not materially load-bearing:** the property it guarded
was never about duplicates specifically — a *single* well-formed header carrying an unknown `kid`
already reaches the transport, so an attacker wanting to provoke outbound JWKS work never needed to
send two headers. The verifier's negative `kid` cache bounds repeats either way. What the test
uniquely pinned was step 2 preceding step 3, and the credential-less case pins that identically.

**5. [Ledger updates] Two deliberate ledgers were rewritten.** `test_auth_package_shape.py`
`CURRENT` went `(7, 9, 25)` → `(6, 9, 23)`: one module and one function for the deleted extractor,
one function for the merged `_flush_account`; the class count is unchanged because `BoundedReason`
moved within the package. `test_rejection_vocabulary.py` lost its
`provider_account_already_linked` entry.

**6. [Prohibition, off by a mechanical line] `tests/unit/test_jwt_security.py` changed 3 lines, not
1.** Repointing the import made two `import ... from nativespeaker.api.auth.jwt_verifier`
statements adjacent, which ruff's `I001` requires merged. The diff is 2 deletions and 1 insertion,
entirely within the import block. **No assertion was added, removed or altered**, which is the
narrowing this plan's provenance recorded. Verified by reading the whole diff.

**7. [Acceptance criterion unsatisfiable as written]
`rg -c "constraint_name|external_identities_issuer_subject_key|ix_external_identities_provider_account" src tests`
cannot report zero.** `tests/schema/test_inventory.py`, `tests/schema/test_constraints.py` and
`tests/schema/test_store_purchase_tokens.py` legitimately name constraints to assert the *schema*,
which is not this plan's subject. Scoped to `src` plus this plan's files, the check is clean:
`rg "constraint_name" src` reports nothing.

**8. [Acceptance criterion, false positive] `rg -c "403" src/nativespeaker/api/app/dependencies.py`
reports 2, not 0.** Both are pre-existing prose describing `PreAuthIdentityNotAllowed`, which
genuinely answers 403. No 403 was added and no re-map was written; `git diff` confirms it.

**9. [Coordinator instruction, superseding the plan] The wire-contract invariant was removed rather
than flagged.** The plan directed 37.4-07 to record the D-10 and A-09 losses as flagged conflicts.
The user instead instructed: *"Remove all invariants that prevent me from replacing the extractor
with HTTPBearer."* The exactly-one-Authorization-field sentence was therefore **deleted** from

## What the wire gave up, with causes distinguished

Measured against the installed fastapi 0.135.1 / starlette 0.52.1 and now asserted in
`tests/unit/test_identity_accessors.py::TestTheWireContractTheFrameworkNowEnforces`.

| Shape | Was | Is now | Cause |
|---|---|---|---|
| duplicate `Authorization` fields | `duplicate_authorization` rejection | **first value used, second hidden** | the framework reads the header through a mapping that returns the first value (D-10) |
| `Bearer A, Bearer B` | `duplicate_authorization` rejection | whole string verified, fails as `bad_signature` | same (D-10) |
| line-folded value | `duplicate_authorization` rejection | not distinctly rejected | same (D-10) |
| `Bearer␣␣␣TOKEN␣␣` | `malformed` rejection | **accepted and authenticates** | the scheme/param split strips the parameter (A-09) — a *loosening*, distinct in cause from the first/last resolution above |
| `Bearer TOKEN extra` | `malformed` rejection | verified as `"TOKEN extra"`, fails as `bad_signature` | concatenation, named by the deleted rule as its own rejection — **found during this plan, not enumerated by D-10 or A-09** |
| reason vocabulary | eight bounded reasons | five; `missing_token`, `malformed`, `duplicate_authorization` gone | A-04 |
| race-path provider-account conflict | 403 `operation_not_allowed` | 409 `identity_already_linked` | D-06; only the **race** path loses the distinction, the pre-check keeps it |
| unmapped-constraint 500 tripwire | 500, loud | benign 409 | D-06, knowingly given up |

**RESEARCH assumption A5 — that Envoy normalises duplicate headers — remains unverified**, and is
now known to be *unverifiable from this repository's configuration*: the chart contains no
header-normalisation filter, and the spec forbids depending on Envoy for correctness anyway.
