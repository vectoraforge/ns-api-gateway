## Two premise corrections a later reader should inherit

1. **T-37.4-20's "high" severity rested on a false premise.** *(Plan `37.4-05`)* The plan, the prior executor and RESEARCH Pitfall 7 all asserted that striking the two attempt-id conjuncts from the lifecycle CHECK leaves a **tautology**. It does not. With A = `claimed_at IS NULL` and B = `consumed_at IS NULL`, the trimmed expression is `(A ∧ B) ∨ ¬A`, which reduces to `¬A ∨ B` — false exactly when `claimed_at IS NULL AND consumed_at IS NOT NULL`. `IS NULL` is two-valued in SQL, so no three-valued subtlety rescues the claim. The prescribed rewrite was correct anyway and was performed; the hazard is real (an unthinking trim leaves an unreadable four-term disjunction) but its severity was overstated. Recorded in the D-03 flagged-conflict entry so the incorrect claim is not inherited.

2. **RESEARCH assumption A5 is false in both directions.** *(Plan `37.4-06`)* A5 assumed no Envoy configuration ships in this repository. One does — `k8s/templates/security-policy.yaml`, a `SecurityPolicy` with a Firebase JWT provider bound to the app-routes and llm-routes `HTTPRoute`s. But it does **not** support the D-10 mitigation: **no header-normalisation filter ships anywhere in the chart**, so Envoy never normalised duplicate `Authorization` headers. `service.type` is `ClusterIP` with no `NetworkPolicy`, leaving an in-cluster caller able to reach the pod directly, and `SHARED-INVARIANTS.md:19` forbids depending on Envoy for correctness in the first place. **The mitigation is unverified and unverifiable from this repository**, and that is recorded under FOUND-01 rather than left as a comfortable assumption.
