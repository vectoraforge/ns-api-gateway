## Summary

This is a codebase-research phase, not a technology-research phase. Almost every question the planner
needs answered is answerable only by reading `src/nativespeaker/api/` at HEAD, which I did. Three
findings dominate everything else.

**First: the repository does not import at HEAD.** Commit `d466a4b` ("Various renames") moved
`api/database/` → `api/crud/` and renamed `ChallengeStore` → `ChallengesDB`, but left 13 modules
importing `nativespeaker.api.database.*` and 9 sites naming `ChallengeStore`. `pytest` aborts during
collection with 4 collection errors and 0 tests run; `python -c "import nativespeaker.api.app.main"`
raises `ModuleNotFoundError`. **No task in this phase can be verified until that is repaired**, and
repairing it must be Wave 0, task 1.

**Second: three of CONTEXT.md's decisions rest on premises that the installed code contradicts.**
D-10 states `HTTPBearer` answers 403 — in the installed FastAPI 0.135.1 it answers **401** with
`WWW-Authenticate: Bearer`, so no re-mapping is needed at all. D-10 states `BoundedReason`'s eight
members die — five of the eight belong to `jwt_verifier.py`, which this phase does not touch, and
deleting the enum breaks 30+ assertions in `test_jwt_security.py` (588 lines, not on any prune list).
D-14 states `tests/schema/` is left alone — `test_create_atomicity.py` and `test_create_race.py`
import `RequestContext`, `PreAuthIdentity`, `ChallengeStore`, `HmacKeyring` and `HmacConfig`
directly and cannot survive D-01/D-03/D-11 unedited. Each is reported below, not resolved.

**Third: the mechanism D-08 needs already exists in the repo, written and tested.**
`tests/unit/test_rejection_vocabulary.py:64-70` (`_family`) and `:78-94` (`_undeclared`) are exactly
the registry-free `__subclasses__()` walk D-08 asks for, complete with negative controls at
`:187-236`. Promote them to production `errors.py` rather than inventing a mechanism. And because
D-08 collapses both trees into **one module**, the classic `__subclasses__()` lazy-import hazard
disappears by construction: importing `errors` makes the walk total.

**Primary recommendation:** Wave 0 repairs the broken tree and re-baselines lint/typecheck; then run
the four fronts as three waves ordered by file collision, not by decision number — the error-tree
collapse (D-08/D-09) and the identity collapse (D-01/D-02/D-03) touch nearly the same file set and
must not run in parallel, while the quota seam (D-07) and the migration edits (D-03 col + D-11) are
genuinely independent of both.

## User Constraints (from 37.4-CONTEXT.md)

### Locked Decisions

**The identity types**

- **D-01: One `Identity` class replaces the union.**
  `Identity(user: User | None, identity: ExternalIdentity | None, issuer: str, subject: str)`,
  both object fields nullable together — unlinked means both `None`. It carries the
  `ExternalIdentity` row and not just the `User`, because the challenge binding keys on
  `bound_external_identity_id UUID REFERENCES core.external_identities (id)`
  (`migrations/20260818_01_initial-release.sql:379`) with a two-arm CHECK at `:407-411`. No
  schema change to that column. `IdentityKind` dies with the union it discriminated.
  `ChallengeStore.issue`/`verify_binding` stop branching on `isinstance` and read the nullable
  fields instead.

- **D-02: `get_identity` admits, `get_linked_identity` narrows.** `get_identity` returns the
  class and admits unlinked callers; `get_linked_identity` depends on it and raises when
  `user is None`. `POST /auth/challenge` and `POST /auth/create-user` declare `get_identity`;
  `chats`, `root` and `examples` declare `get_linked_identity` at router level. The narrowing
  survives the type split's removal — **reversibility:** a handler that reads `identity.user`
  without the narrowing dependency reads unlinked as linked, which is the hazard the two
  dataclasses existed to make unrepresentable. The router-level declaration is the replacement
  control.

- **D-03: `RequestContext` dies, field by field.**
  - `identity` → `get_identity()`.
  - `evaluated_at` → generated at the start of each endpoint that needs it.
  - `attempt_id` → **leaves the code path entirely, and the `claim_attempt_id` column goes with
    it.** Dropped from `tables/auth.py:76` and from the initial migration, edited in place with
    the dev/test database re-applied (the established v2.0 pattern; never an incremental
    migration). `consume`'s WHERE keys on `challenge_id` + `claimed_at IS NOT NULL` +
    `consumed_at IS NULL`. It reads like a compare-and-swap guard whose condition can never
    fail, because nothing anywhere un-claims a challenge. **Flagged conflict 1** against
    `02-create-user.md:65`, which mandates consumption "conditioned on still-claimed under this
    attempt's `claim_attempt_id`".
  - `route` → **gone, and not re-derived.** Neither the rejection handler nor the quota logs
    carry a route field; `RequestLoggingMiddleware` already binds `request_id`, `method` and
    `path` onto every line of a request via contextvars. **Accepted:** the middleware's `path`
    is the concrete URL, not the matched template, so telemetry label cardinality becomes
    unbounded (one series per `chat_id`). Correlate on `request_id`.

**Error distinctions — the withdrawn sweep**

- **D-04: Distinguishing between errors is kept.** `_reject_existing_identity` stays, and so
  does every similar function whose job is to decide which rejection was earned. The developer's
  rule: distinctions are fine as long as exceptions are what carry them. No plan removes a
  distinction on the grounds that it exists only to tell clients apart — except where D-06 and
  D-10 name a specific collapse.

- **D-05: `AccountUnavailable`'s `cause` string becomes two classes.** `HistoricalIdentity` and
  `BlockedUser`, both under one base that declares the single 403 **once**. The `cause` field
  dies — the class name carries it. Same shape as the five challenge rejections. Clients still
  cannot tell the two apart, which `SHARED-INVARIANTS.md:14` requires ("mutually
  indistinguishable").

**The create-user conflict path**

- **D-06: The `IntegrityError` arm collapses.** `_insert_account` and `_flush_account` merge
  into one function; the `begin_nested()` savepoint goes, since `create_user`'s own consume
  moves entirely to the route's `except` arm. The cause-chain walk for `constraint_name` and its
  three-way mapping collapse: **any `IntegrityError` from the insert becomes one already-linked
  exception.** Two consequences the developer accepted when choosing this:
  - `ProviderAccountAlreadyLinked` stops answering its own 403 `operation_not_allowed` and
    answers the already-linked 409 instead. **Flagged conflict 4.**
  - The unmapped-constraint 500 tripwire dies. A constraint rename or a new constraint reads as
    a benign 409 rather than surfacing. This was 37.3 D-03's explicitly preserved
    fail-loudly property and 37.3-REVIEW WR-12's subject; it is knowingly given up.
  The pre-check via `resolve_existing_identity` + `_reject_existing_identity` is untouched (D-04),
  so the common already-linked case still earns its distinct answer before the insert. Only the
  **race** path loses the distinction.

**The quota gate**

- **D-07: `QuotaGate` becomes a plain function the endpoint calls.** The class, the
  `on_admitted` callback wiring in `ChatService.ask_llm` (`services/chats.py:52-61`) and the
  resilience layer's `_AdmissionRejected` re-raise plumbing all go.
  - **Invariant to preserve:** the service's own validation rejections still precede the charge —
    unsupported language, chats limit, chat-not-found, messages limit. Nobody is billed for a
    request the service refuses on its own terms.
  - **Accepted regression:** queue-full (429) and circuit-open (503) become billable, because the
    charge no longer waits on admission.
  - **Left to planning:** the exact seam. An endpoint cannot literally interleave with `ask_llm`
    without splitting the service method or moving its validation outward; the planner picks the
    shape that satisfies the invariant above.

**One exception tree**

- **D-08: Collapse `ServiceError`, `AuthRejected`, `ErrorClass`, `REGISTRY` and `STATUS_TO_CLASS`
  into one tree, one handler.** Classes carry their own status and code. The registry module, the
  `ErrorClass` indirection and the two-tree split all go. Requirements that must survive the
  merge, drawn from both trees:
  - A class declaring no status still answers **500**. The default is a fail-closed control, not
    a convenience.
  - Where several classes deliberately share one client-visible answer — the five challenge
    rejections' one 409, and D-05's two account-unavailable classes' one 403 — that collapse is
    **declared once on a base and inherited, never restated per class.** It denies clients an
    enumeration oracle, and duplicated declarations drift apart.
  - The response body stays **exactly one field**, and an exception's message never reaches it.
    Several classes carry diagnostic detail (grant ids, tier ids, counts) that is server-side only.
  - **Per-class logging policy survives on both sides:** a service-layer failure decides its own
    level and whether it logs at all, with tracebacks on the 500-class failures; a rejection
    contributes structured per-exception fields and must never log anything secret it holds (the
    challenge handle above all).
  - **Response headers survive:** `Retry-After`, `WWW-Authenticate`, and the `Allow` header on a 405.
  - **Framework-raised errors still need mapped answers** — 404, 405, 422 — and an unmapped status
    must fail loudly rather than defaulting silently.
  - **The startup check survives with a new mechanism:** no two classes claim the same code, and
    the declared code vocabulary is exactly total. `assert_registry_total` walked the registry;
    without one it walks the tree.

- **D-09: The merged handler logs class-name-as-event.** `logger.warning(camel_to_snake(
  type(exc).__name__), **fields)` — `camel_to_snake` survives. The service-layer format loses:
  its message becomes a field rather than the event name, and `error_type` is redundant once the
  event *is* the class. One greppable name per outcome. **Risk the developer named:** external
  log queries or alerts referencing the losing format break. 37.3 recorded that no deployed
  dashboard keys on these event names, which bounds the exposure. Note the handler's `route`
  field does **not** survive — see D-03.

**Deleted machinery, each against a spec requirement**

- **D-10: `extract_bearer` is replaced by `fastapi.security.HTTPBearer`.** `auth/extract_bearer.py`
  dies, `BoundedReason`'s eight members die, and `tests/unit/test_wire_contract.py` (110) plus
  `tests/e2e/test_wire_contract.py` (107) die with them. **Flagged conflict 2** against
  `SHARED-INVARIANTS.md:18` and `:55`. What is given up, precisely:
  - `HTTPBearer` reads `request.headers.get("Authorization")`, which returns the **first** value
    and hides the rest — the resolution `:18` forbids by name ("never resolved by taking
    first/last"). Duplicate Authorization headers stop being a distinct rejection.
  - Comma-joined and line-folded values stop being distinctly rejected; they degrade to a
    signature failure.
  - `HTTPBearer` answers **403**; the contract requires **401 `auth_required`**. The planner must
    re-map it, not inherit it.
  - `InvalidExternalJwt` loses the `bounded_reason` field it carries today, and `:55`'s named
    reason vocabulary goes with it.
  The developer's position, recorded verbatim in spirit: *"I would rather sacrifice a requirement
  than bloat my code."*

- **D-11: `auth/hmac_keyring.py` is deleted entirely.** `preauth_subject_hash BYTEA` becomes
  `preauth_subject TEXT` plaintext, edited into the initial migration alongside D-03's
  `claim_attempt_id` drop. Going with it: `hmac_keyring.py` (118), `tests/unit/test_hmac_keys.py`
  (314), `HmacConfig`, the `config/config.yaml` `hmac:` block, the lifespan wiring and
  `app.state.hmac_keyring`, `ChallengeStore`'s keyring constructor dependency, both message
  prefixes, the key-version machinery and `warn_missing_older`. **Flagged conflict 3** against
  `02-create-user.md:49` ("raw subject never stored") and `SHARED-INVARIANTS.md:56`.
  **The finding that drove it:** `core.external_identities.subject` stores the same raw subject
  **permanently, in plaintext** (`tables/identities.py:47`), with `provider_uid` — the stable
  Google/Apple account UID — in plaintext beside it. The keyring protected that value for the
  300 seconds a challenge row lives, and cleared it on consume. 432 lines for a five-minute
  window on a value the schema keeps forever one table over.
  Two pieces were already dead on their own terms and go regardless: `idp_account_hash` and
  `IDP_ACCOUNT_PREFIX` (zero production consumers; the target table
  `core.access_grants_anti_abuse` has no model at all), and the key versioning, which
  `02-create-user.md:49` itself renders inert by storing **no** key version on the challenge row.
  `verify_binding`'s pre-auth arm becomes a plaintext comparison, and its cleared-verifier rule
  keys on `preauth_subject IS NULL` instead of a cleared hash.

```sql
    id UUID PRIMARY KEY,
```

### A. D-07's quota seam

**Recommendation: split each POST service method at the `ask_llm` boundary, and let the router
charge between the halves.** The cut already exists in the code.

### B. How status and code should be declared on classes (D-08)

**Recommendation: two class attributes on one base, with a startup check that they are declared
together.**

```python
class AppError(Exception):
    """Base for every failure that has a client-visible answer."""
    status: int = 500
    code: ErrorCode = "internal_error"
    log_level: int | None = None

    def extra_headers(self) -> dict[str, str] | None:
        return None

    def log_fields(self) -> dict[str, str | None]:
        return {}
```

- **A class declaring nothing answers 500** — D-08's fail-closed requirement, satisfied by the base
  defaults (today: `errors.py:215` and `exceptions.py:31`, both `INTERNAL_ERROR`).
- **A shared answer is declared once on a base and inherited** — the pattern already works in the
  repo. Verbatim `[VERIFIED: src/nativespeaker/api/auth/exceptions.py:180-215]`: `ChallengeRejected`
  declares `error_class = CHALLENGE_REQUIRED` at `:195` and its five leaves `ChallengeNotFound`

- **The `_undeclared` rule is what makes the 500 default a tripwire rather than a hiding place** —
  it requires a *strict ancestor below the root* to declare, so a leaf inheriting only the base's
  500 is reported. Promote it (see §C).

**Property being given up, which D-08 does not list.** Today `ErrorClass` is a frozen dataclass
(`errors.py:29-34`) and `errors.py:212` says: *"One `error_class` per subclass, so a status and a
code can never be named in disagreement."* Splitting into two attributes makes

```python
    return JSONResponse(status_code=exc.status,
                        content=ErrorResponse(code=exc.code).model_dump(),
                        headers=exc.extra_headers())
```
Note the semantic merge the planner must decide deliberately: today service errors log only when
`log_level is not None` (`error_handlers.py:39`, and `TransientLLMError`/`PermanentLLMError` at
`errors.py:242,247` set it back to `None` specifically to stay silent), while every rejection logs
unconditionally at WARNING (`error_handlers.py:50`). Merging means the rejection classes must each
carry `log_level = logging.WARNING` explicitly, or the base must default to WARNING and the two LLM
classes keep their explicit `None`. **Recommend the latter**: base `log_level = logging.WARNING`,
`None` where silence is deliberate, `logging.ERROR` where a traceback is owed. It preserves both
existing behaviours with the fewest declarations.

37.3-REVIEW **WR-03** ("the handler splats `log_fields()` into a call that already binds `route`")
is fixed for free here, because `route` goes with D-03.

### Anti-patterns to avoid

- **Do not reintroduce a dict keyed by status.** D-08 deletes `STATUS_TO_CLASS`; a `dict` built by
  the tree walk *at check time* is fine, a module-level literal is the registry again.
- **Do not make the merged handler branch on `isinstance` over two shapes.** That is the two-tree
  split wearing a handler's clothes.
- **Do not let the migration's lifecycle CHECK become vacuous.** See §5.
- **Do not delete `BoundedReason`.** See Correction 3.
- **Do not treat `ruff`/`ty` as currently clean.** See Finding 0d.
- **Do not write a trailing "apply D-12 everywhere" plan.** Per-file, inside the task that already
  rewrites the file.

## Common pitfalls

### Pitfall 1: expired ORM attributes read inside the handler
**What goes wrong:** a rollback on the way out of a request expires an ORM instance's attributes; the
handler's read of one attempts I/O outside a greenlet; the handler itself raises; the client gets 500
where 409 was owed. **Documented in-repo** at `auth/exceptions.py:36-41` and `routers/auth.py:89-92`.
**How to avoid:** every value an exception carries into a log line stays a plain scalar — `str`,
`UUID`, `None` — never a SQLModel row. D-05's two new classes carry *nothing*, so they are safe by
construction; the merged handler must keep the same rule. 37.3-REVIEW **WR-05** notes the scalar-only
invariant is currently tested for only 8 of 13 raisable classes; the rebuilt vocabulary test should
close that.

### Pitfall 2: the challenge handle leaking into a log
`crud/challenges.py:1` — "this module holds no logger, so none is logged." `routers/auth.py:161` and
`create_user.py:61` log `challenge_row_id=str(challenge.id)` — the **internal** id, never
`challenge_id`. `exceptions.py:190-192` records that none of the five challenge classes has an
`__init__`, *specifically* so none can be handed the handle. **The merged handler must not become a
place where a new field slips in.** `SHARED-INVARIANTS.md:57` forbids the public `challenge_id` in
`details` and says to correlate by internal row id.

### Pitfall 3: `expire_on_commit=False` is load-bearing across the post-claim boundary
`lifespan.py:45-46` sets it. `routers/auth.py:119` commits the claim, then `:127-136` and `:142-143`
read `challenge.challenge_id` and `identity.issuer/subject` off already-committed instances. This is
37.3-REVIEW **WR-06** (undocumented dependency). D-06 removes the savepoint and moves the consume
entirely to the route's `except` arm, which *touches these exact lines* — so WR-06 is in scope for a
fix-in-place, and the planner should have the D-06 task add the one-line comment (D-12 permits a
comment that "resolves a genuine ambiguity" about the lines below it).

### Pitfall 4: the FastAPI dependency cache
`dependencies.py:65` — "Declared, never called directly: FastAPI's cache only sees solver-resolved
deps, so a direct call re-verifies." `get_linked_identity` must keep declaring
`Depends(get_identity)` as a default rather than calling `get_identity()`. `test_app_wiring.py:77`
(`test_one_verify_and_one_query_for_a_doubly_declared_route`) and
`test_identity_accessors.py:276` (`test_the_declaration_resolves_once`) both pin this. Also
`dependencies.py:75` — `get_chat_service` must stay defined *below* the accessors, because its
`Depends()` default is evaluated at definition time.

### Pitfall 5: `run_in_threadpool` around `verify`
`dependencies.py:47-48`: "`verify` is synchronous and can block on a JWKS fetch, so it never runs on
the event loop." When `get_request_context` becomes `get_identity`, this must survive verbatim.

### Pitfall 6: `resolve_identity`'s positive tests
`resolve_identity.py:35` — "Positive tests, so a NULL or any future enum member fails closed on these
same two branches." `identity.identity_state != IdentityState.active` and `user.active is not True`
must stay in that polarity when D-05 substitutes the exception classes. Inverting either to a
negative test opens a fail-open path.

### Pitfall 7: a vacuous CHECK after the column drop
See §5. Reducing the lifecycle CHECK's second arm to `(claimed_at IS NOT NULL)` makes the whole CHECK
a tautology. `tests/schema/test_constraints.py:599` currently proves the CHECK bites; if the
constraint becomes vacuous nothing proves anything, and the test that would have caught it is the one
being edited.

### Pitfall 8: the schema suite uses a scratch database, the e2e suite uses the dev one
`tests/schema/conftest.py:87-101` creates and applies its own database per session, so schema tests
pick up a migration edit automatically. `tests/e2e/conftest.py:35-38` loads `EnvironmentConfig` and
runs against the real dev database, which must be re-applied manually. A green schema suite therefore
does **not** imply the dev database matches the file.
