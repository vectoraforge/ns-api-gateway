# Phase 37.4: Code Review Report

**Reviewed:** 2026-08-30
**Depth:** standard
**Files Reviewed:** 47
**Status:** issues_found

## Summary

The refactor's *control flow* holds up under attack. I traced every guard the phase brief
warned about and could not break them:

- `identity.identity is not None` / `identity.user is None` are not vacuous — `resolve_identity`
  produces exactly two shapes and both branches are reachable (`auth/identity.py:36-51`).
- Handle replay is not reachable. The claim commits before the provider call, and every later
  re-presentation (claimed-not-consumed, consumed preauth, consumed bound) funnels to
  `ChallengeConsumed` via `claim() -> False -> refresh -> claimed_at is not None`.
- The savepoint removal is survivable: `challenge_row_id` is captured *before*
  `session.rollback()` (`routers/auth.py:124`), and nothing on the rollback path reads an
  attribute off the expired instance. `expire_on_commit=False` makes the read at line 124 legal.
- `test_app_wiring.py` genuinely enforces `Depends(get_linked_identity)` on every route outside
  the two literal exemption sets, and the `__wrapped__` control is real.

The defects are elsewhere, and two of them are the exact "green suite, broken artifact" shape:
a **schema migration edited in place** that no deployed database will ever converge to, and a
**`WWW-Authenticate` header that only a dead class emits** while a test asserts it by raising
that dead class directly.

## Critical Issues

### CR-01: An applied migration was edited in place — deployed databases will never get `preauth_subject`

**File:** `migrations/20260818_01_initial-release.sql:373-410`
**Issue:** `20260818_01_initial-release.sql` was mutated, not superseded. Within one file the phase
renamed `preauth_subject_hash BYTEA` to `preauth_subject TEXT`, dropped `claim_attempt_id UUID`,
and rewrote two `CHECK` constraints. The runner is `pogo-migrate` (`pyproject.toml:37`, `:72`),
which records applied migrations **by id (filename) with no content checksum**. The filename is
unchanged, so on any database where the original was already applied the runner reports
"nothing to apply" and the edit is silently discarded.

The resulting divergence is not benign. `AuthChallenge` (`tables/auth.py:71`) maps
`preauth_subject`, and `ChallengesDB.issue` (`crud/challenges.py:49-56`) INSERTs it on every
`POST /auth/challenge` for an unlinked caller — the *only* path that route serves. Against a
pre-edit schema every such request fails with `UndefinedColumnError` (a 500), and
`ChallengesDB.consume`'s `.values(consumed_at=now, preauth_subject=None)` fails the same way.
The surviving `claim_attempt_id UUID` also still carries the old lifecycle `CHECK`
(`claimed_at IS NOT NULL AND claim_attempt_id IS NOT NULL`), which the new `claim()` — which no
longer writes `claim_attempt_id` — violates on every claim.

Tests do not catch this: `tests/schema/` and `tests/e2e/` build the schema from scratch, so they
only ever see the post-edit DDL.

**Fix:** Leave `20260818_01_initial-release.sql` at its committed content and add a forward
migration:

```sql
-- migrations/20260830_01_challenge-preauth-subject-plaintext.sql
-- depends: 20260818_01_initial-release

-- migrate: apply
ALTER TABLE core.auth_challenges
    DROP CONSTRAINT auth_challenges_check,          -- the claim_attempt_id lifecycle CHECK
    DROP CONSTRAINT auth_challenges_check2,         -- the preauth-pair CHECK (confirm names via \d+)
    DROP COLUMN claim_attempt_id,
    DROP COLUMN preauth_subject_hash,
    ADD COLUMN preauth_subject TEXT,
    ADD CHECK (consumed_at IS NULL OR claimed_at IS NOT NULL),
    ADD CHECK (
        (bound_external_identity_id IS NOT NULL
            AND preauth_issuer IS NULL AND preauth_subject IS NULL)
        OR
        (bound_external_identity_id IS NULL
            AND preauth_issuer IS NOT NULL
            AND (preauth_subject IS NOT NULL OR consumed_at IS NOT NULL))
    );
-- Outstanding challenges cannot survive the retype; they expire in 300s regardless.
DELETE FROM core.auth_challenges WHERE consumed_at IS NULL;

-- migrate: rollback
```

If the intent really is "no database has ever applied this file", say so in the file header and
add a CI check that fails when a migration whose id is already in `_pogo_migration` changes
content. Do not leave it implicit.

### CR-02: No real 401 carries `WWW-Authenticate`; the only class that emits it is unreachable

**File:** `src/nativespeaker/api/errors.py:269-274`, `src/nativespeaker/api/errors.py:375-386`
**Issue:** `AuthenticationError` is the sole class in the tree that overrides `extra_headers()`
to return `{"WWW-Authenticate": "Bearer"}`. It is **never raised anywhere in `src/`** — grep
confirms zero production raise sites; its last caller (`get_quota_gate`) was deleted with
`RequestContext` in this phase.

Every 401 the service actually emits comes from either:
- `InvalidExternalJwt` (`errors.py:375`) — raised at `app/dependencies.py:41` and `:47` for a
  missing, malformed, or unverifiable credential — which defines no `extra_headers()`, so
  `AppError.extra_headers()` returns `self._headers`, i.e. `None`; or
- `UserNotFound` (`errors.py:446`), same situation; or
- `AuthRequired` via `http_exception_handler` (`app/error_handlers.py:63`), constructed with
  `headers=getattr(exc, "headers", None)` — also `None` in practice.

So `app_error_handler`'s `headers=exc.extra_headers()` (`error_handlers.py:46`) sends nothing.
RFC 9110 §11.6.1 makes the field mandatory on 401, and clients that key off it (any standard
HTTP auth library, and Envoy's ext_authz consumers) get no challenge.

The suite hides this. `test_exception_handlers.py:533` asserts the header — but only against
`/raise/missing_token`, whose route raises `AuthenticationError("Missing Bearer token")`
(`test_exception_handlers.py:40`) directly. It exercises the dead class, not the live path.
`test_auth_security.py:64-127` walks six real 401 paths and asserts only `status_code == 401` —
no header assertion on any of them.

**Fix:** Move the header onto the class that actually answers, and delete the unreachable one.

```python
# errors.py
class AuthRequired(AppError):
    """The generic 401: no usable credential accompanied the request."""
    status = 401
    code = "auth_required"
    log_level = None
    answers_framework_status = True

    def extra_headers(self) -> dict[str, str]:
        # RFC 9110 11.6.1: a 401 must name the scheme it will accept.
        return {**(self._headers or {}), "WWW-Authenticate": "Bearer"}


class InvalidExternalJwt(AppError):
    status = 401
    code = "auth_required"

    def extra_headers(self) -> dict[str, str]:
        return {"WWW-Authenticate": "Bearer"}
    ...


class UserNotFound(ProviderLookupError):
    status = 401
    code = "auth_required"

    def extra_headers(self) -> dict[str, str]:
        return {"WWW-Authenticate": "Bearer"}
```

Then delete `AuthenticationError` and move the assertion into `test_auth_security.py` so it runs
against a real missing-token request:

```python
def test_a_missing_credential_names_the_scheme(self, client):
    response = client.get("/chats")
    assert response.status_code == 401
    assert response.headers["www-authenticate"] == "Bearer"
```

## Warnings

### WR-01: Quota is now charged before the resilience gate — queue-full and circuit-open 503s bill the user

**File:** `src/nativespeaker/api/services/chats.py:93`, `:117`; `src/nativespeaker/api/quota.py:62-65`
**Issue:** The `on_admitted` seam was removed from `ResiliencePolicy.ainvoke` and
`LLMExecutionGate.run`, and `charge_quota` now runs *before* `ask_llm`. Both local admission
rejections fire strictly after the charge has committed in its own session:
`CircuitBreaker.before_call()` raises `CircuitOpenError` at `resilience.py:57`, and
`_inflight_slot` raises `QueueFullError` at `resilience.py:87` — both inside `attempt()`, which
`ask_llm` only reaches at `chats.py:94`/`:118`.

I acknowledge this is recorded as accepted (`test_quota_seam.py:333` —
`TestTheAcceptedRegression`, "D-07 sanctions this explicitly"). Three things about it are still
defects, not decisions:

1. `quota.py:63` still states the opposite invariant verbatim: *"Raised before the increment: a
   request the service refused must never be charged."* The code now refuses requests it has
   already charged. A comment that contradicts shipped behaviour is worse than no comment.
2. The module docstring excuses only *"A failed provider call is not refunded"*. Circuit-open and
   queue-full are **not provider calls** — `llm.calls` is incremented but `_answer` never runs.
   The docstring does not cover the case the code now produces.
3. Only the circuit-open half is tested. `QueueFullError` bills identically and has no test.

Blast radius: with `circuit_breaker_reset_seconds: 60` (`config/config.yaml:15`) and a 50-request
monthly allowance (`chats_limit: 50`), a single provider outage drains real allowance from a
paying subscriber for requests that never left the process, and there is no refund path.

**Fix:** Either restore the ordering, or make the accepted behaviour honest. To restore it, move
the charge behind admission without reintroducing the callback plumbing — charge inside
`ask_llm` after the gate admits:

```python
# resilience.py
async def ainvoke(self, operation, *, on_admitted=None) -> Any:
    ...
    async def timed_op():
        if on_admitted is not None:
            await on_admitted()          # slot + semaphore held, breaker already consulted
        return await asyncio.wait_for(operation(), timeout=self._timeout_seconds)
```

If the regression stays, at minimum rewrite `quota.py:2` and `:63` to say what actually happens,
and add the missing `QueueFullError` case to `TestTheAcceptedRegression`.

### WR-02: Lifespan startup leaks process-global Firebase apps and the engine when a later step raises

**File:** `src/nativespeaker/api/app/lifespan.py:35-46`, `:56-60`
**Issue:** `build_admin_apps` registers named apps in `firebase_admin`'s **process-global**
registry (line 35), then `create_async_engine` opens a pool (line 38), then `JWTVerifier(...)`
runs `self._jwks_client.get_signing_keys()` (`jwt_verifier.py:105`), a blocking network fetch
that raises `PyJWKClientError` when the JWKS endpoint is unreachable.

None of the setup is in a `try/finally`. If the JWKS fetch (or `LLMService(...)` at line 48)
raises, `db_engine.dispose()` and the `firebase_admin.delete_app` loop at lines 56-60 never run.
The comment at line 58 explicitly names the hazard — *"firebase_admin registers named apps
process-globally and raises on a repeat, so a second boot needs these gone"* — and then does not
guard against it. A second lifespan in the same process (test harness, or any in-process retry)
raises `ValueError: The default Firebase app already exists` from `initialize_app`, and the
original engine's connections are never returned.

Secondarily, the blocking JWKS fetch runs on the event loop during startup and is bounded only
by `fetch_timeout_seconds=3.0`.

**Fix:**

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    ...
    firebase_apps: dict[str, firebase_admin.App] = {}
    db_engine = None
    try:
        firebase_apps = build_admin_apps(config)
        app.state.firebase_adapter = FirebaseAdminLookup(firebase_apps)
        db_engine = create_async_engine(...)
        ...
        yield
    finally:
        if db_engine is not None:
            await db_engine.dispose()
        for firebase_app in firebase_apps.values():
            firebase_admin.delete_app(firebase_app)
        logger.info("shutdown")
```

### WR-05: `get_identity` returns ORM instances that are detached before the handler runs

**File:** `src/nativespeaker/api/app/dependencies.py:50-54`
**Issue:** `resolve_identity` loads `User` and `ExternalIdentity` inside
`async with request.app.state.session_factory() as session:` and the `Identity` holding them
escapes the block. `AsyncSession.__aexit__` closes the session, which `expunge_all()`s both rows;
they reach `routers/chats.py:25` etc. as **detached** instances.

It works today only because every consumer reads an already-loaded scalar (`identity.user.id`,
`identity.identity.id`) and neither `User` nor `ExternalIdentity` declares a `Relationship`. The
moment either becomes true — a `Relationship`, a `deferred()` column, or any code path that
triggers a refresh — the access raises `MissingGreenlet`/`DetachedInstanceError` inside the
handler and the caller gets a 500 where a 200 was owed. This is precisely the failure shape the
phase brief flags, one dependency edit away from firing.

**Fix:** Return only the values the callers need, so nothing session-bound leaves the block:

```python
@dataclass(frozen=True, slots=True)
class Identity:
    issuer: str
    subject: str
    user_id: UUID | None = None
    identity_id: UUID | None = None
    is_linked: bool = False
```

If the row objects must stay, `session.expunge_all()` before exiting is not enough — assert the
contract instead, e.g. a test that adds a `Relationship` to `User` in a subprocess and proves the
handler still answers 200.

### WR-06: The challenge-consume failure path discards every diagnostic except the exception's class name

**File:** `src/nativespeaker/api/routers/auth.py:144-147`
**Issue:**

```python
except Exception as failure:
    logger.error("challenge_consume_failed", challenge_row_id=challenge_row_id,
                 failure=type(failure).__name__)
```

No message, no `exc_info`, no traceback. This is the arm that fires when the service could not

an operator gets is `failure="OperationalError"`, which distinguishes nothing: a connection drop,

secret — the handle appears in the statement's bound parameters only if SQLAlchemy echo is on,
and `logs.py:53` already pins `sqlalchemy.engine` to WARNING.

### WR-07: LLM provider failures produce no log record at all

**File:** `src/nativespeaker/api/errors.py:296-307`, `src/nativespeaker/api/app/error_handlers.py:38-43`
**Issue:** `TransientLLMError` and `PermanentLLMError` both set `log_level = None`, so
`app_error_handler`'s logging block is skipped entirely. The provider's own error text is
captured into the message at `resilience.py:144-145` (`TransientLLMError(str(e))`) — and the new
`app_error_handler` no longer logs `str(exc)` at all (the old `service_error_handler` did:
`logger.log(level, str(exc), error_type=...)`). `log_fields()` returns `{}` for both classes.

Net result: when the LLM provider fails, every trace of *why* is destroyed. The only surviving
signal is the middleware's `request status_code=503` line (`logs.py:74`), which names no cause.
Debugging a provider incident is impossible from logs.

**Fix:** Give the two classes a level and a field, or reinstate the message:

```python
class TransientLLMError(AnalysisError):
    status = 503
    code = "service_unavailable"
    log_level = logging.WARNING   # exc_info stays False; __cause__ text arrives via log_fields

    def log_fields(self) -> dict[str, str | None]:
        return {"provider_error": str(self.__cause__) if self.__cause__ else None}
```

Apply the same to `PermanentLLMError` at `logging.ERROR`.

### WR-08: `IdentityUnresolvable` is a data-integrity 500 logged at WARNING with nothing identifying the row

**File:** `src/nativespeaker/api/errors.py:395-399`, `src/nativespeaker/api/auth/identity.py:43-45`
**Issue:** An `ExternalIdentity` whose `user_id` resolves to no `User` is a broken foreign key —
the same class of invariant break as `MissingUsageRowError`, `UnknownTierError` and
`MultipleEffectiveGrantsError`, all of which declare `log_level = logging.ERROR` and carry the
offending id in their message. `IdentityUnresolvable` declares neither: it inherits
`AppError.log_level = logging.WARNING`, so `exc_info` is `False` (`error_handlers.py:43`), and it
overrides no `log_fields()`. The operator gets `identity_unresolvable` and nothing else — not the
issuer, not the subject, not the identity row id — while the caller gets a 500.

**Fix:**

```python
class IdentityUnresolvable(AppError):
    """An identity row whose `user_id` resolves to nothing, read fail-closed."""
    status = 500
    code = "internal_error"
    log_level = logging.ERROR

    def __init__(self, *, identity_id: UUID, user_id: UUID) -> None:
        self.identity_id = identity_id
        self.user_id = user_id
        super().__init__(f"identity {identity_id} references missing user {user_id}")

    def log_fields(self) -> dict[str, str | None]:
        return {"identity_id": str(self.identity_id), "user_id": str(self.user_id)}
```

and at `identity.py:45`: `raise IdentityUnresolvable(identity_id=identity.id, user_id=identity.user_id)`.
Note both are scalars already loaded on the instance, so this stays greenlet-safe on the rollback path.

### WR-09: A permanently invalid uid burns the whole retry budget and answers a retryable 503

**File:** `src/nativespeaker/api/auth/firebase.py:93-96`
**Issue:** `auth.get_user` raises `ValueError` for a *permanently* invalid input — an empty uid,
one over 128 characters, or a `provider_data` entry with an empty `rawId`. The handler classifies
every `ValueError` as `RetryableLookupError`, so `lookup_with_retry` spends all three attempts
(`FIREBASE_LOOKUP_ATTEMPTS = 3`) on a condition that cannot change, then `_exhausted` answers
`Unavailable` → 503 `verification_temporarily_unavailable`. The client is told to retry something
that will never succeed, and each attempt is a real round trip to Google.

The docstring calls this *"malformed or indeterminate ... retryable rather than definitive"* —
"indeterminate" is defensible for a malformed *response*, but not for an invalid *request*, which
is the strictly larger set `ValueError` covers here.

**Fix:** Split the two. `get_user` validates its argument before any I/O, so an argument-shaped
`ValueError` is definitive:

```python
        except auth.UserNotFoundError:
            logger.info("firebase_get_user_not_found")
            raise UserNotFound(stage="provider_lookup") from None
        except ValueError as error:
            if not entries_started:   # raised before the call: an invalid uid, not a bad response
                logger.warning("firebase_invalid_subject")
                raise NotLinked(stage="provider_lookup", cause="invalid-shape") from None
            logger.warning("firebase_provider_data_malformed", detail=str(error))
            raise RetryableLookupError(str(error)) from error
```

Simplest correct form: validate `subject` against Firebase's uid rules (1-128 chars) in
`get_user_provider_data` before dispatching to the threadpool, and keep the `ValueError` arm for
response-shape failures only.
