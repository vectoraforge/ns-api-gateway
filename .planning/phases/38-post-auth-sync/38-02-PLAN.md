reader finds it rather than discovering it.** `specs/auth-refactor-phases/03-sync.md` says
`monthly_used` is `0` whether the usage row is missing or names an earlier period, and that only two
failures are tripwires. This phase instead fails closed on a missing usage row and on a missing tier
row, exactly where `services/quota.py::charge` fails closed, because ROADMAP success criterion 1

stale-period half of the brief's sentence IS honoured — a usage row naming an earlier period reports
`0`. Only the missing-row half diverges. The zero-grant case is unaffected and reports the
no-grant defaults. No new error class is added.
</deliberate_divergence>

  <action>
Apply the same rule `QuotaService.charge` applies for a usage row naming an earlier period — that the
count for the current period is zero — but as a pure read. Quota resolves this by assigning zero to
the loaded row's used counter and the current period to its period field, inside the transaction it
is about to commit. Sync must produce the same value while leaving the loaded row untouched: select
between the stored count and zero by comparing the row's stored period against the derived period,
and use the result to build the response.

This is the single highest-risk line in the phase. `get_db` ends the request session on exit, so a
dirty attribute on a loaded row here would silently persist a rollover from a strictly read-only
endpoint and break ROADMAP success criterion 3. Copying quota's two assignment lines is the failure
mode; the branch must produce a value, not a state change.

Add a test class that is the explicit mirror of `test_quota_resolver.py`'s rollover class: same
seeded stale-period fixture, opposite assertions — the reported value is zero, the row's stored
period and stored count are both unchanged, nothing was added, and the session was not committed.
Add the companion current-period case asserting the stored count is reported as it stands.
  </action>
