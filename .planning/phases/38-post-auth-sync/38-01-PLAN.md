**`services/sync.py` — new file, `SyncService`.**
Constructed with the request session and one captured instant only: `__init__(self, db: AsyncSession,
evaluated_at: datetime)` assigning `self.session = db`, `self.grants_db = GrantsDB(db)` and
`self.evaluated_at` with the repository's one-line captured-instant comment. It deliberately does not
take `challenge_store` or `adapter`: a read-only sync reads neither, and putting this on
`AuthService` would drag a Firebase adapter into a route that never calls one.
One method, `read_entitlement(self, user_id: UUID) -> Entitlement`, following `QuotaService.charge`
read for read: `read_effective_grants(user_id, self.evaluated_at)`, then the single grant's
`read_usage(grant.id)`, then `monthly_credits(grant.tier_id)`; the period is
`self.evaluated_at.strftime("%Y-%m")` and that is the only place `current_period` comes from.
For this task implement the happy path only — exactly one effective grant whose usage row exists and
whose `monthly_period` already equals the period, and whose tier row exists. Return
`Entitlement(type=EntitlementType(grant.source.value), status=EntitlementStatus.active,
tier_id=grant.tier_id, monthly_credits=<the tier value>, current_period=period,
monthly_used=usage.monthly_used)`. The zero-grant answer, the stale-period rule and the three
fail-closed tripwires are plan 38-02's work and are not written here.
The service is strictly read-only and opens no transaction boundary of its own: it assigns no
attribute on any loaded row, adds nothing to the session, and ends no transaction. `get_db` ends the
request session on exit, so a dirty object here would silently persist — that is the single
highest-risk line in this phase.
It emits no structured-log event of any kind and imports no logging library (D-02): the request
middleware already writes one line per attempt, and the error classes already write their own.
