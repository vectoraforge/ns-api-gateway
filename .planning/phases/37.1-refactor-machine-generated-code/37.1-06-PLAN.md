## Pinned definitions

A **multi-line comment block is a run of two or more consecutive own-line comment lines** — the threshold for this phase is two, not three. A surviving note must fit one line within the 120-character limit.

**For Python test files**, the three commands used verbatim in the acceptance criteria — **the measurement command**, **the AST-equality check**, and **the cross-reference grep** — are written out in full in the `<objective>` of `.planning/phases/37.1-refactor-machine-generated-code/37.1-03-PLAN.md`. Read that section and use them exactly as written.

**No prose-ratio cap applies to test files.** A one-line docstring naming what a case proves is exactly what D-14 asks for, and a test module can legitimately carry one per test. The criteria for tests are `multiline_docstrings=0` and `comment_blocks=0`, nothing more.

**For the migration**, use the SQL analogue — the **stripped-SQL equality check**:

```
.venv/bin/python -c "
import subprocess
p='migrations/20260818_01_initial-release.sql'
def strip(s): return [l.rstrip() for l in s.splitlines() if l.strip() and not l.strip().startswith('--')]
old=subprocess.run(['git','show','HEAD:'+p],capture_output=True,text=True).stdout
print('SAME' if strip(old)==strip(open(p).read()) else 'CHANGED')
"
```

The anti-pattern is a docstring that explains which spec step required the case, argues for the choice of fixture, or narrates the phase in which it was written.
