# Phase 37.1 Plan 02: Replace the auth barrier with FastAPI dependencies Summary

Admission moved from a pure-ASGI middleware plus a parallel route registry into
`get_request_context`, declared on every non-public `APIRouter` and again on each endpoint — 514
lines of source and 380 lines of registry tests deleted, with every admission-matrix expectation
carried across **unedited**.

## The framework assumption, verified rather than assumed

The plan named one load-bearing assumption and told the executor to re-verify it against a real
request. It holds. Driven through the **real app** with a stubbed verifier and session:

| Request | `route` |
|---|---|
| `GET /` | `/` |
| `GET /chats/0199a0d0-…` | `/chats/{chat_id}` |
| `POST /auth/create-user` | `/auth/create-user` |

FastAPI sets the matched route inside `APIRoute.matches`, which runs before any dependency
resolves, so `request.scope["route"].path` is the declared **path template** — never the concrete
path a caller sent. That is exactly what the middleware position denied the barrier and why
`barrier.py::_match_full` existed; the function was deleted outright rather than moved. The
parameterised case is now a permanent test
(`test_app_wiring.py::TestTheAuthDependencyIsResolvedOncePerRequest` asserts
`route == "/chats/{chat_id}"`, and `test_identity_accessors.py` asserts the static form).

This matters beyond tidiness: `route` feeds `record_rejection(route=...)` and `QuotaGate(route=...)`,
and a concrete path would put an unbounded set of client-chosen values into a log field and a
quota key.

## The bug the plan's own probe caught

**The plan's stated shape for the narrowing accessors ran the entire admission path twice.**

PATTERNS §3.2 and the plan both specified `get_linked_identity` as a thin wrapper doing
`identity = (await get_request_context(request)).identity`. Written that way and measured, a single
request to a `/chats` route produced **2 JWT verifies and 2 identity queries**.

The cause: FastAPI's per-request cache lives in the *dependency solver*. It only sees a dependency
the solver resolved, and a direct function call inside a body is invisible to it. A `/chats` route
declares `get_linked_identity` (router level, and again in the signature — correctly cached to one
execution) **and**, through `get_chat_service`, `Depends(get_request_context)`. So the solver ran
`get_request_context` once, and `get_linked_identity`'s direct call ran it a second time.

The fix is to declare rather than call:

```python
async def get_linked_identity(
        context: RequestContext = Depends(get_request_context)) -> LinkedIdentity:
```

Both counts became 1. This is T-37.1-11 exactly, and it would have shipped silently: the responses
were correct throughout, and the only symptom was double work — a second JWT verification and a
second database round trip on every authenticated request.

Two things follow, both kept:
- the accessors no longer take `Request` at all, so they cannot reach app state — a *stronger*
  form of the no-provisioning property than the one this plan had to give up;
- `test_app_wiring.py::TestTheAuthDependencyIsResolvedOncePerRequest` counts verifies and queries,
  so no wrapper of any shape can reintroduce it.

## The `auth_router` departure from D-08's table — recorded as the plan requires

D-08's table names `Depends(get_preauth_identity)` for `auth_router`. **It carries
`Depends(get_request_context)` instead.**

`get_preauth_identity` raises on a *linked* caller. For every other handler that is right — a
linked context arriving at a pre-auth-only handler is a wiring bug. On `POST /auth/create-user` it
is a **client condition** that §02 prepare step 1 names explicitly: a caller who already has an
account is owed `identity_already_linked` (409), not `auth_required` (401), and the two say
incompatible things to a client. 37-07 pinned this; declaring the narrowing accessor would make the
409 unreachable.

What D-07 is actually buying is unaffected. The router-level declaration still makes authentication
default-on for that router: the token is verified and the identity resolved before any handler in it
runs. The only thing this route decides for itself is what to do with the variant that came back.

The same reasoning is why `get_request_context` resolves with `allow_preauth=True` on **every**
route and lets `get_linked_identity` do the narrowing, rather than varying resolution per route:
one cached inner dependency for both accessors, and the create-user route can still read the
variant.

`get_preauth_identity` is kept though nothing declares it — phases 40/41/42 register
challenge-bearing routes that do want the narrowing. Its docstring now says so.

## Rejection delivery — `AuthRejectionError`

The barrier *returned* `error_response(...)` because `add_middleware` places user middleware
outside Starlette's `ExceptionMiddleware`. A dependency runs inside it, so the dependency raises.

One subclass, not three, carrying a **per-instance** `error_class` that shadows
`ServiceError`'s class attribute — admission rejects with three different classes
(`auth_required` 401, `preauth_identity_not_allowed` 403, `account_unavailable` 403) and the
`ErrorClass` is already a value rather than a type. Two deliberate non-features, both of which keep
the wire response byte-identical:

- **`log_level = None`.** `record_rejection` has already emitted `auth_rejected` by the time the
  raise happens; inheriting `AuthenticationError`'s `WARNING` would double-log every rejection.
- **`extra_headers` is not overridden.** `AuthenticationError` adds `WWW-Authenticate: Bearer`. The
  barrier's 401 never carried that header, so reusing it would be a wire change D-10 forbids.

## The enumeration assertion's structural replacement

`assert_route_enumeration`'s conditions 1-2 were set equality between the live router and a
parallel table. The whole failure class was that table drifting from what serves traffic.
`test_app_wiring.py::TestEveryRouteIsAuthenticated` asserts the property directly over
`app.routes`: every `APIRoute` except `/health/ready` and `/auth/create-user` must declare
`get_linked_identity`, create-user must declare `get_request_context`, and the public allowlist
must be exactly `{/health/ready}`. There is no second table left to disagree with.

**Both new structural assertions were negative-controlled** rather than accepted green:

| Injected regression | Result |
|---|---|
| an extra router with an undeclared `/leaked` route | `missing == ['/leaked']` — fails |
| a `functools.wraps` wrapper around `get_linked_identity` | `offenders == ['/wrapped']` — fails |

## Environment note (no repository change)

The worktree has no `.venv` and the main checkout's editable install `.pth` hard-points at the
**main checkout's** `src`. Worse than plan 01 recorded: `nativespeaker.api` and
`nativespeaker.api.app` are **namespace** packages whose `__path__` spans both trees, so a module
deleted in the worktree could silently resolve from the main checkout. `nativespeaker.api.auth` is
a regular package (single-element `__path__`), which is why deleting `auth/barrier.py` and
`auth/registry.py` was safe — confirmed by `import nativespeaker.api.auth.barrier` raising
`ModuleNotFoundError` rather than falling through. Resolved by symlinking `.venv`/`.env` and
exporting `PYTHONPATH=$PWD/src`; neither symlink was ever staged.
