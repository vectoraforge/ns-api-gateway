## Summary

The barrier-to-dependency migration is structurally sound on the two questions that mattered most.
**Route coverage is complete** — all nine registered routes are `APIRoute`s, `/`, `/chats*` and
`/examples` carry `Depends(get_linked_identity)` at router level, `/auth/create-user` carries
`Depends(get_request_context)`, and `/health/ready` is the only route with neither (verified by
enumerating `app.routes` on the real app). **The dependency cache is intact** — no production call
site invokes `get_request_context`, `get_linked_identity` or `get_preauth_identity` as a plain
function; `get_quota_gate` takes the already-resolved context as an explicit parameter.
`AuthRejectionError` is a `ServiceError`, dependencies run inside Starlette's `ExceptionMiddleware`,
and every acceptance failure still produces the registry's shared body. The migration removes
`audit.auth_events`, its four indexes and `core.auth_event_result` without disturbing
`audit.subscription_events`, the `audit` schema, `core.auth_operation`, or any surviving
constraint; the rollback block is unchanged and still correct.

Two defects are serious enough to block.

The first is a **real, uncovered inversion of the phase's central invariant**: with the barrier gone,
FastAPI decodes the request body *before* it solves dependencies, so on every body-carrying route a
syntactically malformed JSON body now yields `422 validation_error` to a caller who has presented no
credential at all. Under the barrier this was a 401. The suite appears to cover this
(`tests/e2e/test_chats.py:118` — "the refusal precedes body validation") but only exercises
*shape*-invalid JSON, which still loses to the dependency; it never sends undecodable bytes.

The second is a pre-existing but now load-bearing hazard in `get_db`: FastAPI 0.135 exits the
request-scoped `AsyncExitStack` **after** the response has been sent, so `session.commit()` runs
after the client already has its `200`/`204`. `POST /auth/create-user?challenge=true` hands out a
challenge handle before the row backing it is committed, and `POST /chats` charges a credit in its
own committed session and returns an AI answer whose chat and messages are only committed
afterwards.

The remaining findings are quality and observability defects concentrated in the seams the phase
touched: dead fields left behind by the audit removal, stale exact-count docstrings in the schema
inventory test, a route-coverage test that keys on path rather than `(method, path)` where the
deleted registry keyed on both, and one test-rewrite weakening in
`test_create_user_precedence.py`.

`ruff check src/ tests/` passes. No debug artifacts, no hardcoded secrets, no injection surfaces
found in the reviewed set.

## Critical Issues

### CR-01: Request body parsing now precedes authentication on every body-carrying route

**File:** `src/nativespeaker/api/app/dependencies.py:47`, `src/nativespeaker/api/routers/auth.py:48`, `src/nativespeaker/api/routers/chats.py:14`

**Issue:** The barrier ran outside routing and refused before the router ever read the body. The
dependency runs inside `APIRoute.get_route_handler`, and FastAPI decodes the JSON body *before*
`solve_dependencies` is called (`fastapi/routing.py:418`, `raise validation_error` on
`json.JSONDecodeError`). A `RequestValidationError` raised there never reaches the auth dependency.

Verified empirically against the real routers with a rejecting verifier and no `Authorization`
header:

```
POST /auth/create-user  body=b"{not json"  ->  422 {"code":"validation_error"}
POST /auth/create-user  body={"challenge_id":"x"}  ->  401 {"code":"auth_required"}
POST /chats             body=b"{oops"      ->  422 {"code":"validation_error"}
POST /chats             body={"lang":"en"} ->  401 {"code":"auth_required"}
```

Three consequences:

1. **The stated invariant is broken.** `tests/e2e/test_chats.py:118` and
   `tests/e2e/test_error_cases.py:73` both assert "a malformed body still answers the refusal,
   never 422, so an unadmitted caller learns nothing". Both pass only because they send
   *shape*-invalid JSON (`{"lang": "en"}`), which FastAPI accumulates into `errors` *after*
   sub-dependencies are solved. Neither sends undecodable bytes. The property they name is no
   longer true and no test covers the gap.
2. **A pre-credential shape oracle.** An unauthenticated caller can distinguish a route that
   accepts a JSON body (422) from one that does not (401) by sending garbage. `GET /chats` with the
   same garbage still answers 401.
3. **Pre-auth body buffering.** `await request.body()` reads the entire body into memory for a
   caller who has proven nothing. The 500 KB probe above completed the read before the 401.

The reachable-in-production case is the *unlinked* caller: a valid Firebase token with no identity
row, sending a malformed body to `POST /chats`, receives 422 where every other rejection on that
route is 403 `preauth_identity_not_allowed`.

**Fix:** Restore ordering by refusing before the body is read. The cheapest structural fix is a
pure-ASGI or `BaseHTTPMiddleware` shim that resolves nothing but runs the wire contract, placed
inside `RequestLoggingMiddleware`; failing that, make the body optional on the auth-sensitive
routes so no `body_field` triggers the early decode, and add the missing coverage:

```python
# tests/e2e/test_chats.py -- the case the suite is missing
async def test_the_refusal_precedes_body_decoding(self, async_client):
    """Undecodable bytes, not merely a missing field: this is the case that regressed."""
    response = await async_client.post(
        "/chats", content=b"{not json",
        headers={"Content-Type": "application/json"})
    assert response.status_code == 403
    assert response.json() == {"code": "preauth_identity_not_allowed"}
```

At minimum, if the ordering is accepted, delete or rewrite the two e2e docstrings that claim the
opposite — they currently document a guarantee the code no longer makes.

### CR-02: `get_db` commits after the response has been sent; `_prepare` returns a handle for an uncommitted row

**File:** `src/nativespeaker/api/app/dependencies.py:36-43`, `src/nativespeaker/api/routers/auth.py:101-118`

**Issue:** FastAPI 0.135 wraps the route in `request_response` (`fastapi/routing.py:106-127`):

```python
async with AsyncExitStack() as request_stack:
    scope["fastapi_inner_astack"] = request_stack
    async with AsyncExitStack() as function_stack:
        response = await f(request)
    await response(scope, receive, send)   # <-- response fully sent here
# <-- request_stack.__aexit__ runs get_db's `await session.commit()` HERE
```

Verified by instrumenting the ASGI `send` callable around a yield dependency:

```
ORDER ['handler', 'response.start', 'response.body', 'commit']
```

So `get_db`'s commit runs after the client has the response. If it raises, the exception escapes
into `wrap_app_handling_exceptions` with `response_started=True`, which re-raises
`RuntimeError("Caught handled exception, but response already started.")` — the client keeps its
success response and the write is silently lost.

Concrete exposures in the reviewed code:

- **`POST /auth/create-user?challenge=true`.** `_prepare` calls `challenge_store.issue`, which does
  `session.add` + `flush` and no commit (`auth/challenges.py:64-72`), then returns a `200` carrying
  `challenge_id`. The client is handed a secret capability handle before the row backing it is
  durable. `_complete` by contrast commits explicitly twice (`routers/auth.py:167`,
  `auth/creation.py:74`) — the same router treats the two paths inconsistently.
- **`POST /chats` and `POST /chats/{chat_id}`.** `QuotaGate.charge` opens and commits its **own**
  session (`quota.py:90-99`), while `ChatsDB` only calls `session.add`
  (`database/chats.py:16`). A failed post-response commit therefore spends a credit and returns an
  AI answer for a chat that was never persisted.
- **`DELETE /chats/{chat_id}`.** Returns `204` before the delete is committed.

Pre-existing rather than introduced by 37.1 (the `fastapi` pin and `get_db` are both unchanged),
but it is in the reviewed surface and it became load-bearing for the prepare path this phase
rewired.

**Fix:** Commit inside the handler for anything whose durability the response asserts, and keep
`get_db`'s commit only as a safety net:

```python
# routers/auth.py::_prepare -- commit before the handle leaves the process
    challenge_id, expires_at = await challenge_store.issue(session, ...)
    # The handle is a capability: it must not be issued before the row backing it is durable.
    await session.commit()
    body = PrepareResponse(challenge_id=challenge_id, expires_at=expires_at)
```

Apply the same treatment in `ChatService.create_chat` / `send_message` / `delete_chat` (commit
before returning), or move the commit into a dependency that runs inside `function_stack` rather
than `request_stack`.

**File:** `src/nativespeaker/api/auth/identity.py:30-31`, `src/nativespeaker/api/app/dependencies.py:71`

(the issuer is a deployment-known string, safe to log; the subject is not — hash it through

### WR-02: Every reachable 401 omits the RFC-required `WWW-Authenticate` header

**File:** `src/nativespeaker/api/errors.py:331-347`

**Issue:** `AuthenticationError.extra_headers()` returns `{"WWW-Authenticate": "Bearer"}`, but
`AuthRejectionError` — the class every real admission failure raises — inherits
`ServiceError.extra_headers()` returning `None`. `AuthenticationError` is now raised only from
`get_preauth_identity` (nothing declares it) and from `get_quota_gate`'s documented-unreachable
branch. So the one 401 in the system that carries the header is the one no caller can reach, and
every 401 a caller actually receives lacks it. RFC 7235 §3.1 makes the header mandatory on 401.

**Fix:**

```python
class AuthRejectionError(ServiceError):
    log_level = None

    def __init__(self, error_class: ErrorClass, message: str):
        self.error_class = error_class
        super().__init__(message)

    def extra_headers(self) -> dict[str, str] | None:
        # Only the 401 class advertises a scheme; a 403 carries no challenge.
        return {"WWW-Authenticate": "Bearer"} if self.error_class is AUTH_REQUIRED else None
```

Note `tests/e2e/test_admission.py:114` compares rejection headers for equality across the two
`account_unavailable` branches — both are 403, so this change does not disturb it.

### WR-03: The structural replacement for the deleted startup assertion keys on path, not `(method, path)`, and silently skips non-`APIRoute` routes

**File:** `tests/unit/test_app_wiring.py:15-16, 27-31`

**Issue:** `auth/registry.py`'s deleted boot assertion was set equality over `(method, path)`.
Its replacement exempts by path alone:

```python
missing = [route.path for route in _api_routes()
           if route.path not in PUBLIC_PATHS | PREAUTH_CALLABLE_PATHS
           and get_linked_identity not in _declared(route)]
```

`PUBLIC_PATHS = {"/health/ready"}`, so a `DELETE /health/ready` added later with no dependency
passes every assertion in the class — the path is already in both exemption sets and in
`unauthenticated`. Separately, `_api_routes()` filters `isinstance(route, APIRoute)`, so a plain
Starlette `Route`, a `Mount`, or a `WebSocketRoute` is invisible to all four tests, including
`test_the_public_allowlist_is_exactly_the_readiness_probe`. No live gap exists today (all nine
registered routes are `APIRoute`s and all carry the right dependency, confirmed by enumerating
`app.routes`), but the assertion is weaker than the boot check it replaced.

**Fix:**

```python
PUBLIC_ROUTES = {("GET", "/health/ready")}
PREAUTH_CALLABLE_ROUTES = {("POST", "/auth/create-user")}

def _route_keys(route) -> set[tuple[str, str]]:
    return {(method, route.path) for method in route.methods}

def test_every_route_carries_auth(self):
    for route in real_app.routes:
        assert isinstance(route, APIRoute), f"non-APIRoute in the app: {route!r}"
        keys = _route_keys(route)
        if keys & (PUBLIC_ROUTES | PREAUTH_CALLABLE_ROUTES):
            continue
        assert get_linked_identity in _declared(route), keys
```

### WR-05: A startup failure after `build_admin_apps` leaks process-global Firebase apps and the engine

**File:** `src/nativespeaker/api/app/lifespan.py:41-52, 62-66`

**Issue:** `build_admin_apps(config)` registers named apps in `firebase_admin`'s process-global
registry (line 41), `create_async_engine` opens a pool (line 44), and only then does
`JWTVerifier.__init__` run — which performs a blocking JWKS fetch (`auth/verification.py:96`,
`self._jwks_client.get_signing_keys()`) and raises on an unreachable endpoint. Cleanup for both
lives *after* `yield` (lines 62-66), so a raise between line 41 and line 60 disposes nothing. The
file's own comment on line 64 states the consequence: `firebase_admin` "raises on a repeat, so a
second boot needs these gone" — a JWKS outage at boot therefore poisons any in-process retry with
`ValueError: The default Firebase app already exists`.

**Fix:** Wrap the startup body so cleanup runs on the failure path too:

```python
    firebase_apps = build_admin_apps(config)
    db_engine = create_async_engine(...)
    try:
        app.state.firebase_adapter = FirebaseAdminLookup(firebase_apps)
        ...
        yield
    finally:
        await db_engine.dispose()
        for firebase_app in firebase_apps.values():
            firebase_admin.delete_app(firebase_app)
```

### WR-08: `exc_info` is computed from the raw level, not the coerced one

**File:** `src/nativespeaker/api/app/errors.py:24-28`

**Issue:**

```python
level = exc.log_level if exc.log_level in _LOGGABLE else logging.ERROR
logger.log(level, str(exc), error_type=type(exc).__name__,
           exc_info=(exc.log_level >= logging.ERROR))
```

The fallback exists so a non-standard level is still recorded at ERROR (structlog's
`LEVEL_TO_NAME` — confirmed in `structlog/_native.py:195` — keys only 10/20/30/40/50 and raises
`KeyError` on anything else, `logging.NOTSET` included). But `exc_info` still reads
`exc.log_level`, so a `ServiceError` declaring `log_level = 25` or `logging.NOTSET` is logged *at*

the fallback is half-applied.

**Fix:**

```python
        level = exc.log_level if exc.log_level in _LOGGABLE else logging.ERROR
        logger.log(level, str(exc), error_type=type(exc).__name__,
                   exc_info=(level >= logging.ERROR))
```

### WR-10: `_insert_account`'s returned user id is dead

**File:** `src/nativespeaker/api/auth/creation.py:116-131`, `src/nativespeaker/api/auth/creation.py:55`

**Issue:** `_insert_account` still declares `-> tuple[UUID | None, AuthEventResult]` and
`_flush_account` still returns `user.id`, but the only call site discards it
(`_, result = await _insert_account(...)`). It was consumed by the deleted `_details` audit
builder. The `UUID` import on line 3 now exists solely for that dead annotation. A two-tuple
return whose first element nobody reads invites a future caller to reintroduce a use that the
`None` arm does not actually support (the conflict path returns `None` for a *successful* row that
another attempt created).

**Fix:** Collapse both to the single value that is used:

```python
async def _insert_account(session: AsyncSession, *, ...) -> AuthEventResult:
    savepoint = await session.begin_nested()
    try:
        return await _flush_account(session, savepoint, ...)
    except IntegrityError as conflict:
        await savepoint.rollback()
        return classify_insert_conflict(conflict)
```

and drop the now-unused `UUID` import.
