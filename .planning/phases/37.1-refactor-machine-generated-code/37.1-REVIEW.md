### CR-31: `insert_account` reports a provider-account collision as `identity_already_linked`, sending the client to a remediation that cannot succeed

**File:** `src/nativespeaker/api/crud/identities.py:87-115`
**Issue:**
The whole account-insert body — the `User` insert, its flush, the `ExternalIdentity` insert, the two
`StorePurchaseToken` inserts, and the second flush — sits inside one `try`, and **every**
`IntegrityError` is rewritten as `IdentityAlreadyLinked` (409, `code: "identity_already_linked"`,
`errors.py:387-390`):

```python
        except IntegrityError as conflict:
            raise IdentityAlreadyLinked() from conflict
```

`core.external_identities` carries more than one uniqueness rule that this insert can violate. Besides
`UNIQUE (issuer, subject)` (`migrations/20260818_01_initial-release.sql:102`), it carries the partial
unique index over the provider account:

```sql
CREATE UNIQUE INDEX ix_external_identities_provider_account
    ON core.external_identities (issuer, provider, provider_uid)
    WHERE provider_uid IS NOT NULL;
```
(`migrations/20260818_01_initial-release.sql:106-108`)

`02-create-user.md:63` (step 11) is explicit that these are two different answers: *"Provider-account
uniqueness conflict on the registered binding write → internal `provider_account_already_linked` →
client `operation_not_allowed`"*, while `:71` reserves `identity_already_linked` for the
`(issuer, subject)` cases whose *"Remediation: `/auth/sync`"*.

Concrete failure. Google provider account `G` is bound to Firebase subject `S1`
(`external_identities` row: issuer `I`, provider `google`, `provider_uid = G`). A new Firebase
subject `S2` for the same Google account — routine after a Firebase user is deleted and the same
Google identity signs in again — completes `POST /auth/create-user`. `resolve_existing(I, S2)` at
`services/auth.py:326` finds nothing, so the code proceeds; the `ExternalIdentity` insert then
violates `ix_external_identities_provider_account` at the flush on line 112. The caller receives
409 `identity_already_linked`, whose documented remediation is `/auth/sync` — but `/auth/sync`
resolves `(I, S2)`, finds no identity row, and rejects `preauth_identity_not_allowed`
(`crud/identities.py:38-42`). The client is left with no path forward, and the operator never sees
`provider_account_already_linked`, the result that would have routed the case to support.

The same collapse hides non-race failures the house style elsewhere insists on distinguishing: a
`core.users` FK failure or the `provider`/`provider_uid` CHECK
(`migrations/20260818_01_initial-release.sql:92-98`) also surfaces as `identity_already_linked`
rather than an internal error. Every other writer in this package holds only the flush inside the
`try` and re-raises anything that is not a unique violation
(`crud/grants.py:188-195`, `crud/subscriptions.py:113-121`); `insert_account` is the one that does
not. `flip_provider` in this same file already models the correct answer for this index
(`crud/identities.py:138-143` raises `ProviderAccountAlreadyLinked`), so the vocabulary exists and
is simply unreachable from the create path.

No test covers it: `provider_account_already_linked` appears in `tests/unit/test_rejection_vocabulary.py`
and `tests/unit/test_upgrade_precedence.py` only, both on the upgrade path.

**Fix:** narrow the `try` to the flush, and discriminate under a savepoint so the aborted flush can
be rolled back before the deciding read — without naming a constraint or parsing a message, which
this package forbids:

```python
        user = User(...)
        self.session.add(user)
        await self.session.flush()

        self.session.add(ExternalIdentity(...))
        for store in PurchaseProvider:
            self.session.add(StorePurchaseToken(...))

        savepoint = await self.session.begin_nested()
        try:
            await self.session.flush()
        except IntegrityError as conflict:
            await savepoint.rollback()
            if not is_unique_violation(conflict):
                # A CHECK or a foreign key is a broken invariant, never a race this lost.
                raise
            # The indexes stay the arbiter: which one fired is decided by re-reading, not by name.
            if await self.resolve_existing(issuer=identity.issuer,
                                           subject=identity.subject) is not None:
                raise IdentityAlreadyLinked() from conflict
            raise ProviderAccountAlreadyLinked(...) from conflict
        return user.id
```

Add a unit case that drives `insert_account` into an `ix_external_identities_provider_account`
violation and asserts `operation_not_allowed` (403), not `identity_already_linked` (409).

### CR-61: The BackendTrafficPolicy rewrites the backend's `quota_exceeded` 429 into `rate_limited`

**File:** `k8s/templates/backend-traffic-policy.yaml:28-37`
**Issue:**
The `responseOverride` matches `statusCodes: [{type: Value, value: 429}]` and replaces the body with `{"code":"rate_limited"}`. Envoy Gateway's response override is a response-path filter: it evaluates every response flowing through the targeted route, upstream responses included, not only the ones Envoy generates. `targetRefs` names `-llm-routes`.

`httproute-llm.yaml:12-16` defines llm-routes as `PathPrefix: /chats` + `method: POST`. That matches `POST /chats` (`src/nativespeaker/api/routers/chats.py:45`) **and** `POST /chats/{chat_id}` (`:61`). Both handlers call `QuotaService.charge` (`src/nativespeaker/api/services/chats.py:96` and `:122`), which raises `QuotaExceededError` — status `429`, code `quota_exceeded` (`src/nativespeaker/api/errors.py:195-198`).

So: a user whose monthly allowance is spent sends `POST /chats/{chat_id}`, the backend answers `429 {"code":"quota_exceeded"}`, and the gateway rewrites the body to `429 {"code":"rate_limited"}`. The client is told "retry in a moment" for a condition that will not clear until next month, and retries against a wall.

This contradicts the policy's own comment three lines above it (lines 24-27: *"`quota_exceeded` … tells the client the month is spent and must not be retried. A burst rejection is the opposite answer: retry in a moment."*) and `SHARED-INVARIANTS.md` § Errors, which requires the registered specialization to reach the client where it applies.

The override cannot be narrowed: Envoy Gateway's `ResponseOverride.match` supports `statusCodes` only, so a gateway-generated 429 and an upstream 429 on the same route are indistinguishable to it.

**Fix:** The collision is structural — the burst limiter and the only backend-429 producer sit on the same route. Either:

(a) Remove `responseOverride` from this policy and let the backend own the 429 body on `/chats`, accepting that the gateway's burst rejection carries no JSON body (record the deviation from `SHARED-INVARIANTS.md` § Errors' "a bare 429 does not satisfy the contract"), or

(b) Drop the gateway burst limiter on this route entirely and rely on `LLMExecutionGate` in `resilience.py`, which the comment at lines 18-19 already names as the in-flight cap — then no 429 originates at the gateway and no override is needed:

```yaml
spec:
  targetRefs:
  - group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: {{ include "ns-api-gateway.fullname" . }}-llm-routes
  # rateLimit and responseOverride removed: the only 429 on this route is the backend's
  # quota_exceeded, and a status-code-only override cannot tell the two apart.
```

Whichever is chosen, the current manifest must not ship: it silently mislabels quota exhaustion as a transient burst rejection.

### WR-11: Three provider-read failures escape `read_for_restore` as a bare 500

**File:** `src/nativespeaker/api/auth/google_play.py:270-283` and `:312-322`

**Issue:** `read_for_restore` enumerates its refusals explicitly — `Unavailable` (503) for an
unconfigured or unreachable Play read, `ProofRejected` (403) for a gone token — and the
comment at lines 258-260 states the classification is deliberate and complete. It is not.
Three reachable exceptions are raised inside the method and caught by nothing:

- `google.auth.exceptions.RefreshError` from `self._credential.refresh(...)` at line 316. The
  `try` at line 270 catches `httpx.HTTPError` only, and a `RefreshError` is not one — it is a
  `GoogleAuthError`. This is the ordinary GCP failure mode (metadata-server blip, revoked
  service-account key), not an exotic one.
- `json.JSONDecodeError` from `response.json()` at line 283, when a 2xx carries a non-JSON
  body (an intermediary's HTML error page, an empty body).
- `pydantic.ValidationError` from `PlaySubscription.model_validate(...)` at line 283, when a
  2xx body omits the required `subscriptionState`.

Verified by construction against the real class over `httpx.MockTransport`:

```
read_for_restore, credential.refresh raises RefreshError
  -> ESCAPED google.auth.exceptions.RefreshError
read_for_restore, 200 body "<html>502 Bad Gateway</html>"
  -> ESCAPED json.decoder.JSONDecodeError
read_for_restore, 200 body {"lineItems": [...]}   (no subscriptionState)
  -> ESCAPED pydantic_core._pydantic_core.ValidationError
```

`services/restore.py:181` calls this method with no surrounding `except`, so all three reach
`generic_error_handler` and answer `POST /subscriptions/restore` with `500 internal_error`
instead of the `503 verification_temporarily_unavailable` the method contracts and the client
can act on. `specs/auth-refactor-phases/10-restore-subscription.md:133` requires
"single-provider-call failure of any kind (transient or non-retryable)" to become a bounded
rejection; an unclassified 500 is not one.

Two secondary consequences: the same `RefreshError` also escapes `read` (line 220-226), which
logs only `httpx` transport failures, so the webhook path loses its bounded
`google_play_read_transport_failed` label for this case; and the escaping `ValidationError`
is rendered by `generic_error_handler`'s `exc_info`, and pydantic's `input_value=` fragment
carries the tail of the Play response — including `obfuscatedExternalAccountId` — into the
log, which is precisely what the module preamble forbids ("every Play value are excluded").
Confirmed: `'ATTRTOKEN-123' in str(ValidationError)` is `True`.

**Fix:** Classify the credential refresh and the body decode inside each entry point, so
neither can leave by the default path.

```python
    async def _get(self, package_name: str, purchase_token: str) -> httpx.Response:
        if not self._credential.valid:
            try:
                await run_in_threadpool(self._credential.refresh,
                                        google.auth.transport.requests.Request())
            except google.auth.exceptions.GoogleAuthError as failure:
                # Not an httpx failure, so each entry point's own handler would never see it.
                raise PlayReadFailed(type(failure).__name__) from failure
        ...
```

and, in both `read` and `read_for_restore`, replace the bare
`PlaySubscription.model_validate(response.json())` with a helper that turns a
`ValueError` (which covers both `JSONDecodeError` and `pydantic.ValidationError`) into the
same bounded outcome the surrounding arms use — `InternalError` after a
`google_play_read_unparseable` line in `read`, `Unavailable(stage=RESTORE_READ_STAGE)` in
`read_for_restore` — never letting the provider's own text reach the log.

### WR-12: `bool()` on Apple's two bits fabricates a bit state from a non-boolean value

**File:** `src/nativespeaker/api/auth/devicecheck.py:108-110`

**Issue:** The membership guard admits any body carrying both keys, and the values are then
coerced:

```python
if not isinstance(payload, dict) or "bit0" not in payload or "bit1" not in payload:
    raise RetryableDeviceCheckError("unrecognised body")
return BitState(bit0=bool(payload["bit0"]), bit1=bool(payload["bit1"]))
```

`"bit0" in payload` is true for `{"bit0": null}`, and `bool(None)` is `False`. So given Apple
answers HTTP 200 with `{"bit0": null, "bit1": null}` — or any other non-boolean value the
module's own docstring admits it is guessing at ("The shapes are [ASSUMED] from secondary
sources", `test_devicecheck_adapter.py:2-3`) — `read_bits` reports both bits clear. Two
things follow, at `services/auth.py:189-206`:

- `state.bit0` is falsy, so `DeviceGrantExhausted` is not raised and the device is granted a
  second anonymous free grant. This is fail-open on the only control that limits it.
- `write_bits_with_retry(..., bit0=True, bit1=state.bit1)` then writes `bit1=False` over a
  bit Apple may actually hold as set. Apple writes both bits in one call and, as
  `services/auth.py:203` records, "nothing in this product clears an Apple bit" — the
  device's registered-grant marker is destroyed with no recovery path.

This is exactly the failure `test_devicecheck_adapter.py:155` names ("a fabricated bit1
destroys state nothing can recover"), and the five-arm parse claims at line 99 that nothing
"falls through to a default" — but `bool()` *is* a default-producing coercion. The suite's
arm-five parametrization (`test_devicecheck_adapter.py:218-221`) covers an unparseable body,
one bit only, and no bits; it never covers a bit present with a non-boolean value.

**Fix:** Make the type part of the guard, so a non-boolean value takes the existing
unrecognised-body arm rather than being coerced:

```python
    bit0, bit1 = payload.get("bit0"), payload.get("bit1")
    if not isinstance(bit0, bool) or not isinstance(bit1, bool):
        raise RetryableDeviceCheckError("unrecognised body")
    return BitState(bit0=bit0, bit1=bit1)
```

(`isinstance(x, bool)` also rejects `0`/`1`; if Apple is later observed to send integers,
widen it deliberately rather than by coercion.) Add the case to arm five's parametrization:
`_ok({"bit0": None, "bit1": None})`.

### WR-13: The ignored-body log line names nothing for the one case it exists to catch

**File:** `src/nativespeaker/api/auth/google_play.py:134-140` (with `:98-108`, `:49`)

**Issue:**

```python
if notification.subscriptionNotification is None:
    # Presence, never a list of names: a body Google adds later must not fall through here.

                bodies=sorted(set(notification.model_fields_set) - _ENVELOPE_FIELDS))
```

`DeveloperNotification` declares no `model_config`, so pydantic's default `extra='ignore'`
applies and an undeclared field never enters `model_fields_set`. The routing decision is

appear in this field, which makes the logging an allow-list of four names even though the
routing is a presence test. An operator watching a newly shipped Google body type sees
`google_play_notification_ignored bodies=[]` and cannot tell what arrived — the one thing the

passes with the field empty.

**Fix:** Let the extras through so they can be named, keeping the closed-set discipline (Google's
own field *names* are a closed vocabulary; no value is logged):


Then extend the test to assert the new body's name reaches `bodies`:

```python
    async def test_a_body_google_adds_later_names_itself_in_the_log(self, play_logs):
```

### WR-21: A concurrent success re-closes a circuit breaker that has just tripped

**File:** `src/nativespeaker/api/resilience.py:60-63`
**Issue:** `record_failure` (lines 65-71) deliberately refuses to touch state while the
breaker is open — `if self._opened_at is not None: return`. `record_success` has no such
guard: it unconditionally sets `self._opened_at = None`. Because `ainvoke` runs up to
`pool_size` operations concurrently under one shared breaker, an attempt that entered
`before_call` *before* the trip can land its `record_success` *after* it and silently
cancel the open state.

Measured with `failure_threshold=2, reset_seconds=60`:

```
opened_at after 2 failures: True
opened_at after one concurrent success: False
before_call ADMITTED a request while the breaker had just tripped
```

Concretely: with `pool_size=5` and `circuit_breaker_failure_threshold=5`, five calls are in
flight against a provider that is failing 90% of requests. Five fail and open the breaker;
the sixth, already in flight, returns 200 and wipes `_opened_at`. `circuit_breaker_reset_seconds`
(60 by default) is never honoured, and every subsequent request pays the full

### WR-32: the schema suite's deferred-constraint tests issue a `BEGIN` that Postgres ignores, so their `COMMIT` acts on the fixture's transaction

**File:** `tests/schema/test_constraints.py:304-310`, `:319-326`, `:334-340`
**Issue:**

```python

        await insert_grant(...)
        with pytest.raises(asyncpg.ForeignKeyViolationError) as exc_info:

```

PostgreSQL does not nest transactions from bare SQL: the inner `BEGIN` emits
`WARNING: there is already a transaction in progress` and does nothing. The `COMMIT` therefore ends

fails, and every later test in the session then runs against polluted state — `test_inventory.py`'s

a cascade of unrelated failures.
