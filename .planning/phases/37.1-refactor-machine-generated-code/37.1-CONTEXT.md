# Phase 37.1: Refactor machine-generated code - Context

**Gathered:** 2026-08-24

<domain>
## Phase Boundary

Phases 34-37 were executed largely by parallel agents, and the code carries the marks of it: an
audit subsystem built to spec but never justified against this product's actual threat model, and
source prose written as an audit trail of the planning process rather than as an explanation for
someone reading the code cold.

This phase does two things:

1. **Deletes the auth-event audit subsystem outright** — the `audit.auth_events` table, the writer,
   and every call site.
2. **Rewrites the prose across `src/`, `tests/` and the migration** — docstrings collapsed to one
   line or removed, multi-line comment blocks removed, and everything that survives rewritten in
   plain English.

It is a behavior-reducing refactor, not a feature phase. No new capability is added and no endpoint
changes shape, with the single exception that auth attempts stop writing audit rows.

**The measured surface:**

|---|---|
| `src/` | 6,687 lines — 903 comment lines + 1,836 docstring lines = **41% prose** |
| Docstrings in `src/` | 155 multi-line, 46 single-line |
| Multi-line comment blocks in `src/` | 121, across 30 files |
| `tests/` | 17,028 lines across 62 files |
| Audit code | `auth/audit.py` 363 lines + call sites in barrier, router, `creation.py`, lifespan, dependencies |
| Audit tests | 1,202 lines dedicated (`unit/test_audit_writer.py` 492, `e2e/test_audit_writer.py` 433, `unit/test_audit_details.py` 277); referenced in 22 test files total |

**Out of scope:** the open `37-REVIEW.md` findings (see Deferred), any endpoint behavior change
beyond the audit removal, and phases 38-45's own work.

<decisions>
## Implementation Decisions

### The audit subsystem — deleted

- **D-01: The auth-event audit subsystem is removed entirely.** `src/nativespeaker/api/auth/audit.py`,
  the `AuditWriter` class and every call site (`auth/barrier.py:203`, `routers/auth.py:197`,
  `auth/creation.py:145`, `app/lifespan.py:53`, `app/dependencies.py:122-128`), the
  `audit.auth_events` table and its four indexes, and the dedicated tests. Nothing writes an auth
  audit row afterward.

  The developer's judgement, and it is consistent with `AGENTS.md`: auditing every auth attempt to a
  dedicated Postgres schema is over-engineering for a pre-launch sub-$5/month grammar app. The
  subsystem was built because `01-foundation.md §4` mandates it, not because a threat model asked
  for it. — **Reversibility:** one-way — the table, its enum type and ~1,600 lines of code and tests
  are deleted; restoring means re-editing the single initial migration, rebuilding the writer, and
  re-wiring five call sites across phases that will have moved on.

- **D-02: `audit.subscription_events` stays, and so does the `audit` schema.** It is the
  subscription/purchase event log, not auth auditing. `SCHEMA-07` deliberately relocated it out of
  `core`, and `tests/schema/test_inventory.py:299-302` asserts it survived that move. The webhook
  phases still need somewhere to record store notifications. Only `auth_events` and its indexes are
  dropped; `DROP SCHEMA audit CASCADE` is **not** the mechanism.

- **D-03: `auth/telemetry.py` stays.** `record_rejection` emits the structured `auth_rejected`
  security-log event for barrier rejections. It is the cheap, no-schema version of what the audit
  table was doing, `REBIND-02` already depends on it, and it costs nothing to keep. Its docstring
  gets the same plain-English rewrite as everything else.

- **D-04: `AuthEventResult` survives as a plain Python enum — this is a hard constraint, not a
  preference.** It is the internal outcome vocabulary, not an audit artifact:
  `auth/identity.py:63` builds every barrier `Reject` from it, `auth/creation.py:93`'s
  `CLIENT_CLASS_FOR_RESULT` maps it to client-visible error classes, and `auth/retry.py:35` and
  `auth/telemetry.py:24` both consume it. Deleting it would take out the rejection classification
  along with the audit rows.

  What does go: `AuthEventResultType` (`models/auth.py:85`, the SQLAlchemy `Enum` binding it to
  `core.auth_event_result`) and the `core.auth_event_result` PostgreSQL type itself, whose only
  consumer is `audit.auth_events.result` at `migrations/20260818_01_initial-release.sql:673`.

  **`core.auth_operation` stays** — `core.auth_challenges.operation` uses it at `:596`. So does
  `AuthOperation`, which `auth/registry.py:31` needs.

- **D-05: The route registry keeps its `operation` metadata field.** Its original purpose was
  deciding whether a request is on the audited path, but `assert_route_enumeration` also enforces
  operation uniqueness and the `challenge_bearing` consistency rule (`registry.py:192-208`), which
  the challenge protocol still needs. Removing the field would take those checks with it.

- **D-06: The migration is edited in place and the dev/test database dropped and re-applied.** Same
  mechanism 37-01 Task 1 resolved for D-13: `SCHEMA-01` is a shipped requirement reading "no
  incremental migration files are added", and `tests/schema/test_apply_rollback.py::TestMigrationDirectory::test_exactly_one_sql_file`
  enforces it live. That test must stay green **unmodified**. — **Reversibility:** one-way —
  destructive schema change, cheap pre-launch with no deployed database.

- **D-07: The ROADMAP and REQUIREMENTS amendments are part of this phase, not follow-up.** Deleting
  the subsystem strands criteria that name it. They must be amended in the same phase, and the
  conflict against `SHARED-INVARIANTS §4` flagged rather than silently resolved — the standing rule
  from 37-CONTEXT.md.

  **`.planning/ROADMAP.md`** — 7 mentions of `audit.auth_events`: `:146` (schema CHECK criterion),
  `:190` (the 35-09 plan checkbox — historical, leave it), `:209`, `:243`, `:307`, `:318`, `:402`.
  Note `:243` and `:318` assert *no* row is ever written, so they become trivially true rather than
  false.

  **`.planning/REQUIREMENTS.md`** — `SCHEMA-06` `:23`, `FOUND-05` `:37`, `REBIND-02` `:49`,
  `SYNC-03` `:66`, `PROF-02` `:71`, `SIGNOUT-02` `:109`, plus `FOUND-09` `:117`'s trailing note
  about the client address recorded in audit `details`.

  `SYNC-03` and `SIGNOUT-02` are the substantive ones — both currently *require* an audit row from a
  phase that has not been built.

### The prose rewrite

- **D-08: Reach is `src/`, `tests/`, and `migrations/20260818_01_initial-release.sql`.** Everything.

- **D-09: Docstrings collapse to one line; docstrings whose purpose is obvious are removed
  outright.** 155 multi-line docstrings in `src/` alone.

- **D-10: Multi-line comment blocks are removed.** 121 blocks across 30 files in `src/`.

- **D-11: Every comment and docstring that survives is rewritten in plain English.** This is the
  qualitative half of the phase and the part a planner is most likely to under-specify.

  What "plain English" rules out, all quoted from live code:

  - **Spec and plan cross-references as load-bearing text.** `routers/auth.py:1-32` cites `37-09`,
    `35 D-02`, `D-10`, `D-11`, `§02 step 14` and `37-RESEARCH Pitfall 6`. A reader without the
    planning directory open cannot resolve any of them.
  - **Arguing with a hypothetical reader.** `routers/auth.py:16` — "It looks like a stray commit
    otherwise -- it is not." `auth/audit.py:20` — "Raising here with a message naming the problem
    beats a constraint violation at insert time."
  - **Instructions to future maintainers.** `models/auth.py:100` — "Do not add a state column, and
    do **not** add an HMAC key-version column." `routers/auth.py:100` — "exactly two fields. Do not
    add a third."
  - **Markdown emphasis and section symbols inside docstrings.**

  What it must **not** destroy: the non-obvious invariants this prose is currently the only record
  of. `routers/auth.py:12-16` explains that a mid-handler `commit()` is deliberate, because holding
  the challenge claim uncommitted across the provider call would let a second attempt win the same
  challenge. That fact has to survive, as one plain sentence. The rewrite is a change of register,
  not an amnesty on documenting surprises.

### Logging

- **D-12: `_LEVEL_TO_METHOD` is replaced by `logger.log(level, ...)`.** `app/errors.py:19-25` is a
  five-entry dict feeding `getattr(logger, method_name)` at `:31-33`, purely to turn a `logging.*`
  integer into a structlog method name.

  The direct replacement works: `logs.py:31` configures
  `wrapper_class=structlog.make_filtering_bound_logger(...)`, and that bound logger exposes
  `.log(level, event, **kw)` taking the stdlib integer level. So `:30-34` becomes one
  `logger.log(exc.log_level, str(exc), error_type=..., exc_info=...)` call. It is `logger.log`, not
  the stdlib `logging.log` — routing through the module-level `logging` would bypass the structlog
  pipeline and lose the contextvars request correlation.

### Claude's Discretion

- Whether the audit deletion and the prose rewrite are one plan or two. They are independent and the
  audit deletion is the one with real blast radius, so separate commits at minimum.
- Ordering within the prose rewrite — the audit deletion removes ~1,600 lines of code and tests that
  would otherwise be rewritten, so doing it first is cheaper. Not mandated.
- Whether `auth/audit.py`'s `build_details` and its redaction helper have any non-audit consumer
  worth preserving. `routers/auth.py:52` and `auth/creation.py:47` both import `build_details`, so
  check before deleting rather than assuming.
- How aggressively to collapse test docstrings, given the developer chose full reach knowing test
  docstrings often name the invariant a case pins.

## Existing Code Insights

### Established patterns that constrain this phase

- **One migration file, edited in place.** `test_exactly_one_sql_file` enforces it. D-06.
- **`Depends()`-only routes, all DI in `app/dependencies.py`.** Removing the `AuditWriter`
  dependency means touching both the route signature and the provider.
- **Zero raw `text()` SQL, ORM constructs only.**
- **The barrier is the only place identity resolution happens.** Removing its audit write must not
  disturb the admission decision itself.

### Integration points

- `auth/barrier.py` — the rejection path loses its audit write, keeps `record_rejection` (D-03).
- `auth/creation.py::create_account` — loses the `audit_writer` parameter and the
  `write_in_transaction` call. Its `begin_nested()` savepoint exists partly so the audit row would
  survive a business rollback; check what the savepoint is still buying once the row is gone before
  removing or keeping it. **Do not remove it reflexively** — 37-09 proved it also delivers the
  race-loser durability that §02 step 12 requires.
- `tests/schema/test_inventory.py` — asserts the full object inventory. D-01 removes a table, an
  enum type and four indexes; D-02 keeps a table this file explicitly guards. It will need careful
  editing, not regeneration.

### Reusable assets

- `auth/telemetry.py::record_rejection` — already the no-schema substitute for an audit row. After
  D-01 it is the only record of a barrier rejection anywhere.

<specifics>
## Specific Ideas

- The developer's four opening directives, verbatim: remove all auditing from the code; collapse all
  docstrings to one line and remove them where the purpose is obvious; use `logging.log` instead of
  `_LEVEL_TO_METHOD`; remove all multiline comments. Then, on reach: "Everything. Also, rewrite all
  docstrings and comments that are left in plain English."
- The framing to internalize: this code was written to be *reviewed against a plan*, not to be
  *read*. `routers/auth.py:1-32` is a defence of implementation choices addressed to someone holding
  `37-CONTEXT.md`. Once the planning directory is not in front of you, it is unresolvable. That is
  the specific failure mode D-11 corrects.
- The audit subsystem is well-built. D-01 is not a quality judgement on it — it is a judgement that
  the product does not need it, in the same spirit as Phase 36 retiring `RejectionCounter` and
  Phase 37 D-04 retiring `BudgetGate`. Three phases running, this codebase's pattern has been to
  delete carefully-built machinery once its justification is re-examined.

</specifics>
