### CR-31: `insert_account` reports a provider-account collision as `identity_already_linked`

**Commit:** `58c1d23`
**Files:** `src/nativespeaker/api/crud/identities.py`, `src/nativespeaker/api/services/auth.py`,
`tests/unit/test_conflict_classification.py`, `tests/unit/test_create_user_rollback.py`,
`tests/e2e/test_create_user.py`

Not fixed as the review proposed. The review's snippet reinstates a `begin_nested()` savepoint,
which `tests/unit/test_conflict_classification.py::test_the_inserts_open_no_savepoint_of_their_own`
forbids by name ("D-06: one transaction, owned by the route"), and which is unnecessary here —
`AuthService._complete` already rolls back and consumes the challenge in a fresh transaction, so
the savepoint's stated job is done elsewhere.

Instead, `AuthService.create_user` now reads the provider account before the insert, exactly as it
already reads `(issuer, subject)`, through a new `IdentitiesDB.resolve_provider_account`. A held
account raises `ProviderAccountAlreadyLinked` (403 `operation_not_allowed`), which
`02-create-user.md:63` step 11 requires, before any row is added.

This is precisely what `REQUIREMENTS.md:218` (Phase 37.4 D-06/A-07) *claims* is already true — "the
distinct answer is lost only on the race path … only two completions racing on the same provider
account collapse onto the 409". That claim was false: the pre-check keys on `(issuer, subject)`, so
the routine non-race case (a new Firebase subject for a Google account another subject already
holds) fell through to the insert. The fix makes the recorded divergence true as written, and
narrows the residual to a genuine race, which is self-healing — the retry hits the pre-check.

Second half of the finding: the insert's `try` was narrowed to the flush that can lose, and now
classifies by SQLSTATE through `is_unique_violation`, as every other writer in the package does, so
a CHECK or a foreign key propagates to the internal-error path instead of reading as a benign 409.
The user-row flush sits outside the arm: `core.users` carries no uniqueness this insert can lose.

Tests updated to the correct expectation rather than weakened: the two synthetic `IntegrityError`
factories now carry a real SQLSTATE (they had `Exception("dialect-level wrapper")` as `orig`, which
is not a unique violation); `TestEveryConflictCollapsesToOneAlreadyLinkedAnswer` is renamed to
`TestTheInsertsUniqueViolationIsTheSubjectRace` and gains a parametrized case over fk/check/not-null;
a new `TestTheProviderAccountEarnsItsOwnAnswer` covers active and historical holders, the free
account, and the anonymous path (which issues no extra read at all). `tests/e2e/test_create_user.py`
`TestTheProviderAccountReservation` — the one status/code pair D-06 knowingly moved — is moved back
to `403 operation_not_allowed`.

**Note for the orchestrator:** `.planning/REQUIREMENTS.md:218` still describes the divergence as
open. It is now only partly true (the race path). Planning artifacts were deliberately not edited.

### CR-61: The BackendTrafficPolicy rewrites the backend's `quota_exceeded` 429 into `rate_limited`

**Commit:** `c7a3de4`
**Files:** `k8s/templates/backend-traffic-policy.yaml` (deleted), `k8s/templates/NOTES.txt`,
`k8s/values.yaml`

Verified the finding against the manifests before acting, as instructed:

- `httproute-llm.yaml:12-16` is `PathPrefix: /chats` + `method: POST`, which matches
  `POST /chats` (`routers/chats.py:45`) **and** `POST /chats/{chat_id}` (`:61`).
- Both handlers reach `QuotaService.charge` (`services/chats.py`), which raises
  `QuotaExceededError` — 429, `quota_exceeded` (`errors.py:195-198`).
- `ResponseOverride.match` carries `statusCodes` only, so a gateway-generated 429 and an
  upstream 429 on one route are indistinguishable to it. The override **cannot** be
  narrowed; the finding is right.
- I also checked the two ways the finding did not consider: retargeting the policy at a
  different HTTPRoute does not help (both quota-charging endpoints are the LLM route), and
  the Envoy Gateway CRD exposes no status code for `rateLimit.local`.

Chose the finding's option (b) over (a) on the merits:

- (a) — keep the burst limiter, drop only the override — leaves the gateway's burst
  rejection a bare 429. `SHARED-INVARIANTS.md` § Errors forbids that outright: *"a bare 429
  does not satisfy the contract."* Under the binding-spec rule that option is not
  available.
- (b) violates no spec clause. Nothing in `specs/` requires a gateway burst limit on
  `/chats`; `08-rate-limits-and-admission-control.md` does not mention the route at all.
- On merits rather than rules: the limiter was **one bucket per Envoy pod shared by every
  caller** — a crude global ceiling, not a per-caller abuse control. `LLMExecutionGate`
  already caps in-flight work and refuses immediately with `QueueFullError`, which carries
  the registered `service_unavailable` body **and** a `Retry-After` (`errors.py:311-322`) —
  a strictly more contract-compliant answer than either 429. AGENTS.md also records that
  the cluster's Envoy Gateway rate-limits by IP/user/URL independently of this chart, so
  this is not the deployment's only edge control.

`rateLimits.burst` went with the policy rather than being left as config nothing reads, and
NOTES.txt now tells an operator that the only 429 on `/chats` is the backend's quota answer.

### WR-42: a concurrent restore leaves `ingest` locking the wrong account's grants

**Commit:** `dffc993`
**Files:** `src/nativespeaker/api/services/subscriptions.py`,
`src/nativespeaker/api/crud/subscriptions.py`, `tests/unit/test_subscription_attribution.py`

The finding holds, but not by the mechanism the review describes, and the correction matters for the
fix. The review says `upsert_subscription`'s own second `read_subscription` "recomputes the owner"
and yields B. It does not: that read returns the instance already in the identity map, with the
value the first read saw. **Verified against a live server** — with a `Subscription` loaded, another
connection committing a new `user_id` leaves `stored.user_id` answering the old value.

So the real shape is a stale in-memory row, and on the commonest interleaving it is worse than
described: when the unlocked read saw an unowned row, `owner` is `None`, `lock_grants` is never
called at all, `subscription.user_id` stays `None`, and the service's `if subscription.user_id is
not None:` guard skips the grant write entirely — an `expired` notification commits its event row
and ends nothing.

Root cause: the pre-lock read of `core.subscriptions` is never re-validated, while restore protects
itself by re-stating its read in the `WHERE` of `claim_subscription_owner`. The fix gives ingestion
the equivalent: a new `SubscriptionsDB.read_owner` re-reads the owner **as a column select** (an
entity re-read would answer from the identity map — the staleness itself), taken after the grant
locks; a settled owner that differs from the locked one logs `store_notification_owner_moved` and
raises `InternalError`, which is exactly how `_settle` answers a lost race. The store resends and
the resend locks the settled owner.

A subscription-row `FOR UPDATE` would close the window completely but is forbidden by the module's
own lock order ("the subscription row is never locked", 45 D-08), so this narrows the window and
fails closed rather than pretending to eliminate it.

Three cases added to `tests/unit/test_subscription_attribution.py`: an expiry whose owner moved, an
adoption of a row read unowned, and a control where the owner did not move. The first two fail
without the fix; the control passes either way.

### WR-51: `/auth/challenge` hands out the handle before its row is durable, and three `/chats` writes answer before their rows are

**Commit:** `5ca8363`
**Files:** `src/nativespeaker/api/routers/auth.py`, `src/nativespeaker/api/services/chats.py`,
`tests/unit/test_challenge_endpoint.py`, `tests/unit/test_quota_seam.py`

I was asked to judge this on the merits rather than cite the prior disposition. **The
finding is right and the prior disposition does not answer it.**

The mechanism is real, re-confirmed here on the pinned FastAPI 0.135.1 by spying on the
ASGI `send` callable around a yield dependency:
`['handler', 'http.response.start', 'http.response.body', 'teardown/commit']`. `get_db`'s
commit therefore cannot become the caller's 500 — it surfaces as
`RuntimeError("Caught handled exception, but response already started.")` while the client
keeps an answer for rows that were never written.

`37.1-VERIFICATION.md:196` downgraded this to Info **as pre-existing** — a provenance
argument, not a merits one, and it does not survive either half of the reviewer's
counter-argument. `_prepare` is now the `/auth/challenge` route, so it is reviewed code;
and the package has since adopted the opposite standard out loud —
`services/subscriptions.py:139` commits with *"the store reads the status code, so 200 must
mean the rows are durable"*, and `AuthService._complete` commits explicitly. These four were
the only mutating routes left that did not.

The sharpest case is `POST /chats`: `QuotaService.charge` commits a monthly credit in its
**own** session (`get_quota_service` takes the session factory, not `get_db`), so a lost
teardown commit bills a paying user for a chat that does not exist. That is not
client-retryable in the way the prior disposition assumed.

Placement follows AGENTS.md, which puts transaction boundaries in `services/`: the three
`/chats` commits went into `ChatService`, not the handlers. `ChatsDB` and `ChallengesDB`
both document that no method of theirs commits, and that stays true. `/auth/challenge` has
no service, so its one line sits in the handler, which is that route's boundary.
`expire_on_commit=False` and Python-side `default_factory` timestamps make the returned
objects readable after the commit — checked, not assumed.

Tests updated to the new correct expectation, not weakened:
`test_challenge_endpoint`'s recording session raised `AssertionError("no path in this module
may commit")`; it now **counts** commits, and both arms assert the count — one on the
issuing arm, zero on every refusal, which is a stronger claim than the old blanket refusal.
`test_quota_seam`'s two ordering cases gain the trailing commit; the "nothing is held across
the provider call" ordering they exist for is untouched.

### WR-33: `core.auth_challenges` stores the raw verified external subject in plaintext

**Files:** `migrations/20260818_01_initial-release.sql:301-302`,
`src/nativespeaker/api/tables/auth.py:39-40`, `src/nativespeaker/api/crud/challenges.py:47,101-104`
**Reason:** the code is as the review describes, and it does contradict `00-schema.md`; but the
correct close is a spec amendment, not a code change, and the code change the spec's letter demands
is a subsystem rebuild that this product's own standard rejects. Escalated rather than applied.

The reasoning, since the assignment asked for it either way:

1. **The finding is accurate.** `00-schema.md` §7 declares `preauth_subject_hash BYTEA` holding
   HMAC-SHA-256, ruling 4 repeats it, §4 says `core.external_identities` is "the ONLY table that
   stores a recoverable external subject", and §8 forbids any purge. The migration ships
   `preauth_subject TEXT` and `ChallengesDB.issue` writes `identity.subject` verbatim.
2. **What "restore the hashed column" actually costs.** Phase 37.4 D-11/A-08 deleted
   `auth/hmac_keyring.py` (118 lines), `tests/unit/test_hmac_keys.py` (314 lines), `HmacConfig`, the
   `config/config.yaml` `hmac:` block, the lifespan wiring, both message prefixes and the key-version
   machinery. Restoring the column means restoring all of that, plus a new secret to provision in
   the k8s manifests, plus amending the shipped migration and the lifecycle CHECK, plus the schema,
   e2e and unit cases that name the column. That is a phase of work, not a review fix.
3. **The merits, weighed fresh rather than by appeal to the record.** The value the hash protects is
   a Firebase uid. `core.external_identities` stores that same uid in plaintext permanently, beside
   the Google/Apple `provider_uid`, for every user who completes a signup — so against a
   database-read adversary the hash buys nothing for linked users. The genuine residual, which the
   original decision did not weigh and the review is right to raise, is the *unlinked* population:
   abandoned prepares keep their subject forever, because consumption is the only thing that clears
   it and §8 forbids a sweeper. But a Firebase uid is an identifier, not a credential — holding it
   grants nothing without a signed ID token. Rebuilding key-versioned HMAC machinery, and taking on
   a production secret to rotate, to obscure the identifiers of abandoned signups in a pre-launch
   sub-$5/month app is the over-engineering `AGENTS.md` names, and it is not the "normal security
   measure" the same paragraph insists on keeping.
4. **A cheaper middle path was considered and rejected.** An unkeyed SHA-256 of `(issuer, subject)`
   would close the gap in ~15 lines with no key to manage, and a 28-character random uid is not
   brute-forceable. It was rejected because it matches neither the spec nor the recorded decision:
   it would replace one flagged conflict with a third position no written document holds, which is
   the worst outcome for a later reader.

**Recommendation:** amend `00-schema.md` §7, ruling 4 and §4 through `/spec-amend` so the plaintext
column and the retention rule are the specification, and close the `REQUIREMENTS.md:218` D-11/A-08
flag against the amendment. §8's "never purged" rule was written for a table that held no
recoverable subject and should be revisited in the same amendment. If the author would rather have
the hash, it needs a phase, not a fix commit.
