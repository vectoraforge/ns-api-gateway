## CR-01 — `aab00a7`

**Root cause:** the breaker verdict the quota charge was committed against was re-taken inside
`attempt()` on the *first* attempt, across the unbounded wait for a provider permit. Two verdicts,
one charge, so a charged request could be refused 503 having made zero provider calls.

`resilience.py::ainvoke` now consults the breaker before every attempt **after the first**; the
first rides the verdict `admission()` gave. This closes the hole while keeping both decisions that
opened it intact:

- **41 D-14** is preserved verbatim — its stated property is "a request already in flight when the
  breaker opens fails on its **next** attempt". A request that has made no provider call is not in
  flight. The pass-through `except (QueueFullError, CircuitOpenError): raise` arm stays reachable
  and first.
- **41 D-15** is untouched — the charge still commits and releases its connection before any permit
  is taken. The review's suggested option 2 (move the charge behind the permit) was **rejected**
  because it reinstates exactly what D-15 removed; option 1 (a refund path) was rejected because
  D-07 states "a failed provider call is still not refunded" and `QuotaService` deliberately has no
  compensating write.
- **37.5 D-07** is literally true again: a charged request always reaches the provider at least once.

`AGENTS.md` § Resilience amended to state the new rule and why. New case
`test_quota_seam.py::test_a_breaker_opening_while_a_charged_request_waits_still_reaches_the_provider`
— confirmed to **fail** against the pre-fix condition and pass after. Three attempt-count assertions
in `test_resilience_retry.py` updated to the correct expectation (`checks == calls - 1`).

## CR-09 — `read_private_key` lets two exception types escape and crashloops the pod

**Commits:** `04afd27`, plus `caebba4` (see note below)

**Root cause:** `read_private_key` is a two-outcome classifier ("usable key" or the same absent
state an unset path is), but it caught `(OSError, ValueError, jwt.PyJWTError)` only. `PyJWT`'s
`ECAlgorithm.prepare_key` loads a public-key PEM successfully and fails later at `.sign()` with
`AttributeError`, and fails a passphrase-wrapped PKCS#8 PEM with `TypeError`. Both reproduced
against the installed `PyJWT` and `cryptography`:

```
ec-public-key              -> ESCAPED AttributeError: 'ECPublicKey' object has no attribute 'sign'
encrypted-ec-private-key   -> ESCAPED TypeError: Password was not given but private key is encrypted
good                       -> returned text
```

`lifespan.py:146` calls it inside a `try:` whose only handler is `finally:`, so either mount takes
down ASGI startup and the whole pod crashloops. The `except` tuple is now `except Exception`, which
is correct precisely because no caller can act on the distinction. The two proven forms were added
to the parametrisation in `tests/unit/test_devicecheck_adapter.py`; both fail without the fix.

**Note on the second commit.** `caebba4` shortens the docstring of the case added in `04afd27` from
four lines to three. `tests/unit/test_docstring_bar.py` records `tests/unit: 0` docstrings over the
three-line bar, and `04afd27` broke that baseline. It is one finding in two commits because
`git reset --hard` (to amend `04afd27` in place) is denied in this environment.

## WR-16 — `_instant` has no range guard, so one out-of-range Apple stamp 500s the webhook forever

**Commit:** `e9768a3`

**Root cause:** `datetime.fromtimestamp(milliseconds / 1000, UTC)` with no guard, against a library
that models every Apple stamp as an unbounded `Optional[int]`. Reproduced: `10**18`,
`253402300800000` and `-10**18` each raise `ValueError: year must be in 1..9999`, which escapes
`verify`, escapes `verify_app_store_notification`, and reaches the generic 500 — the answer that
makes Apple resend the same body on its whole retry schedule. `_instant` now has the same
`(ValueError, OverflowError, OSError)` arm its Google sibling `instant_from_millis` already carries,
and keeps an unusable stamp absent. No log line was added: this module holds no logger by design.

Fail-closed is preserved rather than assumed: an entitled status left with no term is still refused
by `SubscriptionsService.ingest:111-123`, so a dropped `expiresDate` cannot write an endless grant.

## WR-17 — the seam converts only `VerificationException`, so a structurally invalid payload is a 500

**Commit:** `54c87f7`

**Root cause:** `SignedDataVerifier` calls `_get_cattrs_converter(...).structure(...)` **outside**
`_decode_signed_object`'s own `try/except` (verified in the installed library at
`signed_data_verifier.py:58,72,89`), so a payload that verifies cryptographically but carries a
field of the wrong JSON type raises `cattrs.ClassValidationError`, which is not a
`VerificationException`. Reproduced on three of the four arms:

```
envelope    {"data": 5}                 -> cattrs.errors.ClassValidationError
transaction {"expiresDate": "nope"}     -> cattrs.errors.ClassValidationError
renewal     {"gracePeriodExpiresDate": "nope"} -> cattrs.errors.ClassValidationError
verify_transaction {"expiresDate": "nope"}     -> cattrs.errors.ClassValidationError
```

`08-webhook-app-store.md:45` requires **401** for a malformed payload (envelope or any nested
payload) and reserves 5xx for internal failure "so Apple's retry schedule covers transient errors";
a body that will never structure is not transient. All four arms now carry a second
`except Exception` raising `NotificationRejected(stage="payload_unstructurable")` — and
`ProofRejected` with the same stage on the restore path, keeping the `:148` distinction. The catch
wraps one library call only, so it hides nothing of this project's own code. New cases in
`test_app_store_notifications.py` (three arms) and `test_restore_proof.py` (the proof arm); all four
fail without the fix.

## WR-19 — SKIPPED: the proposed bound cannot prevent the buffering it is asked to prevent

**Reason:** the finding's stated harm is that an unauthenticated caller makes the pod buffer and
JSON-parse an arbitrarily large body before the OIDC check. A pydantic `max_length` runs *after*
that read and that parse (FastAPI's `get_request_handler` does `await request.body()` and
`await request.json()` before `solve_dependencies`), so it mitigates nothing. Measured on an 8.0 MB
body through a real ASGI app, warmed up and repeated in both orders:

```
bounded (WR-19 fix)    status=422 peak=40.0 MB
unbounded (today)      status=200 peak=24.0 MB
```

The bound makes the per-request peak **worse**, because the oversized value is copied into
pydantic's error context and the 422 body. It also reintroduces the failure class the ratified 37.2
fix removed (`37.2-REVIEW-FIX.md:236-238`: the bound was moved out of the schema and into
`developer_notification_from` precisely because "Pub/Sub acknowledges 2xx alone", so any body
pydantic refuses is a 422 the subscription retries until retention expires). A body over the bound
would loop forever instead of being dropped with a 200, and Cloud Pub/Sub permits messages up to
10 MB, so the loop is reachable from the topic, not only from an attacker.

The effective control is a bound applied **before** the body is read — Envoy's `buffer` filter
(`max_request_bytes`) on the two webhook `HTTPRoute`s, or an ASGI middleware that counts bytes off
`receive`. Neither is in this partition: `AGENTS.md` assigns gateway concerns to Envoy, and `k8s/`
belongs to part 6. Recorded here rather than fixed.

## Fixed

**`559deaa` CR-25 — read the restore term from whatever decided the status**

Root cause: `RestoreService.restore` took the entitlement *status* from the canonical row (D-06) and
the entitlement *window* from the client's proof. On Apple the two can never agree for
`grace_period`, because `AppStoreNotifications.verify_transaction` sets
`grace_period_expires_at=None` unconditionally — Apple's grace window lives in the renewal payload
a bare signed transaction does not carry — so `term_end_for` returned `None` and every restore by a
subscriber the store had actually put in grace was refused `restore_not_found`.

Fix: where a canonical row decided the status, the term is read from the grant that row's own
webhook wrote, which `lock_grants_of` already holds — one source for both. The proof remains the
term's source only where no grant records one (adoption, adoption-with-creation). This also closes
the finding's second wrong 403, a stale original signed transaction against an `active` row, and
moves the same-account branch onto `10-restore-subscription.md:77(a)`/`:90` (the grant keeps its id,
later terms come from ingestion and never from restore) — the writer now answers `replayed`.

Deliberately **not** taken: the review's narrow fallback ("fall back to the proof's paid expiry when
the row says `grace_period`"). During grace the paid expiry is by definition in the past, so
`term_ends_at <= evaluated_at` still fires and the subscriber is still refused — it does not fix the
defect. Also deliberately not taken: persisting a term-end column on `core.subscriptions`, which
needs a migration change outside this partition.

`45-07-PLAN.md` Task 1 ratified the *refusal*, but under three prohibitions, one of which is "a
refusal must not be so broad that it strands a paying customer who presents a genuinely current
proof". This fix satisfies all three: the window written is one the webhook verified, never `NULL`,
and no refusal is distinguishable from another.

**`60a9835` WR-46 — write the device bit only where the anonymous claim wrote the grant**

Root cause confirmed against current code: `activate_anonymous_device_grant` answers `lost_race`
from two arms, and the second is the flush's unique violation
(`src/nativespeaker/api/crud/grants.py:213-219`), whose arbiter
`ix_access_grants_one_active_per_user` covers an active grant of *any* source. So the comment at
`services/auth.py:218-219` ("the only attempt that can win this race is another anonymous claim")
was false, and the unconditional `bit0=True` burned a device's one lifetime anonymous slot for a
grant this product never wrote. The `_settle` return value was already computed and discarded;
it is now the guard, exactly as the registered sibling's `if state is not None and wrote:` is.

**`e98ecc1` WR-47 — roll the monthly period forward only, never backwards**

Root cause: `if usage.monthly_period != period` is an inequality where the rule is an ordering.
A request whose captured instant predates the stored period — one admitted before a UTC month
boundary that reaches the locks after a later request rolled the row over — reset `monthly_used` to
zero and wrote the row back to its own month, erasing the later request's committed charge and
leaving the next request of the new month to roll over a second time. `monthly_period_for` writes
zero-padded `YYYY-MM`, which sorts chronologically, so `<` is the correct test. Behind the stored
period the charge now spends the stored month's counter.

`SyncService.read_entitlement` carried the mirror of the same `!=` and reported zero used against a
counter the charge will spend from; changed to the same ordering in the same commit.

**`c1bc549` WR-48 — carry the month's count across a term change inside it**

Root cause: `write_subscription_grant` minted `monthly_used=0` on every supersession. The allowance
is a UTC calendar month's, not a store term's, so a grace bounce (`DID_FAIL_TO_RENEW` then
`DID_RENEW`) handed one account three allowances inside one month, and a mid-term tier change one
more. The counter now travels the way `activate_registered_account_grant` already travels it: the
superseded row of *this* account, and only where its `monthly_period` is the period being written.
A renewal at a month boundary still starts at zero, so 43-04's ratified "its fresh usage row" still
describes what a renewal does; `10-restore-subscription.md:80`'s "**No fresh monthly counter**" is
now honoured. No new lock and no second lock tier: `lock_grants` locked these usage rows before the
writer ran, so the carry is a plain read.

**`0c3de79` WR-49 — run the real writer in the attribution recorder, not a copy of it**

Root cause: `_RecordingSubscriptions.upsert_subscription` re-implemented the crud's rules and had
drifted on both — it moved `store_signed_at` backwards where production only advances it (the exact
column the service's out-of-order guard reads) and answered `applied` where production answers
`replayed`, and it modelled the conditional owner claim's `lost_race` not at all. The stand-in now
delegates to `SubscriptionsDB.upsert_subscription` over a one-row session, the shape
`test_subscription_store_clock.py` already uses. Three cases added pinning the outcomes and the
one-way clock.

The finding's second half — "the superseded branch has no unit case in this file at all" — no longer
holds: fixer 3's CR-17 commit `c84f590` added
`TestADeliveryThatCommitsInTheWindowSupersedesThisOne` with its control.

**`7f7143f` WR-51 — name the spent credit when the write it paid for fails**

`QuotaService.charge` commits a credit in its own session and nothing reverses it, so a failure of
the commit that follows bills a chat that does not exist, and the caller's 500 carried nothing an
operator could match a complaint against. Both charged branches now commit through
`_commit_the_charged_write`, which logs `charged_write_failed` with the user and the branch and
re-raises unchanged. No ledger and no compensating write — the failure still reaches the handler.

## Skipped

**WR-50 — an entitled notification whose term has already closed**

Skipped: both proposed fixes are forbidden by `SHARED-INVARIANTS.md` § Fail-closed defaults, which
this phase's specs make binding.

The finding's option (a) rewrites `status` to `expired` from the payload's dates. The invariant
reads: *"Anything unresolvable, indeterminate, malformed, or of unexpected shape rejects. Never fall
back to a client declaration, token claim, header, email, display name, or cached/stored stand-in"*,
and `services/subscriptions.py:111-112` states the same rule locally — "The store's own word, read
live or from the signed envelope: never derived here." A store that reports `active` with a window
already closed is a self-contradicting payload, and deriving the status from the dates is exactly
the fallback the clause forbids.

The finding's option (b) — append the event row and commit before raising — makes the *second*
delivery of the same contradiction take the replay arm and answer 200 having written no grant and no
canonical update. The invariant reads: *"Divergent stored state is refused, never auto-rewritten or
converged by retry (operator repair only)."* Converging the divergence on the redelivery is that
clause verbatim, and it replaces a loud repeated refusal with a silent success.

The current arm already writes the operator's signal (`logger.error("store_notification_without_term",
…)`) and writes nothing, which is what the invariant requires. The residual cost the finding names
is real but bounded: a closed term grants nothing either way, and on the Google path
`verify_google_play_notification` re-reads `subscriptionsv2.get` live per redelivery, so that store's
case resolves itself once Google's state and expiry converge.

## WR-61 — `fbff9e0` take the shared instant in the challenge route

Root cause: `issue_challenge` computed `datetime.now(UTC)` in its body, the only handler in `src/`
that read the clock instead of taking `Depends(get_evaluated_at)`. The handler now declares

rule 37.4 applied to `get_chat_service`, and it is what `SHARED-INVARIANTS.md` § Grants and
evaluation time requires: one captured evaluation time per request.

## WR-62 — `a1f7da9` leave one log line for an unserved restore store

and `app_error_handler` wrote a second record for a rejection the route had already logged with the
store name it refused. The class is now `log_level = None`, exactly as `InvalidRequest` is for the

`45-01-PLAN.md:425` lists both event names, but it spells the second `restoreproviderunknown`,

Files: `src/nativespeaker/api/errors.py`, `tests/unit/test_rejection_vocabulary.py`.

## WR-63 — `660c215` acknowledge an attributes-only Pub/Sub push instead of looping on 422

Root cause: `PubSubPushMessage.data` was still required, so a push carrying attributes and no data —
a shape Cloud Pub/Sub permits, and what the Cloud Console's "Publish message" with an empty body
sends — answered 422. Pub/Sub acknowledges 2xx alone, so that delivery redelivered until the
retention window expired. `data: str = ""` now defaults, and `developer_notification_from` already
answers `None` for an empty string, so the route logs once and answers 200 with nothing written.

Checked before changing the status code: 44 D-04 ratified "200 and log it" over "422 from a strict
model" and over "5xx so Pub/Sub retries"; `44-03-SUMMARY.md:205` records that Pub/Sub acknowledges
only 102/200/201/202/204, so a 4xx redelivers exactly like a 5xx. Spec
`09-webhook-google-play-rtdn.md` requires 401 for an authentication failure, 200 once the state is
durable and 5xx on internal failure; it requires no 422 for an unusable body. Commit `ffe3092`
landed the same reasoning for the length bound only.

This is a different question from WR-19, which fixer 2 skipped: WR-19 asked for a Pydantic
`max_length`, which cannot bound peak memory because FastAPI reads and parses the body before
validation. Making a field optional removes a refusal rather than adding one, so that measurement
does not apply.

Files: `src/nativespeaker/api/schemas/webhooks.py`, `tests/unit/test_models.py`.

## WR-64 — `372811d` publish the challenge route's response schema

Root cause: `issue_challenge` returned a raw `JSONResponse`, so it declared no `response_model` and

`jsonable_encoder` renders `expires_at` the same as `model_dump(mode="json")` did — and
`test_challenge_endpoint.py`'s key-set and header cases hold unchanged.

Files: `src/nativespeaker/api/routers/auth.py`.

## WR-65 — `f9fbb69` catch both spellings of a re-introduced operation list

Root cause: Application Default Credentials has exactly two routes into a pod, and the chart

### WR-80 — `3301c82` a claim-pin failure was logged as `bad_signature`

### WR-81 — `6ddfb16` the Apple refusal matrix ran one path seven times and missed an arm
