## Phase Boundary

Continue 37.1/37.2/37.3/37.4's de-complication. The phase's specification is the five directives
the developer opened this discussion with; the roadmap goal was still the placeholder
`[Urgent work - to be planned]` when it opened (`.planning/ROADMAP.md:431`), exactly as 37.4's was.

1. **The layered architecture is restored and written down.** Business logic lives in `services/`,
   database access in `crud/`, request and response bodies in `schemas/`, tables in `tables/`,
   HTTP handlers in `routers/`. The auth feature broke this pattern by putting all of it in `auth/`;
   quota broke it by sitting at the top level. Both are moved. The rule goes into `AGENTS.md` so a
   future agent does not break it again.

   in its caller is deleted. One that states a rule or marks a boundary stays.
4. **`assert_tree_total()` is deleted from production code.** Verifying the shape of the code is a
   test's job, not the application's.
5. **The circuit breaker stays** — resolved on the evidence during this discussion, against the

**Out of scope:** which routes are authenticated; phases 38-46's own work; the migration and

## Implementation Decisions

### The layered architecture

- **D-01: The layering rule, written into `ns-api-gateway/AGENTS.md`.** Every file has exactly one
  home, decided by what it is and not by which feature it serves:
  - `services/` — business logic. Orchestration, rules, transaction boundaries.
  - `crud/` — database access. Every `select()`, `add()` and `flush()` in the codebase.
  - `schemas/` — Pydantic request and response bodies, and domain value types.
  - `tables/` — SQLModel table definitions and the enums that mirror database types.
  - `routers/` — HTTP handlers only. `Depends()`-only, no business logic, no queries.
  - `auth/` — external-SDK seams (see D-02).

  This is added to the existing `AGENTS.md`, which already carries 37.4 D-12's prose rules.
  — **Reversibility:** costly — undoing it moves every auth and quota import in `src/` and across
  roughly forty test files. No published contract or migration is involved.

- **D-02: `auth/` keeps only the three external-SDK seam files and nothing else.**
  `jwt_verifier.py` (167), `firebase.py` (164) and `adapters.py` (35) stay. Everything else in the
  package moves out under D-03, D-04 and D-05. These three are the one category the
  services/crud/schemas rule has no home for: they wrap someone else's API, hold no business rule
  and touch no database. Chosen over a new `providers/` package and over folding them into
  `services/` — smallest diff, and the package name still describes what the three files are for.

- **D-03: Business logic moves to a new `services/auth.py`.** `routers/auth.py::_complete`
  (`:85-155`, 71 lines — challenge lookup, binding, claim, commit, provider read, account creation,
  consume) and the business logic in `auth/create_user.py` both move here. `routers/auth.py` is left
  as two thin handlers. This is the largest single violation of the pattern in the codebase.

- **D-04: Database access moves to a new `crud/identities.py`.** `auth/identity.py::resolve_identity`
  (`:26`, the outer-join admission query), `auth/create_user.py::resolve_existing_identity` (`:42`)
  and the insert block in `_insert_account` (`:62-97`, the user, identity and purchase-token rows).
  There is no identity CRUD class today; these queries live in `auth/` directly.

- **D-05: The auth request and response bodies move to a new `schemas/auth.py`.**
  `ChallengeRequest`, `PrepareResponse`, `CreateUserRequest` and `CompletionResponse` are Pydantic
  bodies currently living in `tables/auth.py:27-47`, beside the SQLModel table. `tables/auth.py`
  keeps `AuthChallenge` and `AuthOperation` and nothing else.

- **D-06: `quota.py` becomes `services/quota.py`.** The top-level module dies. **`crud/grants.py`
  is unchanged** — `GrantsDB` already holds every database call quota makes, so the CRUD half of
  the developer's directive was already satisfied. It keeps its name: renaming to `QuotaDB` was
  offered and declined.

### The billing fix

- **D-07: A user is never charged for a request that did not reach the provider.** Today
  `charge_quota()` runs before the request reaches the queue and the circuit breaker, so a
  queue-full 429 and a circuit-open 503 both bill. 37.4 knew this and accepted it (D-07's
  "accepted regression", placed by A-03); this phase reverses that while quota is being rebuilt
  anyway. It is `37.4-REVIEW.md`'s WR-01, still open.

  **Invariants that must survive:**
  - The service's own validation rejections still precede the charge — unsupported language,
    chats limit, chat-not-found, messages limit. This is 37.4 D-07's invariant and it is unchanged.
  - The 429-not-503 property at `resilience.py:73-79` must not regress: a quota rejection must never
    read to a client as a provider outage.
  - **Do not reinstate the callback chain.** 37.4 D-07 deleted `QuotaGate`, the `on_admitted`
    wiring and `_AdmissionRejected` deliberately, and they stay deleted. The charge must remain a
    plain function called at a visible point.
  - A failed provider call is still not refunded. The charge moves earlier-to-later within
    admission, not to after the provider answers.

  **Left to planning:** the exact seam. The charge has to land after the gate and breaker admit but
  before the provider call, which is between two points that currently sit inside
  `ResiliencePolicy.ainvoke`. This is the hardest single piece of the phase and the planner should
  treat it as such.
  — **Reversibility:** reversible — the charge's position is a few lines, and the tests pin the
  behaviour on both sides.

### Function shape

- **D-08: Delete a function that is only a step; keep one that states a rule or marks a boundary.**
  Written into `AGENTS.md`. A boundary is a lock, a transaction, or a callable a library requires.
  The check: inline it, then read the call site — if the call site now needs a comment to explain
  what the code does, the name was carrying meaning and the function stays.

  **Deleted (steps):**
  - `routers/auth.py:85 _complete` — the caller forwards every argument and adds one timestamp.
    Dissolves into D-03's move regardless.
  - `auth/create_user.py:62 _insert_account` — the only thing left in `create_user` after one check.
  - `quota.py:22 consume_quota` and `:72 charge_quota` — the same subject split in two; one opens a
    session and calls the other. They merge under D-06.
  - `resilience.py:108 _sleep_if_positive` — three lines and an `if`.

  **Kept (rules and boundaries):**
  - `firebase.py:133 _verified_email` — the name is the rule: copy the address only when non-empty
    and verified. Also the rule 37.3 deliberately put behind the seam so no consumer re-derives it.
  - `firebase.py:118 _resolve_provider` — the provider classification rule, four rejection branches.
  - `firebase.py:145 _exhausted` — tenacity's `retry_error_callback` must be a separate callable.
  - `jwt_verifier.py:115 _is_known_unknown` and `:126 _record_unknown` — each takes
    `self._cache_lock`; the name marks where the critical section starts and stops.
  - `auth/create_user.py:50 _reject_existing_identity` — decides which rejection an existing row
    earned. A rule, and 37.4 D-04 kept it deliberately. It moves with D-03; it does not dissolve.

  `resolve_existing_identity` needs no ruling: it is a query and moves to `crud/identities.py`
  under D-04.

  **Note for the planner:** 37.2 D-10 already ran a single-caller inline sweep (plan `37.2-06`).
  These are what survived it. Writing the rule into `AGENTS.md` is the part that stops a third pass.

### Self-checks leave production code

- **D-09: `assert_tree_total()` and its two helpers are deleted; the check becomes a test.**
  `errors.py:126 assert_tree_total`, `:80 _tree_problems` and `:65 _undeclared` — roughly 66 lines —
  together with the call at `app/lifespan.py:30` and its import at `:13`. The same checks are
  rebuilt as a unit test: no two classes claim the same code, every leaf declares status and code,
  the declared `ErrorCode` vocabulary is exactly total, and no two classes answer the same framework
  status. Precedent: `tests/unit/test_auth_package_shape.py` already keeps a quality ratchet in
  tests.

  **`_family()` and `class_answering_status()` survive — they are live dispatch, not self-checks.**
  `app/error_handlers.py:58` calls `class_answering_status` on every framework-raised 404, 405 and
  422 to find the class that answers a bare status. Deleting them breaks request handling. The
  planner must not read them as part of the same block.

  **Consequence, recorded and accepted:** a defective error tree currently refuses to boot. It will
  fail in the test run instead. Deploying without running the tests turns a refused start into
  served 500s. This is the ordinary trade and the developer chose it knowingly.

  `assert_tree_total` is the last startup self-check in `src/` — `warn_missing_older` went with the
  HMAC keyring and the route-enumeration assertion went in 37.1. There is no second instance to
  find. The two `assert isinstance` lines in `app/error_handlers.py:37,57` are type narrowing for
  the checker, not quality gates; they are `37.4-REVIEW.md` IN-03's subject and are left to
  Claude's discretion under the standing rule.

- **D-10: Four dead exception classes are deleted — not five.** `InvalidCursorError` (`:233`),
  `PageSizeLimitError` (`:240`), `WebhookVerificationError` (`:256`) and
  `DatabaseNotInitializedError` (`:302`) have zero raise sites and no reference anywhere in `src/`
  outside `errors.py`. They are leftovers from deleted features, and every one of them is walked by
  `_family()` on each framework-status rejection. This is `37.4-REVIEW.md` IN-01, unactioned.

  **`ChallengeRequired` (`:177`) stays.** It was offered for deletion in this discussion and the
  offer was wrong: it declares `answers_framework_status = True` at status 409, so
  `class_answering_status(409)` resolves to it, and it carries the `challenge_required` code that
  `02-create-user.md` requires the registry be pre-populated with. Deleting it would turn a bare
  framework 409 into `error_registry_unmapped_status` and a 500, and would drop a mandated code from
  the vocabulary. **The planner must not delete it.**

  None of the four deleted classes declares its own `code`, so no code leaves `ErrorCode` and
  D-09's relocated totality test is unaffected. A handful of tests reference them and are pruned
  with them.

### Resilience

- **D-11: The circuit breaker stays, and why is written into `AGENTS.md`.** The developer opened
  this discussion expecting a hand-rolled rate limiter in `resilience.py` still awaiting replacement
  by a library already in the tree. The evidence, gathered during the discussion:
  - **The retry loop was already replaced with tenacity** — commit `2afa7fd`, *"run ainvoke's retry
    on tenacity, retiring the last hand-rolled loop"*. `resilience.py:8,149-160` is tenacity. That
    is the library, and it is already in.
  - **`limits` was never in this project.** `git log -S'limits' -- pyproject.toml` is empty. Phase
    35 D-05 deleted the whole backend rate-limit engine before it was ever added (PROJECT.md:112).
  - **What remains hand-rolled is not rate limiting.** It is `CircuitBreaker` (`:39-70`, 32 lines),
    `LLMExecutionGate` (`:73-100`, 28 lines) and the OpenAI transient classifier (`:14-36`).
  - **No installed package replaces them.** All 110 packages in `.venv` were enumerated: the only
    resilience-relevant ones are `tenacity` (in use) and `anyio` (transitive, has `CapacityLimiter`,
    has no circuit breaker). Finishing the idea would mean adding a new dependency, not adopting a
    present one.

  Deletion was then costed at the configured values (`pool_size: 5`, `queue_size: 25`,
  `timeout: 30`, `attempts: 3`, `threshold: 5`, `reset: 60`) and declined:
  - tenacity bounds one request — 3 attempts at 30s plus backoff, about 91.5s. It bounds nothing
    across requests, so every request during an outage pays the full 91.5s from scratch. The breaker
    is the cross-request control, and `CircuitOpenError` is re-raised unclassified in `attempt()` so
    tenacity does not retry it. The two bound different things.
  - With 30 slots each held 91.5s instead of released instantly, the gate saturates and the
    client-visible answer flips from 503 with `Retry-After: 60` to 429 with `Retry-After: 2` —
    wrong advice, and it reads as "you are rate-limited" when the truth is the provider is down.

  **`resilience.py` is therefore not a refactor target this phase**, beyond D-08's deletion of
  `_sleep_if_positive` and D-12's sweep.

## Specific Ideas

- The developer's example of a comment that fails the bar, quoted directly:
  *"'A malformed or indeterminate response, which is retryable rather than definitive.' goes before
  `logger.warning("firebase_provider_data_malformed", ...)` — the log already says the data is
  malformed, why would you repeat the same in the comment? It's useless."* D-12 is written against

- On the architecture: *"My app had a neat architecture where all business logic lived in services/
  which called DB operations using DB classes from crud/. The new authentication system broke this
  pattern."* The `AGENTS.md` half of D-01 matters as much as the moves — the pattern was broken by
  agents who had no written rule to follow.
- On split functions: *"create_user() has only one call `_complete()` — WTF? Why would you write a
  function that all it does is calling another function?"* D-08's rule is the durable form of that
  objection.
- On self-checks: *"This is a job for the test to verify the code quality. It's inherently stupid to
  bloat the production code with this nonsense."*
- **The resilience item resolved against the developer's initial expectation.** They asked why the
  hand-rolled rate-limit code had not been replaced by a library already in the tree, then asked for
  the full consequences of deleting the breaker before deciding. The retry replacement had already
  happened (tenacity, `2afa7fd`); `limits` was never present; nothing installed replaces a circuit
  breaker; and deletion costed badly at the configured values. Recorded because the reasoning, not
