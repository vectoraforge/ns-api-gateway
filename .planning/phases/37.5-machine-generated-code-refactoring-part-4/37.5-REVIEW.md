# Phase 37.5: Code Review Report

**Reviewed:** 2026-08-31
**Depth:** standard

## Summary

The admission/charge seam does what the phase claims on the *narrow* question asked of it:
a request rejected by the breaker or the queue is not billed, and the charge sits outside the
retry so three attempts bill once. I could not construct a double-charge or a
charged-but-never-called path through `ChatService`.

The seam is not clean, though. Moving the gate hold from around the provider call to around
the *whole* caller body put a second database connection checkout inside the LLM concurrency
semaphore. At the shipped defaults (`db.pool_size = 5`, `max_overflow = 0`,
`resilience.pool_size = 5`) that is a hard connection-pool deadlock at five concurrent chat
POSTs, and a self-amplifying 503 storm below that (CR-01). The same move silently removed the
per-attempt circuit-breaker check (WR-02) and left a now-unreachable `except` clause behind
(WR-03).

The other three blockers are not in the billing seam. The validation-error handler writes the
offending request body into the log, which is a concrete leak path for the secret challenge
handle that four separate comments in this tree promise is never logged (CR-02). And the chat
message ordering contradicts its own OpenAPI description in two directions — clients get the
transcript backwards (CR-03), and the LLM gets the conversation history in unspecified order
(CR-04).

The docstring sweep is the weakest part of the phase relative to its own stated goal. The gate
that landed (`tests/unit/test_docstring_bar.py`) enforces only the *line count* from
AGENTS.md, not the substantive rules in the same section; a large fraction of shipped
docstrings still define their subject by naming code that is not in them. Several comments
were compressed into statements that are now false (WR-01, WR-05, WR-13, WR-14).

The known open item is confirmed: `routers/auth.py::issue_challenge` violates the
`Depends()`-only rule this phase itself wrote. Two further layering violations are reported
alongside it (WR-07, WR-08).

## Critical Issues

### CR-01: Quota charge now runs inside the LLM admission hold, deadlocking the DB pool

**File:** `src/nativespeaker/api/resilience.py:133-138`, `src/nativespeaker/api/services/chats.py:92-93,116-117`, `src/nativespeaker/api/app/dependencies.py:69-71`

**Issue:** Before this phase, `LLMExecutionGate` was entered inside `attempt()` and held only
around the timed provider call; `charge_quota` ran before it, holding nothing. The phase moved
the hold out to `admission()` and moved the charge inside it. The charge opens a **second**
database session from the same engine (`get_quota_service` deliberately passes the factory,
not `get_db`), while the request session opened by `get_db` is already holding a connection —
`ChatsDB.count_chats` / `get_chat` runs before admission and SQLAlchemy holds that connection
in an open transaction until `get_db` commits at the end of the request.

`lifespan.py:34` builds the engine with `max_overflow=0`, and `config.py:25` defaults
`db.pool_size` to 5. `config.py:34` defaults `resilience.pool_size` to 5 — exactly the number
of connections in the pool.

Trace five concurrent `POST /chats`:

1. Each runs `count_chats` → all 5 pool connections are checked out and held.
2. All 5 pass admission (semaphore has 5 slots).
3. All 5 call `QuotaService.charge`, each requesting a **sixth** connection.
4. Nobody can release a connection, because every holder is blocked inside `charge`.
5. All 5 block for SQLAlchemy's 30 s pool timeout, then fail with 500.

Below five concurrent requests it is not a permanent deadlock, but it is worse than before:
each stalled charge now holds an LLM semaphore slot, so the 30 s of DB waiting fills the gate
and every other request gets `QueueFullError` 503 for LLM capacity that is completely idle.
A slow database is now indistinguishable from a saturated LLM.

**Fix:** The engine must be able to hand out two connections per in-flight request. At
minimum:

```python
# lifespan.py
db_engine = create_async_engine(
    config.db.url,
    pool_size=config.db.pool_size,
    # Two concurrent checkouts per request: the request session and the quota session.
    max_overflow=config.db.pool_size,
    pool_timeout=5,
)
```

and size `db.pool_size >= resilience.pool_size + resilience.queue_size` in `config/config.yaml`,
or add a `model_validator` on `AppConfig` that rejects a configuration where
`db.pool_size < resilience.pool_size`. Better still, take the charge back out of the admission
hold — it needs the breaker's verdict, not the concurrency slot:

```python
# services/chats.py
async with self.llm_service.admission() as admitted:
    ai_message = await self.ask_llm(chat, human_message, admitted)
```
with the charge issued immediately before `async with`, after the breaker is consulted via a
separate `policy.check_breaker()` call. That restores the pre-phase concurrency shape while
keeping the "not billed if the breaker is open" property the phase was after.

### CR-02: The validation-error handler logs the request body, leaking the secret challenge handle

**File:** `src/nativespeaker/api/app/error_handlers.py:48`

**Issue:**

```python
logger.error("Validation error", exc_info=exc)
```

`exc` is a FastAPI `RequestValidationError`. Its `args` carry Pydantic's error list, and every
entry in that list contains an `input` key holding the **offending value verbatim**. Rendering
the traceback writes that list into the log.

`CreateUserRequest.challenge_id` (`schemas/auth.py:26`) is the secret capability handle. A
caller who sends it with the wrong JSON type triggers the leak:

```
POST /auth/create-user  {"challenge_id": ["<live-handle>"]}
→ RequestValidationError: [{'type': 'string_type', 'loc': ('body','challenge_id'),
                            'input': ['<live-handle>'], ...}]
→ written to stderr by ConsoleRenderer
```

This directly defeats the invariant asserted in four places in this tree:
`crud/challenges.py:1` ("this module holds no logger, so none is logged"),
`tables/auth.py:32-34` ("never in a URL, a log, a trace, or error text"),
`routers/auth.py:44` ("a handle never is"), and `routers/auth.py:67` ("never logged"). The
handle stays live for its full 300 s TTL. Blast radius is modest — the value is the caller's
own, single-use, and short-lived — but the invariant is load-bearing and the leak is trivially
reproducible, and any future secret-bearing body field inherits it.

Note `hide_input_in_errors=True` is set on `BaseConfig` in `config.py:16` (settings only) and
on none of the API schemas, so nothing suppresses this today.

**Fix:** Never pass the exception object; log only the shape of the failure.

```python
async def validation_error_handler(request: Request, exc: Exception) -> JSONResponse:
    assert isinstance(exc, RequestValidationError)
    # Locations and types only: `input` carries the caller's value, which may be a secret.
    logger.warning("validation_error",
                   problems=[{"loc": ".".join(str(p) for p in e["loc"]), "type": e["type"]}
                             for e in exc.errors()])
    return await app_error_handler(request, ValidationError())
```

Add a regression test that posts `{"challenge_id": ["SENTINEL"]}` to `/auth/create-user` and
asserts `SENTINEL` appears nowhere in captured log output.

### CR-03: `GET /chats/{chat_id}` returns messages newest-first while its OpenAPI description promises chronological order

**File:** `src/nativespeaker/api/routers/chats.py:32` (contract), `src/nativespeaker/api/crud/chats.py:46` (cause)

**Issue:** The endpoint ships this description into the OpenAPI document:

```python
description="Returns all messages in a chat session, ordered chronologically."
```

`ChatsDB.get_messages` orders by `col(Message.id).desc()`. `Message.id` is
`default_factory=uuid7` (`tables/chats.py:26`), which is time-ordered, so `.desc()` is
strictly **reverse** chronological. Any client written against the published contract renders
the transcript backwards, and the human/AI turn pairing inverts. There is no test asserting
message order in the returned list.

This is pre-existing rather than introduced by the phase, but `routers/chats.py` is in scope
and the contradiction is unambiguous: one of the two is wrong.

**Fix:** Correct the implementation, not the description — chronological is the order a chat
transcript wants.

```python
# crud/chats.py::get_messages
.order_by(col(Message.id).asc())
```

Add `test_messages_come_back_oldest_first` asserting the returned `created_at` sequence is
non-decreasing.

### CR-04: LLM conversation history is built from an unordered relationship load

**File:** `src/nativespeaker/api/services/chats.py:50-54`

**Issue:**

```python
for history_msg in chat.messages:
```

`chat` comes from `ChatsDB.get_chat`, which loads `Chat.messages` via
`selectinload(Chat.messages)`. The relationship is declared with no ordering
(`tables/chats.py:44`: `Relationship(cascade_delete=True, passive_deletes=True)`), and
`selectinload` emits `SELECT ... WHERE chat_id IN (...)` with no `ORDER BY`. PostgreSQL
guarantees nothing about the row order of such a query — it depends on the plan, and changes
when the table is updated, vacuumed, or grows past a seq-scan threshold.

The consequence is that a multi-turn follow-up can hand the model an out-of-order transcript.
The model then answers the wrong turn, and the user is charged for it (the charge has already
committed by the time `ask_llm` runs). It is silent: no error, no log, just a worse answer.

`send_message` also appends the new `human_message` to `chat.messages` **after** `ask_llm`
(lines 118-120), so at least the current turn is not duplicated into its own history — but
that is the only ordering property currently guaranteed.

**Fix:** Pin the order at the relationship, so every loader path gets it:

```python
# tables/chats.py
messages: list[Message] = Relationship(
    cascade_delete=True,
    passive_deletes=True,
    sa_relationship_kwargs={"order_by": "Message.id"},
)
```

Add a test that seeds a chat whose rows are inserted out of id order and asserts the
`HumanMessage`/`AIMessage` sequence handed to the mocked LLM is chronological.

### WR-01: `Admitted` enforces nothing, and its docstring says otherwise

**File:** `src/nativespeaker/api/resilience.py:105-107,140`, `src/nativespeaker/api/services/llm.py:36-40`

**Issue:** The docstring claims `"Only ResiliencePolicy.admission mints one."` That is false.
`Admitted` is a public frozen dataclass with a public zero-argument `__init__`; anything that

docstring asserts a guarantee the code does not provide — precisely the register AGENTS.md
§ Comments and docstrings bans.

**Fix:** Either make the token real, or delete it and say what is actually true. Real version:

```python
@dataclass(frozen=True, slots=True)
class Admitted:

    _policy: "ResiliencePolicy"

# in ainvoke
if admitted._policy is not self:
    raise RuntimeError("ainvoke called without an admission from this policy")
```

Honest version: drop the parameter and rewrite the docstring to
`"""A marker that the caller entered `admission()`."""`

### WR-02: The circuit breaker is no longer consulted between retry attempts

**File:** `src/nativespeaker/api/resilience.py:136`

**Issue:** Before this phase, `await self._circuit_breaker.before_call()` was the first line of
`attempt()`, so every retry re-consulted the breaker and a request in flight when the breaker
tripped aborted immediately with `CircuitOpenError`. The phase moved it to `admission()`,
where it runs exactly once.

An admitted request now burns all three attempts against a provider the breaker has already
declared dead: 3 × 30 s timeout + backoff ≈ 91.5 s, with an LLM semaphore slot held the whole
time. AGENTS.md § Resilience states the breaker's purpose is exactly that "without the breaker
every request during a provider outage pays that from scratch" — the phase reintroduced that
cost for every request already past admission.

**Fix:** Re-consult the breaker at the top of each attempt, letting `CircuitOpenError` escape
through the existing pass-through clause:

```python
async def attempt() -> Any:
    await self._circuit_breaker.before_call()
    try:
        result = await asyncio.wait_for(operation(), timeout=self._timeout_seconds)
    except (QueueFullError, CircuitOpenError):
        raise
    ...
```

This also makes WR-03's `except` clause live again.

### WR-04: `_is_transient_error` — the `APIStatusError` branch is subsumed by the code below it

**File:** `src/nativespeaker/api/resilience.py:30-36`

**Issue:**

```python
if isinstance(exc, APIStatusError):
    status = _extract_status_code(exc)
    if status in {408, 409, 429, 500, 502, 503, 504}:
        return True
status = _extract_status_code(exc)
if status in {408, 409, 429, 500, 502, 503, 504}:
    return True
```

Lines 34-36 run `_extract_status_code` and the identical set membership unconditionally. The
`isinstance` branch can never return `True` for a case the unconditional block would miss —
it is dead, and it duplicates the magic status set.

Separately, `_extract_status_code` returns `getattr(exc, "status_code")` untyped: a provider
that exposes `status_code` as a string (`"429"`) fails the set membership and is misclassified
as permanent.

**Fix:**

```python
_TRANSIENT_STATUSES = frozenset({408, 409, 429, 500, 502, 503, 504})

def _is_transient_error(exc: Exception) -> bool:
    if isinstance(exc, (asyncio.TimeoutError, TimeoutError)):
        return True
    if isinstance(exc, (APIConnectionError, APITimeoutError, RateLimitError, InternalServerError)):
        return True
    status = _extract_status_code(exc)
    return status is not None and int(status) in _TRANSIENT_STATUSES
```

### WR-05: `ChallengeRequest.operation` is unbounded and logged verbatim; the comment claims it is bounded

**File:** `src/nativespeaker/api/routers/auth.py:44-45`, `src/nativespeaker/api/schemas/auth.py:13`

**Issue:**


`operation: str` carries no `max_length` and no `pattern`. Nothing between the client and this

```python
class ChallengeRequest(BaseModel):
```

### WR-06: `issue_challenge` violates the `Depends()`-only rule AGENTS.md establishes for `routers/`

**File:** `src/nativespeaker/api/routers/auth.py:35-55`

**Issue:** AGENTS.md § Package layout: "`routers/` — HTTP handlers, `Depends()` only", and
`services/` owns "orchestration, rules, transaction boundaries". `issue_challenge` breaks all
three:

- **Business rule** (line 43): `if body.operation != AuthOperation.create_user.value` — the
  issuable-operation set is a domain rule, decided in the handler.
- **Direct query** (line 48): calls `challenge_store.issue(session, ...)`, a `crud/` method,
  with no service between them.
- **Session as a parameter** (line 37): takes `session: AsyncSession = Depends(get_db)` and
  hands it to a CRUD method. Every other route reaches the database only through a service.
- **Clock read** (line 41): `evaluated_at = datetime.now(UTC)` in a router. Everywhere else the
  instant is captured in `dependencies.py` and injected (`get_chat_service:86`,
  `get_auth_service:107`).

The result is that the only transaction boundary for challenge issuance is the implicit commit
in `get_db`, invisible from `services/`.

**Fix:** Add `AuthService.issue_challenge` and reduce the handler to a call:

```python
# services/auth.py
async def issue_challenge(self, *, operation: str, identity: Identity) -> tuple[str, datetime]:
    """Issue one challenge for an issuable operation, or raise."""
    if operation != AuthOperation.create_user.value:
        logger.warning("auth_challenge_operation_not_issuable", operation=operation)
        raise InvalidRequest
    result = await self.challenge_store.issue(self.session,
                                              operation=AuthOperation.create_user,
                                              identity=identity,
                                              now=self.evaluated_at)
    await self.session.commit()
    return result
```

The handler then takes only `body`, `identity` and `service: AuthService = Depends(get_auth_service)`.

### WR-11: A deterministic `ValueError` is classified retryable, costing three provider calls to reach a permanent answer

**File:** `src/nativespeaker/api/auth/firebase.py:86-88`

**Issue:** `except ValueError` → `RetryableLookupError`. Two things reach that arm, and neither
is transient:

1. `auth.get_user(subject, app=app)` raises `ValueError` for a malformed uid. The `subject`

**Fix:** Classify the deterministic arm as permanent. `NotLinked` (403, `operation_not_allowed`)
already exists for exactly this shape:

```python
except ValueError as error:
    logger.warning("firebase_provider_data_malformed", detail=str(error))
    raise NotLinked(stage="provider_lookup", cause="invalid-shape") from error
```

### WR-12: Quota rollover can rewind the period and zero the current month's usage

**File:** `src/nativespeaker/api/services/quota.py:55-60`

**Issue:**

```python
period = evaluated_at.strftime("%Y-%m")
if usage.monthly_period != period:
    usage.monthly_used = 0
    usage.monthly_period = period
```

The comparison is inequality, not ordering, so it rolls **backwards** as readily as forwards.
`evaluated_at` is captured in `get_chat_service` at the start of the request, and the charge
commits after the row lock is acquired, so at a UTC month boundary two requests can interleave:

- Request A (`evaluated_at` in `2026-09`) takes the lock, rolls over to `used=0`, charges to 1,
  commits.
- Request B (`evaluated_at` in `2026-08`, started seconds earlier, blocked on the lock) now
  sees `monthly_period == "2026-09" != "2026-08"`, **resets `monthly_used` to 0**, writes the
  period back to `2026-08`, charges to 1, commits.

Request A's charge is erased. The next request in September rolls over again to 0. The window
is narrow (seconds around the UTC month boundary, once a month) and the product is a ~$5/month
subscription, so this is not an economic threat — but it is a silent write of stale state over
fresh state, and the comment on line 58 asserts a safety property the code does not have.

**Fix:** Roll over only forwards, and treat a backwards period as a stale request:

```python
if usage.monthly_period < period:
    usage.monthly_used = 0
    usage.monthly_period = period
elif usage.monthly_period > period:
    # A request whose captured instant predates the stored period: charge the stored one.
    period = usage.monthly_period
```

`"%Y-%m"` strings sort correctly, so `<` / `>` are safe here.

### WR-13: `lifespan` has no `try`/`finally`; a failed startup leaks the named Firebase app and the engine

**File:** `src/nativespeaker/api/app/lifespan.py:31-58`

**Issue:** `build_admin_apps` registers process-global named apps at line 31, and
`create_async_engine` allocates a pool at line 34. Everything after that — `JWTVerifier`
construction, `LLMService` construction (which calls `init_chat_model` and can raise on a bad
model name or missing API key) — runs outside any handler. If any of it raises, `yield` is
never reached, so `db_engine.dispose()` and `firebase_admin.delete_app(...)` at lines 52-56
never run. The same is true if the ASGI server throws into the generator at the `yield`.

The comment on line 54 states the consequence precisely — "firebase_admin registers named apps
process-globally and raises on a repeat, so a second boot needs these gone" — and the code
does not deliver it. In-process retries (uvicorn `--reload`, or a test that boots the app twice
after one failure) hit `ValueError: The default Firebase app already exists`, masking the real
startup error with a confusing second one.

**Fix:**

```python
    try:
        ...
        yield
    finally:
        await db_engine.dispose()
        for firebase_app in firebase_apps.values():
            firebase_admin.delete_app(firebase_app)
        logger.info("shutdown")
```

with `db_engine` and `firebase_apps` initialized to `None` / `{}` before the `try` and guarded
in the `finally`.

### WR-14: Expired challenges are never reaped, retaining `preauth_subject` in plaintext indefinitely

**File:** `src/nativespeaker/api/crud/challenges.py:77-88`, `src/nativespeaker/api/tables/auth.py:43`

**Issue:** `tables/auth.py:43` documents `preauth_subject` as "The verified subject in
plaintext, cleared by consumption", and `consume()` does clear it. But consumption only happens
on the completion path. A challenge that is issued and then abandoned — the overwhelmingly
common case for a client that starts sign-up and stops — is never claimed, never consumed, and
never deleted. Its row keeps the user's verified provider subject in plaintext forever.

There is no reaper, no TTL-based delete, and no cap on issuance per identity (`issue_challenge`
inserts a row for every authenticated `POST /auth/challenge` with no per-user limit). The table
grows monotonically with a plaintext identifier per abandoned attempt.

The stated invariant is therefore true only on the happy path, and the comment reads as if it
holds always.

**Fix:** Add a periodic reaper — a `DELETE FROM core.auth_challenges WHERE expires_at < now() -
interval '1 day'` on a Kubernetes CronJob is enough — and correct the comment to
`# The verified subject in plaintext, cleared on consumption.` Consider clearing
`preauth_subject` in the reaper's `UPDATE` rather than only in `consume()`.

### WR-15: The docstring gate enforces only the line count, and does not cover new `tests/` subdirectories

**File:** `tests/unit/test_docstring_bar.py:42-53`

**Issue:** Two gaps.

**Coverage.** `BASELINE` enumerates `src`, `tests`, `tests/e2e`, `tests/schema`, `tests/unit`,
and `_measure` walks the `tests` root with `recurse=False`. A new `tests/integration/`
directory is measured by nothing — the `tests` entry does not descend into it, and it has no
entry of its own. The gate silently stops covering the tree it is supposed to ratchet.

**Substance.** AGENTS.md § Comments and docstrings states four rules: three lines maximum,
*state what the entity does*, *do not describe what lives somewhere else*, and *do not define
the entity by what it is not*. The gate measures only the first. Shipped code still violates
the other three throughout:

- `resilience.py:107` — "Only `ResiliencePolicy.admission` mints one." (names other code; and
  is false, see WR-01)
- `resilience.py:111` — "`TransientLLMError` and nothing else, already classified by the
  attempt body." (defines by negation; names other code)
- `crud/challenges.py:1` — "this module holds no logger, so none is logged" (defines by absence)
- `firebase.py:1-3` — "never a `[DEFAULT]` app. Never take the first recognized entry, and
  never classify non-empty providerData as anonymous. Never read `firebase.sign_in_provider`"
  (three consecutive negations; rules enforced elsewhere)
- `adapters.py:2` — "Failure is raised, never returned."
- `errors.py:30` — "Exactly one field -- do not add more."
- `dependencies.py:65` — "The one factory the lifespan built." (names another module)
- `crud/identities.py:54` — "Not the race arbiter, and never to be one."

The phase's own summary claims the docstring bar was met; the gate that certifies it cannot see
most of what the bar says.

**Fix:** For coverage, walk `tests` recursively with a single entry rather than enumerating
subdirectories:

```python
BASELINE: dict[str, int] = {"src": 0, "tests": 0}

def _measure(root: str) -> int:
    return len(over_long(REPO / root))
```

For substance, either add a mechanical check for the negation register (a regex over docstrings
for `\bnever\b|\bnot\b|\bnothing\b|\belsewhere\b` with a recorded baseline, ratcheted the same
way), or drop the claim that the gate enforces AGENTS.md and rename it to what it measures —
`test_docstring_length.py`.

### WR-16: `Dockerfile` pins Python 3.12; the in-scope table modules require 3.14

**File:** `src/nativespeaker/api/tables/auth.py:5`, `src/nativespeaker/api/tables/identities.py:5` (cause), `Dockerfile:1,10` (site)

**Issue:** Both table modules do `from uuid import UUID, uuid7`. `uuid.uuid7` landed in Python
3.14, and `pyproject.toml:4` correctly declares `requires-python = ">=3.14"`. The Dockerfile
builds and runs on `python:3.12-slim`. The container cannot import `tables/auth.py` — it fails
at boot with `ImportError: cannot import name 'uuid7' from 'uuid'`.

The Dockerfile also runs `uvicorn app.main:app`, but the module is
`nativespeaker.api.app.main`, and its `HEALTHCHECK` GETs `/`, which `routers/root.py:10` puts
behind `get_linked_identity` — an unauthenticated healthcheck that can only ever 401.

`Dockerfile` is outside the reviewed file set, so this is reported from the in-scope side: the
`uuid7` dependency these two modules introduce is not satisfiable by the shipped image.

**Fix:** `FROM python:3.14-slim` in both stages, `CMD ["uvicorn", "nativespeaker.api.app.main:app", ...]`,
and point the healthcheck at the unauthenticated `/health/ready` route.

### WR-17: The charge commits independently; a failure of the request-session commit bills a user who gets no answer

**File:** `src/nativespeaker/api/services/chats.py:92-98`, `src/nativespeaker/api/app/dependencies.py:22-29`

**Issue:** `QuotaService.charge` commits in its own transaction (`quota.py:79`). The chat and
its messages are added to the *request* session and committed later, in `get_db`'s teardown.
Between those two commits sit the provider call and the whole rest of the handler.

If `get_db`'s `session.commit()` fails — FK violation, connection dropped, pool timeout per
CR-01 — the exception propagates, the client receives a 500 with no analysis, and the charge
stands. There is no compensating decrement anywhere in the tree, and no log line correlating
the charge to the failed write.

The module docstring's "A failed provider call is not refunded" (`quota.py:2`) covers the
provider; it does not cover the service's own failure to persist after a *successful* provider
call. That case is unstated and unhandled.

**Fix:** At minimum, make the case observable so it can be reconciled:

```python
# services/chats.py::create_chat
self.chats_db.create_chat(chat)
# The charge is already committed in its own transaction; a failure past this point is billed.
```

and add an `except Exception:` around the persist that logs
`logger.error("charged_write_failed", user_id=..., branch="create_chat")` before re-raising.
Better: move the chat persist ahead of the charge, or record charges in an append-only ledger
keyed by request id so a reconciliation job can find orphans.
