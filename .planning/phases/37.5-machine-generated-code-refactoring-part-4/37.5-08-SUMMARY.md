## Three flags on the list, for the developer

**Flag 1 — the wire-contract class had eight cases, and the eighth was kept.** The plan describes "seven cases", names two keeps and directs five deletions. The file holds eight. Five went; `test_trailing_content_after_the_token_degrades_to_a_verification_failure` stayed.

It stayed because nothing else covers it. `HTTPBearer` splits the header at the first space, so a `Bearer <token> extra` value hands `<token> extra` to the verifier whole. If a future framework version took `param.split()[0]` instead, a valid token followed by arbitrary content would authenticate. The comma-joined case (deletion 5) does **not** cover this: `"<token>, Bearer <token>".split()[0]` is `"<token>,"`, which still fails verification, so that case would go on passing. `test_an_unverifiable_token_answers_auth_required` feeds `"Bearer not.a.jwt"`, a different input entirely.

This is the same reasoning that keeps the two A-09 cases: they record what `HTTPBearer` does with a value the deleted extractor judged differently, and this is the third such record. **If the developer wants the plan's literal count, deleting it costs seven lines and the property goes unenforced.**

**Flag 2 — deletion 3's log-event half rests on a code-path argument, not on a second case.** `test_a_non_bearer_scheme_answers_401_and_still_records_the_event` asserted two things: the 401, which two survivors cover directly, and that the `invalid_external_jwt` record is still emitted for a `Basic` scheme. No surviving case parametrizes the recording spy over a non-Bearer scheme. The argument for deleting it anyway is that `HTTPBearer(auto_error=False)` returns `None` for both an absent header and a non-Bearer one, so the raise is literally the same `credential is None` arm the `[absent-token]` case drives — a claim about the code path, not about the response shape. It is named here because it is the one deletion in this plan whose survivor is an argument rather than a case.

**Flag 3 — `TestTheLockingStatements` is not duplicated at the wire level, and was kept whole.** The plan directs a cut on the ground that "the compiled-SQL grep cases duplicate the effective-grant statement class at the wire level". The wire-level file is `tests/schema/test_grant_locks.py`, and its `_LOCK_GRANTS` is a hand-written SQL string with the comment *"Mirrors GrantsDB.lock_effective_grants"*. It is a mirror: it proves what PostgreSQL does with that SQL, not that the resolver emits it.

Concretely, if `FOR UPDATE` were dropped from `lock_effective_grants` tomorrow, `test_grant_locks.py` would go on passing — it never touches the resolver. `test_the_effective_grant_statement_locks_and_orders_ascending_by_id`, `test_the_usage_statement_locks` and `test_the_tier_statement_takes_no_lock` are the only cases in the repository that read the resolver's own compiled statement. The three predicate-boundary cases (`starts_at <=` not `<`, `ends_at >` not `>=`, `ends_at IS NULL`) are likewise unreachable behaviourally, because the stub session returns scripted rows rather than executing the predicate. **All six were kept.** This is a cut the plan asked for and this execution declined; if the developer wants it, the honest version is a schema-level case that executes the resolver's real statement, not a deletion.
