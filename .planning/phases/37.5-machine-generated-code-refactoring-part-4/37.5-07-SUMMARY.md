## Four flags on the list, for the developer

**Flag 1 — `test_the_one_401_the_responses_block_documents_is_the_answering_class` was not a retired-string check.** Four of `TestRetired401Code`'s five cases checked an absence; the fifth checked two live facts — that `real_app.router.responses[401]["model"] is ErrorResponse`, and that `class_answering_status(401).code == "auth_required"`. Nothing else in the repository covers either. `test_no_status_is_folded_onto_another` still checks that 401 has *an* answering class at status 401, but not which code it carries. The plan's acceptance criterion is `grep -c 'class TestRetired401Code'` returning 0, and its no-weakening gate forbids adding an assertion line anywhere in the same commit, so the case could not be relocated into `TestTheFrameworkStatusMap` — it had to go whole or stay whole. It went. **Restoring it as two lines inside `TestTheFrameworkStatusMap` is the cheapest fix if the developer wants the property back.**

**Flag 2 — the challenge store's four scans were architectural guarantees, not language ones.** This is the distinction plan 06 raised about `test_foundation_calls_no_adapter_method_anywhere_in_src`, and it applies to all four here:

| Deleted case | What now enforces it |
|---|---|
| `test_the_module_takes_no_database_lock` | Nothing. The conditional update is meant to be the single serialization point; a second lock added later fails no test. |
| `test_the_module_embeds_no_raw_sql` | Nothing. The v1.6 zero-raw-`text()` convention is unenforced for this module. |
| `test_the_module_logs_nothing` | Nothing, **for this module**. See below. |
| `test_the_module_derives_no_hash_of_its_own` | Nothing. A second, plausible-looking digest that silently never matches at completion would ship green. |

**`test_the_module_logs_nothing` is the one worth a decision.** It backed a security property — the challenge handle is a secret capability, and the module that mints it held no logger to log it with. The *behavioural* handle-secrecy cases the plan protects are elsewhere and survive untouched: `test_create_user_precedence.py::test_the_handle_never_reaches_either_log` and `test_create_user_body.py::test_a_padded_handle_reaches_completion_untouched`. But those cover the completion handler, not `crud/challenges.py` itself. `grep -n 'structlog\|logging' src/nativespeaker/api/crud/challenges.py` returns nothing today, so the property holds; nothing fails if a later phase adds a logger there. Restoring just that one case as a three-line class would cost about six lines.

**Flag 3 — `test_rejects_token_signed_with_different_key` was the only case covering a well-formed token an attacker signed with their own key.** The surviving `test_rejects_tampered_payload` covers the signature spanning the payload; `test_rejects_hs256_signed_with_the_public_key` covers the algorithm list being honoured. Neither covers an RS256 token signed by an *unknown but valid* RSA key — that is the JWKS key-matching path, exercised indirectly by `TestTheJwksTransportIsNotHitPerRequest` (every unknown-`kid` case there ends in `bad_signature`) but never with a genuinely different signing key under a *known* `kid`. It went under the plan's one-case-per-path instruction and is named here because it is the one JWT deletion not entailed by a survivor.

**Flag 4 — `test_accepts_token_with_extra_claims` was the only case covering that unrecognised claims do not break acceptance.** A future `options={"strict": …}` or a claim allow-list would now ship green. Real Firebase tokens carry a `firebase` object and custom claims, so this is a live shape, not a hypothetical one. It went under "collapse to one case each"; restoring it costs three lines.

## The security case for keeping two algorithm cases

The plan says one representative per distinct path and names "a bad algorithm" as one. `TestAlgorithmSecurity` kept **two**: `test_rejects_alg_none` and `test_rejects_hs256_signed_with_the_public_key`.

These are distinct *implementation defects*, not distinct samples of one. `alg:none` is the "signature never verified at all" defect; HS256-over-the-public-key is the "wrong algorithm accepted, public key used as an HMAC secret" defect. Neither case entails the other, and `TestProductionVerifier` covers only the second against the real verifier. `test_rejects_hs256_token` — HS256 with the string `"secret-key"` — *is* entailed by the public-key variant, since both fail at the same `algorithms=["RS256"]` check and the public-key one is the harder input. That one went; the other two stayed.

This is the plan's rule applied one level finer, and it deletes less rather than more. It is called out because it is a deliberate reading rather than a literal one.
