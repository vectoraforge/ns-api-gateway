`auth/firebase.py` (D-01, D-02, D-05, D-06) — add four names beside their read twins:
  - `FirebaseAdminLookup.revoke_refresh_tokens(self, issuer, subject) -> None`, an async method
    placed under `get_user_provider_data`. It reads `self._apps.get(issuer)`; when that is `None`
    it raises `RevocationUnconfirmed(stage="issuer_selection")` and makes no call; otherwise it
    awaits `run_in_threadpool(self._revoke, app, subject)`.
  - `FirebaseAdminLookup._revoke(app, subject) -> None`, a `@staticmethod` holding the synchronous
    body. It calls `auth.revoke_refresh_tokens(subject, app=app)` and catches, in this order:
    `auth.UserNotFoundError` first, which logs INFO `firebase_revoke_not_found` and raises
    `UserNotFound(stage="token_revocation") from None`; then `ValueError`, which logs WARNING
    `firebase_revoke_subject_malformed` with `detail=str(error)` and raises
    `RevocationUnconfirmed(stage="subject_rejected") from error`; then
    `google.auth.exceptions.GoogleAuthError`, which logs WARNING `firebase_credential_unavailable`
    and raises `RetryableLookupError(str(error)) from error`; then `exceptions.FirebaseError`,
    which logs WARNING `firebase_revoke_failed` with `code=error.code` and `detail=str(error)` and
    raises `RetryableLookupError(str(error)) from error`.
    Two orderings are load-bearing and are the phase's two known mistakes. `UserNotFoundError`
    must be listed before the `FirebaseError` it subclasses, or the 401 arm is unreachable
    (Pitfall 2). And the `ValueError` arm must NOT be classified retryable here, unlike in `_read`:
    here it comes from the SDK's own `validate_uid` before any network call, so a retry could
    never change the answer (Pitfall 1, D-02, D-05).
  - `_revocation_exhausted(retry_state)`, a module function returning `NoReturn`, raising
    `RevocationUnconfirmed(stage="token_revocation") from retry_state.outcome.exception()`. It must
    be its own callback and must not reuse `_exhausted`, which raises `Unavailable` (Pitfall 3).
  - `revoke_with_retry(adapter, issuer, subject) -> None`, the twin of `lookup_with_retry`: an
    `AsyncRetrying` with `stop=stop_after_attempt(FIREBASE_LOOKUP_ATTEMPTS)`,
    `retry=retry_if_exception_type(RetryableLookupError)` and
    `retry_error_callback=_revocation_exhausted`, awaiting `adapter.revoke_refresh_tokens`.
    Do not add a new attempts constant and do not rename `FIREBASE_LOOKUP_ATTEMPTS` (D-02).
    Do not write one generic wrapper shared with the read: the two need different exhaustion
    leaves, and a shared wrapper would need a comment at each call site to say which.
    Leave the class name `FirebaseAdminLookup` unchanged; the rename is deferred.

<flagged_assumptions>
Two edge-coverage rows for this phase are unresolved by any specification section, so they are
recorded here rather than dropped. Both are about concurrency and interruption, and CONTEXT.md
already implies the answer. Neither is verified by a test in this phase.

- **SIGNOUT-01, concurrency — "if interrupted or run in parallel, what is guaranteed?"**
  ASSUMED: the route holds no state and writes no row, so two parallel calls for one subject each
  make their own Firebase revocation. `revoke_refresh_tokens` advances the subject's
  `tokens_valid_after_timestamp` at the IDP, so a repeat only re-asserts a later timestamp. The
  operation is therefore idempotent and needs no lock, no coalescing and no queue.
  RISK IF WRONG: two calls could write two different timestamps; the later one still wins, so the
  client outcome is the same.

- **SIGNOUT-02, concurrency — "if interrupted or run in parallel, what is guaranteed?"**
  ASSUMED: an interrupted call answers 503 `verification_temporarily_unavailable` through
  `RevocationUnconfirmed` (D-05) and never 204. Nothing durable records the attempt: the record is
  the middleware `request` line plus one WARNING from the shared handler. That loss was accepted
  milestone-wide by Phase 38 D-03 and is recorded again by plan 46-05.
  RISK IF WRONG: a revoked-but-unreported call makes the client retry a revocation that already
  happened, which is harmless because the operation is idempotent.
</flagged_assumptions>
