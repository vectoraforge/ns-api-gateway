<objective>
Prove the two properties the wire cannot show: which app the revocation used, and how many attempts
each outcome costs.

Purpose: the 503 `RevocationUnconfirmed` answers is byte-identical to `Unavailable`'s, so only a
unit assertion on the class can tell the fail-closed leaf from the read's leaf. And an attempt count
is invisible to an end-to-end case.
Output: the revocation cases in `tests/unit/test_firebase_adapter.py` and
`tests/unit/test_firebase_retry.py`.

Ordering note: this plan depends on 46-02 as well as 46-01, because Task 2's gate is
`uv run pytest -q` and that cannot be green until 46-02 re-writes the four hand-written literals.
</objective>

Add a revocation fixture and one test class, twinning what the file already does for the read.

The fixture is `revoke_calls`, the twin of `get_user_calls`: it monkeypatches
`firebase_admin.auth.revoke_refresh_tokens` with a function taking `(uid, app=None)`, records
`{"uid": uid, "app": app}` into a list, raises the scripted answer when it is a `BaseException`,
and otherwise returns `None`. The scripted success answer for a revocation is `None`, not a record.
Reuse `RecordingApp`, the `app` fixture and the `adapter` fixture unchanged.

Write these cases:
  - A configured issuer passes its own app explicitly: after `await adapter.revoke_refresh_tokens(ISSUER, SUBJECT)`
    the recorded calls equal `[{"uid": SUBJECT, "app": app}]`. This is the case that proves no
    `[DEFAULT]` app is reachable.
  - A confirmed revocation returns `None`.
  - An unconfigured issuer raises `RevocationUnconfirmed` with `stage == "issuer_selection"` and the
    recorded call list stays empty.
  - An adapter built on an empty apps mapping does the same.
  - `RevocationUnconfirmed` answers `status == 503` and `code == "verification_temporarily_unavailable"`.
  - A scripted `auth.UserNotFoundError` raises `UserNotFound`, not `RevocationUnconfirmed` and not
    the retry marker. This is D-06's arm and it is only reachable because `_revoke` lists it before
    the `FirebaseError` it subclasses.
  - A scripted `ValueError` raises `RevocationUnconfirmed` with `stage == "subject_rejected"`, and
    explicitly **not** `RetryableLookupError`. In `_read` this arm is retryable; here it is not,
    because the SDK's own `validate_uid` raises it before any network call.
  - A scripted `exceptions.FirebaseError` subclass raises `RetryableLookupError`, so the retry tier
    can see it. Use an SDK exception the file already constructs elsewhere rather than inventing one.
  - A scripted `google.auth.exceptions.GoogleAuthError` raises `RetryableLookupError` too.

Add a counting fake and one test class for the revocation wrapper, twinning what the file already
does for `lookup_with_retry`.

The counting fake is the revocation twin of `CountingAdapter`: it exposes an async
`revoke_refresh_tokens(issuer, subject)`, records every call, raises `AssertionError` when the call
count exceeds the scripted sequence, raises a scripted `BaseException`, and otherwise returns
`None`. Name it so it cannot be confused with `CountingAdapter`.

The revocation `DEFINITIVE` table has four entries, each costing exactly one attempt: a completed
call (`None`), `UserNotFound(stage="token_revocation")`,
`RevocationUnconfirmed(stage="issuer_selection")` and `RevocationUnconfirmed(stage="subject_rejected")`.
Parametrize over it as the read's table is parametrized, and assert the call count is 1 in each.

Write the exhaustion cases, on the `TestTheExhaustionConversion` model:
  - Three retry markers exhaust the budget and raise `RevocationUnconfirmed`, with
    `stage == "token_revocation"`.
  - Neither `tenacity.RetryError` nor `RetryableLookupError` escapes. Assert the class of the raised
    value, and assert it is **not** an instance of `Unavailable`. This is the assertion the whole
    plan exists for: `Unavailable` carries the same 503 and the same code, so no status assertion
    and no wire assertion can see a wrapper that reused the read's exhaustion callback.
  - The last marker survives as `__cause__`, so the provider's own diagnosis stays reachable.
  - A budget that was not exhausted does not fire the conversion: two scripted answers, the second
    a confirmation, returns normally after two calls. This is the control that would pass a callback
    which raised unconditionally.
  - The client-facing pair is `status == 503` and `code == "verification_temporarily_unavailable"`.
  - Exhaustion is not the `UserNotFound` mapping: the raised value is not a `UserNotFound` and its
    status differs.
  - `revoke_with_retry` spends exactly `FIREBASE_LOOKUP_ATTEMPTS` attempts and no more, proven by
    the counting fake's overrun `AssertionError`.

Every docstring is three lines or fewer and every comment is one ASD-STE100 line (D-11).
  </action>

## Trust Boundaries

|----------|-------------|
| the retry tier -> the client's answer | An exhausted budget crosses here; a wrong conversion turns a fail-closed 503 into a 500 or, worse, a silent success. |
| the seam -> the Firebase Admin SDK | Which app is used crosses here; a missing `app=` would reach an ambient client. |
