<objective>
Bind the chat response schema to the model call so the provider cannot emit an unconstrained shape,
replacing the parse-then-validate chain that has always shipped.

Purpose: this gap already cost a defect — a grammatically correct phrase returned 500 because the
model omitted two declared keys. Phase 36 shipped the narrow instance fix (empty-list defaults); this
is the general fix. The prompt is demonstrably not holding the constraint, so wording it harder will
not close it.

Output: a strict schema bound at the call, a provider-free unit gate on the emitted schema, a
real-provider e2e gate, and the folded todo archived with its two open questions answered.

**This is an independent workstream.** It touches no auth code and shares no file with any other plan
in this phase. Its commits are its own.
</objective>

  <behavior>
    - `convert_to_json_schema(ChatModelResponse, strict=True)` yields `required == ["resolved_mode", "response", "issues", "suggestions"]` and `additionalProperties is False`
    - The same conversion applied to the nested `Issue` object also yields `additionalProperties is False` and both of its keys required

  <action>
    Move shape enforcement from post-hoc parsing to the provider call.

    In `src/nativespeaker/api/models/llm.py`, add one **flat** model named `ChatModelResponse`
    carrying every field any of the three modes can produce:
    `resolved_mode: Literal["analyze", "follow_up", "reject"]`, `response: str`,
    `issues: list[Issue] = []`, `suggestions: list[str] = []`.

    Flat is deliberate and load-bearing. Do NOT bind a discriminated-union root
    (`RootModel[Annotated[Union[...], Field(discriminator="resolved_mode")]]`): the strict conversion
    rewrites an object schema by forcing every property into `required` and setting
    `additionalProperties` to false, and it does not descend into a root-level `oneOf`. A union root
    would ship looking strict while leaving the branches — and the nested `Issue` object — unconstrained.
    That is the single most likely way this change fails without failing loudly. Say so in one plain
    sentence in the model's docstring, in the 37.1 prose register.

    Leave `AnalyzeResponse`, `FollowUpResponse` and `RejectResponse` exactly as they are. They remain
    the client-facing contract and the post-hoc validation `ChatService.ask_llm` performs; the new
    model describes only what the provider is asked for.

    In `src/nativespeaker/api/services/llm.py::create_chain`, replace the trailing parse step. The
    chain becomes the prompt template, then the model with the schema bound —
    `self.llm.with_structured_output(ChatModelResponse, method="json_schema", strict=True)` — then a
    step that converts the returned model instance to a plain dict via `model_dump()`. Keep the
    prompt-template construction byte-identical. Remove the `JsonOutputParser` import if it becomes
    unused; keep the `create_chain` return annotation truthful to what it now returns.

    The dict-out seam is a deliberate choice, not an oversight: `ChatService.ask_llm` consumes a dict
    and re-validates into the mode-specific model, and that re-validation stays as defense in depth.
    `strict` rides in provider-specific keyword arguments and is honored by some provider wrappers and
    merely accepted by others, so a second, in-process check of the shape still earns its place. Record
    this decision in the plan summary — the todo asks for it to be decided deliberately, not left
    unexamined.

    Also record, in the summary, the second question the todo asks: the empty-list defaults on
    `AnalyzeResponse` stay. Under a strict schema they no longer do provider-boundary work (the strict
    rewrite marks every field required regardless of a Pydantic default), but they remain the
    client-facing contract and a fallback if the strict call is ever not honored. Keeping them is the
    decision; the reason is that they stopped being a workaround and became a contract.

    Create `tests/unit/test_llm_chain_schema.py` asserting the emitted schema directly, with no
    provider call: import `convert_to_json_schema` from `langchain_core.utils.function_calling`,
    convert `ChatModelResponse` with `strict=True`, and assert that all four property names appear in
    `required`, that `additionalProperties` is false at the top level, and that the nested `Issue`
    definition is equally constrained. Add one case asserting `create_chain` produces a runnable whose
    output is a `dict` — the contract `ChatService.ask_llm` depends on.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app → LLM provider | Untrusted, non-deterministic output crosses back into the app and is persisted as message content |
| user phrase → prompt | User text reaches the model; it has always done so and this plan does not change that surface |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-37.2-09 | Tampering | Unconstrained provider output persisted as message content | medium | mitigate | The schema is bound at the call with `additionalProperties` false, so undeclared keys cannot arrive; `ChatService.ask_llm` still re-validates into the mode model and persists the validated dump, not the raw payload. Both halves are asserted. |
| T-37.2-10 | Denial of service | A missing key turning a 200 into a 500 | medium | mitigate | This is the defect the todo names. Strict makes every declared key required at the provider, and the real-provider e2e gate exercises exactly the phrase that once produced the 500. |
| T-37.2-11 | Information disclosure | Provider error text reaching a client | low | accept | Unchanged by this plan — the existing error handling already answers with the shared one-field body and never forwards provider text. |
| T-37.2-12 | Spoofing | A schema that looks strict but is not | high | mitigate | The union-root failure mode is avoided by construction (flat model, no `RootModel`), asserted negatively by grep, and proved positively by the provider-free schema conversion gate plus the blocking human checkpoint on the real-provider run. |
| T-37.2-SC | Tampering | package installs | low | accept | No package is added, removed or upgraded — `langchain`, `langchain-core` and `langchain-openai` are already installed and pinned. `pyproject.toml` is unchanged. |
