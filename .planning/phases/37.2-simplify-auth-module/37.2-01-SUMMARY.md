# Phase 37.2 Plan 01: The challenge endpoint, wired end to end Summary

**`POST /auth/challenge` issues a single-use `create_user` challenge that completes an account at the existing create-user route against real PostgreSQL, with the 400/422 partition pinned by 24 unit cases.**

## Accomplishments

- `POST /auth/challenge` serves the split path end to end: an unlinked caller obtains a handle and spends it at `POST /auth/create-user`, creating exactly one account, verified against real PostgreSQL.
- `ChallengeRequest` and `PrepareResponse` now live in `models/auth.py` and are eagerly re-exported from `models/__init__.py`; `routers/auth.py` defines one fewer Pydantic model.
- The operation vocabulary is not discoverable through this route — `sync`, `sign_out_all`, `restore_subscription`, `claim_anonymous_grant`, `nope`, `""`, `create-user` and `CREATE_USER` all return the identical 400 `invalid_request`.
- The framework's own type-error arm is documented rather than worked around: a non-string, a missing field and an absent body all render as `{"code": "validation_error"}` through the shared handler.
- `/auth/challenge` is declared pre-auth callable as a one-line literal edit, so the widening is reviewable.

## Decisions Made

- **`operation: str`, not `Literal["create_user"]`.** A `Literal` or enum annotation would make Pydantic answer 422 before the handler runs, which would move the rejection out of the 400 bucket the phase pins. The docstring on `ChallengeRequest` states this so a later "tightening" of the annotation is visibly a contract change.
- **No enum-membership branch in the handler.** The handler compares against `AuthOperation.create_user.value` directly. A membership check would have to be proven not to leak the vocabulary; a single equality cannot leak it.
- **`Cache-Control: no-store`, not `no-cache`.** Asserted in both the unit and e2e suites.
- **No already-linked pre-check on the issuance route,** per the phase's decision that the DB UNIQUE constraint plus `classify_insert_conflict` is the sole authority. The route therefore executes no DB statement of its own, which the unit suite asserts.
- **`requirements-completed` lists CREATE-01 and CREATE-02 because they are this plan's declared requirements, but I did not edit `REQUIREMENTS.md`.** CREATE-01 still reads "the *only* pre-auth-callable route" and there are now two; CREATE-02 still describes the mode-signal partition that plan 05 removes. Plan 07 owns both amendments — editing the file here would have collided with it.
