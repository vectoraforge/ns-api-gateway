key-decisions:
  - "`CreateUserRequest.challenge_id` carries `min_length=1` rather than a bare `str`. Without the constraint an empty string passes validation and falls through to a not-found 409, which puts a syntactically unusable handle in the challenge-rejection bucket instead of the validation bucket. With it, the empty string is a 422 and the byte-for-byte store comparison still decides everything a real handle can mean"
  - "The whitespace-only handle is deliberately NOT trimmed and deliberately NOT rejected. The length constraint counts characters, so `'   '` validates and reaches the store untrimmed, ending as a not-found 409. Trimming would widen one secret capability handle into a family of handles that all locate the same row; rejecting it would hand the client a distinguishable answer for a value the store can already answer for"
  - "`_already_linked` and `_prepare` were deleted outright rather than moved to the challenge route. Issuance now serves an already-linked caller a challenge, and the 409 arrives at completion from `create_account`'s in-transaction re-resolution. The pre-check was documented in its own comment as best-effort and racy; preserving it on the new route would have preserved a guess that the transaction then overrules anyway"

# Phase 37.2 Plan 05: Create-User Becomes Completion-Only Summary

**`POST /auth/create-user` loses its query-string mode signal, its loosely-typed field, its classifier module and its racy already-linked pre-check — becoming a body-only completion endpoint whose malformed-body rejection belongs to the framework and whose already-linked 409 belongs to the database.**

## Performance

- **Duration:** ~35 min
- **Tasks:** 3
- **Commits:** 4
- **Files changed:** 6 modified/created, 3 deleted
- **Net lines:** +349 / −519

## Accomplishments

### Task 1 — create-user becomes completion-only, the mode signal is deleted (`4704aa9`)

`CreateUserRequest` and `CompletionResponse` moved from `routers/auth.py` into `models/auth.py`,
keeping both class names. `routers/auth.py` now defines no class at all — `grep -c '^class '` is 0 —
and imports all three request/response models from `models/auth.py`. Both new names were added to
`models/__init__.py`'s `__all__` and eager import list in sorted position.

`CreateUserRequest.challenge_id` went from `Any = None` to a required `str` with `min_length=1`. The
loose typing existed only so an unusable handle could be routed to a hand-chosen 400; with the
classifier deleted it had nothing left to serve. `models/auth.py` already imports `Field` from
sqlmodel for the `AuthChallenge` table, so pydantic's is imported as `PydanticField` with a comment
saying why.

The `create_user` handler lost the raw-query parameter, the mode classification block, both of its
imports, and its `| None = None` body default. Its whole body is now one call into `_complete` with
`body.challenge_id` forwarded untouched. `_prepare`, `_already_linked` and `_classification_cause`
were deleted; the last of these was folded into its single call site as an inline conditional in the
`cause=` keyword argument. The route's `summary=` and `description=` now describe completion and point
at `/auth/challenge` as where a handle comes from.

`src/nativespeaker/api/auth/modesignal.py` was deleted entirely, and `get_raw_query_string` was
deleted from `app/dependencies.py`. The comment block above it is shared with `get_challenge_store`
and `get_firebase_adapter`, which still exist for the same Depends-only reason, so it was reworded
rather than deleted alongside the function.

`resolve_existing_identity` was explicitly **not** deleted: it lost the router as a caller but keeps
its live one inside the consuming transaction at `auth/creation.py:52`.

### Task 2 — the unit suites follow the split, the body partition flips (`8d5bd9d`)

`tests/unit/test_mode_signal.py` deleted in full (129 lines) — its subject no longer exists.

`tests/unit/test_create_user_modes.py` renamed to `tests/unit/test_create_user_body.py` and
rewritten. `TestTheTwoModesDispatch` is gone; its issuance half was already covered by
`test_challenge_endpoint.py`, and its completion half became `TestTheHandleReachesTheStore`.
`TestTheInvalidRequestPartition` became `TestTheValidationPartition`: the same unusable handles now
expect 422 and `{"code": "validation_error"}`. The four query-parameter ambiguity cases — both signals
together, neither signal, a duplicated parameter, and any value other than exactly `true` — were
deleted rather than moved, and one case was added posting `?challenge=true` with no body and asserting
422, pinning that the query string is now simply ignored.

`TestTheWhitespaceAsymmetry` survives unchanged in substance, joined by `TestTheModelArmsDirectly`
which pins the three arms on the model itself. `TestTheRejectionHasNoSideEffects` was reduced to the
body-shape parameters and keeps its full assertion set — nothing issued, nothing located, no statement
executed, no provider call.

`tests/unit/test_create_user_precedence.py` passed with **zero edits**, as the plan required.

### Task 3 — the e2e suite moves to the new route (`f6b9ece`)

Every call that obtained a challenge through the query parameter now posts
`{"operation": "create_user"}` to `/auth/challenge` with the same headers; the assertions on the
response — status, two-key body, `no-store` header — are unchanged. That covers the happy-path block,
the still-issues suite, the two rejection setups, the CREATE-01 exemption case, and the shared helper
(renamed `_prepare_and_complete` → `_issue_and_complete`).

`TestPrepareRejectsAnAlreadyLinkedCaller` became `TestCompletionRejectsAnAlreadyLinkedCaller` and both
its cases were rewritten, not moved. The first now asserts the challenge **is** issued (200, two-key
body) and that completion answers 409 `identity_already_linked`. The second dropped its "the rejection
issued no challenge" assertion — no longer true, and not a regression — for row counts: no second
account, exactly one identity row for the pair, and a spent challenge. A class docstring records in
plain English that an already-linked caller now costs a challenge row and one provider lookup before
its 409, which is latency rather than correctness.

`tests/e2e/test_admission.py` passed with **zero edits**.

## Notes on Acceptance Criteria

Two of the plan's mechanical grep criteria could not be satisfied as literally written. Both are
reported here rather than worked around in the code.

**1. Task 1: `grep -rn -E '...|_already_linked|...' src` returning nothing.** The alternation matches
`identity_already_linked` and `provider_account_already_linked`, two `AuthEventResult` enum members
in `models/auth.py` and their uses in `errors.py` and `auth/creation.py`. Those are load-bearing and
entirely out of this plan's scope — the criterion matched them before the plan ran too. Verified with
the boundary-aware form instead: `grep -rnE --include='*.py' '\b_already_linked' src` exits 1, so the
deleted helper is genuinely gone.

**2. Task 3: `grep -rn 'challenge=true' src tests` returning nothing.** This contradicts Task 2's own
action, which *requires* a case "posting an old-style query-parameter call with no body and asserting
422", and the plan's must-have truth that such a call "fails body validation with 422". The truth and
the explicit action were honored; the string survives on exactly two lines of
`tests/unit/test_create_user_body.py`, both inside the one case that asserts the parameter is now
ignored. The criterion's intent — no production path and no e2e call still uses the parameter — is
met exactly: `grep -rn 'challenge=true' src` exits 1, and
`grep -c 'challenge=true' tests/e2e/test_create_user.py` is 0.

## Accepted Consequence (T-37.2-20)

An already-linked caller now spends one challenge row and one bounded provider lookup before hearing
409, where the deleted pre-check refused it before either. This is the cost of making the consuming
transaction the sole authority. It fails closed, the cost is one row plus one bounded lookup, and
per-minute request limiting is the gateway's job. This is the plan's own `accept` disposition,
recorded here as it requires.
