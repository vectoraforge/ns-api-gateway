# Phase 37.2 Plan 06: Cohesion Merges and a Measured Package Summary

Three modules that existed only to serve one flow were folded into it — the providerData classifier
and the lookup retry policy into `auth/firebase.py`, the rejection log into `app/dependencies.py` —
taking the auth package from 14/28/57 to 10/19/44, with a test that now asserts the shrink.

## What was built

**Task 1 — the classifier and the retry policy move beside the lookup** (`f4cc09b`)

`auth/classifier.py` and `auth/retry.py` moved verbatim into `auth/firebase.py` and were deleted.
The attempt-budget constant and the unavailable result/error-class pair sit beside the existing
HTTP-timeout constant; the classifier functions, the retry predicate and the retrying caller sit
below the `FirebaseAdminLookup` class they serve. Both deleted modules' docstrings were merged into
the Firebase module docstring — this was load-bearing, not cosmetic: `test_provider_classifier.py`
asserts five prohibition phrases against `__doc__`, and each had to survive on a single line to keep
matching.

Five importers were retargeted: `routers/auth.py` (two import blocks collapse to one) and four test
files (import lines, plus the three in-body `auth.classifier` module references in
`test_provider_classifier.py`). `ADAPTER_IMPLEMENTORS` lost its `api/auth/retry.py` key, which no
longer names a file — the mapping's own
`test_every_allow_listed_path_resolves_to_a_file_that_exists` would have caught a stale key, and the
Firebase key already permits the same single method.

**Task 2 — the rejection log moves to where rejections are raised** (`d904050`)

`auth/telemetry.py` (16 lines, one production caller) was inlined into `app/dependencies.py::_reject`
and deleted. The event name `auth_rejected` and its `result` / `bounded_reason` / `route` keys are
byte-identical, including the `None` rendering of an absent bounded reason. `app/dependencies.py`
gained the two-line house structlog logger it did not have.

The four affected cases in `test_identity_resolution.py` were retargeted, not rewritten: the three
that called `record_rejection` directly now drive `_reject` through a `_record` helper that swallows
the expected `AuthRejectionError`, so every assertion line is unchanged; the fourth monkeypatches
`dependencies.logger` instead of `telemetry.logger`. The class was renamed `TestRecordRejection` →
`TestTheRejectionLog` because the old name named a function that no longer exists.

**Task 3 — the shrink under a machine-checked assertion** (`0d74602`)

`tests/unit/test_auth_package_shape.py` parses every top-level module in the auth package and walks
each tree, counting modules, classes and functions. `BASELINE = (14, 28, 57)` and
`CURRENT = (10, 19, 44)` are literals, so growth is a deliberate edit a reviewer sees. Six cases: three
parametrized axes asserting strictly-below-baseline, one asserting the recorded current shape, and two
controls.

## Deviations from Plan

None affecting behavior. Two notes on the plan's own acceptance criteria, and one on the TDD gate.

**1. Three `grep -c` criteria were written as occurrence counts but `grep -c` counts lines.**
Task 1 expected `grep -c 'run_in_threadpool'` to be 1 (measured 2) and `grep -c 'retry_if_result'`
to be 1 (measured 3); task 2 expected the three log keys to span ≥3 lines (measured 1). In all three
cases the intent holds and the numbers are *unchanged from pre-merge* — I verified against `HEAD`
before the merge: `run_in_threadpool` was already 2 lines (import + call) and `retry_if_result`
already 3 (import + comment + call), and the log statement was one line in `telemetry.py` too. I
confirmed the underlying facts by occurrence count instead: exactly one threadpool call site, one
result-shaped predicate, and all three log keys present. I did not reformat working code to satisfy a
miscounted line-grep — doing so would have made the "verbatim move" claim false.

**2. Task 3's TDD RED could not fail in the ordinary way, and was proven a different way.**
The thing this test asserts — the shrink — is a precondition established by tasks 1 and 2 of this same
plan, so a correctly-written test passes the moment it exists. Rather than commit a knowingly-wrong
test to manufacture a red bar, I proved non-vacuity directly: extracted the auth package as it stood
at `cd95152` and ran the measurement against it. It measures (14, 28, 57), and **both** assertions
fail on it. I then made that proof permanent rather than one-off by adding two in-file controls
following the codebase's existing `_control` idiom from `test_adapter_interfaces.py` — one showing a
package at the baseline shape is not strictly smaller, one showing a method and a nested helper both
count. A measurement that silently returned zeros would now fail.

## Accepted consequences

- **`routers/auth.py` now imports `auth/firebase.py` directly**, so importing the router pulls the
  Firebase Admin SDK into the import graph. The application already did this at boot through its
  lifespan, so this changes unit-test import cost and nothing else. Noted in the plan as accepted.
  Worth knowing: `test_adapter_interfaces.py::TestNoProviderDependency` still passes — it asserts
  `auth/adapters.py` imports no `firebase_admin`, and the seam is untouched.
- **The rejection log now lives outside the `auth/` package**, in the composition root. A reader
  looking for it under `auth/` will not find it; it is where rejections are raised.
  `.planning/REQUIREMENTS.md`'s FOUND-05 amendment blockquote still names `record_rejection` — plan 07
  updates that note, as planned.
