# Phase 37.2: Simplify auth module - Context

**Gathered:** 2026-08-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Continue Phase 37.1's de-complication into the auth feature itself. Five directives from the
ROADMAP entry, plus one folded todo:

1. Drop the `credentials.Certificate()` path — Firebase initializes via Application Default
   Credentials only.
2. Move `CreateUserRequest`, `PrepareResponse`, and `CompletionResponse` out of `routers/auth.py`
   into `models/auth.py`; the router defines no Pydantic models.
3. Replace the `?challenge=true` mode signal with an explicit `POST /auth/challenge` endpoint
   taking `{"operation": "create_user"}`; delete `auth/modesignal.py`; `POST /auth/create-user`
   handles completion only.
4. Inline or delete single-caller indirections that exist to name a value rather than compute one
   (`_classification_cause` and kin).
5. Shrink the `auth/` package measurably below the 14-file / 28-class / 57-function baseline, every
   deletion justified as carrying no behavior.
6. **Folded todo:** restore `with_structured_output(strict=True)` on the LLM chain — an
   independent workstream in `services/llm.py`, not auth code (see Folded Todos).

The admission rules, status codes, and the Phase 37 e2e matrix survive unchanged **except** where
a decision below explicitly moves or deletes them — this discussion sanctioned three such changes
(D-03, D-04, D-05).

**The measured baseline** (live source, 2026-08-25): `auth/` is 14 files, 1,166 lines;
`routers/auth.py` 263 lines; `models/auth.py` 98 lines. Roughly 12 of the 28 classes are unbuilt
adapter interfaces with zero consumers.

**Out of scope:** any change to which routes are authenticated, the auth dependency mechanism
itself (37.1 D-06/D-07/D-09 stand), phases 38–46's own work, and `secret-manager-integration`
(reviewed, not folded).

</domain>

<decisions>
## Implementation Decisions

### The challenge endpoint

- **D-01 — `POST /auth/challenge` accepts `{"operation": "create_user"}`; every non-issuable value is one bucket: 400 `invalid_request`.** A value outside the `AuthOperation` enum and a valid
  member whose phase isn't built ("sync", "sign_out_all", …) reject identically — the endpoint
  discloses nothing about the operation vocabulary, consistent with the error contract's
  anti-oracle stance. The accepted set is exactly `{create_user}` today; later phases widen it.

- **D-02 — Success is 200 with `{challenge_id, expires_at}` and `Cache-Control: no-store`, verbatim from today's prepare mode.** The e2e prepare tests move to the new endpoint with only the URL and
  request body changed. Rejected: 201, and echoing `operation` back.

- **D-03: The already-linked pre-check does NOT move to issuance — it is deleted.** Today
  `_prepare` rejects an already-linked caller with 409 `identity_already_linked` before issuing;
  that check was always best-effort and racy, with the consuming transaction's unique constraints
  as the real authority. Now the challenge issues to anyone the auth dependency admits, and the
  409 surfaces at completion via the constraint-conflict path (`classify_insert_conflict` →
  `CLIENT_CLASS_FOR_RESULT`). Consequences the planner must carry: the 409-at-prepare e2e cases
  are **rewritten to assert at completion**, not moved; an already-linked caller now burns a
  challenge row and one Firebase lookup before hearing 409; and `_already_linked` /
  `resolve_existing_identity`'s issuance-time call site disappears (check what remains of
  `resolve_existing_identity` — its other consumer is the completion path's conflict handling).
  — **Reversibility:** reversible — re-adding a pre-check is a small handler addition.

### The create-user completion contract

- **D-04: `challenge_id` becomes a required `str` and malformed bodies get standard FastAPI 422 `validation_error`.** The `Any`-typed field existed only to route unusable handles to the
  mode-signal's 400; with the classifier dead, the trick dies too. Several Phase 37 e2e cases flip
  400 → 422 — sanctioned as part of the split. Planner: constrain with `min_length=1` so empty
  strings stay in the 422 bucket rather than falling through to `locate()` → 409 not-found.
  Whitespace-only handles pass validation and fall through as not-found, which is fine — the
  byte-for-byte philosophy already treats a padded handle that way.

- **D-05: Query parameters are ignored entirely.** All query parsing goes: `classify_mode_signal`,
  `auth/modesignal.py`, and the `get_raw_query_string` dependency (verify it has no other
  consumer). An old-style `?challenge=true` call fails body validation with 422. The mode-signal
  e2e cases (duplicate param, non-true value, both-signals, neither-signal) are **deleted, not
  moved** — the ambiguity they guarded can no longer be expressed.

### Firebase — ADC only

- **D-06: The entire service-account config surface is deleted.** `FirebaseConfig`, the
  `AppConfig.firebase` field, the `.env.example` `FIREBASE_SERVICE_ACCOUNT_JSON` line, and the
  `credential_dict()` branch in `build_admin_apps`. No Firebase config key remains; ADC is
  discovered from the environment. Note `build_admin_apps` already has the ADC path
  (`_application_default_credential`) — this is deleting the first branch, not building anything.

- **D-07: Warn-and-boot stays when ADC is absent.** ADC probe fails → warning log, no Admin app,
  completion attempts fail closed as 503 `verification_temporarily_unavailable`. Dev and test runs
  with fake adapters need no credentials; the e2e matrix is untouched. Rejected: fail at boot
  (would break every credential-less dev/test run).

- **D-08: FLAGGED CONFLICT — ADC-only reverses Phase 37 D-08 and diverges from `SHARED-INVARIANTS.md`.** Phase 37 D-08 explicitly rejected ADC because SHARED-INVARIANTS
  forbids any ambient, default, or fallback client, and ADC can silently pick up local gcloud user
  credentials in dev. The developer's directive knowingly reverses that: production runs on GKE
  where ADC is Workload Identity (strictly better than a mounted key), and the sub-$5/month threat
  model does not justify a parallel credential path. Phase 37 D-08 is **superseded**; the
  SHARED-INVARIANTS conflict is recorded here per the standing rule, not silently resolved. The
  named-app-per-issuer discipline (never a `[DEFAULT]` app) is unchanged and still satisfies the
  no-ambient-*client* rule at the app-selection layer. — **Reversibility:** reversible — the
  deleted branch is ~30 lines and the config class is in git history.

### Deletion reach

- **D-09: All zero-consumer adapter interfaces are deleted.** `StoreAdapter`, `VendorProofAdapter`,
  `VerifiedNotification`, `VerifiedTransaction`, `StoreState`, `ClaimKind`, `DeviceBitState`,
  `RevocationOutcome`, and `FirebaseAdminAdapter`'s unconsumed `verify_id_token` and
  `revoke_refresh_tokens` methods. What survives of `adapters.py` is the providerData surface the
  live code consumes (`ProviderDataOutcome`, `ProviderDataEntry`, `ProviderDataResult`, and the
  one-method `FirebaseAdminAdapter`). **FOUND-08 is amended and flagged forward to phases 43–46:**
  each of those phases defines its adapter interface beside its first implementation, the same
  treatment 37.1 gave the provider-callback category. — **Reversibility:** reversible — the
  Protocols are ~80 lines with no consumers; git history holds them.

- **D-10: Files merge by cohesion; the planner sets the target.** No fixed file-count goal.
  Modules that serve one flow merge (e.g. `classifier.py` + `retry.py` into the Firebase lookup
  module; `telemetry.py` into where rejections are raised). Each merge is justified by cohesion,
  each deletion by carrying no behavior. Rejected: a forced ~5–6-file collapse (large diffs in
  behavior-stable files) and dead-code-only deletion (leaves the 14-file sprawl).

- **D-11: The `auth/__init__.py` lazy re-export facade is deleted.** The 98-line
  `__getattr__`/`__dir__` machinery goes; `__init__.py` shrinks to (near) empty and every consumer
  imports from the concrete submodule. Import-site edits across `src/` and `tests/` are mechanical.

### Claude's Discretion

- Directive 4's sweep: which single-caller indirections to inline vs delete
  (`_classification_cause`, `_result_for_existing`, `_flush_account`-style helpers) — judged
  per-case during the rewrite.
- Module names and final layout under D-10, and where `FIREBASE_HTTP_TIMEOUT_SECONDS` /
  `FIREBASE_LOOKUP_ATTEMPTS` land after merges.
- The challenge endpoint's request-model name in `models/auth.py` and whether the accepted-set
  check is a `Literal["create_user"]` field or a handler check (both yield the D-01 contract; note
  a Literal rejects with 422, a handler check with 400 — D-01 pins 400, so the handler check is
  the likely shape unless the planner decides the 422/400 split differently for *unknown* values;
  whichever ships, the e2e tests pin it).
- For the folded LLM todo: whether `ChatService.ask_llm`'s post-hoc validation stays as defense in
  depth once the schema is enforced at the call, and whether the D-12 (Phase 36) empty-list
  defaults stay — the todo file says decide deliberately.

### Folded Todos

- **`restore-strict-structured-output.md`** (source: Phase 36 D-13). Bind `AnalyzeResponse`,
  `FollowUpResponse`, `RejectResponse` as a strict schema on the chat-model call
  (`with_structured_output(strict=True)` or equivalent) so the provider cannot emit an
  unconstrained shape; today `services/llm.py:30` is `prompt_template | self.llm |
  JsonOutputParser()`. The three modes dispatch on `resolved_mode`, so binding needs a
  union/discriminated schema. **Requires real-provider e2e coverage** — a mocked chain proves
  nothing about whether the provider honored the constraint. The prompt is not the fix
  (`config/prompt.txt:124` is already ignored). This is an independent workstream touching
  `services/llm.py` / `services/chats.py`, not auth code — plan it as its own plan with its own
  commits. Read the todo file itself; it is the spec for this item.

## Specific Ideas

- The five directives are the developer's, recorded in the ROADMAP entry; this discussion pinned
  their contracts rather than re-opening them.
- The user consistently chose the deletion-leaning option when offered: dropping the already-linked
  pre-check (against the recommendation to move it), 422 over preserving the 400 trick, full
  config-surface deletion, all adapter interfaces gone, facade gone. The phase's center of gravity
  is *fewer moving parts over contract stability*, with the e2e matrix as the safety net — plan
  test edits deliberately, not as fallout.
- The strict-structured-output fold was deliberate (chosen over a "neither" recommendation):
  the user wants the LLM-chain fix shipped alongside this cleanup phase, not parked again.
