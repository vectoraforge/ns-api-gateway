# Phase 37.2 Plan 07: The Written Record Catches Up Summary

The three requirements this phase's sanctioned changes touched are amended in the register Phase 37.1
established, the Application Default Credentials decision is written down as the third unresolved
conflict against the binding specification, and every planning note that named a module this phase
deleted or moved now names something that exists.

## What was built

**Task 1 — the requirements file** (`25090ef`)

*CREATE-01, amended.* Its line said the endpoint was "the only pre-auth-callable route", which stopped
being true the moment `POST /auth/challenge` shipped — an unlinked caller needs a challenge in order
to create an account at all, so that route must be callable before a link exists. The line now states
the set as exactly two enumerated routes and the note explains that the *count* changed while the
substance — a closed, enumerated set, everything outside it rejecting with
`preauth_identity_not_allowed` — did not. The note names the enforcement point:
`tests/unit/test_app_wiring.py`'s `PREAUTH_CALLABLE_PATHS` literal, which is hand-maintained rather
than derived, so widening it is a visible edit. I verified the claim rather than repeating it — a
third pre-auth route added without touching that literal fails
`TestEveryRouteIsAuthenticated::test_every_route_but_the_two_exemptions_requires_a_linked_identity`.

*CREATE-02, amended rather than retired.* Both phases of the operation still exist and both are still
challenge-bearing; only the partition mechanism changed, from a query-parameter mode signal to one
route per phase. The note records what died (the `?challenge=true` signal, `auth/modesignal.py` and
its `classify_mode_signal`, the `get_raw_query_string` dependency, the `_prepare` branch), what a
route cannot express that a query parameter could (an *ambiguous* mode — which is why those e2e cases
were deleted rather than moved), and the two sanctioned status-code moves.

*FOUND-08, amended and flagged forward.* Eight zero-consumer adapter types and two unconsumed Protocol
methods are named individually as deleted, with what survives — the providerData surface — named
against the live file. The forward flag went to phases 43, 44, 45 and 46, and each of those phases'
entries picked up its own note under the requirement that references the seam it lost: APPLEHOOK-01
(`StoreAdapter` and friends), PLAYHOOK-02 (inherits Phase 43's rather than defining a second),
RESTORE-01 (`VendorProofAdapter`), SIGNOUT-01 (`revoke_refresh_tokens` and `RevocationOutcome`).

*The third flagged conflict.* Written under CREATE-01 in the same shape as the two existing ones:
the rule quoted verbatim from `SHARED-INVARIANTS.md` § "Wire contract", the statement that the
document binds every phase and has not been amended, then this project's knowing divergence and its
reasoning — GKE Workload Identity has no key material at rest, the sub-$5/month threat model does not
justify a parallel credential path, and Phase 37 D-08 is superseded. It says plainly what is *not*
in dispute: the named-app-per-issuer discipline is unchanged, so the no-ambient-**client** rule is
still satisfied at the app-selection layer and the divergence is confined to the credential layer.

*Repointing.* Four notes named the rejection log by its old module path or old function name —
FOUND-05, REBIND-02, PROF-02 and (by bare function name) SYNC-03. All four now name
`app/dependencies.py::_reject`, in one clause each, with the surrounding argument untouched.

*The tail.* Treatment-summary rows split by phase, the new conflict added as the third entry, the
forward flags for 43–46 recorded, Traceability updated for FOUND and CREATE (and for the four phases
that inherited the adapter flag), the standing heading retitled to cover both phases, and the
last-updated line rewritten.

**Task 2 — the roadmap entry** (`4547322`)

Success criterion 3 now describes what was actually built rather than what was proposed: challenge
issuance as its own route taking the operation in the body, every non-issuable operation as one
`400 invalid_request` rejection class disclosing nothing about the vocabulary, the query-parameter
mode and its classifier deleted, create-user completion-only.

A cross-cutting constraints block records the three things that had to stay true and were checked:
the 23-case admission matrix passed with zero edits, the completion precedence suite passed with zero
edits to any status code or body literal, and the only status codes that moved are the two sanctioned
ones. A measured-outcome line records the package shape as a fact — 10 files, 19 classes, 44
functions against the 14/28/57 baseline, with the arithmetic broken out and
`tests/unit/test_auth_package_shape.py` named as what asserts it.

The plan list and the `**Plans:**` count were already correct in the entry and were left alone, as
were the checkbox and every progress row — those belong to the orchestrator.

## Deviations from Plan

**1. [Rule 2 — missing critical correctness] Two ROADMAP criteria outside the Phase 37.2 entry were
repointed, knowingly failing one task acceptance criterion.**

- **Found during:** Task 2 verification.
- **Issue:** the plan contains a direct contradiction. Task 2's action says "never touch another
  phase's entry" and its criteria require `git diff .planning/ROADMAP.md | grep -c 'Phase 3[456789]:'`
  to be 0. But the plan-level `<verification>` block greps `.planning/ROADMAP.md` for `auth/telemetry`
  and requires nothing outside the Phase 37.2 entry, and `must_haves.truths` says *every* note naming
  a module this phase moved must name something that exists — with ROADMAP.md listed as an artifact.
  Two ROADMAP lines violate that: Phase 35's success criterion 4 says "What survives is
  `auth/telemetry.py::record_rejection`" in the present tense, and Phase 38's criterion 4 tells the
  next phase that "`record_rejection` already covers the rejection arm". Both name something plan 06
  deleted.
- **Resolution:** I repointed both to `app/dependencies.py::_reject`, one clause each, with the
  surrounding argument untouched. I judged a mechanical scoping grep the weaker of the two
  obligations: that criterion exists to prevent *scope creep* into other phases, and a two-clause
  factual repoint is not scope creep — it is this plan's stated purpose ("a note pointing at a
  deleted module is how a later reader loses an afternoon") applied consistently. Phase 38 is the
  very next phase and criterion 4 is an instruction addressed to it, so leaving it pointing at a
  deleted function is the exact harm the plan exists to prevent.
- **Cost, stated honestly:** `git diff .planning/ROADMAP.md | grep -c 'Phase 3[456789]:'` measures
  **2**, not 0. Both matches are `git diff` hunk *headers* naming the enclosing section, not changed
  content — under `-U0` the whole diff is four hunks: lines 214 and 381 (the two repoints) and lines
  335 and 363 (the in-scope Phase 37.2 edits). No other phase's scope, goal, criteria substance, plan
  list, checkbox or count was altered.
- **Files modified:** `.planning/ROADMAP.md`. **Commit:** `4547322`.

**2. The `**Plans:**` count and the plan list were left as found, contrary to Task 2's action text.**
Task 2 says to "replace the placeholder plan list with the seven plans and their wave numbers, and set
the plan count to match". There was no placeholder — the entry already lists all seven plans with
their waves, and reads `**Plans:** 6/7 plans executed`. The orchestrator owns the numerator and the
checkbox per this run's instructions, so I changed neither. Both criteria still pass: seven plans are
listed and the denominator is seven.

**3. `ROADMAP.md:273` still names `FirebaseConfig`, deliberately.** It is a completed-plan checkbox —
`- [x] 37-03-PLAN.md … add FirebaseConfig from .env only` — recording what Phase 37 built, which was
true when it was built. Phase 37.1 established the convention explicitly: "Completed-plan checkboxes
record what was built and are left exactly as written." Editing it would falsify Phase 37's own
delivery record, the same argument that kept SCHEMA-06 withdrawn rather than reworded. The plan-level
verification's "outside the Phase 37.2 entry's own account" clause is therefore met in substance: the
only live, forward-facing references to deleted symbols are gone.
