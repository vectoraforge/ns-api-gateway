# Phase 37.2: Code Review Report

**Reviewed:** 2026-08-26T03:16:50Z
**Depth:** standard
**Files Reviewed:** 26
**Status:** issues_found

## Summary

The refactor itself is faithful: the merged modules (`classifier.py`, `retry.py`, `telemetry.py`)
were moved verbatim into their consuming flows, the deleted adapter facade left no dangling
importers, `ruff` is clean, and all 762 unit tests pass. The defects are not in the mechanics of
the move — they are in what the move *changed about behaviour* and in what the new public endpoint
assumes about its environment.

The two critical findings both trace to the same root: `POST /auth/challenge` was introduced as a
new, state-inserting public endpoint whose entire safety argument is "the gateway rate-limits"
(`AGENTS.md`), but no Envoy Gateway route or rate-limit policy covers `/auth/*` at all. On top of
that, the phase deleted the only pre-issuance gate that existed (`_prepare`'s already-linked
check) without adding any replacement cap, and nothing in the system ever deletes an expired
challenge row.

The remaining findings cluster into three groups: a dead diagnostic branch and unbounded
caller-controlled strings in the new request models; a seam whose declared `Protocol` contradicts
its only implementation, with the type annotations deliberately removed to keep it compiling; and
the new strict-JSON-schema binding on the chat model, which introduces a user-content-triggerable
failure mode that is charged to the shared circuit breaker and whose contract now contradicts the
tracked system prompt.

Note on scope: `AGENTS.md` explicitly de-prioritises exotic threat models for a pre-launch $5/month
product. The critical findings below are not exotic — CR-01 is reachable by anyone with a browser
(the Firebase web API key mints anonymous ID tokens for free, exactly as `tests/e2e/conftest.py:81`
demonstrates), and CR-02 means the flow this phase built does not work in the deployed cluster.

## Critical Issues

### CR-01: `POST /auth/challenge` is uncapped state insertion, with no rate limit and no reaper

**File:** `src/nativespeaker/api/routers/auth.py:49-70`
**Also:** `src/nativespeaker/api/auth/challenges.py:46-72`, `k8s/templates/backend-traffic-policy.yaml:9-12`, `migrations/20260818_01_initial-release.sql:373-417`

**Issue:** Every call to `/auth/challenge` inserts one `core.auth_challenges` row. Three
independent controls that would have bounded this are all absent:

1. **No application-side cap.** The phase deleted `_prepare`, which rejected an already-linked
   caller *before* issuing (`git show 9ecebed:src/nativespeaker/api/routers/auth.py`). Nothing
   replaced it. `issue_challenge` now issues to any admitted identity, unconditionally, and
   `ChallengeStore.issue` never counts outstanding rows for the identity. The e2e test at
   `tests/e2e/test_create_user.py` (`test_two_issuances_produce_two_distinct_challenges`)
   deliberately pins that two calls mint two rows.
2. **No gateway rate limit.** `BackendTrafficPolicy.spec.targetRefs` names only
   `{{fullname}}-llm-routes`. `/auth/*` is not in any HTTPRoute (see CR-02), so it inherits no
   rate-limit rule at all. The comment at `routers/auth.py:125` — "Per-minute traffic limits live
   in the gateway, not here" — is not true for this path.
3. **No reaper.** `ix_auth_challenges_expires_at` exists, but no code, migration, or CronJob ever
   issues a `DELETE` against `core.auth_challenges`. Rows accumulate forever, including consumed
   ones.

The "authenticated caller" precondition is not a meaningful cost: the project's own e2e fixture
mints a fresh, valid, anonymous Firebase ID token with an unauthenticated `POST` to
`identitytoolkit.googleapis.com/v1/accounts:signUp` using the public web API key
(`tests/e2e/conftest.py:81-89`). Anyone can do the same, then loop on `/auth/challenge`.

**Fix:** Do all three, or at minimum (1) and (3):

```python
# src/nativespeaker/api/auth/challenges.py
MAX_OUTSTANDING_PER_IDENTITY = 5

async def issue(self, session, *, operation, identity, now):
    outstanding = await self._count_outstanding(session, identity=identity, now=now)
    if outstanding >= MAX_OUTSTANDING_PER_IDENTITY:
        raise TooManyOutstandingChallengesError()
    ...
```

and add a reaper migration plus a scheduled `DELETE FROM core.auth_challenges WHERE expires_at <
now() - interval '1 day'`, and add `/auth` to an HTTPRoute covered by the `BackendTrafficPolicy`
(see CR-02).

### CR-02: `/auth/challenge` and `/auth/create-user` are matched by no HTTPRoute

**File:** `k8s/templates/httproute-app.yaml:11-24`
**Also:** `src/nativespeaker/api/routers/auth.py:49,73`

**Issue:** The four HTTPRoutes in `k8s/templates/` match `/chats`, `/users`, `/examples`,
`/webhooks/apple` and `/health`. Nothing matches `/auth`. A Gateway listener with no matching
route answers 404, so **the account-creation flow this phase built is unreachable in the deployed
cluster** — the client cannot obtain a handle, so it cannot complete `create-user` either.

`/auth/create-user` was already unrouted before this phase, so half of this is pre-existing. But
the phase added a *second* endpoint under the same prefix, made it the mandatory first step of the
flow, and shipped no manifest change — so the phase converted a partly-broken path into a fully
broken one and pinned the new shape in e2e tests that run against the ASGI app directly
(`ASGITransport`, `tests/e2e/conftest.py:102`) and therefore cannot catch it.

Secondary consequence: `SecurityPolicy.spec.targetRefs` is per-HTTPRoute *by name*
(`k8s/templates/security-policy.yaml:9-15`). Whoever adds the `/auth` route later must remember to
add it to both the SecurityPolicy and the BackendTrafficPolicy; neither is a Gateway-wide default.
(In-process JWT verification in `get_request_context` means a missed SecurityPolicy entry is not an
auth bypass — but a missed BackendTrafficPolicy entry is exactly CR-01.)

**Fix:** Add `/auth` to `httproute-app.yaml`, and add that route's name to both policies:

```yaml
# k8s/templates/httproute-app.yaml
  - matches:
    - path:
        type: PathPrefix
        value: /auth
    backendRefs:
    - name: {{ include "ns-api-gateway.fullname" . }}
      port: {{ .Values.service.port }}
```

Then extend `BackendTrafficPolicy.spec.targetRefs` to include `-app-routes` (or a dedicated
`-auth-routes`) so `/auth/challenge` is rate limited.

### WR-02: Caller-controlled strings are unbounded, and one of them is logged verbatim

**File:** `src/nativespeaker/api/models/auth.py:75-90`, `src/nativespeaker/api/routers/auth.py:56-60`

**Issue:** `ChallengeRequest.operation` is a bare `str` with no `max_length`, and the rejection
path logs it directly:

```python
logger.warning("auth_challenge_operation_not_issuable", route=..., operation=body.operation)
```

The comment on line 57 asserts "The rejected string is caller-supplied and **bounded**, so logging
it is safe". It is not bounded. Nothing in this repo caps request body size — there is no Envoy
`ClientTrafficPolicy`, no buffer filter, and no Starlette limit. A caller can post a multi-megabyte
`operation` and have it written to the structured log on every request, which is a log-volume and
log-cost amplification against a service whose logs are the *only* record a rejection leaves
(`dependencies.py:84`).

`CreateUserRequest.challenge_id` has the same gap (`min_length=1`, no `max_length`). It is not
logged, but it is forwarded into a `WHERE challenge_id = $1` with no length ceiling.

**Fix:**
```python
class ChallengeRequest(BaseModel):
    # Bounded so the rejection log really is bounded, as the router's comment claims.
    operation: str = PydanticField(..., max_length=64)

class CreateUserRequest(BaseModel):
    # 22 characters today (16 CSPRNG bytes, base64url, unpadded); the ceiling leaves headroom.
    challenge_id: str = PydanticField(..., min_length=1, max_length=128)
```

### WR-03: The adapter `Protocol` declares a sync method its only implementation implements as `async`

**File:** `src/nativespeaker/api/auth/adapters.py:35-40`
**Also:** `src/nativespeaker/api/auth/firebase.py:72`, `src/nativespeaker/api/app/dependencies.py:132-135`, `src/nativespeaker/api/auth/firebase.py:146`

**Issue:** `FirebaseAdminAdapter.get_user_provider_data` is declared `def ... -> ProviderDataResult`.
`FirebaseAdminLookup.get_user_provider_data` is `async def ... -> ProviderDataResult`, i.e. it
returns a coroutine. `FirebaseAdminLookup` therefore does not satisfy the `Protocol` it exists to
implement.

The code works around this rather than fixing it, and says so:

- `dependencies.py:132` — `def get_firebase_adapter(request: Request):` with no return annotation,
  commented "deliberately unannotated" and "implements the Protocol's one reachable method
  asynchronously, not synchronously".
- `routers/auth.py:81,95` — the `adapter` parameter is untyped in both `create_user` and `_complete`.
- `firebase.py:146` — `lookup_with_retry(adapter, ...)` is untyped.

The result is that the *entire* call chain from HTTP handler to provider SDK is unchecked by `ty`,
on the one seam whose module docstring (`adapters.py:1-3`) declares the security rules ("no
provider call while a database lock is held", "never leak provider text to clients"). Worse,
`tests/unit/test_adapter_interfaces.py:234` asserts the sync return annotation, cementing the wrong
contract in a test.

**Fix:** Make the Protocol match reality, then restore the annotations:
```python
class FirebaseAdminAdapter(Protocol):
    async def get_user_provider_data(self, issuer: str, subject: str) -> ProviderDataResult: ...
```
```python
def get_firebase_adapter(request: Request) -> FirebaseAdminAdapter:
    return request.app.state.firebase_adapter

async def lookup_with_retry(adapter: FirebaseAdminAdapter, issuer: str, subject: str) -> ProviderDataResult:
```
and update `test_adapter_interfaces.py` to assert the coroutine form.

### WR-04: `.env.example` documents a credential route that does not work for the running app

**File:** `.env.example:18-35`
**Also:** `src/nativespeaker/api/config.py:16-18`, `pyproject.toml:55`

**Issue:** The new block instructs the operator to set `GOOGLE_APPLICATION_CREDENTIALS` in `.env`.
`google.auth.default()` reads `os.environ`. Nothing in this repo puts `.env` into `os.environ` for
the *application*:

- `BaseConfig.model_config` (`config.py:16-18`) sets `env_nested_delimiter`,
  `env_nested_max_split` and `hide_input_in_errors` — but **not** `env_file`.
- There is no `load_dotenv()` call anywhere in `src/`.
- `docker-compose.yml` applies `env_file: .env` to the `db` service only; there is no app service.

The only thing that loads `.env` into the process environment is `pytest-dotenv`
(`pyproject.toml:55`), i.e. tests. So a developer who follows `.env.example` and runs the service
gets `firebase_admin_credential_absent` at boot (`firebase.py:42`) and a 503 on every completion,
with the documentation insisting the setup is correct. Production on GKE is unaffected (Workload
Identity supplies ADC with no variable), which is exactly why this will not be caught until someone
tries to run the flow locally.

**Fix:** Either state plainly in `.env.example` that the variable must be exported into the shell
(`export GOOGLE_APPLICATION_CREDENTIALS=...`, or `gcloud auth application-default login`, which
needs no variable at all), or add `env_file=".env"` to `BaseConfig.model_config` **and** read the
credential path from config so it is actually applied.

### WR-05: The boot-time ADC probe is not the credential that gets used

**File:** `src/nativespeaker/api/auth/firebase.py:55-63`

**Issue:**
```python
try:
    google.auth.default()
except google.auth.exceptions.DefaultCredentialsError:
    return None
return credentials.ApplicationDefault()
```
The probe's result is discarded, and `credentials.ApplicationDefault.__init__` does not resolve
anything — `firebase_admin/credentials.py:140-148` sets `self._g_credential = None` and defers to
`get_credential()`, which calls `google.auth.default(scopes=_scopes)` with Firebase scopes on first
use. So the probe and the real resolution are two different calls with different scopes, and the
probe never attempts a token refresh.

Consequence: the probe can succeed where the real credential later fails (unscoped ADC present but
not authorised for the Firebase scopes, revoked refresh token, etc.). The comment on line 57
("probing at boot avoids a late 503") and the same claim in `.env.example:20-21` overstate what
this buys. Separately, only `DefaultCredentialsError` is caught; anything else raised during
discovery propagates and kills the lifespan, which contradicts "never a raise" on line 56.

**Fix:** Resolve once and keep the result, or drop the probe and let `build_admin_apps` catch on
first use:
```python
def _application_default_credential() -> credentials.ApplicationDefault | None:
    try:
        credential = credentials.ApplicationDefault()
        credential.get_credential()  # forces the same scoped resolution the SDK will use
    except google.auth.exceptions.GoogleAuthError as error:
        logger.info("firebase_admin_no_application_default_credentials", detail=str(error))
        return None
    logger.info("firebase_admin_using_application_default_credentials")
    return credential
```

### WR-06: The lookup retry has no backoff, so one request can hold a worker for ~24 seconds

**File:** `src/nativespeaker/api/auth/firebase.py:146-155`, `src/nativespeaker/api/auth/firebase.py:28`

**Issue:** `AsyncRetrying(stop=stop_after_attempt(3), retry=retry_if_result(_is_retryable))` has no
`wait=` argument, so tenacity retries immediately. Each attempt is bounded only by the app-level
`httpTimeout` of 8 seconds, and each runs in a threadpool worker
(`run_in_threadpool`, line 78). Under a Firebase outage each create-user request occupies a
threadpool slot for up to 24 seconds and issues three back-to-back calls against a provider that is
already failing.

Compare `ResiliencePolicy`, which does exactly the right thing for the LLM call
(`resilience.py:175-183`: `wait_exponential`, plus an outer `asyncio.wait_for` deadline). The
provider lookup has neither.

**Fix:**
```python
from tenacity import wait_exponential

retrying = AsyncRetrying(
    stop=stop_after_attempt(FIREBASE_LOOKUP_ATTEMPTS),
    wait=wait_exponential(multiplier=0.25, max=2.0),
    retry=retry_if_result(_is_retryable),
    retry_error_callback=lambda retry_state: retry_state.outcome.result(),
)
```

### WR-07: A retryable 503 permanently spends the caller's challenge

**File:** `src/nativespeaker/api/routers/auth.py:128-133,186-206`

**Issue:** When `lookup_with_retry` exhausts its budget on `retryable_failure` (or when the app has
no Firebase credential at all and every issuer selection returns `selection_failure`), `_complete`
routes to `_consuming_rejection`, which **consumes the challenge** and returns
`verification_temporarily_unavailable` (503).

The client is told the condition is temporary and it should retry — but retrying the same request
returns 409 `challenge_required`, because the handle is spent. The two halves of the contract
contradict each other, and a client implementing naive 503 retry will loop on 409 forever.

`selection_failure` is doubly wrong: it is a permanent misconfiguration (no admin app for this
issuer, e.g. no credential at boot), yet `_LOOKUP_REJECTIONS` maps it to the same "temporarily
unavailable" pair as a transient outage (`routers/auth.py:179-182`).

**Fix:** Leave the challenge claimed-but-unconsumed on a retryable outcome so the same handle can
be re-presented within its TTL, or return a class whose copy tells the client to obtain a fresh
challenge. At minimum, document the "fetch a new challenge on 503" requirement in the route
description at `routers/auth.py:75-76`.

### WR-09: `default_factory` on required nested config blocks produces a misleading boot failure

**File:** `src/nativespeaker/api/config.py:72-73`
**Also:** `src/nativespeaker/api/config.py:15-18`

**Issue:** `db: DatabaseConfig = Field(default_factory=DatabaseConfig)` and
`jwt: JWTConfig = Field(default_factory=JWTConfig)` declare defaults for models whose fields are all

### WR-10: `answer.model_dump()` is unguarded against the parser's documented `None`

**File:** `src/nativespeaker/api/services/llm.py:34`

**Issue:** `RunnableLambda(lambda answer: answer.model_dump())` assumes the structured-output
runnable always yields a Pydantic instance. langchain-openai's parser is typed
`_oai_structured_outputs_parser(...) -> PydanticBaseModel | None`
(`langchain_openai/chat_models/base.py:3798-3800`); today every fall-through raises, so the `None`
arm is unreachable *in this version*. It is not unreachable by contract, and the same wrapper falls
back to a plain `JsonOutputParser` (returning a `dict`, which has no `.model_dump`) for other
methods (`base.py:2299`). The model name is configuration (`config/config.yaml:3`) fed to
`init_chat_model`, so a provider swap can reach a different `with_structured_output` implementation
without touching this file.

**Fix:**
```python
def _to_dict(answer) -> dict[str, Any]:
    if answer is None:
        raise AnalysisError("structured output produced no parsed value")
    return answer if isinstance(answer, dict) else answer.model_dump()

return prompt_template | constrained | RunnableLambda(_to_dict)
```

### WR-11: Model refusals now trip the shared circuit breaker and answer 503 instead of `out_of_scope`

**File:** `src/nativespeaker/api/services/llm.py:31`
**Also:** `src/nativespeaker/api/resilience.py:167-171`, `config/config.yaml:5,14-15`

**Issue:** Binding `method="json_schema", strict=True` makes `OpenAIRefusalError` a reachable
exception on the happy path (`langchain_openai/chat_models/base.py:3805-3806`) — the provider
refuses, no `parsed` field is produced, and the wrapper raises. `ResiliencePolicy.attempt` catches
every `Exception`, calls `self._circuit_breaker.record_failure()`, and re-raises as
`PermanentLLMError` → `SERVICE_UNAVAILABLE` (503).

Two consequences:

1. A **user-content-triggerable** failure is charged to a **process-wide** counter. With
   `circuit_breaker_failure_threshold: 5` and `circuit_breaker_reset_seconds: 60`, five refusals
   inside the window open the breaker for every user for a minute. This product's input is
   untrusted user text by definition, and its own prompt has a `reject` mode for exactly this case
   (`config/prompt.txt:81-85`) — a refusal should map to `out_of_scope`, not to a shared health
   signal.
2. Truncation has the same shape. `max_tokens: 1000` is now also spent on `issues` and
   `suggestions`, which the strict schema forces the model to emit in **every** mode including
   `follow_up` and `reject`. A `finish_reason: length` completion has no `parsed` field, so it too
   becomes a breaker failure and a 503.

**Fix:** Classify refusal before the breaker sees it:
```python
from langchain_openai.chat_models.base import OpenAIRefusalError
...
except OpenAIRefusalError:
    raise OutOfScopeError() from None   # not a provider health signal
```
and raise `max_tokens` to account for the two now-mandatory arrays.

### WR-12: The tracked system prompt contradicts the newly bound schema

**File:** `config/prompt.txt:59-85` (unchanged this phase), against `src/nativespeaker/api/models/llm.py:52-55`

**Issue:** `ChatModelResponse` makes all four keys required under `strict=True`
(`tests/unit/test_llm_chain_schema.py:28-29`). The prompt still instructs the model to emit
two-key objects for `follow_up` and `reject`:

```

```

The API will win — the model is forced to emit all four keys — so this is not a runtime failure.

documents the real contract for the next person who reads it.

**Fix:** Update the three Output Format blocks in `config/prompt.txt` to the single flat four-key
shape, stating that `issues` and `suggestions` are `[]` outside analyze mode.
