## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01: `POST /auth/challenge` accepts `{"operation": "create_user"}`; every non-issuable value
  is one bucket: 400 `invalid_request`.** A value outside the `AuthOperation` enum and a valid
  member whose phase isn't built ("sync", "sign_out_all", …) reject identically — the endpoint
  discloses nothing about the operation vocabulary, consistent with the error contract's
  anti-oracle stance. The accepted set is exactly `{create_user}` today; later phases widen it.

- **D-02: Success is 200 with `{challenge_id, expires_at}` and `Cache-Control: no-store`, verbatim
  from today's prepare mode.** The e2e prepare tests move to the new endpoint with only the URL and
  request body changed. Rejected: 201, and echoing `operation` back.

- **D-03: The already-linked pre-check does NOT move to issuance — it is deleted.** Today
  `_prepare` rejects an already-linked caller with 409 `identity_already_linked` before issuing;
  that check was always best-effort and racy, with the consuming transaction's unique constraints
  as the real authority. Now the challenge issues to anyone the auth dependency admits, and the
  409 surfaces at completion via the constraint-conflict path (`classify_insert_conflict` →
  `CLIENT_CLASS_FOR_RESULT`). Consequences the planner must carry: the 409-at-prepare e2e cases
  are **rewritten to assert at completion**, not moved; an already-linked caller now burns a
  challenge row and one Firebase lookup before hearing 409; and `_already_linked` /
  `resolve_existing_identity`'s issuance-time call site disappears (check what remains of
  `resolve_existing_identity` — its other consumer is the completion path's conflict handling).
  — **Reversibility:** reversible — re-adding a pre-check is a small handler addition.

- **D-04: `challenge_id` becomes a required `str` and malformed bodies get standard FastAPI 422
  `validation_error`.** The `Any`-typed field existed only to route unusable handles to the
  mode-signal's 400; with the classifier dead, the trick dies too. Several Phase 37 e2e cases flip
  400 → 422 — sanctioned as part of the split. Planner: constrain with `min_length=1` so empty
  strings stay in the 422 bucket rather than falling through to `locate()` → 409 not-found.
  Whitespace-only handles pass validation and fall through as not-found, which is fine — the
  byte-for-byte philosophy already treats a padded handle that way.

- **D-05: Query parameters are ignored entirely.** All query parsing goes: `classify_mode_signal`,
  `auth/modesignal.py`, and the `get_raw_query_string` dependency (verify it has no other
  consumer). An old-style `?challenge=true` call fails body validation with 422. The mode-signal
  e2e cases (duplicate param, non-true value, both-signals, neither-signal) are **deleted, not
  moved** — the ambiguity they guarded can no longer be expressed.

- **D-06: The entire service-account config surface is deleted.** `FirebaseConfig`, the
  `AppConfig.firebase` field, the `.env.example` `FIREBASE_SERVICE_ACCOUNT_JSON` line, and the
  `credential_dict()` branch in `build_admin_apps`. No Firebase config key remains; ADC is
  discovered from the environment. Note `build_admin_apps` already has the ADC path
  (`_application_default_credential`) — this is deleting the first branch, not building anything.

- **D-07: Warn-and-boot stays when ADC is absent.** ADC probe fails → warning log, no Admin app,
  completion attempts fail closed as 503 `verification_temporarily_unavailable`. Dev and test runs
  with fake adapters need no credentials; the e2e matrix is untouched. Rejected: fail at boot
  (would break every credential-less dev/test run).

- **D-08: FLAGGED CONFLICT — ADC-only reverses Phase 37 D-08 and diverges from
  `SHARED-INVARIANTS.md`.** Phase 37 D-08 explicitly rejected ADC because SHARED-INVARIANTS
  forbids any ambient, default, or fallback client, and ADC can silently pick up local gcloud user
  credentials in dev. The developer's directive knowingly reverses that: production runs on GKE
  where ADC is Workload Identity (strictly better than a mounted key), and the sub-$5/month threat
  model does not justify a parallel credential path. Phase 37 D-08 is **superseded**; the
  SHARED-INVARIANTS conflict is recorded here per the standing rule, not silently resolved. The
  named-app-per-issuer discipline (never a `[DEFAULT]` app) is unchanged and still satisfies the
  no-ambient-*client* rule at the app-selection layer. — **Reversibility:** reversible — the
  deleted branch is ~30 lines and the config class is in git history.

- **D-09: All zero-consumer adapter interfaces are deleted.** `StoreAdapter`, `VendorProofAdapter`,
  `VerifiedNotification`, `VerifiedTransaction`, `StoreState`, `ClaimKind`, `DeviceBitState`,
  `RevocationOutcome`, and `FirebaseAdminAdapter`'s unconsumed `verify_id_token` and
  `revoke_refresh_tokens` methods. What survives of `adapters.py` is the providerData surface the
  live code consumes (`ProviderDataOutcome`, `ProviderDataEntry`, `ProviderDataResult`, and the
  one-method `FirebaseAdminAdapter`). **FOUND-08 is amended and flagged forward to phases 43–46:**
  each of those phases defines its adapter interface beside its first implementation, the same
  treatment 37.1 gave the provider-callback category. — **Reversibility:** reversible — the
  Protocols are ~80 lines with no consumers; git history holds them.

- **D-10: Files merge by cohesion; the planner sets the target.** No fixed file-count goal.
  Modules that serve one flow merge (e.g. `classifier.py` + `retry.py` into the Firebase lookup
  module; `telemetry.py` into where rejections are raised). Each merge is justified by cohesion,
  each deletion by carrying no behavior. Rejected: a forced ~5–6-file collapse (large diffs in
  behavior-stable files) and dead-code-only deletion (leaves the 14-file sprawl).

- **D-11: The `auth/__init__.py` lazy re-export facade is deleted.** The 98-line
  `__getattr__`/`__dir__` machinery goes; `__init__.py` shrinks to (near) empty and every consumer
  imports from the concrete submodule. Import-site edits across `src/` and `tests/` are mechanical.

## Summary

This phase is almost entirely subtraction against a codebase that has already been read and
measured. The ROADMAP's `14 files / 28 classes / 57 functions` baseline is **exact** — an AST count
reproduces it to the digit — and the shrink is arithmetic rather than aspirational: the deletions
CONTEXT already sanctions (D-05, D-09, D-11) remove 1 file, 9 classes and 12 functions on their own,
before any D-10 cohesion merge. There is no new dependency, no schema change, and no library
question to research on the auth side. The genuine risk is not "will it work" but "will a deletion
quietly take a behavior with it", and the only instrument that answers that is the test suite.

Two findings materially de-risk the work versus what CONTEXT assumed. First, **D-11 costs zero
import-site edits**: no module anywhere imports a *name* from the `auth` facade — all nine
`from nativespeaker.api.auth import X` hits import a *submodule*, which keeps working when
`__init__.py` empties. Second, **deleting the `firebase` config field cannot break a developer's
boot**: pydantic-settings only reads env vars matching declared fields, so a leftover
`FIREBASE_SERVICE_ACCOUNT_JSON` in someone's `.env` is silently ignored rather than rejected, even
though the effective `extra` policy is `forbid`. Both were verified by running them.

Two findings add work CONTEXT did not anticipate. `POST /auth/challenge` makes a **second**
pre-auth-callable route, which contradicts CREATE-01 as written and trips a literal allowlist in
`test_app_wiring.py` — a requirement amendment, not just a test edit. And on the folded LLM todo,
binding the three response models as a discriminated-union *root* produces a schema that
`strict=True` **silently declines to rewrite**, so the union shape would ship looking strict while
being loose — the single most likely way that workstream fails without failing loudly.

**Primary recommendation:** Sequence as (1) delete the provably-dead surface (D-05/D-09/D-11 +
mode-signal tests) — large, mechanical, low-risk; (2) split the endpoint (D-01–D-04) with its test
rewrites, the only step that changes a client contract; (3) collapse Firebase to ADC (D-06/D-07);
(4) merge by cohesion (D-10) last, when the surviving set is known; (5) the LLM todo as its own
independent plan with its own commits, gated on real-provider e2e. Steps 1 and 5 can run in
parallel with the rest; steps 2→4 are ordered because each narrows the next one's target.

### Pattern 1: The challenge handler is a thin copy of `_prepare` minus the pre-check

**What:** The new endpoint's whole body is the two statements `_prepare` runs after its rejection.
**When to use:** Directly — do not redesign it.

```python
# Source: derived from src/nativespeaker/api/routers/auth.py:111-118, verbatim call shape
challenge_id, expires_at = await challenge_store.issue(
    session,
    operation=AuthOperation.create_user,
    identity=context.identity,
    now=context.evaluated_at,
)
return JSONResponse(
    content=ChallengeResponse(challenge_id=challenge_id, expires_at=expires_at)
              .model_dump(mode="json"),
    headers={"Cache-Control": "no-store"},   # not no-cache: the handle is a secret
)
```

`[VERIFIED: src/nativespeaker/api/auth/challenges.py:46-49]` — `issue` is declared
`async def issue(self, session: AsyncSession, *, operation: AuthOperation, identity: LinkedIdentity | PreAuthIdentity, now: datetime) -> tuple[str, datetime]:`,
so the call above needs no adaptation.

### Pattern 2: `Depends()`-only routes; handlers never take `Request`

Established and enforced. The new endpoint declares `context`, `session`, `challenge_store` — and
notably **not** `adapter` (issuance makes no provider call) and **not** `get_raw_query_string`
(deleted by D-05).

### Anti-Patterns to Avoid

- **Re-introducing a loosely-typed field to force a 400.** D-04 kills the `Any` trick on
  `challenge_id`; do not resurrect it as `operation: Any` to make every bad `operation` a 400. The
  400/422 split described in Pitfall 2 is the honest shape.
- **Adding a pre-check "just in case" to the challenge endpoint.** D-03 deleted it deliberately;
  re-adding it silently restores the racy authority the phase removed.
- **Letting a D-10 merge rewrite behavior.** A cohesion merge is a file move plus import fixes. If a
  merge's diff shows changed logic, split it into two commits.
- **Deleting `resolve_existing_identity` because D-03 removed a caller.** It has a second, live
  caller inside the consuming transaction. `[VERIFIED: src/nativespeaker/api/auth/creation.py:52]` —
  `existing = await resolve_existing_identity(session, issuer=identity.issuer, subject=identity.subject)`.

## Common Pitfalls

### Pitfall 1: `POST /auth/challenge` breaks `test_app_wiring.py` and contradicts CREATE-01
**What goes wrong:** The new route is added, every auth test passes, and
`tests/unit/test_app_wiring.py::test_every_route_but_the_two_exemptions_requires_a_linked_identity`
fails — because the route legitimately must admit a pre-auth caller but is not on the allowlist.
**Why it happens:** The allowlist is a hand-maintained literal, deliberately:
`[VERIFIED: tests/unit/test_app_wiring.py:11-12]` —
```python
PUBLIC_PATHS = {"/health/ready"}
PREAUTH_CALLABLE_PATHS = {"/auth/create-user"}
```
with the comment on line 10: `# Literals rather than derived from anything, so widening the exemption is a visible edit here.`
**How to avoid:** Add `"/auth/challenge"` to `PREAUTH_CALLABLE_PATHS` **as a deliberate, reviewed

### Pitfall 2: D-01's "one bucket: 400" cannot cover non-string `operation` values
**What goes wrong:** The planner writes `operation: str` + a handler check expecting every bad value
to be 400, then a test sends `{"operation": 123}` and gets 422.
**Why it happens:** Pydantic rejects the *type* before the handler runs. Measured this session
against FastAPI 0.135.1 / Pydantic 2.12.5:

| Body | `Literal["create_user"]` | `str` + handler check |
|---|---|---|
| `{"operation": "create_user"}` | 200 | 200 |
| `{"operation": "sync"}` | 422 | **400** ✅ |
| `{"operation": "nope"}` | 422 | **400** ✅ |
| `{"operation": 123}` | 422 | 422 |
| `{"operation": null}` | 422 | 422 |
| `{}` / no body | 422 | 422 |

`[VERIFIED: measured]`
**How to avoid:** Use `str` + handler check — it delivers D-01 exactly as written, because D-01's two
named cases ("a value outside the enum" and "a valid member whose phase isn't built") are **both
strings**, and both land on 400. Document the type-error arm as 422 in the plan so the e2e tests pin
it. Both shapes are anti-oracle-safe: `validation_error_handler` returns only
`{"code": "validation_error"}`, leaking no field detail.
`[VERIFIED: src/nativespeaker/api/app/errors.py:32-34]` — `async def validation_error_handler(...)` returns `error_response(VALIDATION_ERROR)`.

### Pitfall 3: D-04's `min_length=1` leaves whitespace-only handles passing validation

### Pitfall 6 (folded todo): a discriminated-union root silently defeats `strict=True`
**What goes wrong:** The three response models are bound as
`RootModel[Annotated[Union[...], Field(discriminator="resolved_mode")]]`, the call ships, and the
provider is *not* actually constrained — because the strict rewrite never reached the branches.
**Why it happens:** `convert_to_json_schema(schema, strict=True)` rewrites an object schema by
forcing every property into `required` and setting `additionalProperties: False`. It does **not**
descend into a root-level `oneOf`. Measured this session on the project's own models:

- `convert_to_json_schema(AnalyzeResponse, strict=True)` → `required: ['resolved_mode', 'response', 'issues', 'suggestions']`, `additionalProperties: False`
- the same call on the union root → branches keep `required: ['resolved_mode', 'response']` and the nested `Issue` object gets no `additionalProperties: False` at all

`[VERIFIED: measured]`
**How to avoid:** Do not use a union root. Either (a) bind one flat model carrying `resolved_mode`
plus all fields, or (b) if a union is required, assert the emitted schema in a unit test —
`convert_to_json_schema(...)` is importable and cheap, so the test costs no provider call.
**Warning signs:** A plan that treats "bind a union" as a one-line change.

### Pitfall 7 (folded todo): `strict=True` makes D-12's empty-list defaults inert at the provider
**What goes wrong:** The planner keeps the `issues: list[Issue] = []` defaults believing they still
protect against an omitted key, when under strict the provider is now *required* to send both keys.
**Why it happens:** Pydantic marks defaulted fields optional
(`AnalyzeResponse.model_json_schema()['required'] == ['resolved_mode', 'response']`), but the strict
rewrite overrides that and marks all four required. `[VERIFIED: measured]`
**How to avoid:** This *is* the todo's "revisit the D-12 defaults" question, and the measurement
answers it: under strict the defaults no longer do provider-boundary work. They remain justifiable
as (i) the client-facing contract and (ii) defense in depth if the strict call ever falls back.
Decide deliberately and record it — do not leave them unexamined.
