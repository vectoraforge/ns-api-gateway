<objective>
Finish the issuance handler: every challenge-bearing operation issues, everything outside the enum is
one indistinguishable 400, and a caller with no account may prepare create-user and nothing else.

Purpose: `/auth/challenge` sits behind the deliberately unnarrowed router dependency so an unlinked
caller can prepare its own account creation. That is exactly the hole D-10 closes, and it closes it
with one derived condition rather than a table — the developer's stated concern is lists that have to
be kept in step, and this design has none.
Output: the handler's final shape, and a challenge-endpoint test file whose premise matches the
four-value vocabulary rather than the seven-value one it was written against.
</objective>

Add D-10's condition to the issuance handler, after the membership test and before the issue call: any
operation other than create-user, presented by a caller whose identity carries no account row, raises
the existing pre-auth refusal. Reuse that class; declare nothing new and add no error code.

Order matters and is part of the contract. The membership test runs first, so a caller outside the
vocabulary gets the same 400 whether or not it holds an account — putting the account check first
would make the two refusals discriminate, telling an account-less caller which strings are real
operation names.

not move the rule into the challenge store, and do not derive the issuable set from route metadata —
D-10 rejected all three with reasons this task does not re-open. Create-user is the only operation an
account-less caller may prepare because it is the only route that admits unlinked callers, and that
fact is already pinned elsewhere; the condition stays correct for Phases 41 and 42 with nobody
touching it.

Leave the rejected-operation log line, the no-store header and both existing comments exactly as they
are.
