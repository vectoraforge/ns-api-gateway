<objective>
Build the per-run Google-linked Firebase session that D-18's success-path case needs, and prove it
against the real Admin read before any endpoint depends on it.

Purpose: D-18 asked for a real Google `providerData` response because a fake cannot prove the shape
of one. The mechanism is exchange-and-link, not minting: one browser consent by hand yields a
long-lived Google refresh token, supplied in `.env` before the run; each run redeems it for a fresh
Google ID token, creates a fresh anonymous Firebase user over Identity Toolkit REST with the Web API
key the repository already holds, links the Google credential to that user, and deletes the user
afterwards so the Google account is free again. No service-account credential, no signer, and no
minted token is involved anywhere.
Output: three documented environment variables, a `google_linked_firebase_credential` fixture, and a
canary case that reads the linked user back through the production Firebase seam and asserts exactly
one `google.com` entry.
</objective>

Run the five steps and record, for each, the exact call made and the exact keys or attribute names in
the answer:

1. **Redeem the stored Google refresh token.** `POST https://oauth2.googleapis.com/token` with the
   client id, the client secret, the stored refresh token and `grant_type=refresh_token`. Record
   whether an `id_token` comes back. If it does not, the one-off consent was performed without the
   `openid` scope and the developer must redo it — report that as a blocked precondition rather than
   working around it.
2. **Read the Google subject out of that ID token** without verifying it, using the PyJWT already
   installed. Record the claim name that carries it.
3. **Create a fresh anonymous Firebase user.** `POST accounts:signUp` against Identity Toolkit with
   the Web API key from `JWT_API_KEY` and `returnSecureToken`. Record the response keys.
4. **Link the Google credential to that user.** `POST accounts:signInWithIdp` with the anonymous
   user's ID token, a `postBody` carrying the Google ID token and the `google.com` provider id, a
   `requestUri`, and `returnSecureToken`. Record the response keys and confirm the returned local id
   is the same one step 3 produced — the whole point is that no second Firebase user appears.
5. **Read the linked user back and then delete it**, through the Admin app the lifespan already
   built. Reach that app by its documented name rather than constructing a second one, and record:
   the exact accessor used to reach it; the `providerData` entries the read reports; the exact name
   and signature of the Admin delete call; and the exact name and constructor of the identifier type
   that looks a user up by its Google provider uid, which the fixture's recovery preamble will need.

Record every observed name, signature and response key in the summary as a table. Where an
observation contradicts anything written in `40-RESEARCH.md` or `40-CONTEXT.md`, say so explicitly
rather than silently adopting the observation — a contradiction is a finding this phase owes the next
reader.

Leave the working tree unchanged apart from the summary: this task's deliverable is knowledge, and
its one written artefact is the record. Delete any Firebase user it creates.
