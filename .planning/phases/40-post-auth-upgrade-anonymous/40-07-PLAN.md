<objective>
Prove the three things that cannot be proven from inside the endpoint: that a real Google
`providerData` response drives the flip correctly, that the two read endpoints report the upgrade
afterwards, and that no row anywhere sits in the half-upgraded state.

Purpose: D-18 exists because a fake cannot prove the shape of a real Google response, and plan 40-03
built the credential that makes a real one obtainable per run without minting anything. D-20 exists
because ROADMAP criterion 3 names two endpoints, so it is proven through the endpoints a client calls.
D-12 exists because the users-and-identity pairing is an invariant spanning two tables that no CHECK
constraint can express — the flip makes it structural by writing both halves in one method, and this
scan is what keeps that honest.
Output: three tests, one per claim, each in the suite that can actually make it.
</objective>

  <action>
Create `tests/schema/test_registration_pairing.py`, carrying the schema marker and using asyncpg
directly like every other file in that suite.

The subject is the invariant no CHECK constraint can express, because it spans two tables: a user's
registration timestamp is set if and only if its identity row's provider is registered. This is a
**scan**, not a rejection case — the database will happily accept a row in the third state, which is
exactly why the invariant has to be structural in the code and observed here.

Write two cases, each a count query asserting zero: no user carrying a registration timestamp whose
identity row is anonymous, and no identity row carrying a registered provider whose user has no
registration timestamp.

A count query that returns zero because it matched nothing at all is a vacuous pass, so each case
ships with a control: insert one row in the offending state, assert the same query now counts it, then
roll that insertion back through the savepoint helper and assert the count returns to zero. Without
the control this file would keep passing if the query were silently wrong.

Use the module-level SQL literal and per-table helper style the constraints file uses, generating
provider_uid values that cannot collide by accident. Do not import from the e2e suite and do not use
its rollback fixture: this suite has its own scratch database and its own transaction discipline.

Three-line docstring maximum, one-line comments only.
