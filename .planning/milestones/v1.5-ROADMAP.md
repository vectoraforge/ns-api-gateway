## Phase Details

### Phase 18: Test Infrastructure Cleanup
**Goal**: Tests run in isolated transactions that auto-rollback, leaving zero database artifacts
**Depends on**: Nothing (first phase of v1.5)
**Requirements**: TEST-01, TEST-02, TEST-03
**Success Criteria** (what must be TRUE):
  1. Each test runs inside a database transaction that rolls back automatically on completion
  2. No `cleanup_chat` or similar manual cleanup helpers exist in the test codebase
  3. Running the full test suite twice in succession produces identical results with no leftover data
**Plans:** 1/1 plans complete
Plans:
- [ ] 18-01-PLAN.md — Transaction isolation fixtures + async client migration for all e2e tests

### Phase 19: Service Layer Refactoring
**Goal**: Service and database layers are organized into packages ready for new modules
**Depends on**: Phase 18
**Requirements**: SVC-01, SVC-02, SVC-03
**Success Criteria** (what must be TRUE):
  1. `app/services/` package exists with separate `llm_service.py` and `chat_service.py` modules
  2. `app/database/` package exists with separate `chats_db.py` module
  3. All existing tests pass without modification after the refactoring
  4. Import paths are clean with no circular dependencies
**Plans:** 1/1 plans complete
Plans:
- [ ] 19-01-PLAN.md — Create services/ and database/ packages, update all imports

### Phase 20: Structured Logging
**Goal**: Application emits minimal, structured logs — only what's needed for production debugging without cluttering the codebase
**Depends on**: Phase 19
**Requirements**: LOG-01, LOG-02, LOG-03, LOG-04
**Success Criteria** (what must be TRUE):
  1. Production logs emit JSON-formatted structured output via structlog
  2. Development logs emit human-readable console-formatted output
  3. Every log entry within a request includes a unique request ID
  4. Logging is minimal: info for request boundaries and errors only, debug for implementation details — no verbose per-step logging that clutters application code
  5. Log statements do not add visual noise to the codebase — prefer middleware/decorator patterns over inline log calls
**Plans:** 1/1 plans complete
Plans:
- [ ] 20-01-PLAN.md — Replace stdlib logging with structlog, add request middleware, wire through app, unit tests

### Phase 21: User Management
**Goal**: Users have local profiles created automatically from JWT identity with safe concurrent provisioning
**Depends on**: Phase 19
**Requirements**: USER-01, USER-02, USER-03, USER-04
**Success Criteria** (what must be TRUE):
  1. First authenticated API request from a new user creates a local user record without any explicit registration step
  2. `GET /users/me` returns the authenticated user's profile including email, name, and plan tier
  3. Two simultaneous first requests from the same user do not produce duplicate records or errors
  4. A user cannot retrieve or modify another user's profile data
**Plans:** 3/3 plans complete
Plans:
- [ ] 21-01-PLAN.md — User model, auth identity, UsersDB, UserService, migration
- [ ] 21-02-PLAN.md — Dependency refactor, chat route wiring, users router, app registration
- [ ] 21-03-PLAN.md — Test infrastructure updates and user management unit tests

### Phase 22: Apple Subscription Integration
**Goal**: Apple subscription lifecycle events update user plan tiers and propagate to Firebase for JWT enrichment
**Depends on**: Phase 21
**Requirements**: SUBS-01, SUBS-02, SUBS-03, SUBS-04, SUBS-05, SUBS-06, SUBS-07
**Success Criteria** (what must be TRUE):
  1. `POST /webhooks/apple` receives and acknowledges Apple Store Server Notifications V2
  2. Notifications with invalid JWS signatures are rejected before any state mutation
  3. A subscription purchase, renewal, grace period, billing retry, expiration, and revocation each update the user's plan tier correctly
  4. Receiving the same Apple notification twice (identical `notificationUUID`) does not change state or produce errors
  5. After a plan change, the user's Firebase custom claim reflects the new tier (without blocking the event loop)
**Plans:** 3/3 plans complete
Plans:
- [x] 22-01-PLAN.md — Subscription models, enums, config, DB layer, migration, dependencies
- [x] 22-02-PLAN.md — FirebaseService, SubscriptionService, webhooks router, app wiring
- [x] 22-03-PLAN.md — Unit tests for webhook endpoint and subscription processing

### Phase 23: Envoy Gateway Rate Limiting
**Goal**: API requests are rate-limited at the infrastructure edge based on user subscription tier
**Depends on**: Phase 22
**Requirements**: ENVOY-01, ENVOY-02, ENVOY-03, ENVOY-04, ENVOY-05
**Success Criteria** (what must be TRUE):
  1. Envoy Gateway extracts the JWT `plan` claim and forwards it as `x-user-plan` header to the application
  2. Per-user request rate limits differ by plan tier (free < silver < gold < platinum)
  3. The `/webhooks/apple` endpoint is accessible without JWT authentication
  4. Rate limiting uses local per-pod rate limiting (backend PostgreSQL quota is authoritative)
  5. `GET /users/me` response includes the user's current request count and plan limits
**Plans:** 4/4 plans complete
Plans:
- [x] 23-01-PLAN.md — Backend foundation: models, migration, UsageDB, error contract, schema, rename
- [x] 23-02-PLAN.md — Backend integration: ChatService quota, SubscriptionService zero-on-change, users endpoint, tests
- [x] 23-03-PLAN.md — Helm chart: deployment, service, HTTPRoutes, SecurityPolicy, BackendTrafficPolicy
- [x] 23-04-PLAN.md — Gap closure: complete project rename (root.py branding + package re-install)

### Phase 24: Migration Merge
**Goal**: Merge two migration files into a single migration with correct FK constraints from users.plan and subscriptions.plan to plans.tier
**Depends on**: Phase 23
**Requirements**: MIG-01, MIG-02, MIG-03
**Success Criteria** (what must be TRUE):
  1. A single migration file creates all tables in correct FK dependency order (plans first)
  2. `users.plan` and `subscriptions.plan` columns have `REFERENCES plans(tier)` FK constraints
  3. SQLModel model fields declare `foreign_key="plans.tier"` matching the SQL constraints
  4. E2E tests seed the plans table so FK constraints are satisfied
**Plans:** 2/2 plans complete

Plans:
- [x] 24-01-PLAN.md — Merge migrations, add FK constraints to models, seed plans in e2e tests
- [x] 24-02-PLAN.md — Drop and recreate database tables via pogo migrate
