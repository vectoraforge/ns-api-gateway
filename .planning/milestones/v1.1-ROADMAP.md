## Phase Details

### Phase 1: Exception Foundation
**Goal**: Typed exceptions cover all error cases; HTTP handlers return consistent, well-shaped error responses
**Depends on**: Nothing (first phase)
**Requirements**: EXCP-01, EXCP-02, EXCP-03, EXCP-04
**Success Criteria** (what must be TRUE):
  1. A request with a missing, invalid, or expired token receives a 401 with a structured body (not a bare 500 or untyped error)
  2. A request accessing another user's chat receives a 404 with a structured body via `ChatOwnershipError`
  3. Application startup failure due to database unavailability raises `DatabaseNotInitializedError` (visible in logs, not `Exception`)
  4. A parametrized test for each exception handler passes, asserting HTTP status code and response body shape
**Plans**: 3 plans

Plans:
- [x] 01-01-PLAN.md — Extend exception hierarchy + standardize error response shape to {status, error}
- [x] 01-02-PLAN.md — Parametrized tests for all exception handlers (TDD)
- [x] 01-03-PLAN.md — Gap closure: fix missing Authorization header returning 422 instead of 401

### Phase 2: Auth Structure + LLM Errors
**Goal**: JWT verification is swappable via protocol without touching routes; LLM retry failures carry typed, chained exceptions
**Depends on**: Phase 1
**Requirements**: AUTH-01, AUTH-02, AUTH-03, RETRY-01
**Success Criteria** (what must be TRUE):
  1. `TokenVerifier` protocol exists and a conforming implementation can be substituted without modifying any route handler
  2. `UnsafeBase64Verifier` implements the protocol and preserves current decode behavior (existing tests pass unchanged)
  3. `get_user_id` dependency resolves the verifier from `app.state`, confirmed by a test that swaps the verifier via state
  4. LLM retry exhaustion raises a typed subtype (transient vs permanent) with the original exception attached as `__cause__`
**Plans**: 2 plans

Plans:
- [x] 02-01-PLAN.md — TokenVerifier protocol + UnsafeBase64Verifier + get_user_id wired to app.state
- [x] 02-02-PLAN.md — TransientLLMError / PermanentLLMError typed exception chain in _invoke

### Phase 3: Validation + Security Tests
**Goal**: Malformed cursors are rejected early; circuit breaker limitation is documented; cross-user isolation is verified end-to-end
**Depends on**: Phase 2
**Requirements**: CURS-01, CB-01, TEST-01
**Success Criteria** (what must be TRUE):
  1. A request with a malformed cursor parameter receives a 400 before any base64 decode is attempted
  2. The circuit breaker implementation contains an inline comment describing the in-memory limitation and a concrete migration path for multi-instance deployment
  3. Integration tests confirm user A cannot read, post to, or delete user B's chats (tests run against a real database, no mocked data layer)
**Plans**: 2 plans

Plans:
- [x] 03-01-PLAN.md — InvalidCursorError typed exception + cursor validation at route entry; circuit breaker in-memory comment
- [x] 03-02-PLAN.md — Cross-user isolation integration tests against real PostgreSQL database
