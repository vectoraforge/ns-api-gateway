## Phase Details

### Phase 25: Config and Model Foundation
**Goal**: Application models and configuration are type-safe with native PG enum definitions and config-driven quota mapping
**Depends on**: Phase 24 (v1.5 complete)
**Requirements**: QUOTA-01, QUOTA-02, QUOTA-05, ENUM-01, ENUM-02, ENUM-03, ENUM-04, ENUM-05, SCHEMA-02
**Success Criteria** (what must be TRUE):
  1. `AppConfig` loads a `quotas` section from YAML that maps every SubscriptionPlan value to a monthly integer limit
  2. ENUM-02 dropped per D-05 -- no `sa_type=PG_ENUM(...)` on fields; SQLAlchemy auto-infers from StrEnum
  3. `User.subscription_plan`, `Subscription.plan` are typed as `SubscriptionPlan` (not `str`), and `SubscriptionEvent.old_plan`/`new_plan` are `SubscriptionPlan | None`
  4. `UserProfileResponse.subscription_plan` is typed as `SubscriptionPlan`
  5. `Plan` SQLModel class no longer exists in the codebase
**Plans:** 2/2 plans complete
Plans:
- [x] 25-01-PLAN.md -- Rename enums, narrow model fields, QuotaConfig, config.yaml, schema update
- [x] 25-02-PLAN.md -- Propagate renames through services, database, dependencies, routers

### Phase 26: Service and Database Rewiring
**Goal**: Quota enforcement reads from configuration instead of the plans table, with no JOIN to `core.plans` in any query
**Depends on**: Phase 25
**Requirements**: QUOTA-03, QUOTA-04
**Success Criteria** (what must be TRUE):
  1. `UsageDB.try_increment` accepts a `monthly_quota: int` parameter and its SQL contains no JOIN to `core.plans`
  2. `UsageDB.get_monthly_limit` method no longer exists
  3. `ChatService` resolves the user's quota from `QuotaConfig` and passes it as an integer to `UsageDB.try_increment`
  4. `GET /users/me` returns the monthly limit from config, not from a database query against `core.plans`
**Plans:** 2/2 plans complete
Plans:
- [x] 26-01-PLAN.md -- Remove QuotaConfig, flatten config.yaml, rewrite UsageDB.try_increment, delete get_monthly_limit
- [x] 26-02-PLAN.md -- Wire quotas through ChatService and dependencies, update chat and user routers

### Phase 27: Migration
**Goal**: Database schema matches the new model definitions -- native PG enum types, no FK to plans, no plans table
**Depends on**: Phase 26
**Requirements**: SCHEMA-01
**Success Criteria** (what must be TRUE):
  1. A single pogo-migrate migration file exists that atomically creates four PG enum types (`core.chat_role`, `core.subscription_plan`, `core.subscription_provider`, `core.subscription_status`), converts TEXT columns to enum types, drops FK constraints, and drops `core.plans`
  2. Running the migration against the current production schema succeeds without error
  3. After migration, inserting a row with an invalid enum value into any converted column is rejected by PostgreSQL
**Plans:** 1/1 plans complete
Plans:
- [x] 27-01-PLAN.md -- Rewrite migration SQL with native PG enum types, renamed columns, no plans table

### Phase 28: Test Updates

  3. Full test suite (`pytest`) passes with zero failures
